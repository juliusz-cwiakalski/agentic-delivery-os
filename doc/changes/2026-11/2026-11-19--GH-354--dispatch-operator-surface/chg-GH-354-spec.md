# CHANGE SPECIFICATION

> **PURPOSE**: Give the typed dispatch lane the per-ref operator surface the shell lane still owns — `status`, `log`, `is-delivering`, and `last-message` as one typed command family with `--json` — so an operator or the CEO agent can inspect a delivery (live, finished, or absent) without reading the shell's marker files, PID files, stdout captures, or last-message files, and without reading or executing a shell script. The durable `dispatch.lane` record is the state source; a bounded per-ref harness-stdout artifact family (one append-only file per stream of a streaming adapter, the newest two retained, a 2 × 1 048 576-byte family bound) and — where the lane's harness declares `session-introspection` — the harness's own persisted session transcript are the only two new persisted reads.

## 1. SUMMARY

The dispatch lane is parity-complete for delivery semantics but has no inspection surface: the four queries the CEO prompt uses today (`--status`, `--log`, `--is-delivering`, `--last-message`) exist only on `scripts/deliver-ticket.sh`, and the typed path persists nothing an operator can read back. This change delivers one typed command family — `dispatch status <ref>`, `dispatch log <ref> [--tail <n>]`, `dispatch is-delivering [<ref>]`, `dispatch last-message <ref>`, each with the delivered global `--json` — and the two data sources they need.

The state source is the durable `dispatch.lane` record: `status` and `is-delivering` are pure folds over its newest record per ref, with the owner process facts read through an injected advisory liveness probe. `log` reads a new bounded, reference-scoped per-ref harness-stdout artifact that a dispatch writes while its session streams — one append-only file per stream of a streaming adapter, the newest two retained — and `last-message` reads the harness's own persisted session transcript through an injected adapter-owned read seam, returning the PM's final assistant message — never a synthesized classifier sentence — where the lane's harness declares the existing `session-introspection` capability. The typed tail is the harness's own stdout (for opencode, its JSON event stream), not the shell's `--log`, which tails the opencode child's stderr; the divergence is declared in this specification and in the operator documentation.

Nothing on the delivery write path changes: no result token, projection, exit, attempt-record field, lane-record field, or error identity moves, no new configuration key is added, and no read path writes, repairs, or clears anything. The shell entry points keep working as the documented fallback.

## 2. CONTEXT

### 2.1 Current State Snapshot

- **The durable lane exists and is the declared read surface.** `dispatch.lane` / `delivery.dispatch.lane.v1` / key prefix `dispatch.lanes:` is declared with the closed states `active` and `terminal` (`packages/core/src/contracts/dispatch.ts:571-579`), and the record type carries `schema`, `ref`, `repository`, `attemptId`, `sessionId`, `harnessKind`, `owner: { processId, startedAt }`, `iterationOrdinal`, `restartsConsumed`, `state`, optional `lastToken`/`lastOutcome`, and `recordedAt` (`contracts/dispatch.ts:594-608`). TDR-0049 names GH-354 as the record's deferred read surface and records that the owner facts are advisory, never an exclusion mechanism (`doc/decisions/TDR-0049-dispatch-owned-durable-lane-record.md:41,277`).
- **The lane read is a bounded prefix-scoped fold.** `readDispatchLanes` reads the kind/schema/prefix with the retained-window bound (`packages/core/src/app/dispatch-ledger.ts:468-479`), `latestDispatchLaneFor` returns the newest record for a ref (`dispatch-ledger.ts:498-...`), and `resolveDispatchLane` composes the dispatch lane with resumable daemon lanes for resume only (`packages/core/src/app/dispatch-lane.ts:70-...`). No read-side surface folds these records for an operator today.
- **The dispatch family has four write/read subfamilies and no inspection query.** The grammar table lists `dispatch <ref>`, `dispatch attempts`, `dispatch dual-run summary|resolve`, and `dispatch handover` (`doc/spec/features/feature-dispatch-engine.md:59-67`); the handler declares `--revert`, `--harness`, `--resume-prompt`, `--repo`, `--note` and refuses any undeclared flag as `fallback.invocation` (`packages/cli/src/commands/dispatch.ts:260-262,311-340`). There is no `status`, `log`, `is-delivering`, or `last-message` form.
- **`--json` is a global flag.** The CLI parses `--json`, `--verbose`, and `--pretty` at the root (`packages/cli/src/index.ts:434,549`), so a new subfamily inherits envelope output without a new flag.
- **Commands never choose an exit digit.** A command definition projects its data to a projection class (`exitProjection`) and the projection module owns the digits 0/1/2; the only permitted numeric exit sites are the CLI projection module and the MCP lifecycle (`scripts/checks/exit-code-literals.ts:1-26`). The dispatch definition already projects data-driven answers — `attempts` to `success`, an unmet handover to `user-validation` and a recorded flip to `success` (`commands/dispatch.ts:274-289`).
- **The attempt read side is the read-only-precedent.** `dispatch attempts` performs zero appends and zero fence acquisitions, resolves identity with persistence disabled so the checkout marker is never created or repaired, and reports an empty history as success (`feature-dispatch-engine.md:493-504`).
- **The lane record deliberately carries no content.** "No prompt, transcript, diff, credential, or provider payload" (`feature-dispatch-engine.md:218-220`, `contracts/dispatch.ts:587-593`), and the attempt record's evidence vocabulary is bounded to 16 identifier-only references (`contracts/dispatch.ts:554`).
- **Nothing persists per-ref session output in the typed path.** The production dispatch observes the session through the streaming spawn seam's line iterable (`packages/core/src/contracts/harness.ts:391-433`), and the opencode adapter already exposes a per-session observation side-channel — `telemetrySinkFor({ workItemRef })`, "ingest observes the decoded frames beside the delivered drain; an absent sink keeps the delivered stream behavior exactly … an ingest failure never changes the delivery's outcome" (`packages/adapters/src/harness/opencode.ts:93-103`). It is not the seam this change needs: it receives only decoded frames, because blank, non-JSON, and non-object lines are skipped before it is called (`opencode.ts:239-243,365-380`), so it is a pattern to copy rather than a raw-line sink. No equivalent sink writes a per-ref stdout artifact.
- **The session port has no transcript read.** The closed session port exposes spawn, deliver, resume, collect, classify, liveness, listSessions, and the additive optional `terminate` (`contracts/harness.ts:478-507`); `HarnessEvidence` carries completion/exit facts only and no assistant text (`harness.ts:206-215`). The adapters already read persisted session storage read-only for telemetry — the opencode message store and Claude Code transcript files with a declared per-file byte and line cap (`packages/core/src/contracts/harness-telemetry.ts:272-275`) — so the storage and the read-only posture exist; no shared read returns the final assistant message.
- **The lifecycle-capability vocabulary already covers a session read.** `session-introspection` is a closed member of the lifecycle-capability union (`packages/core/src/contracts/harness.ts:44-50`), and an adapter either declares it supported or declares it as a gap. opencode declares it supported (`packages/adapters/src/harness/opencode.ts:51-57`); Claude Code declares it as a gap with reason `headless-mode-limitation` (`packages/adapters/src/harness/claude.ts:47`, documented at `doc/spec/features/feature-harness-adapters.md:321`), its supported lifecycle capabilities being `headless-spawn` and `telemetry-extraction` (`claude.ts:31`). Claude Code's only persisted-session reader is its telemetry capture, which parses statistics and not content (`packages/adapters/src/harness/telemetry-claude.ts:1-10`). The specification names the capability without narrowing it to metadata (`feature-harness-adapters.md:104`).
- **The two adapters' invocation shapes differ.** opencode **streams** stdout: a stream's handle settles on its first identified line and the engine sees every value (`packages/adapters/src/harness/opencode.ts:373-384`). Claude Code is a **one-shot runner**: its `spawn` awaits a bounded invocation through an injected runner and answers with a result, its supported operations are `spawn` and `collect`, and there is no `stream.lines` for the engine to observe (`packages/adapters/src/harness/claude.ts:153-200`); line `claude.ts:31` remains the `lifecycleCapabilities` declaration. A harness-stdout artifact can therefore exist only for a streaming adapter.
- **The stream channel carries no terminatedness marker.** The line channel is `AsyncIterable<string>`: the host splits on LF, strips the delimiter, and pushes the final buffered remnant as a value when the stream closes (`packages/core/src/contracts/harness.ts:409-421`; `packages/adapters/src/host/index.ts:186-194,239-241`). Line-level code therefore cannot tell a terminated value from an unterminated remnant, which is why the writer applies one rule to every yielded value and the reader treats an unterminated tail as a torn write.
- **The typed envelope's `lastMessage` is a synthesized sentence.** It is the derivation's bounded summary (for example `harness evidence unreadable (…)` or `liveness stalled; …`) bounded to 512 characters (`contracts/dispatch.ts:379-380,551`; `packages/core/src/app/dispatch.ts:1146,1217,1236`). It is not the PM's final message.
- **Per-ref session output lives outside the store today and only for the shell lane, in three distinguishable streams.** The shell sends the **opencode child's stdout** to `tmp/deliver-ticket/<ref>.pm.out` and the **opencode child's stderr** to `tmp/deliver-ticket/<ref>.log` (the redirection applies to the child, `scripts/deliver-ticket.sh:1753-1755`), while its own `log_info`/`log_warn` progress lines go to the wrapper's stderr and therefore reach the operator's terminal, not either file (`:229-234`). It also writes the final message to `.ai/local/delivery/<ref>.last-message`, derived from the last non-blank line of the child's stdout (`:1858-1865`), the delivering marker to `.ai/local/delivery/delivering`, and PID files to `.ai/local/delivery/<REF>.pid` (`:1735,793-810`). For opencode that child stdout is a JSON event stream decoded line by line and skipped when undecodable (`packages/adapters/src/harness/opencode.ts:239-243`).
- **The shell parity contract for the four queries is explicit.** `cmd_is_delivering` exits 0 when a delivery is in progress and prints nothing, with self-healing of a stale PID file (`deliver-ticket.sh:2131-2158`); `cmd_status` always exits 0 and prints `delivering`, `ref`, `pid`, `session_id`, `stale`, `delivering_marker`, where `stale=yes` means the PID file exists but its owner is dead (`deliver-ticket.sh:2164-2212`); `cmd_log` prints the newest `tail -n` lines of `<ref>.log` — the opencode child's stderr, not the harness's stdout and not the wrapper's progress lines — with default 50 (`deliver-ticket.sh:2217-2242`); `cmd_last_message` prints the stored wrapper-derived message and returns non-zero when nothing is stored (`deliver-ticket.sh:2252-2260`).
- **The owner probe is a start-time-tolerant liveness check.** The shell requires the recorded process to be alive, to match the script and working tree, and to have started within `PID_START_TOLERANCE_SECONDS = 5` of the recorded epoch, so a reused process id is rejected (`deliver-ticket.sh:637`, `owner_pid_if_live`).
- **The state layer keeps content out of the ledger and has a precedent for sidecar artifact families.** The store layout lists the ledger, header, index, fence, derived documents, and beside them the retro-evidence sidecar and the `ceremony-artifacts.<workspace>/` family, described as living "beside the ledger outside the store's record set" (`doc/spec/features/feature-state-layer.md:92,104-116`). The `ceremony-artifacts.<workspace>/` family is a directory of per-run files, the same shape the new per-ref family takes.
- **The operator routine does not yet name the typed queries.** `doc/guides/engine-first-operations.md` covers the daily dispatch/verify/merge loop, the gate, the flip, and the shell fallback; the four per-ref queries are absent, while the CEO prompt still names the shell forms (`.opencode/agent/ceo.md:146-158,273,289-294`).
- **The milestone split is decided.** GH-347 records NG-1 and §7.3 deferring the operator surface to this change (`doc/changes/2026-11/2026-11-18--GH-347--dispatch-core-parity/chg-GH-347-spec.md:107,246`); the M4 backlog row requires per-ref status, a bounded per-ref log, the is-delivering query, last-message from the persisted transcript, and per-ref harness-output persistence (`doc/planning/oss-tooling/milestones/m4/backlog.md:46-53`); the flip plan places F1b after F1a and records that only `status` and `is-delivering` gate the F6 evidence window (`doc/planning/oss-tooling/milestones/m4/flip-plan.md:47,52,104-107`).

### 2.2 Pain Points / Gaps

- **PG-1 — No typed per-ref state query.** An operator or the CEO cannot ask the typed lane whether a ref is being delivered, by which owner, under which session, or with what last outcome; the durable lane record is inspectable only by reading the store.
- **PG-2 — The shell is the only inspection path.** Answering any of the four questions requires `scripts/deliver-ticket.sh`, whose marker/PID/stdout files are a second truth source the typed path never writes.
- **PG-3 — `stale` has no typed meaning.** The shell derives staleness from a PID-file-plus-liveness probe and silently repairs the file; the durable lane has an advisory owner but no read that says whether that owner is still the owner.
- **PG-4 — No per-ref session output survives a dispatch.** Nothing persists the harness's per-ref stdout, so a failed or stalled typed dispatch leaves no bounded tail to read, and a restart loses the previous iteration's output.
- **PG-5 — No typed access to the PM's final message.** The only typed "message" is a classifier-family sentence on the envelope, so an operator cannot tell a blocker explanation from an engine summary.
- **PG-6 — No boolean in-flight query for scripts.** The CEO loop's "is the CEO blocked on a delivery" check has no typed equivalent, and an exit-code-only convention is unreadable to a JSON consumer.

## 3. PROBLEM STATEMENT

Because the typed dispatch lane exposes no per-ref inspection surface and persists no per-ref session output, an operator or the CEO agent cannot ask `status`, `log`, `is-delivering`, or `last-message` of a typed delivery — live, finished, or absent — without falling back to `scripts/deliver-ticket.sh` and its marker/PID/stdout files, so the shell lane cannot stop being the operator's inspection path and the F6 evidence window cannot be gated on typed `status`/`is-delivering`, even though the durable lane that answers those questions already exists.

## 4. GOALS

- **G-1**: `dispatch status <ref>` answers a complete, honest per-ref state for a live dispatch, a finished dispatch, and a ref with no lane, from the durable lane record alone.
- **G-2**: `dispatch log <ref> [--tail <n>]` answers a bounded, reference-scoped tail of the harness output a dispatch persisted for that ref, and states honestly when nothing was persisted.
- **G-3**: `dispatch is-delivering [<ref>]` answers the in-flight question for one ref and for the repository, with a script-usable exit and a JSON boolean.
- **G-4**: `dispatch last-message <ref>` returns the PM's final assistant message from the persisted session transcript — never a synthesized classifier sentence — and names why it cannot when it cannot.
- **G-5**: The four queries are one command family with the delivered grammar, refusal identities, and `--json` envelope, and they add no token, projection, exit row, record kind, or configuration key.
- **G-6**: The operator read path is read-only and shell-free: zero ledger appends, zero fence acquisitions, zero repairs, zero process starts, and zero reads of any shell-lane artifact.

## 5. FUNCTIONAL CAPABILITIES

| ID | Capability | Rationale |
|----|------------|-----------|
| F-1 | Per-ref `status` over the durable lane | The lane is the single typed truth for "is this ref being delivered, by whom, under which session, with what last outcome"; without a read fold an operator must read the store. |
| F-2 | Bounded, reference-scoped `log` | A failed delivery is diagnosed from its output; a tail must be bounded and must never mix two refs. |
| F-3 | `is-delivering` per ref and repository-wide | The CEO loop's single scriptable question is "is a delivery in progress"; it must answer without a marker file and read as a boolean in JSON. |
| F-4 | `last-message` from the persisted transcript | The message that explains a blocker is the PM's final assistant message; a synthesized sentence cannot replace it. |
| F-5 | One command family with `--json` | Four queries with one grammar, one refusal vocabulary, and one envelope keep the operator surface learnable and scriptable. |
| F-6 | Read-only, shell-free operator posture | An inspection surface must not perturb the lane it inspects, must preserve resumability, and must not reintroduce the shell dependency the typed path removed. |
| F-7 | Per-ref harness-stdout persistence | `log` needs a durable, bounded, reference-scoped artifact written during the dispatch, which does not exist today. |

### 5.1 Capability Details

**F-1 — Per-ref `status`.** The query resolves the repository identity of the current checkout with persistence disabled, takes one bounded retained-window read of `dispatch.lane` records, **filters those records to the resolved repository first**, and only then folds the filtered set to the newest record per ref, answering for that `(repository, ref)`. The order is normative: the lane key carries no repository component, so a fold performed before the filter would let a newer record for the same ref under a foreign repository win and turn a local answer into `absent` or carry foreign facts into it. It answers `delivering`, `stale`, `marker`, `probe`, `pid`, `sessionId`, and the lane facts (`attemptId`, `harness`, `iterationOrdinal`, `restartsConsumed`, `ownerStartedAt`, `lastToken`, `lastOutcome`, `recordedAt`). `marker` is the shell's operator-visible marker name derived from the durable record's state: `active` for an `active` record, `terminal` for a `terminal` record, and `absent` when the ref has no lane in this repository. No marker file is read, written, or invented. `delivering` is true exactly when the newest record is `active` and the advisory probe has not confirmed the owner gone; `stale` is true exactly when the newest record is `active` and the probe reports the owner gone. The probe is tri-state — `live`, `dead`, `unknown` — and an `unknown` probe never asserts staleness: the durable state stands and the reader sees `probe=unknown`. The probe matches a process id with the recorded start instant within a declared 5 000 ms tolerance (the shell's tolerance), so a reused process id is not reported live. A `dead` verdict, and therefore a `stale` answer, is an observation about the advisory owner facts only: the queue lease remains the exclusion mechanism, and the read never rewrites, clears, or repairs the lane, because a stale-but-recorded lane is still the resumable artifact. An absent ref is a successful answer, not a failure. Source: ticket task "per-ref `status` (delivering, pid, session id, stale, marker)"; TDR-0049; `feature-dispatch-engine.md` lane-record section.

**F-2 — Bounded, reference-scoped `log`.** The query lists only the addressed reference's own directory under the artifact family described in F-7 — that listing is the only listing it performs and reads are confined to files inside it, never listing, globbing, or reading across references and never touching another ref's directory. It stitches the retained files in name order into one byte stream, drops an unterminated tail (a torn write, never returned as content), splits on LF, and returns the newest `--tail <n>` lines oldest-to-newest; because the stitching precedes the split, a value continued across a segment boundary is reconstructed rather than read as two fragments. Reads are snapshots: a segment switch or an append in flight may mean the newest bytes are not yet in the answer, which states what was durable at read time. `--tail` is a canonical decimal in 1..500 with a default of 50 (the shell's default), refused rather than clamped; a value outside the range, a sign, whitespace, or a leading zero is an input refusal. A tail is bounded twice: by the requested line count, and by the delivered machine `data` bound of 65 536 bytes and the declared human bound of 200 lines and 32 768 bytes. When a bound binds, the answer carries **exactly one** truncation fact naming the bound that bound, the bound value, and the omitted line count, following the delivered digest convention. The precedence is declared so that only one fact can ever be emitted: the byte bound is applied after line selection, so a binding byte bound (the machine `data` bound, or the human 32 768-byte bound) yields scope `bytes`; otherwise a shorter line count than requested — the requested tail, or the retained window holding fewer lines, a returned continuation whose beginning retention removed, or only the stream's first segment — yields scope `tail`. The human 200-line bound is a line bound and therefore a `tail`-scope fact, not a `bytes` one. A ref whose artifact directory does not exist — including any lane written before this change and every lane of a one-shot adapter such as Claude Code, which has no stream to capture — answers `available=false` with the reason `no-log` at exit 0, where `no-log` means "no artifact exists for this ref", and it has exactly two named causes — a one-shot adapter that streams nothing for `log`, and a pre-change lane that has no artifact — and it never means "the session printed nothing"; a file that exists but cannot be read answers `available=false` with the reason `unreadable` at exit 1. A retained file that holds no complete line answers `available=true` with an empty line list, so "no output" and "no capture" are never conflated. **Declared divergence from the shell's `--log`:** the typed tail is the harness's own stdout — for opencode, its JSON event stream — while `cmd_log` tails `<REF>.log`, which holds the opencode child's stderr, and the wrapper's own `log_info`/`log_warn` progress lines reach the wrapper's terminal and neither file. The typed tail therefore captures neither the child's stderr nor the wrapper's progress; the ticket's requirement (persist harness stdout per ref) is the authority, and the divergence is stated in the reference page and the operations guide. Source: ticket task "per-ref `log` with bounded tail"; shell `cmd_log` parity with the stream difference declared.

**F-3 — `is-delivering`.** One query with two admissible forms inherited from the shell's `--is-delivering [REF]`: a per-ref form and a repository-wide form with no ref. The per-ref form answers whether that ref's newest lane is active and not stale; the repository-wide form answers whether any ref in the current repository has such a lane and lists up to 20 of them, with one truncation fact when more exist. Both forms read one bounded retained-window read, **filter it to the resolved repository first, and fold the filtered set to the newest record per ref afterwards** — the same order as `status` and for the same reason, since the lane key carries no repository component and a fold-then-filter would let a newer foreign record for one ref decide a local answer, or `absent` for a ref that does have a local lane. The answer is a boolean fact, and the exit mirrors the shell: 0 for "in progress", 1 for "not in progress". The JSON form carries the boolean explicitly, so no consumer has to infer the answer from an exit code, and the negative answer is a data-bearing envelope with no error object. A stale active lane does not make the answer true (this is the one deliberate divergence from a naive state fold, and it matches the shell's live-PID semantics). A failed lane-store read is the store's typed failure at that row's projection, never a fabricated "no". Source: ticket task "`is-delivering`/is-delivering query"; the PM-recorded interpretation that both forms are admissible; shell `cmd_is_delivering` parity.

**F-4 — `last-message`.** The query resolves the newest `dispatch.lane` record for the `(repository, ref)`, takes its session identity and harness kind, and — only where that harness declares the existing `session-introspection` lifecycle capability as supported — reads the harness's own persisted session transcript through one injected, adapter-owned read seam. The seam hands back the stored final assistant text under the adapter's own read cap and does nothing else: it does not flatten, bound, redact, or mark the text, so no message bound exists at the seam. The **query** composes the answer in a fixed order: the delivered serialization chokepoint first replaces **registered credential values** with `[redacted]` in derived output, then the text is flattened to a single line, then bounded to 512 characters, and only then is `truncated` set from the post-redaction length, true exactly when text was cut, so a registered credential straddling the cut cannot survive as a disclosed prefix. The answer makes no general content-scrubbing claim: prose, values the harness itself printed, and anything outside the declared credential set are returned within the bound. It never composes a sentence: it reads no attempt record, no derivation payload, and no envelope field, and it performs zero session operations (no spawn, resume, deliver, collect, terminate, or listing), so reading a message can never start, resume, or disturb a delivery. The answer declares finality: `final` is true exactly when the lane's newest record is `terminal`; on an `active` lane the answer is the latest assistant message observed so far — it may be partial, because a live transcript can be mid-write — and it is declared not final, so an in-flight or partial message is never presented as a conclusion. The fallback ladder is closed and ordered: no lane → `no-lane`; the lane's harness declares `session-introspection` as a gap → `capability-gap` (the Claude Code lane, whose declared reason is `headless-mode-limitation`); the session is unknown to the harness storage → `session-unknown`; the transcript holds no assistant message → `no-message`; the storage cannot be read → `unreadable`. Every negative answer is a data-bearing envelope with the reason and exit 1; an unreadable lane store keeps its delivered `state.*` failure identity; no new error identity is introduced for any ladder step. The read adds no operation, no capability-union member, and no gap reason: it is the content use of the declared capability, so adapter conformance parity and the gap inventory are unchanged, and giving Claude Code a transcript read would change its capability declaration and is a separate decision. Source: ticket task "`last-message` from the persisted session transcript"; ticket AC "returns the PM's final message rather than a classifier sentence"; TDR-0056; shell `cmd_last_message` parity.

**F-5 — One command family with `--json`.** The four forms join the existing dispatch family rather than creating a top-level command: `dispatch status <ref>`, `dispatch log <ref> [--tail <n>]`, `dispatch is-delivering [<ref>]`, `dispatch last-message <ref>`. The reference is the family's canonical `[A-Z]+-\d+` shape; an undeclared flag is `fallback.invocation` (the family's delivered guard), and a malformed or missing ref, an unexpected extra positional, or an invalid `--tail` value is `input.value.rejected`, each decided before any runtime call and therefore before any store read. Each answer carries one declared discriminator (`query`) and is available as human key=value output and as the standard machine envelope through the global `--json`; no query emits a delivery `result` token, appends an attempt record, or writes a lane record, so an inspection never changes what a later dispatch or attempt read reports. A surface that is not composed refuses `input.value.rejected` rather than crashing, following the delivered uncomposed-subfamily pattern. Source: ticket task "wire all four into one command family with `--json`"; delivered family grammar.

**F-6 — Read-only, shell-free operator posture.** All four queries resolve the repository identity with persistence disabled, perform at most one bounded lane-ledger read over the retained window and at most one bounded artifact read — a stitched join of at most the two retained files, after listing only the addressed reference's own directory — or one transcript read, take no fence, append nothing, delete nothing, start no process (the owner probe only observes the process table through the injected seam), and make no network call. They read no shell-lane artifact: the delivering marker, PID files, `<REF>.pm.out`, `<REF>.log`, `<REF>.last-message`, and the wrapper's terminal output are neither read nor written, so the shell's files can never become a second answer for a typed dispatch, and the typed answer is unaffected by their presence, absence, or content. The new read surfaces join the declared dispatch-flow list the no-shell invariant scans, and a planted shell reference in them fails by name. Source: ticket AC "no shell script is read or executed"; TDR-0049 C-4; `feature-dispatch-engine.md` no-shell and read-only-posture sections.

**F-7 — Per-ref harness-stdout persistence.** During a dispatch of a **streaming** adapter, the engine writes the harness's own stdout for the reference into `dispatch-logs.<workspace>/<REF>/`: a directory per work-item reference holding one append-only file per **stream** the reference opens, where a stream is a spawn, a resume, or a deliver. A **one-shot** adapter (Claude Code) yields no `stream.lines`, so it opens no stream, gets no sink, and produces no artifact directory — its lanes answer `no-log`, which means "no artifact exists for this ref" (here because a one-shot adapter streams nothing; the other named cause is a pre-change lane with no artifact), never "the session printed nothing". Each stream's sink is bound when that stream starts and before its first yielded value, so the line on which the handle settles and everything before it are captured, and a restarted iteration's output lands in its own file. A file is `0600`, receives only `O_APPEND` appends — one per value that fits, several for a value longer than the cap — is never modified after it is written, and needs no coordination or lock file because no two streams share a write target. **One writer rule:** every yielded value is written followed by exactly one LF — including the stream's final remnant, which is a yielded value like any other — so nothing is appended verbatim and each value contributes its own terminating LF; a value that fits — in the current file, or whole at the start of the next — is appended in one `O_APPEND` write, while a value longer than the cap is appended in several; **the concatenation of one stream's files in name order therefore reproduces that stream's value stream exactly, every value followed by one LF**. The single stated exception belongs to the oversized-value rule below: a file filled by a value longer than the cap ends mid-value and continues in the next file, so a file taken alone need not end on a record boundary even though the concatenation does. A file is capped at 1 048 576 bytes by starting the stream's next segment; a value with its LF that does not fit and is longer than the cap is split at the boundary — the current file is filled to exactly the cap and the remainder continues at the start of the next file — while a shorter value that does not fit starts the next file whole, so only a value longer than the cap can leave a file beginning mid-line and no value is ever dropped for being large. **One tear rule:** an unterminated tail in a file is a torn write left by a killed process and is dropped by the reader, never returned as content. File names derive from data the writer already holds — the stream's recorded time, the attempt identity, the iteration ordinal, the **stream kind** (spawn, resume, deliver) or an explicit stream ordinal, and the segment ordinal, zero-padded — so the inputs separate every stream, including two streams of the same attempt and the same iteration recorded at the same instant, which cannot therefore collide on one name; lexical order equals creation order across restarts and concurrent streams, and the requirement is that equality, with the exact encoding implementation-decided (Appendix D). This is deliberately **not** a shared counter, because a counter would reintroduce coordination. Retention is the newest two files per reference by name, so the family is bounded at 2 × 1 048 576 bytes per reference; when a third file appears the oldest is removed best-effort after the new file exists. The family lives inside the dispatch project state root and outside the delivery store's record set, derived-document set, salvage path, and repair path — the delivered sidecar-artifact pattern. Writing is an observation beside the delivered stream drain and is non-gating rather than non-blocking: the append runs on the delivered line iteration and therefore adds latency to the drain, and a sink fault never changes the delivery token, the exit, the attempt record, the lane record, or the evidence, and adds no evidence identifier. The family exists only for a streaming adapter; the only payloads this change persists are harness stdout (this family) and the boundedly read final assistant message (never written by the engine); the engine adds no prompt, diff, credential, tool argument, or provider payload of its own and removes none, so the artifact is unscrubbed by design. It never enters the ledger, a record, an evidence reference, or an envelope beyond the tail the operator asked for. The typed tail is the harness's stdout, not the shell's `<REF>.log` (the opencode child's stderr) and not the wrapper's terminal progress lines. Source: ticket task "persist harness stdout per ref during a dispatch"; backlog row M4-S12 "persist harness output per ref"; TDR-0056; the delivered `telemetrySinkFor` observation pattern and the state layer's sidecar-artifact pattern.

## 6. USER & SYSTEM FLOWS

```
Flow 1: Operator inspects a live dispatch
  dispatch status GH-354
    → resolve identity (persistence disabled) → one bounded lane read
    → newest dispatch.lane for (repository, GH-354) = active
    → advisory owner probe on {processId, startedAt} → live, unknown, or dead
    → answer: delivering=true, marker=active, pid, sessionId, harness, iteration, restarts, probe
    → exit 0 (absent ref is also exit 0, with marker=absent)
```

```
Flow 2: CEO gates on a live delivery
  dispatch is-delivering GH-354        → exit 0 / 1, delivering=true/false
  dispatch is-delivering --json        → refs=[…] over this repository, exit 0 / 1
    → no marker file read; a stale active lane answers false
```

```
Flow 3: Diagnosing a failed dispatch
  dispatch log GH-354 --tail 200
    → list only dispatch-logs.<workspace>/GH-354/ (the one permitted listing; no scan across refs)
    → stitch the retained files in name order into one byte stream (at most two files)
    → drop an unterminated tail (a torn write), split on LF, take the newest 200 lines
    → a value continued across a segment boundary is reconstructed by the stitching
    → the read is a snapshot: an append or a segment switch in flight may not be in the answer
    → one truncation fact when an output bound binds or the retained window is short
      (including the single-retained-file case and a returned continuation whose start is gone)
    → no artifact directory → available=false, reason=no-log, exit 0
      (a one-shot adapter lane always answers this: it streams nothing for `log`)
    → unreadable file → available=false, reason=unreadable, exit 1
    → the content is a streaming harness's stdout (opencode: its JSON events), not the shell's child-stderr log
```

```
Flow 4: Reading the PM's final message
  dispatch last-message GH-354
    → newest lane for the ref → sessionId, harnessKind
    → does the harness declare session-introspection supported? (opencode yes; Claude Code a declared gap)
    → adapter-owned transcript read (read-only, no session operation)
    → final assistant message, 512 chars, one line, registered credential values replaced; final=true iff lane terminal
    → otherwise one closed reason (no-lane | capability-gap | session-unknown | no-message | unreadable), exit 1
```

```
Flow 5: A dispatch persists its own output
  dispatch GH-354 (a streaming harness)
    → each stream (spawn, then a resume or a deliver) binds its sink before its first yielded value
    → create that stream's file in dispatch-logs.<workspace>/<REF>/ (0600), single O_APPEND writes
    → every yielded value followed by exactly one LF, including the stream's final remnant
    → value longer than the file's remaining room: fill to the cap, continue the remainder next file
    → next segment before an append would cross 1 048 576 bytes; newest two files retained (2 × cap)
    → names sort in creation order (recorded time, attempt, iteration, stream kind or ordinal, segment); no shared counter
    → classification → terminal lane record; a sink fault changes no token, exit, record, or evidence
    → a one-shot harness (Claude Code) has no stream and writes no artifact
```

## 7. SCOPE & BOUNDARIES

### 7.1 In Scope

- The four query forms, their grammar, their refusal identities, their human and `--json` payloads, and their exit projections.
- The lane-view fold over the durable `dispatch.lane` record, including repository scoping and the absent-ref answer.
- The tri-state advisory owner-liveness probe and the declared start-instant tolerance.
- The bounded per-ref harness-stdout artifact family, its per-stream write points and binding, its per-file cap with cross-boundary continuation, its 2 × 1 048 576-byte family bound (two retained files), its one writer rule and one tear rule, its posture, and its privacy boundary.
- The injected adapter-owned transcript read seam and the `last-message` fallback ladder.
- The read-only, shell-free operator posture across all four queries and the extension of the no-shell invariant to them.
- The dispatch composition seams the queries need (lane view, artifact tail, delivering fold, transcript read, owner probe) and the production supply of each.
- The decision log for the four-query interpretation, the marker derivation, the staleness rule, the log artifact, the transcript source, the exit projections, the read-only posture, and the scope boundaries.

### 7.2 Out of Scope

- [OUT] Daemon-lane inspection: `dispatch status`/`is-delivering` do not report a lane supervised by the resident daemon.
- [OUT] Any change to delivery semantics: result tokens, projection classes, exits, classifier, derivation, admission, restart, stall handling, or spawn identity.
- [OUT] Any attempt-record field, evidence identifier, schema version, record kind, or `dispatch.lane` field.
- [OUT] Per-ref lane history (all records), a cross-ref operator dashboard, and any change to the top-level `status` digest, `brief`, `board`, or `lanes list`.
- [OUT] Reading, writing, repairing, or deleting any shell-lane artifact (`tmp/deliver-ticket/**`, `.ai/local/delivery/**`), and any shell entry-point change.
- [OUT] New configuration keys, new flags beyond `--tail`, new telemetry rows, metrics, alerts, or events.
- [OUT] The CEO loop's own `loop status`/`loop log` surface (M4-S10), merge/closeout/queue/provider-policy work, and installed-binary work.
- [OUT] Live-kernel process-list parity beyond the declared probe contract and the offline proof boundary.

### 7.3 Deferred / Maybe-Later

- **Daemon-lane answers.** Reporting a daemon-supervised delivery from the same four queries needs a read-side agreement across two record owners (the dispatch lane and `daemon.lane`). TDR-0049 already names "a future shared lane-resolution implementation spanning one-shot and daemon lanes" as a revisit trigger; this change keeps the query surface dispatch-lane-only and defers the shared read. Owner: `@decision-advisor` if a daemon-driven delivery needs the operator surface.
- **Per-ref lane history.** "Show me every lane record for this ref" (iterations, restarts) rather than the newest: TDR-0049's unresolved question about lane history. Revisit when a restart-timeline question cannot be answered from the attempt record and the log artifact.
- **A phase-ledger position on the `status` payload.** TDR-0049's open question about carrying the phase position on the lane. This surface does not need it: the ledger remains the resume-position source, and adding a field would be a payload-schema decision under `delivery.dispatch.lane.v1` key-set rules.
- **Tunable bounds.** The per-file cap, the tail range, and the probe tolerance are declared policy constants, and the retained-file count and the resulting 2 × cap family bound are decided policy in TDR-0056; a configuration key is added only if an operator need to tune them appears (the shell exposed `LOG_LINES` for the same reason the typed tail flag exists).
- **Pinning a one-shot adapter's output.** A one-shot harness (Claude Code) yields no stream, so it has no artifact and `log` answers `no-log`; capturing its output after the fact would be a different artifact shape written from a completed invocation, and it is a different decision (TDR-0056 revisit trigger).
- **Capturing the opencode child's stderr or the wrapper's progress lines.** The typed artifact holds the harness's own stdout only; the child's stderr (the shell's `<REF>.log`) and the wrapper's `log_info`/`log_warn` lines are different streams, and either would need its own shape, bound, mode, and privacy statement. Revisit if an operator reports that the typed tail is insufficient to diagnose a failure.
- **Redaction-at-write for the log artifact.** The artifact is the harness's own stdout, operator-local and `0600`, and the engine adds and removes nothing; a scrubber fed by the declared credential set would imply a general guarantee the system cannot make. Revisit if the artifact ever leaves the local state root or gains a second consumer.
- **Log rotation by date or size generations.** Today one reference has a two-file retained window with a per-file cap; rotating would break "reference-scoped" and complicate the tail contract.
- **Extending the surface to `batch-deliver`-style multi-ref views.** Out of scope for one milestone story.

## 8. INTERFACES & INTEGRATION CONTRACTS

### 8.1 REST / HTTP Endpoints

No inbound or outbound HTTP endpoint is added, changed, or removed. The interfaces are the command family, its payloads, and the injected seams:

| ID | Surface | Contract |
|----|---------|----------|
| API-1 | `dispatch status <ref> [--json]` | Answers the newest `dispatch.lane` record for `(resolved repository, ref)`: `delivering`, `stale`, `marker` (`active`\|`terminal`\|`absent`), `probe` (`live`\|`dead`\|`unknown`\|`not-applicable`), `pid`, `sessionId`, and the lane facts (`attemptId`, `harness`, `iterationOrdinal`, `restartsConsumed`, `ownerStartedAt`, `lastToken`, `lastOutcome`, `recordedAt`) or a null lane. Exit 0 whenever the reads succeed, including the absent answer; a failed lane-store or identity read is a typed failure at its row's projection. Zero appends. |
| API-2 | `dispatch log <ref> [--tail <n>] [--json]` | Answers `available`, the newest `n` lines oldest-to-newest, and **exactly one** truncation fact (`scope` `tail`\|`bytes`, `bound`, `omittedLines`) naming the binding bound; the byte bound is applied after line selection, so a binding byte bound yields scope `bytes` and otherwise a shorter line count (`tail` or the retained window) yields scope `tail`, with the human 200-line bound a line bound and therefore a `tail`-scope fact; a `tail`-scope fact also covers a short retained window, including the single-retained-file case and a returned continuation whose beginning is gone. | API-3 | `dispatch is-delivering [<ref>] [--json]` | Answers `delivering` for the ref, or for the repository with up to 20 delivering refs and one truncation fact. Exit 0 for in progress, 1 for not in progress; the JSON answer carries the boolean with no error object. A failed lane-store read keeps its typed identity. Zero appends. |
| API-4 | `dispatch last-message <ref> [--json]` | Answers `available`, `final`, `message` (composed redact → flatten → bound → mark: registered credential values replaced first, then flattened, then bounded to 512 characters, with `truncated` set from the post-redaction length; no general scrubbing claim), `truncated`, `recordedAt`, and one closed `reason` when unavailable (`no-lane`\|`capability-gap`\|`session-unknown`\|`no-message`\|`unreadable`), where `capability-gap` means exactly that the lane's harness declares `session-introspection` as a gap. Exit 0 when produced, 1 for every closed negative reason, the store's typed failure when the lane store cannot be read. Performs zero session operations. |
| API-5 | Grammar and refusal contract | The canonical reference is `[A-Z]+-\d+`. An undeclared flag is `fallback.invocation`; a missing or malformed ref, an unexpected positional, and an invalid `--tail` value are `input.value.rejected`; each is decided before any runtime call. An uncomposed query surface is `input.value.rejected`, never a crash. Each answer carries exactly one `query` discriminator (`status`\|`log`\|`is-delivering`\|`last-message`). |
| API-6 | Lane-view read contract | One bounded retained-window read of kind `dispatch.lane`, schema `delivery.dispatch.lane.v1`, prefix `dispatch.lanes:`, **filtered to the resolved repository first and only then folded to the newest record per ref** — the declared order for `status` and for both `is-delivering` forms, because the key carries no repository component and a newer foreign record for the same ref would otherwise win. Daemon lanes contribute nothing. An unreadable fold is the store's typed failure, never an empty answer. Identity resolves with persistence disabled, so no checkout marker is created, repaired, or re-persisted. |
| API-7 | Log artifact read contract | Lists only the addressed reference's own directory — the only permitted listing — and reads only files inside it; it never lists, globs, or reads across references. Stitches the retained files in name order into one byte stream, drops an unterminated tail (a torn write, never returned), splits on LF, and returns the newest requested lines; a value continued across a segment boundary is reconstructed. Bounded to the requested tail and the declared output bounds, with exactly one truncation fact when a bound binds or the retained window is short (including the single-retained-file case and a returned continuation whose beginning retention removed). Reads are snapshots. No shell read, no deletion. An absent directory (`no-log`, the answer for every one-shot lane) and an unreadable file (`unreadable`) are distinct answers; a retained file with no complete line is an empty, available answer. |
| API-8 | Per-stream stdout observation seam | The dispatch composition supplies a per-ref sink for every stream a **streaming** adapter opens — spawn, resume, and deliver — bound when that stream starts and before its first yielded value, so the acquisition-settling line and values the event decoder skips are captured; a one-shot adapter has no stream and gets no sink. | API-9 | Transcript read seam | An injected, adapter-owned, read-only read: given a harness kind, a session identity, and a work-item reference, it returns the **stored final assistant text under the adapter's own read cap** or one closed absence (`capability-gap`, `session-unknown`, `no-message`, `unreadable`). It imposes no message bound of its own — it does not redact, flatten, bound to 512 characters, or set `truncated`; that composition (redact → flatten → bound (512) → mark truncated) belongs to the query and is the **sole** place the 512-character bound and the single-line flattening happen, so the seam cannot cut a value before redaction and a registered credential straddling the published cut cannot survive as a prefix. It is called only for a harness that declares the existing `session-introspection` lifecycle capability supported (opencode) and is not called for one that declares it as a gap (Claude Code, `headless-mode-limitation`), where the answer is `capability-gap`. It adds no operation, capability-union member, or gap reason. It takes no live handle, performs no session operation, spawns nothing, and administers nothing on a live session store. |
| API-10 | Owner-liveness probe seam | An injected advisory probe: given `{ processId, startedAt }`, it returns `live` when a process with that identity exists and its observed start instant is within the declared 5 000 ms tolerance of the recorded instant, `dead` when it is confirmed absent or outside the tolerance, and `unknown` when the process table cannot be read. It is advisory only: no admission, exclusion, or resumability decision reads it. |
| API-11 | Query exit projection | The query payloads project through the command definition's data projection: `status` → `success`; `is-delivering` → `success` when delivering, `user-validation` when not; `log` → `success` for a produced tail or `no-log`, `user-validation` for `unreadable`; `last-message` → `success` when produced, `user-validation` for every closed negative reason. No error-table row and no delivery-result token is involved. |
| API-12 | No-shell and no-script contract (extended) | The four query surfaces and the per-stream log sink are added to the declared dispatch-flow surface list the no-shell invariant scans. A script-path literal, a shell-capable child-process use, or a shell invocation in those surfaces fails the invariant by name. No query reads a shell-owned artifact path. |

No event, message, or telemetry record is added. The four queries append no durable record and publish no event; their invocation is recorded only by the delivered command audit ledger entry that every command invocation already produces. The log artifact and the transcript read are data reads and not records. The delivery path's existing event and record families are untouched.

### 8.4 External Integrations

One local content read is added and no network integration is touched: the opencode persisted session store, read-only and bounded, reached only for a lane whose harness declares `session-introspection` supported (the delivered telemetry capture already opens the same store with a query-only pragma). Claude Code is not a read source for this change: its adapter declares `session-introspection` as a gap (`headless-mode-limitation`), its only persisted-session reader is the statistics-only telemetry capture under `telemetry-extraction`, and a Claude lane therefore answers `capability-gap`; giving it a content read would change that adapter's capability declaration and is a separate decision. The artifact family is local storage the engine writes itself, not an integration. Both are local and adapter- or engine-owned, and absent from the offline battery, which injects the transcript seam and the artifact path. Live provider reads, credentials, and tracker access are untouched: no query resolves a credential, makes a network call, or performs a tracker read.

### 8.5 Backward Compatibility

- **Delivery behaviour unchanged.** No token, projection, exit, classifier, derivation, admission, restart, stall, or spawn fact moves. A dispatch invocation and its envelope are byte-identical to the delivered contract apart from the log artifact's side effect on local disk.
- **Lane and attempt records unchanged.** `dispatch.lane` keeps its kind, schema, fields, states, write points, and latest-wins read; `dispatch.attempt` keeps its schema version, field set, and 16-reference evidence budget. Pre-change records read unchanged and need no migration.
- **Pre-change lanes answer honestly.** A ref whose lane was written before this change has no artifact directory, so `log` answers `no-log`; its lane record still answers `status`, `is-delivering`, and (through the transcript) `last-message`. Nothing is fabricated or backfilled.
- **Grammar additive.** Four new forms and one new value flag (`--tail`) are added to the dispatch family; the four delivered forms, the `attempts` subfamily's own refusal convention (unknown option → `input.value.rejected`), and `--resume-prompt` semantics are unchanged.
- **Exit convention declared.** `is-delivering` returns 1 for "not in progress" and `last-message` returns 1 for "no message", mirroring the shell's 0/non-zero contract. Because 1 is also the `user-validation` exit, every negative answer carries its fact in the payload (and in `--json`), and the reference page states the convention explicitly. This is a declared, documented divergence from "a non-zero exit always means a refusal" and it follows the delivered handover precedent where a readable-but-unmet bar projects `user-validation`.
- **Human-output shape for one query differs deliberately.** `dispatch log` human output is the raw tail (followed by at most one `truncation=` line), because a log rendered as key=value would not be a log; the family's other forms stay key=value. `last-message` human output is the declared key set (`available`, `final`, `reason`, `last_message`) rather than the shell's bare message line, so the family keeps one human convention while the message remains machine-extractable.
- **The typed tail is not the shell's log stream.** `dispatch log` returns a streaming harness's own stdout; the shell's `--log` returns the opencode child's stderr held in `<REF>.log`, and the wrapper's own progress lines reach its terminal. The two surfaces answer related but different questions, the difference is documented in the reference page and the operations guide, and neither becomes the other's truth source (RSK-12).
- **A one-shot adapter has no tail, and the absence is stated.** Claude Code opens no stream, so no artifact directory exists and `dispatch log` answers `no-log` for every Claude Code lane. `no-log` means "no artifact exists for this ref" and has exactly two named causes — a one-shot adapter that streams nothing and a pre-change lane that has no artifact; it never means "the session printed nothing". `status` still answers and `last-message` follows its own capability rule, and the reference page and operations guide say so (RSK-17).
- **Shell lane untouched.** The shell keeps its files, its queries, its exits, and its self-healing behaviour. The typed path neither reads nor writes them, so a repository in `dual-run` can use both surfaces without either becoming a second truth source for the other.
- **Stale is not repaired.** The shell clears a stale PID file; the typed read does not touch the lane, because the lane is the resumable artifact and a read must not destroy resumability. An operator who wants the ref re-dispatched relies on the queue lease and the lane's own state, not on a repair side effect.
- **Documentation moves with the contract.** The current-truth dispatch page, the autonomous-delivery page, the engine-first operations guide, and the command reference page are reconciled in the documentation phase (Appendix A); no page is left saying the typed path has no status/log surface.

## 10. TELEMETRY & OBSERVABILITY REQUIREMENTS

- The durable `dispatch.lane` record is the observability surface for per-ref state and becomes operator-visible through `status`; it gains no field.
- The per-ref log artifact is an operator debugging artifact, not telemetry: it is not a record, has no retention schedule beyond the declared per-file cap and two-file rule, and is not read by any evaluator, gate, summary, or fleet row.
- No new metric, alert, event, telemetry row, or derived document is introduced. The command audit ledger records the invocation as delivered for every command.
- `last-message` reads the harness's own persisted transcript — only where the harness declares `session-introspection` supported — and writes nothing; no transcript content is copied into any record, evidence list, log line, or derived document.
- The probe verdict is reported in the answer (`probe`) and is never persisted, so a stale observation cannot become durable truth.
- An operator can distinguish "no artifact exists" (`no-log`) from "no output" (available, empty), "cannot read" (`unreadable`), and "the retained window is shorter than the request" (one truncation fact) without inspecting files.

## 12. ASSUMPTIONS

- The durable `dispatch.lane` record is the authoritative typed per-ref state and its latest-wins read is sufficient to answer `status` and `is-delivering`; no additional durable fact is required.
- The owner process facts are advisory; the queue lease remains the exclusion mechanism, and no query may derive an exclusion or admission decision from them (TDR-0049 C-1/C-6).
- A stale active lane is still resumable, so a read must not repair it; the shell's PID-file self-healing is a shell-file concern that does not transfer to a durable record.
- The harness session outlives its process, so a finished lane's session identity still resolves a transcript; a failure to resolve one is an honest negative answer.
- The seam is capability-gated through the existing `session-introspection` declaration rather than a new capability: opencode declares it supported and serves the read, and Claude Code declares it as a gap (`headless-mode-limitation`) and answers `capability-gap`, so this change adds no Claude transcript read. The specification does not narrow the capability to metadata, and this change reads it as "the adapter can introspect a session it owns", applied to content.
- Harness stdout is the operator's diagnostic payload and may be persisted locally unscrubbed, matching the shell's existing `tmp/` capture: the engine adds and removes nothing, the family is local and `0600`, and the two-file window bounds it at 2 × 1 048 576 bytes per reference. If the artifact ever leaves the local state root, scrubbing at write or export becomes a new decision.
- A value's appends — one for a value that fits the current file, several for a value longer than the cap — go to a file no other stream writes, so they do not interleave with another stream's bytes; a process killed mid-write leaves at most one unterminated tail, which the reader drops as a torn write.
- The steady-state write cost is dominated by the bytes written — one file creation per segment and one append per yielded value, with no per-value work proportional to the file or the family — and the append latency on the delivered line iteration is acceptable; it never changes the token, exit, record, or evidence.
- The newest two files (2 × 1 048 576 bytes) are an adequate diagnosis window for a single dispatch; an operator who needs the start of a longer run is a revisit trigger for the retained count, not a correctness failure.
- Reads are snapshots: a segment switch or an append in flight can make `log` answer a slightly stale tail, and an active lane's transcript read can be partial. Both are declared rather than locked against, because an inspection must not coordinate with the writer.
- A one-shot adapter yields no stdout stream, so it has no artifact family member and `log` answers `no-log` for every such lane; the absence is a property of the adapter's invocation shape, not a capture failure.
- The delivered retained-window bound (5 000 records) is an adequate scan bound for the repository-wide `is-delivering` form; refs beyond the window are indistinguishable from absent refs, which is the same trade the attempt read side already makes.
- `--json` is a global flag, so no per-command envelope work is required beyond a valid payload.
- The four queries are the complete F1b scope; `log` and `last-message` may land after `status` and `is-delivering` (flip-plan F6 gating), but the change delivers all four.

## 21. PRIVACY / COMPLIANCE REVIEW

- **No personal data is introduced.** The answers carry a work-item reference, a repository identity, a session identity, a process id, timestamps, counts, closed reason words, and the PM's final message. The first five are operational identifiers already present in the delivered lane and attempt records.
- **The final message is the one content payload in output.** It is the PM's own final assistant text, composed redact → flatten → bound → mark: the delivered serialization chokepoint replaces **registered credential values** with `[redacted]` first, then the text is flattened, then bounded to 512 characters, and `truncated` is derived from the post-redaction length — so a credential straddling the cut cannot be disclosed as a prefix. That is the whole guarantee: prose, values the harness itself printed, and anything outside the declared credential set are returned within the bound, and no general content scrubbing is claimed. It is released only when an operator explicitly asks for it.
- **The log artifact is the one content payload at rest.** It is a streaming harness's own stdout: one append-only file per stream in a per-ref directory inside the local project state root, `0600`, whose concatenation — one stream's files in name order — reproduces that stream's value stream exactly (every yielded value followed by exactly one LF, with nothing appended verbatim, and the sole exception that a file filled by a value longer than the cap ends mid-value and continues in the next file), capped per file at 1 048 576 bytes by segmentation (such a value is continued, not dropped), and bounded to the newest two files, 2 × 1 048 576 bytes per reference. An unterminated tail is a torn write and is never served as content. The files are never committed, never placed in the ledger or a record, and never served beyond the tail an operator requests. They are **unscrubbed by design** — the engine adds and removes nothing — because a scrubber fed by the declared credential set would imply a guarantee the system cannot make; this mirrors the shell's pre-existing local stdout capture rather than introducing a new class of data.
- **Content is scoped and bounded.** One directory per reference and one file per stream mean one work item's output can never be read as another's or as another iteration's; the reader lists only the addressed directory, and the two-file retention bounds the family at 2 × 1 048 576 bytes per reference.
- **No secret is written by the engine.** The engine writes only what the harness itself printed; it adds no prompt, environment value, credential, or tool argument to the artifact. The credential and environment seams are untouched.
- **No new flow of data leaves the machine.** The added read is a local storage read — served only where the harness declares `session-introspection` supported — and no telemetry, network, or provider path carries session content.
- **Read-only posture over user data.** The transcript read is read-only, bounded, and administers nothing on a live session store, mirroring the delivered telemetry-capture posture; no query deletes an artifact file.
- **Compliance posture is unchanged.** No retention, export, residency, or consent obligation is created by a local, bounded, operator-local debugging artifact.

## 22. SECURITY REVIEW HIGHLIGHTS

- **The inspection surface is not an authority.** The probe and the lane view are advisory; admission, exclusion, and resumability still come from the queue lease and the durable records. A stale answer can never authorise a second dispatch.
- **No write path is added to a read path.** Zero appends, zero fence acquisitions, zero repairs, and persistence-disabled identity resolution mean the queries cannot be used to mutate, truncate, or re-key delivery state — the failure mode that a "self-healing status" would introduce.
- **No shell surface.** The queries never read or execute a script, and never read a shell-owned path, so a stale or attacker-influenced file under `tmp/` or `.ai/local/` cannot steer a typed answer.
- **Bounded inputs and outputs.** Ref and `--tail` are shape-checked before any read; every read and every output has a declared bound; a bound that binds is declared rather than silently dropped; a query deletes nothing inside the artifact family, whose only deletion path is the declared retention rule.
- **Content at rest is local and minimal.** The artifact is `0600` under the project state root, one directory per ref with one file per stream, capped per file by segmentation and bounded to two files (2 × 1 048 576 bytes per reference), and never indexed as evidence; an unterminated tail is a torn write and is never returned, and the artifact is unscrubbed by design, so no reader may infer that a value present in it was approved for disclosure. The transcript read is read-only and returns one bounded message with registered credential values replaced.
- **The message is redacted before it is bounded.** Composition is redact → flatten → bound → mark, so a registered credential straddling the 512-character cut is replaced before the cut is applied and cannot survive as a disclosed prefix; `truncated` reflects the post-redaction length. The claim stops there: prose and values the harness itself printed are returned within the bound, and no page may present this as content filtering.
- **One divergence, declared.** The typed tail does not carry the opencode child's stderr or the wrapper's progress lines; an operator who needs those keeps the shell lane, whose files the typed path never touches and never treats as a second truth source.
- **No new identity or taxonomy row.** Every negative answer is a data fact, so no error class is widened and no consumer can mistake a "no message" for a security event.
- **Scope safety.** No delivery semantic, record, or shell change is introduced, so the security review surface is the new read seam, the probe, and the artifact family — all explicitly bounded.

## 23. MAINTENANCE & OPERATIONS IMPACT

- **Four stable read forms:** an operator routine can be written against them, and the CEO prompt can name the typed forms instead of the shell ones.
- **One new artifact family with declared bounds:** operating it means knowing one path shape, one per-file cap, one 2 × cap family bound, and one privacy boundary; there is no retention job, no rotation, and no index to maintain, and a one-shot harness simply has no member of the family.
- **The transcript read follows the capability declaration.** opencode implements it; Claude Code's existing `session-introspection` gap (`headless-mode-limitation`) answers `capability-gap`; a new harness either declares the capability or keeps the gap, and only `last-message` degrades either way.
- **One derivation, one source.** `status` has no second truth source: given a lane record and a probe verdict, any reviewer can compute the answer.
- **No configuration surface to operate.** Every bound is declared policy (the retained-file count and family bound in TDR-0056, the rest in this specification); changing one is a documented contract change, not a config edit.
- **Diagnosis is cheaper.** A failed delivery now has a bounded typed tail and a real final message, so tokens are not spent rediscovering facts from files.
- **Cost:** four local reads per inspection; no session, no network, no model call. The write-side cost is one `O_APPEND` write per observed stdout value that fits the current file — a value longer than the cap is continued in further appends across segments — on the delivered line iteration, non-gating, but it adds latency to the drain (RSK-16).

## 24. GLOSSARY

| Term | Definition |
|------|------------|
| Lane view | The folded, repository-scoped newest `dispatch.lane` record for a work-item reference, joined with the advisory probe verdict; a derivation, not a record. |
| Marker | The operator-visible state name derived from the lane record's `state`: `active`, `terminal`, or `absent`. No marker file exists on the typed path. |
| Stale lane | An `active` lane record whose recorded owner process is confirmed gone; still the resumable artifact, never repaired by a read. |
| Advisory probe | The injected, tri-state (`live`/`dead`/`unknown`) observation of the recorded owner facts with a start-instant tolerance; never an exclusion input. |
| Log artifact | The per-ref artifact directory `dispatch-logs.<workspace>/<REF>/` and its append-only per-stream segment files, written during a dispatch and read by `dispatch log`; outside the state store's record set. |
| No-log | The `log` answer `available=false, reason=no-log`, meaning "no artifact exists for this ref"; its two named causes are a one-shot adapter that streams nothing and a pre-change lane with no artifact. It never means "the session printed nothing". |
| Stream | One spawn, resume, or deliver of a reference on a streaming adapter; its stdout becomes that reference's own append-only file (or a sequence of segment files), so output is attributable by file name. A one-shot adapter opens no stream. |
| Segment file | One file of a stream's output, `0600`, capped at 1 048 576 bytes: the writer starts the next segment rather than modifying bytes already written, and continues a value longer than the cap across the boundary, so only such a value leaves a file beginning mid-line. |
| Family bound | The declared ceiling on one reference's artifact family: the newest two files, 2 × 1 048 576 bytes, decided policy in TDR-0056 and not a per-change constant. |
| Declared transformation | The only change the engine makes to a stream's stdout: every yielded value followed by exactly one LF, including the stream's final remnant. Nothing else is added or removed, so the concatenation of one stream's files in name order reproduces its value stream exactly — except that a file filled by a value longer than the cap ends mid-value and continues in the next file — and an unterminated tail is a torn write rather than content. |
| Torn write | An unterminated tail in an artifact file, left by a process killed mid-write; the reader drops it and never returns it as content. |
| Reference-scoped | Bound to exactly one work-item reference: one artifact directory, one lane, never a scan across refs. |
| Transcript read seam | The injected, adapter-owned, read-only read of the harness's persisted session storage that returns the final assistant message; covered by the harness's `session-introspection` capability (opencode supported; Claude Code a declared gap, answered `capability-gap`). |
| Final message | The final assistant message of the recorded session — the PM's own words — as distinct from the envelope's synthesized `lastMessage`. |
| Finality fact | The `final` boolean on a `last-message` answer: true exactly when the lane's newest record is `terminal`. |
| Closed negative reason | One of `no-lane`, `no-log`, `capability-gap`, `session-unknown`, `no-message`, `unreadable`; a data fact, not an error identity. |
| Read-only posture | Zero appends, zero fence acquisitions, zero repairs, zero process starts, zero network reads, persistence-disabled identity resolution. |
