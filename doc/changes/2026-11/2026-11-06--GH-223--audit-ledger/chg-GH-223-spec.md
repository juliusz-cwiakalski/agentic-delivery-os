# CHANGE SPECIFICATION

> **PURPOSE**: Give every command invocation exactly one durable, tamper-evident audit record — including caller identity when claimed — so scripted outputs can drop context fields agents do not need and auditor or retro consumers get a trustworthy record.

## 1. SUMMARY

This change adds the M1-S22 command audit ledger: an append-only, schema-versioned record in the state layer that captures one record per CLI invocation — runId, command, arguments (through the redaction chokepoint), exit code, timing, outcome class, scope/repo, a wall-clock start timestamp and monotonic audit-sequence ordinal, and the calling agent's claimed identity when provided. It specifies the agent-identity convention (an environment variable named through the branding seam, recorded as claimed, never inferred when absent) while the spawn-side setter and harness-plugin rendering stay out of scope. Landing the ledger activates the owner-pinned scripted-mode trim of the M0-S3 machine envelope — scripted `--json` emits one minified `{"data":...}`/`{"error":...}` line while schemaVersion, runId, and timing live in the audit record (errors keep runId as the correlation key) — and adds tamper-evident hash chaining with a chaining key that never enters lane environments, plus a bounded, filtered read surface for retro and auditor consumers.

## 2. CONTEXT

### 2.1 Current State Snapshot

M0-S3 delivered the command-surface result contract: every command renders one `CommandResult` envelope (`schemaVersion` `delivery.result.v1`, opaque `runId`, `exitCode`, `timing`, exactly one of `data`/`error`); failures resolve through a machine-readable error table with a binding bidirectional documentation sync check; exit codes exist only in the standalone CLI projection (`{0, 1, 2}`); and a single serialization chokepoint redacts registered secret values before any byte reaches a stream. The surface is exercised through a deterministic, in-process entry point taking injected streams, clock, run-id factory, brand, secrets, and command program; a testkit conformance validator and golden fixtures (each case requires its golden; none may be skipped) bind the envelope bytes.

M0-S5 delivered the state layer: an append-only, schema-versioned JSONL ledger (`delivery.state.v1`) as single durable truth over one store per workspace, composed through a driver-neutral public port (append, verified reads with key-set assertions, fences, derived-document replace, salvage). Consumers (delivery registry, provider parks, closeout outcomes) add record kinds additively inside the same schema version; validated artifact boundaries classify valid, verified-empty, torn, and unknown verdicts; runtime APIs appear only at the driver edge; retention is forever; evidence names paths, positions, and counts — never payload or checksum bytes. The state layer imports contracts and its own modules only and never imports branding.

The branding seam derives `BrandIdentity.environmentPrefix` (uppercase prefix with a trailing `_`) as the naming root for the environment layer; a forbidden-literal scan binds in CI and user-facing docs must be registered in its registry. The M1 milestone pack proposes the envelope formatting amendment: interactive terminals keep the full pretty envelope; scripted or piped output (the agent case) trims to one minified line carrying only `data` or `error`, with the trimmed context fields moving to the command audit ledger and errors keeping `runId`. The milestone architecture places the command audit ledger in the learning plane, feeding the retro pipeline, and pins the identity trust model: unauthenticated attribution, recorded as claimed, not proven. Nothing audit-related exists today: invocations leave no durable trace, the CLI has no scripted-vs-interactive output distinction, and no agent identity is captured anywhere.

### 2.2 Pain Points / Gaps

- **No invocation trail:** when a delivery misbehaves — wrong verdict, surprising exit, unexpected side effect — there is no durable record of which command ran, with which arguments, producing which outcome. Retro and auditor agents have nothing trustworthy to read.
- **Agent context pays for context it cannot use:** every scripted `--json` consumer receives schemaVersion, runId, and timing on every line. The owner has pinned that these fields belong in an audit ledger, not in the agent's context — but the ledger that makes the trim safe does not exist, so the trim cannot land.
- **No caller attribution:** nothing records which agent invoked a command. The identity convention (seam-named environment variable, set at spawn from agent role plus lane id) is unpinned in the delivered system, and nothing records the claimed value.
- **No tamper-evidence:** the state layer's per-record checksum detects corruption but is not keyed — an altered record with a recomputed checksum reads as valid. The backlog pins keyed hash chaining so records cannot be altered undetectably within the trust model.
- **Unbounded reads would be unsafe by default:** once the ledger exists, a naive dump exposes every historical command line in one payload; retro/auditor access must be bounded and filtered.

## 3. PROBLEM STATEMENT

Because the delivered system keeps no durable per-invocation record — no command, arguments, outcome, timing, scope, or claimed caller identity — an operator or retro/auditor agent cannot reconstruct what any invocation did, scripted agents receive context fields the owner has ruled belong in an audit ledger rather than their context, and a record that did exist could be altered without detection because the state layer's integrity checks are unkeyed; consequently the delivery engine cannot trust its own history, and the pinned scripted-mode trim stays blocked.

## 4. GOALS

- **G-1**: Complete per-invocation audit trail — exactly one audit record per command invocation (success, classified failure, unknown failure, broken invocation alike), carrying runId, command, redacted arguments, exit code, timing, outcome class, scope/repo, and claimed identity when provided; idempotent re-runs are distinct records distinguished by runId.
- **G-2**: Specified agent-identity convention — an environment variable named through the branding seam, recorded verbatim as claimed attribution when present and never inferred when absent; the setter-side convention (harness adapter at spawn from agent role + lane id, per-lane-unique; harness-plugin rendering into agent shells) is specified, not implemented.
- **G-3**: Scripted-mode context trim enabled — the envelope context fields (schemaVersion, runId, timing) are recorded in the ledger, activating the owner-pinned trim: scripted `--json` emits one minified `{"data":...}`/`{"error":...}` line; errors keep runId as the correlation key; interactive output is unchanged.
- **G-4**: Tamper-evident ledger integrity — keyed hash chaining over the audit-record sequence with a chaining key that never enters lane environments; any alteration within the trust model is flagged as a chain break; wording is cannot-alter-undetectably, never cannot-alter.
- **G-5**: Durable, classified, data-preserving behavior — the ledger composes the state layer's verified-read, classification, salvage, fence, and retention discipline (forever) and survives a malformed entry without data loss.
- **G-6**: Bounded, filtered read access — a read surface for retro and auditor consumers that returns verified records under explicit bounds and filters, with no unbounded dump path.

| ID | Capability | Rationale |
|----|------------|-----------|
| F-1 | One audit record per command invocation | The ticket's core guarantee: exactly one record (idempotent re-runs distinguished by runId) with the full field set, written through the state layer as durable truth |
| F-2 | Agent-identity convention (consume-only) | The calling agent's name is captured when provided and never inferred when absent; recorded as claimed, not proven, per the pinned S18 trust model |

### 5.1 Capability Details

- **F-1 Per-invocation audit record**: every invocation that runs through the command surface produces exactly one audit record, appended through the state layer's public port under one shared audit fence (verified; the closeout precedent — a single fence serializes the whole audit domain because every record participates in one chain) on every outcome class — success, void success, classified failure, unknown failure, and broken invocation — with the envelope's own context fields retained in the record: `runId`, the command name (raw argv tokens preserved for broken invocations where no command name resolves), arguments, exit code, timing, the outcome class (the projected outcome classification consistent with the exit taxonomy), the rendered envelope's schema version (`resultSchemaVersion` — the envelope `schemaVersion` value at invocation time, `delivery.result.v1` at v1; v1.4), the invocation scope (`scope` — the store/workspace scope identity — and `repo` — the target repository when the command targets one, absent otherwise), the wall-clock start timestamp (`startedAt` — integer epoch milliseconds UTC, the same integer-millisecond discipline as `timing.totalMs`, taken from the injected clock the runtime edge already carries), the audit-sequence ordinal (`auditSeq` — the audit consumer's own monotonic per-store ordinal, consumed durably via the reservation-first two-phase append described below), its `chainValue` chain link chaining from the preceding reservation (F-4), and the claimed agent identity when provided. A re-run of an identical command appends a second record under a new runId; records are never deduplicated or overwritten.

  **Ordinal consumption is durable (reservation-first two-phase append, v1.2 — DEC-8):** still under the same fence acquisition, the consumer first appends one `audit.reservation` record (additive kind, payload schema `delivery.audit.reservation.v1`, same store-scoped key family; payload `{auditSeq, runId, chainValue}` — ordinal and integrity evidence, not an invocation record: no invocation metadata (no arguments, no outcome, no identity); the integrity field `chainValue` is present so the reservation is chain-covered even when orphaned — v1.3, MR-1), then appends the `audit.invocation` record carrying that same ordinal. The ordinal is allocated from verified ledger truth — the highest ordinal across existing reservations plus one, starting at 1 on an empty audit domain — so consumption is durable and monotonic across processes: a reservation is ledger truth, and no process-memory counter exists to lose or reuse. Two appends per invocation is the accepted cost of durable consumption (audit writes ride the existing fenced port appends; invocations are human/agent-scale operations) — a deliberate tradeoff, not an oversight. Reservations are a distinct internal record kind and are NOT invocation records: the exactly-one-invocation-record guarantee (AC-F1-1, AC-F1-2, ticket AC1) counts `audit.invocation` records only. The audit ledger composes the public state port as additive record kinds within the existing state schema version — `audit.invocation` (payload schema `delivery.audit.invocation.v1`) and `audit.reservation` (payload schema `delivery.audit.reservation.v1`), store-scoped key `audit.invocations` — with no schema bump, no new runtime-API location, no driver discriminant (DEC-5).
- **F-2 Agent identity (claimed, consume-only)**: the identity variable is named through the branding seam — the derived `environmentPrefix` plus a declared suffix — and is read as injected environment data at the runtime-aware edge, never via an ambient read inside the surface or state tier. Presence is decided on the trimmed value: leading and trailing whitespace is stripped for the presence decision only, and an absent, empty, or whitespace-only value counts as ABSENT — nothing is inferred from user, host, session, or any other signal, and no empty-valued identity is recorded. When present, the variable's value is recorded verbatim (unmodified) as a claimed identity together with an explicit attribution-kind marker (`claimed`), so auditors can always distinguish a claimed attribution from any future proven identity; the claim is attribution only — never verified, never an authorization input. The pinned convention this story specifies — the harness adapter sets the variable at spawn from the agent role and lane id in a per-lane-unique shape, and the harness plugin renders it into shells the agent starts — is documented as the convention; the setter and rendering behaviors are out of scope (NG-1).
- **F-3 Scripted-mode trim**: the machine-output channel adapts by mode (DEC-2). Interactive mode — the machine-output stream presents as an interactive terminal, determined from an injected stream-capability fact at the runtime-aware edge, never probed ambiently inside the surface — renders the full envelope exactly as the M0-S3 contract defines it (all five keys, pretty-indented). Scripted mode — piped or otherwise non-interactive — renders one minified single line: on success exactly `{"data":...}` (an explicit empty `data` object for void successes); on failure exactly one minified line carrying the `error` object with the full error-table fields plus `runId` as a top-level key of that line — the ticket-pinned correlation key, placed at the top level so agents extract it without descending into the error object. Neither line carries `schemaVersion`, `exitCode`, or `timing`: the process exit code always carries status, and the trimmed context fields live in the audit record — which retains the envelope's `schemaVersion` as its `resultSchemaVersion` field: the envelope `schemaVersion` value at invocation time (currently `delivery.result.v1`), explicitly DISTINCT from the audit record's own payload schema id `delivery.audit.invocation.v1`, so future envelope schema bumps stay auditable per invocation (v1.4). A documented flag override forces the full envelope in any mode (the milestone contracts name `--verbose`); a pretty-printing flag affects indentation only and never re-expands the trim; stream outputs (a future `--watch`) stay line-delimited in every mode. The trim activates when this story lands — commands shipped before it emitted the full envelope until then — with no rollout flag (DEC-1). Golden fixtures and the envelope conformance validator extend to both modes: interactive cases validate under the existing envelope rules (extra or missing keys remain contract violations); scripted cases validate under scripted-projection rules (exactly one line, exact key set, trimmed tokens absent, error lines carry runId and full error fields); every case keeps its required golden with no skip path.
- **F-4 Tamper-evident chaining**: each audit-domain record — reservation and invocation alike — carries a `chainValue` field in its payload (v1.3, MR-1: the reservation carries it too, so an orphan reservation — no following invocation record, its keyed integrity evidence stored nowhere else — is still alteration-detected), computed under a chaining key, covering the previous audit-domain record's chain value and the new record's audited content — a keyed chain over the audit-domain record sequence in ledger order, a continuous link sequence across both audit kinds, with the link alternation pinned (v1.3): each reservation's `chainValue` chains from the preceding audit-domain record (of either kind), each invocation record's `chainValue` chains from its preceding reservation — the reservation is therefore the previous link — and the first audit-domain record chains from the store's chain anchor; interleaved records of other domains neither break nor participate in it. The chaining key is durable store-managed key material (OQ-T2 resolution, DEC-4 amended): generated cryptographically randomly at the runtime edge on the store's first audit append, persisted through the public port as the store-managed `chain-key.<workspace>.json` artifact — a named member of the existing store layout family beside `header.<workspace>.json` and `fence.<workspace>.lock` (v1.2, NEW-GAP-5; created/read only through the port's store-managed artifact path, no new runtime-API location) — under the same least-privilege permissions as store files (created `0600`, verified on open), and read from that artifact by every later process — so chain verification spans processes without false flags, and a per-process key is explicitly rejected (it would flag every record written by an earlier process as a chain break, eroding trust in the flag). Open-failure semantics for the key artifact reuse the existing state identities — no new rows (v1.2, NEW-GAP-2; DEC-7): an artifact absent on a non-first open fails `state.keys.missing`; a corrupt or unparsable artifact fails the `state.store.torn` family; wrong permission bits fail `state.permission.denied`. First-open creation is unchanged. The key never enters lane environments — the pinned constraint concerns the environment lanes see — and is never written into the ledger's record payloads, never exported to configuration or ambient environment, and never rendered into shells or lane-visible surfaces by this story's behavior; on a single-user host, same-user readability of the state directory is within the pinned tamper-evidence (not prevention) trust model. Verification recomputes the chain over the verified audit-domain sequence; any mismatch flags a chain break naming the record position — never payload or checksum bytes, per the evidence model. Within the pinned trust model (single-user host, claimed identity, evidence not prevention), altering a record undetectably is not achievable without the key: the state layer's unkeyed per-record checksum alone would accept a recomputed-checksum edit, and the chain is what flags it. Terminal-tail repair and guided salvage of the underlying store remove bytes after the last valid frame and report the removal in their own evidence; removal is byte-contiguous and kind-agnostic — a removed tail takes trailing invocation records AND trailing reservations wholesale, and no partial frame of either kind survives in the surviving prefix (v1.2, NEW-GAP-4). Verification of the chain over the surviving verified sequence is continuous across such removals — a reported removal is not a chain break, and no re-anchoring failure arises on a salvaged ledger (DEC-4). A reservation that is itself the last valid frame (its invocation record torn or never landed) legitimately survives salvage as durable ordinal-consumption evidence — the DEC-8 skipped-ordinal finding — and is never silently dropped by a read (see F-5).
- **F-5 Bounded, filtered read surface**: a library read surface over the state port serves verified audit records to retro and auditor consumers under explicit filters — at minimum by scope, by time window over the record's `startedAt` (implementable because every record carries the UTC epoch-millisecond start timestamp from the injected clock; window bounds are inclusive `[from, to]`, and an omitted `from` or `to` means unbounded on that side — v1.2, NEW-GAP-3), and by command/outcome class — and an explicit bound (records and/or bytes); when a result set is truncated by the bound, truncation is reported in-band — never silently clipped. Filter semantics: `scope` matches by exact comparison against the record's workspace scope identity; `repo` matches by exact comparison against the record's repo value, and records without a repo are excluded from repo-constrained results while remaining reachable through unfiltered or scope-constrained queries; the command filter matches by EXACT comparison against the recorded command token, whatever it is — including the raw first token recorded for a broken invocation (unknown command, leading `-` token), which is filterable by its recorded token (v1.4, Finding 1b). A missing or invalid bound or filter value refuses the query classified with the existing `input.value.rejected` identity — no new error-table row (DEC-7). The read surface also reports the skipped-ordinal finding: any `audit.reservation` whose matching `audit.invocation` record is absent from the verified ledger is reported in-band, naming the gap — durable evidence that an ordinal was consumed but no invocation record is ledger truth (an omitted or failed invocation append), not a new error-table row (DEC-8). The finding is folded from verified ledger truth on every read — reservation and invocation records are both ledger truth, so gap evidence survives any derived-document rebuild by construction (nothing derived carries ordinal truth; the closeout/status fold precedent). Reads are verified (torn and unknown classify per the state layer, never silent zeros), acquire no fence, and write nothing. There is no unbounded full-ledger dump path through this surface (DEC-6; no new CLI command in this story).
- **F-6 Record hygiene**: arguments are recorded only after passing through the single serialization/redaction chokepoint — the same path that guards output streams guards record content — so registered secret values never appear in any record field, on success, failure, or broken invocation alike. The exclusion guarantee is exactly the chokepoint's guarantee: the covered set is the non-empty, unique values registered at the runtime-aware edge; values never registered there are outside the guarantee, identical to the output-stream contract — the "no secret patterns" assertion means no edge-registered secret value survives into any record field. Record evidence follows the state layer's model: paths, positions, counts — never payload or checksum bytes beyond the audited arguments themselves.

## 6. USER & SYSTEM FLOWS

```
Flow 1: Invocation audited and rendered
  An agent (or human) runs a command with --json
    → the surface determines the outcome, measures timing, generates runId
    → inside the shared audit fence, ordinal consumption is recorded first:
      one audit.reservation (runId + auditSeq + chainValue) is appended
      through the public port, its ordinal allocated from verified ledger truth
    → the audit write path assembles the invocation record: runId, command,
      arguments (through the redaction chokepoint), exit code, timing,
      resultSchemaVersion (the envelope's schemaVersion value), outcome
      class, scope/repo, start timestamp (UTC epoch ms, injected clock),
      audit-sequence ordinal, chainValue, claimed identity when the
      identity variable is present
    → the invocation record is appended under the same fence acquisition
      (both frames are ledger truth and chained under the store's durable
      chaining key)
    → the machine channel renders: interactive → full envelope (unchanged);
      scripted → one minified {"data":...} or {"error":...} line
      (error lines keep runId)

Flow 2: Scripted agent correlates a failure
  A scripted agent reads one minified error line
    → error object carries the full error-table fields plus runId
    → the agent uses runId as the correlation key (blockers, audit lookup)
    → the full context (schemaVersion, timing, args, identity, outcome)
      lives in the audit record under that runId

Flow 3: Chain verification and break flag
  An auditor reads audit history through the bounded read surface
    → verification recomputes the keyed chain over the verified sequence
    → an altered record (even with a recomputed unkeyed checksum) breaks
      the chain → a break flag names the record position
    → records before the break remain verified-readable (no data loss)

Flow 4: Salvage/repair interaction
  The store's terminal tail is truncated by terminal-tail repair or guided
  salvage (state-layer operations, explicitly invoked)
    → removal is byte-contiguous and kind-agnostic: trailing invocation
      records AND trailing reservations are removed wholesale, reported by
      the operation's own evidence (counts, extent)
    → the audit chain verifies continuously over the surviving verified
      sequence; the removal is not a chain break
    → the next audit-domain record chains from the last surviving one
    → a reservation that was itself the last valid frame survives as
      durable gap evidence (the skipped-ordinal finding, F-5)

Flow 5: Malformed entry survival
  A malformed audit entry lands in the ledger (broken frame or checksum)
    → the state layer classifies the condition (integrity identities)
    → pre-existing records stay verified-readable and unchanged
    → the explicit salvage path preserves the torn tail as evidence
    → no bytes are silently dropped; retention remains forever
```

## 7. SCOPE & BOUNDARIES

- The per-invocation audit record write path at the command surface, covering all outcome classes (success, void success, classified failure, unknown failure, broken invocation), with the full field set and exactly-once semantics per invocation.
- The additive audit record kinds — `audit.invocation` and, added v1.2, the ordinal-evidence `audit.reservation` — payload schemas, store-scoped key, and validated artifact boundary inside the existing state schema version, composed through the public state port.
- The agent-identity consumption contract: seam-named environment variable read as injected data, claimed-not-proven recording, absent-never-inferred; plus the specification of the setter-side convention (spawn-time value from agent role + lane id, per-lane-unique; harness-plugin rendering) as documented convention only.
- The scripted-vs-interactive mode contract for the machine-output channel (mode from an injected stream-capability fact; full-envelope override; indentation-only pretty flag semantics; stream-output line discipline) and the trim's activation in this change.
- Golden-fixture and envelope-conformance extension to both modes, preserving the no-case-without-golden rule.
- Keyed, tamper-evident hash chaining over the audit-record sequence; the durable store-managed chaining-key artifact generated at the runtime edge and persisted through the public port (v1.1); chain-break flagging with position; the salvage/repair interaction.
- The bounded, filtered library read surface for retro/auditor consumers.
- Tests demonstrating all six ticket acceptance criteria, inheriting and extending seeded scenario SC-M1-23.

### 8.5 Backward Compatibility

- **The envelope contract is unchanged; its scripted rendering is amended (owner-pinned).** Interactive machine output keeps the exact M0-S3 envelope (all five keys; extra or missing keys remain contract violations). Scripted/piped `--json` output changes from the full envelope to the trimmed one-line shape. This is the owner-pinned amendment of the M0-S3 rendering (DEC-1): the trim activates when this story lands, with no compatibility flag. Scripted consumers that parsed schemaVersion, runId, or timing from success lines must move to the process exit code (status) and the audit ledger (context) — the pinned intent of the change.
- **Error correlation is preserved:** every scripted failure line keeps `runId` as the correlation key, and error objects keep the full error-table fields, so code/category/retryable/consequence branching is unaffected.
- **Existing stores open unchanged:** the audit record kind is additive within `delivery.state.v1`; no migration; the first audit record seeds the chain anchor on any store.
- **No error-table change:** no new rows are introduced; audit and state failures reuse the existing state identities (torn, unknown, lock busy, storage exhausted, write failed, permission denied); the bidirectional sync check passes unchanged (DEC-7).
- **Text output and key=value continuity are untouched:** non-`--json` behavior, diagnostics, and bash-continuity keys are unchanged; the trim concerns only the scripted machine channel.

## 10. TELEMETRY & OBSERVABILITY REQUIREMENTS

Observability is evidence-based, consistent with the state layer's evidence model; no external telemetry system is introduced:

- The audit record itself is the observability surface for invocations; runId correlates machine output, human diagnostics, and the audit record.
- Chain-break flags name the record position with remediation guidance; they never carry payload or checksum bytes.
- Salvage and terminal-tail removal continue to report their own evidence (counts, extents) per the state layer; verification distinguishes a reported removal from an unexplained chain break.
- An audit write that fails is loud: the classified state failure appears on the diagnostics stream with its existing state identity; the command's own outcome is unchanged (DEC-8). Omission evidence is durable: a reservation that landed without its invocation record is a reservation orphan, reported as the in-band skipped-ordinal finding by the read surface on the next verified read; a failed reservation consumed nothing and claims no gap.
- The read surface reports result counts and in-band truncation whenever a bound clips a result set.

## 12. ASSUMPTIONS

- M0-S3 (result contract, redaction chokepoint, deterministic in-process surface, golden + conformance tooling) and M0-S5 (state layer: ledger truth, verified reads, fences, classification, salvage, additive kinds, artifact boundaries) are delivered as specified on the integration branch (verified at HEAD c6699302).
- The scripted-vs-interactive distinction is determinable from an injected stream-capability fact at the runtime-aware edge, consistent with the contracts tier's runtime neutrality (no ambient probe inside the surface).
- The chaining key is durable store-managed key material generated at the runtime edge (resolution of the test-plan durability question, OQ-T5/T2 → OQ-5): a per-process key is ruled out because it would flag every record written by an earlier process as a chain break; the durable artifact is not configuration, so `config.secret.forbidden` and the no-ambient-env-reads rules are untouched — the key involves no environment read at all and lives only as injected runtime state and state-store bytes.
- The chain verification is cross-process by construction: every process holding the store verifies the same durable key material, so records from earlier processes verify continuously (asserted by AC-F4-2/NFR-4).
- The identity environment variable name is derived as the branding seam's `environmentPrefix` plus a declared suffix; the suffix vocabulary is pinned at delivery; no product token is hardcoded (forbidden-literal scan stays green).
- The pinned trust model holds: single-user host, local-first state with least-privilege permissions, identity claimed not proven (S18), tamper-evidence not prevention.

## 20. PRIVACY / COMPLIANCE REVIEW

- The ledger is local-only under the state layer's least-privilege contract (0700 directory / 0600 files; Windows current-user ACL); no data leaves the machine.
- Audit records retain command arguments — potentially sensitive operational content — forever per the state layer's retention model. Operators should treat the state directory accordingly; redaction removes registered secret values before recording, but unregistered values are outside the guarantee (consistent with the existing redaction contract).
- The claimed identity is operator-observable attribution data (agent role + lane id shape); it is not personal authentication data and carries no credential material.
- No telemetry export exists; evidence and flags stay local and name paths, positions, and counts.

## 21. SECURITY REVIEW HIGHLIGHTS

- **Trust model wording:** the ledger is tamper-EVIDENT, not tamper-proof — the guarantee is cannot-alter-undetectably within the pinned single-user trust model; the chaining key never enters lane environments (NFR-4, AC-F4-2) and exists only as durable store-managed key material and runtime-edge-injected data — never configuration, never an ambient environment read.
- **Claimed identity discipline:** identity is recorded as claimed, never verified, and is never an authorization input anywhere in the system; consumers must treat it as attribution only.
- **Redaction precedence:** record content passes the single serialization/redaction chokepoint before persistence; the chokepoint remains the only path; no secondary serialization path is introduced for audit writes.
- **No new ambient reads:** the identity variable is read as injected environment data at the runtime-aware edge; the chaining key involves no environment read at all — it is generated runtime state persisted as a store-managed artifact; no new ambient environment probing enters the surface or state tier; no third-party dependency, no network access.
- **Key-artifact containment:** the chaining-key artifact is a store-managed file under the state directory's least-privilege contract (created `0600`, verified on open like every store-managed file); it is never exported to configuration, environment, lanes, or record payloads; on a single-user host, same-user readability of state artifacts is within the pinned tamper-evidence trust model.
- **Chain-verification honesty:** a reported repair/salvage removal must never be suppressible into a false "verified" verdict, and verification evidence never leaks payload or checksum bytes.

## 22. MAINTENANCE & OPERATIONS IMPACT
