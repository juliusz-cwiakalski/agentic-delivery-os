# CHANGE SPECIFICATION

> **PURPOSE**: Give the coordinator session the same managed lifecycle lanes already have — recorded join-or-resume decisions, artifact-evidence stuck detection, kill with grace, a bounded restart budget, and wake-on-typed-question — so the last unmanaged actor in the M1 end state is supervised and the bash stack can retire at M4-S5.

> **REVISION**: v1.4 (2026-11-09) — DoR iteration-3 remediation. See §25 for the change summary.

## 1. SUMMARY

Deliver coordinator supervision as a distinct supervised process with a distinct durable restart budget and a small command family (`coordinator start`, `stop`, `status`, and a bounded `tick` for one collection cycle). It replaces `ceo-loop.sh`'s actual function with typed decisions: join a live coordinator session, resume it when its context is recoverable, or spawn a fresh one when it is not; detect a stuck coordinator from artifact evidence (no digest consumed, no merge, no answer within declared windows, never CPU); kill the coordinator process tree with a grace period; bound restarts and escalate classified exhaustion to the owner brief; and wake the coordinator within one collection cycle when the M1-S16 rank-1 pickup predicate is satisfied.

The change also defines the shared supervisor-regime descriptor (state-dir scope, single-instance lease, unit identity, distinct budget) and leaves coordinator OS-unit wiring as the named M1-S18 seam: the delivered `daemon install` owns installation, and hosting a coordinator unit would require an additive explicit `command` vector, so coordinator `install`/`uninstall` is out of scope. Coordinator single-instance ownership is a durable, append-only **instance lease** carried by `coordinator.fence` records, claimed as one fenced critical section that re-reads the lease and decides holder liveness from the process port's `alive(handle)` before any age fallback; an undeclared alive capability at claim time is a fail-closed capability gap, not an age takeover. In v1 the supervisor runs only in the foreground (`coordinator start --foreground`), and that command runs a declared claim-free evaluation loop with one lifetime lease pair and declared stop, fatal, and signal exits; detached or OS-unit hosting is the M1-S18 seam. Every `tick` attempts exactly one lease pair as expected volume (with `released` attempted in a `finally` and any release failure disclosed). The delivered state write fence is used only for the duration of one append, never held for the supervisor's lifetime; claim-time and non-claim fence-busy handling are two distinct named rules, so a dead writer's stale lock can never permanently wedge `start` or `tick`. It does not build a daemon command, a control socket, lane supervision, an OS unit installer, the dispatch loop, or prompt changes.

## 2. CONTEXT

### 2.1 Current State Snapshot

The coordinator session is kept alive today by `ceo-loop.sh`: the loop joins a live session, resumes when its context is small enough, kills a session that shows no session traffic and no healthy delivery, and counts restarts until a maximum. Those functions are bash, repository-specific, and scheduled to disappear when the bash stack retires. They are not typed, not recorded as decisions, not escalated to the owner brief, and not exposed to the M1-S16 pickup contract.

The delivered M1 surfaces this change consumes are already in the tree:

- **Session lifecycle economics (M1-S15, GH-235, merged `c4f6cd63`)** — progress-based liveness (heartbeat, session traffic, token delta; CPU is never the only signal), additive sourced signals `heartbeat-age` and `token-delta`, a durable per-delivery restart budget with `economics.restart` and `economics.budget-exhaustion` records, a classified fail-loud exhaustion path, and the configuration branch `lane.liveness-interval` / `lane.restart-budget`. The lane budget is per delivery and is not reused here.
- **Typed blocker and question channel (M1-S16, GH-230, merged `03edcdd7`)** — typed questions with a closed four-value type set, the closed `owner` / `coordinator` audience, the shared ranking, the payload-determinable `isCoordinatorPickup` predicate (rank 1, open, audience coordinator), the state-sourced `typed-questions` digest section, and the brief's real `blocker-questions` anchor. The channel makes the pickup predicate determinable; it wakes nothing and starts no iteration. M1-S23 is its enforcement arm.
- **Harness session port (M1-S11)** — spawn, deliver, resume, collect, classify, liveness, and list sessions for the opencode and Claude Code adapters. The port has no kill operation and exposes no process identity; the delivered `DaemonProcessPort` (M1-S18) is the process port this change reuses and extends additively rather than forking a second one.
- **Resident dispatch daemon (M1-S18, delivered)** — the `daemon` command family (`start`, `stop`, `status`, `install`, `uninstall`), the `DaemonProcessPort` (`spawnDetached`, `signal(pid, "SIGTERM" | "SIGINT")`, `isAlive(pid)`), the `DaemonSupervisorDescriptor`/`SupervisorPort` install seam, and `renderSystemdUnit` (which hardcodes `ExecStart=<binary> daemon start --foreground`). The port's liveness probe is `isAlive(pid)`; this specification refers to it as the `alive` capability, with the recorded holder supplying the pid. The daemon's own single-instance lock is a heartbeat-age file lock (`daemon.lock`), not the coordinator's ledger lease. The coordinator change consumes these surfaces and adds no daemon command, control socket, lane supervision, or installer.
- **State layer (M0-S5, M1-S2)** — additive record kinds under the delivered artifact boundary with `STATE_SCHEMA_VERSION` unchanged, torn/unknown classification, fenced appends, and post-append coverage reads. The delivered state write fence is a **short-lived write lock**: `acquireFence` is non-blocking and returns `state.lock.busy` whenever a lock file exists, stale or not; `releaseFence` requires the in-process handle returned by `acquireFence`; `fenceStatus()` reports `held`, `stale`, and `token`; and `recoverFence()` clears only a held-and-stale lock. Coordinator single-instance ownership is therefore carried by append-only `coordinator.fence` lease records; the supervisor acquires the state write fence only for the duration of each individual append, and the delivered blocker append path (which acquires and releases its own fence) composes without collision. Because a holder can die between acquire and release, the claim acquire and every non-claim append each perform the same one-shot stale-lock recovery; §5.1 F-1/F-8 name the two rules and their distinct refusal identities.
- **Status and brief** — the status digest's `typed-questions` section is a read-only verified blocker read (`readBlockerLedger`); the brief mirrors it into the `blocker-questions` anchor via `projectBrief`. Neither has a coordinator-supervision section, and this change does not add one.
- **Pure helpers consumed as delivered** — `evaluateRestartBudget` (restart admission shape), `isCoordinatorPickup` and `rankBlockerQuestions` (pickup predicate and shared ranking), `readBlockerLedger` and `appendBlockerQuestion` (verified ledger read and question append), and `projectBrief` (owner-brief projection). These are consumed as current contracts, never re-implemented or widened.
- **Command and error conventions** — the command registry, the CommandResult envelope, the internal error table with a reserved two-segment fallback namespace, and the `{0,1,2}` exit projection.

The following remain **out of scope and are not preempted by this change**: a change to the delivered `daemon` command, a control socket, lane supervision, a resident daemon process change, and a `dispatch` command (M1-S9). The delivered M1-S18 daemon is consumed, not redefined: its process port is extended additively, its supervisor descriptor/install seam is the M1-S18 handoff, and coordinator `install`/`uninstall` is out of scope. The command audit ledger is delivered (M1-S22) but is deliberately not used as a digest-consumption signal here (DEC-4). The ticket's dependency list names only M1-S15 and M1-S16, so this story remains deliverable without adopting the daemon's installer or unit definition.

**Users and current impact.** The owner (human) currently has no typed signal when the coordinator stalls or exhausts its restarts; the coordinator (CEO-style agent) has no managed lifecycle; the operator (private-fleet operator) cannot retire the bash stack because `ceo-loop.sh` remains the only coordinator supervisor; and lifecycle agents see coordinator questions wait until a human or a manual loop happens to run an iteration. The business impact is delivery reliability and cost: a silent coordinator loop burns tokens and stalls the queue, and the M4-S5 bash retirement is blocked until the last actor is managed.

### 2.2 Pain Points / Gaps

- **No typed coordinator lifecycle.** Join, resume, kill, and restart decisions are bash conditionals. Nothing records why a coordinator was resumed or killed, so the behavior cannot be verified, audited, or reconciled after a crash.
- **Stuck detection is not artifact-evidence based.** The bash probe watches session traffic and delivery health, not typed artifacts. It can miss a wedged coordinator whose process still looks alive, and it has no declared window or classified reason.
- **No kill seam in the session port.** The harness session port has spawn/deliver/resume/collect/classify/liveness/list but no kill-with-grace and no process identity. The delivered `DaemonProcessPort` supplies `spawnDetached`, `signal`, and `isAlive`; it needs an additive `SIGKILL` half and a PID-plus-start-time identity capability before a typed supervisor can safely terminate the coordinator tree.
- **No distinct coordinator budget.** The delivered `lane.restart-budget` counts per delivery; the coordinator is a single long-lived session, not a delivery. Reusing the lane budget or the `economics/<workItemRef>` records would conflate two actors and two policies.
- **Exhaustion can be silent.** The bash loop counts restarts but has no typed owner escalation. A restarted-to-exhaustion coordinator can leave the fleet idle with no visible question.
- **The pickup contract is determinable but unenforced.** `isCoordinatorPickup` exists, but no actor consumes it to wake the coordinator. A top-of-digest coordinator question waits for the next manual iteration.
- **The supervisor regime is undefined.** The ticket requires the same supervisor regime as the daemon (`daemon install` scope). M1-S18 delivered the daemon, its unit renderer, and its installer seam, but the `SupervisorInstallRequest`/`renderSystemdUnit` pair hardcodes `daemon start --foreground`, so a coordinator unit needs an additive explicit `command` vector. Without a shared regime contract, a coordinator supervisor would either duplicate the delivered installer or diverge from it.
- **Single-instance ownership is neither atomic nor liveness-aware.** Two loop instances can race to claim the same state dir, and a lease that is merely old says nothing about whether its holder is still alive. Without a fenced claim that re-reads the lease and checks the recorded process identity — and without a distinct claim-acquire rule for the shared state write fence — a live coordinator can be stolen, a crashed one can block the one-shot surface, or a dead writer's stale fence can refuse every claim.

## 3. PROBLEM STATEMENT

Because the only coordinator lifecycle mechanism is an untyped, repository-specific bash loop and the typed harness session surface exposes no kill or process identity (while the delivered daemon process port must be extended with the kill escalation and start-time identity before it can safely terminate a coordinator tree), the coordinator cannot be given the same managed lifecycle as lanes; it can stall or exhaust restarts silently, a top-of-digest coordinator question can wait indefinitely, and the bash stack cannot retire at M4-S5 without leaving one actor unmanaged.

**Who is affected.** The owner loses a reliable escalation surface; the coordinator loses crash-safe recovery and a bounded restart policy; the operator cannot complete the strangler migration; lifecycle agents wait on coordinator answers that no actor wakes.

- **G-1** Deliver a typed coordinator supervision process and command family, distinct from the lane daemon and distinct from any delivery lane.

### 5.1 Capability Details

**F-1 — Supervision process and command family.**
The command family is `coordinator` with four subcommands: `start --foreground [--fresh-budget]`, `stop`, `status [--live]`, and `tick`. In v1 the only start shape is `coordinator start --foreground`: a bare `start` without `--foreground` is an invocation error (`fallback.invocation`, exit `1`) naming that `--foreground` is required in v1 and that detached or OS-unit hosting is the M1-S18 seam; the supervisor process records its own `pid` and `processStartTimeMs` in the lease. Coordinator single-instance ownership is a durable **instance lease**, not a hold on the delivered state write fence. The lease is folded from the latest `coordinator.fence` record by **ledger sequence** (`recordedAt` is descriptive only except as the lease-age anchor defined below) over the four actions (`acquired`, `released`, `stale-takeover`, `stop-requested`) and carries `instanceId`, `coordinatorId`, `holder` (process identity: pid plus process start time), `pid`, `processStartTimeMs`, `supervisorMode` (`foreground` in v1; `detached` is a reserved closed value never produced in v1), `externalUnit` (`absent`), and `previousHolder` / `fenceAgeMs` on a takeover. State write fence handling has two named rules. **Claim acquire** (`start`, `tick`): on `state.lock.busy`, read `fenceStatus()`; when `stale === true`, perform exactly one `recoverFence` and exactly one acquire retry; only a still-busy or non-stale result maps to `coordinator.already-running` at exit `2`, with no lease record and no append. **Non-claim coordinator appends** (every `coordinator.fence` record and every coordinator action record): the same one-shot stale recovery, then the append and `releaseFence`; a still-busy fence after that recovery maps to the delivered `state.lock.busy` identity. No write-fence handle is held across a cycle, and the supervisor never releases another process's handle. The claim-acquire refusal is a deliberate fail-safe for the shared fence: a non-coordinator state writer (lane, blocker, or audit append) holding the fence produces the same `coordinator.already-running` identity, so the refusal's remediation hint must disclose that ambiguity — retry, because another state writer may hold the lock — and `--live`/`degradation` disclosure reports "state write fence busy". The escalation publish path performs the same one-shot stale recovery before calling the delivered blocker append (F-6). The escalation question is published through the delivered blocker append path, which acquires and releases its own fence. `start` claims the lease as **one fenced critical section**: it acquires the state write fence, re-reads the lease fold and the holder's liveness under the fence, decides, and appends either one `acquired` record or one `stale-takeover` record (which is itself the new acquisition) before releasing the fence. A live holder is never taken over regardless of lease age; a dead holder is takeover-eligible; when the declared alive capability is present but returns no answer for the handle (`unknown`), the lease is takeover-eligible only when its age exceeds two `coordinator.collection-interval`s, otherwise it is treated as held; an alive capability that is **not declared** at claim time is `coordinator.process.capability-gap` at exit `2` with no lease record and no takeover (fail closed, never an age takeover). Lease age is the injected now minus the acquisition record's `recordedAt` (the `acquired` or `stale-takeover` record) and `fenceAgeMs` is the same quantity; a later `stop-requested` does not re-anchor it. The claim acquire follows the claim-acquire stale-fence rule above: a stale fence is recovered once and retried once; only a still-busy or non-stale fence refuses `coordinator.already-running` at exit `2`, naming the holder when the lease is readable. The claim's under-fence state read is the tick's single verified state read, so NFR-4 stays true. `start` then runs the declared foreground supervision loop. Its cycle body is the claim-free evaluation cycle — the same evaluation cycle as `tick` minus claim/release — because its own live lifetime lease would refuse a claiming tick. It waits between cycles through an injected cycle-driver/clock seam (a bounded cancellable wait); no ambient wall clock, `setTimeout`, or wall-clock timer exists in the decision or cycle path, so NFR-1, NFR-8, and NFR-9 stay satisfiable. The loop appends exactly one acquisition record at loop start (`acquired`, or `stale-takeover` on a dead holder) and exactly one `released` at loop exit for the supervisor's lifetime, and appends no per-cycle lease record. It observes a `stop-requested` at the cycle boundary, appends `released`, and exits `0`. A fatal cycle error exits with its typed `{0,1,2}` identity, attempting `released` in a `finally`; SIGINT/SIGTERM exits gracefully with `released` and the declared exit `0` after a successful release, or exit `2` with the `released` append-failure identity when it cannot land. The cycle driver is the test seam that drives a live foreground supervisor to N cycle boundaries in-process without a second process. On start, the supervisor rebuilds the coordinator session identity, budget epoch and count, active expectation, last wake dedupe, and escalation state from durable records; no fact that matters lives only in memory, and a start after a crash converges to the same state without duplicating work. `stop` is a request, not a remote release: when the latest lease action is `acquired`, `stale-takeover`, or `stop-requested` and the recorded holder is alive (or the declared alive capability returns no answer for the handle and the lease age is at most two `coordinator.collection-interval`s, so the lease is treated as held), it appends one `stop-requested` fence record and reports `requested=true`, `released=false`; a `stop-requested` record does not release the lease, so the instance remains the holder until it observes the request at the next cycle boundary, stops, and appends `released`. When the latest lease is `released`, or its holder is not alive, or the declared alive capability returns no answer for the handle and the lease age exceeds two `coordinator.collection-interval`s, `stop` appends nothing and reports `not-running` at exit `0`; an undeclared alive capability is `coordinator.process.capability-gap` at exit `2`, never `not-running`. `status` reads durable state (and, with `--live`, the live process facts) and reports the instance from the latest lease record (`instanceId`, `pid`, `holder`, `startedAt` derived from the acquisition record — `acquired` or `stale-takeover`, `supervisorMode`, `externalUnit`), coordinator session, last decision, restart count and bound, the last persisted stuck verdict with its phase, reason, and evidence, last wake, escalation state, and lease holder. `status` never mutates state, performs no evaluation, and reports `tickVerdict: null`; only `coordinator tick` populates `tickVerdict`. `tick` performs exactly one bounded collection cycle and returns the same `data` shape. It uses the **same atomic claim/takeover decision as `start`**: a tick with a live holder is refused `coordinator.already-running`; a tick with a dead holder may append a single `stale-takeover` (the new acquisition), run exactly one cycle, and append `released`; a tick with a released or absent lease appends `acquired`, runs one cycle, and appends `released`. Every `tick` therefore attempts exactly one lease pair — `acquired`+`released` or `stale-takeover`+`released` — even when the cycle is otherwise quiet; that pair is expected volume and NFR-6 covers action records, not the per-tick lease pair. A tick while a live supervisor lease is held is refused with `coordinator.already-running` (AC-F8-1), so two evaluators can never race; an uncontended `tick` evaluates exactly one cycle (AC-F1-2). The claim acquire uses the claim-acquire stale-fence rule, and `released` is attempted in a `finally` for every claimed tick, including non-zero exits; if `released` cannot land, the tick discloses it and liveness-first self-healing clears the dead lease on the next claim. The claim's under-fence state read is reused as the tick's single verified state read, so NFR-4 stays true. `start --fresh-budget` opens a new budget epoch after the owner chooses recovery, preserving the old history. It is a start-time option: a live supervisor must be stopped first, otherwise the start is refused with `coordinator.already-running` and a hint to stop first.

**F-2 — Join-or-resume-or-spawn decision.**
On every lifecycle evaluation the supervisor inspects the durable coordinator session record and chooses exactly one decision:

- `join-live` — the recorded session is alive. Attach and observe; consume no restart ordinal.
- `resume-context` — no live session, the prior session did not complete cleanly (it was interrupted or failed), it is resumable, its recorded context token count is known and below `coordinator.resume-context-limit`, and the **harness session port** declares and can perform resume. Resume is a harness-session capability consumed by the decision: when resume is undeclared or unavailable it is not a failure and raises no error identity — the decision instead selects `spawn-fresh` with reason `session-interrupted` and consumes one recovery ordinal (DEC-7). Resume without re-paying prefill; consume one restart ordinal.
- `spawn-fresh` — no live session, and either there is no prior session (`initial-start`), the prior session completed cleanly (`clean-iteration-end`), or the prior session did not complete cleanly but its context is at or above the limit, its context reading is unknown, it is not resumable, or resume is undeclared or unavailable (`context-pressure`, `context-unknown`, or `session-interrupted`). Spawn a fresh session; the three recovery reasons consume one restart ordinal, while `initial-start` and `clean-iteration-end` consume none.

The distinction matters: the restart budget counts **recoveries** (a resume or fresh spawn after an interruption, a stuck kill, or a context-forced replacement), not a first start or a planned iteration after a clean completion. The decision, the session identity, the context reading (or its explicit absence), the reason, the ordinal consumption, and the iteration identity are recorded before the action is applied. A killed coordinator therefore resumes or respawns per the last recorded decision, and already closed-out work (phase records, merge records, answers) remains untouched and is not re-executed.

**F-3 — Artifact-evidence stuck detection.**
An *iteration expectation* is created on a start, a wake, a restart, or an actionable digest change while the coordinator is live. At most one expectation is active per coordinator; a new trigger refreshes the window and records a new iteration record rather than opening a second expectation. The supervisor then evaluates three read-only evidence classes:

1. `digest-consumed` — the digest-input fingerprint advanced after the expectation **and** the coordinator session produced a **new turn**. The fingerprint is a bounded, opaque identity over (a) the state event-log cursor and (b) the count of open coordinator-audience questions. Both inputs are state-sourced: the fingerprint performs no tracker or CI read, no network call, and no new composition, and it contains no question text.
2. `merge` — a terminal merge record landed after the expectation.
3. `answer` — a blocker answer record landed after the expectation.

A **new turn** is sourced from the delivered harness liveness facts: a positive `token-delta` reading OR a positive `session-traffic` reading observed since the expectation. The process-port adapter maps the delivered liveness report's `token-delta` and `session-traffic` readings to the `newTurn` / `progressing` facts the domain consumes; an absent or unsupported reading maps to `unknown`, never to zero or stale.

Positive sourced session progress within `coordinator.progress-bound` (default 300 000 ms) is the **prefill-safety corroborator**: it vetoes a stuck verdict even when all three classes are stale, so a large working session is never killed. A `stuck` verdict requires the expectation's `coordinator.stuck-window` to elapse, no class to have advanced, no positive session progress within `coordinator.progress-bound`, and at least one class to be evaluable and stale. A verified-empty merge or answer store is a legitimate count of zero and contributes a `stale` class when no record landed after the expectation; only an unreadable or unknown store is `unknown`. An `unknown` class (for example, a harness that cannot source session progress) is disclosed but never fabricated as stale; an absent progress source is an `unknown` evidence class, never a failure identity, and absence of session signals alone never triggers a kill. If every class is unknown or a required store is unreadable, the verdict is `unevaluable` with reason `evidence-unevaluable`, and no kill or restart occurs; `unevaluable` produces exactly one `coordinator.stuck` record with `phase=verdict` and `killOutcome=not-attempted` and no `phase=outcome`, because no kill is attempted. A persisted verdict is recorded **before** any kill as one `coordinator.stuck` append with `phase=verdict` and `killOutcome=not-attempted`; the kill outcome is a second append (F-4). The verdict and its bounded `key=value` evidence are recorded; CPU is never read. Every coordinator fold — lease, stuck, last decision, and last wake — orders by ledger sequence; `recordedAt` is descriptive only and never a tie-break.

**F-4 — Kill with grace.**
On a `stuck` verdict, the supervisor first appends the `coordinator.stuck` record with `phase=verdict` and `killOutcome=not-attempted` (F-3), then invokes the delivered `DaemonProcessPort` — extended additively with `"SIGKILL"` for the grace-escalation half and an optional `startTimeMs(pid)` identity capability — with the recorded session and process-tree handle. Before signalling, the port verifies that the recorded `pid` plus `processStartTimeMs` identity still matches the live process; on a mismatch it sends no signal, records `killOutcome=failed` with reason `identity-mismatch`, and returns `coordinator.session.kill-failed` at exit `2`. When the `startTimeMs` identity capability is undeclared at kill time, the port sends no signal and returns `coordinator.process.capability-gap` at exit `2`. When the identity matches, the port sends TERM, waits `coordinator.kill-grace`, sends SIGKILL if the tree is still alive, and returns `terminated`, `forced`, or `failed`. After the kill, the supervisor appends a second `coordinator.stuck` record with `phase=outcome`, the same `stuckId`, and the resulting `killOutcome` (`terminated`, `forced`, or `failed`); reads fold to the latest record per `stuckId` by ledger sequence (`recordedAt` is descriptive only). The target is always the recorded handle and tree; no name, pattern, or shell-interpolated kill exists. A failed kill is classified `coordinator.session.kill-failed` at exit `2`, never a silent success.

**F-5 — Durable coordinator restart budget.**
The coordinator budget uses the delivered `evaluateRestartBudget` shape and is per **budget epoch** — a durable identity that survives supervisor restarts and is reset only by `start --fresh-budget` — and is stored in the coordinator restart namespace (`coordinator/<coordinatorId>`), not in `lane.restart-budget` and not in `economics/<workItemRef>`. The fold counts contiguous restart ordinals starting at `1` within the current epoch; a torn or gapped ordinal is unevaluable, never count `0`. A restart below `coordinator.restart-budget` appends one restart record with the next ordinal and proceeds. A restart attempt at or above the bound appends no restart record and starts no replacement; the stuck response's kill, if one already happened, is still recorded, and the command returns `coordinator.restart-budget-exhausted` at exit `1` with the history reference and runs the escalation path. `start --fresh-budget` opens a new epoch with count `0` after an owner decision; the old epoch and its escalation remain in history.

**F-6 — Classified, loud exhaustion escalation.**
When exhaustion is observed, the supervisor publishes exactly one owner-audience `decision-needed` question through the delivered blocker channel (`appendBlockerQuestion`) and the existing brief projection (`projectBrief`). The question carries the coordinator identity and budget epoch as its `ref`, the restart count and bound, the durable history reference, and the declared recovery options (`restart-fresh-budget`, `park-owner-review`). Because the brief's `blocker-questions` anchor already mirrors every open typed question, the escalation appears in the owner brief without a new anchor or question type. To make "never silent" robust under the normal eight-question cap, the digest `typed-questions` section and the brief `blocker-questions` anchor keep one **reserved escalation slot** for an open owner-audience `decision-needed` question that satisfies one pure payload predicate: `type === "decision-needed"` AND `audience === "owner"` AND `lane === "coordinator"` AND `ref` matching the coordinator epoch identity shape `<coordinatorId>#<budgetEpochId>` (exactly one `#`, both sides non-empty). The predicate is payload-only: it adds no coordinator-state read to the digest or the brief and does not change the eight-question bound. The reserved question renders **first** in both the digest `typed-questions` section and the brief `blocker-questions` anchor, even when the cap is reached. The other questions follow in normal rank order, up to seven, and the lowest-ranked question is the one displaced and counted as omitted. The slot lives **inside** the declared rendered-question bound: while an exhaustion escalation is pending, at most seven other questions render after it, so the bound stays at eight rendered questions and no ninth question is added. The render position is deterministic and assertable by index; no other ordering rule changes. This is a bounded rendering rule, not a new section or anchor. Because the supervisor holds no lifetime state write fence, publishing the escalation through the delivered blocker append path composes without a lock collision: the supervisor acquires the state write fence only for each of its own appends, and the blocker append acquires its own. Before calling the blocker append the supervisor performs the same one-shot stale-fence recovery as every coordinator append — read `fenceStatus()`; when `stale === true`, one `recoverFence` and one retry — and a still-busy fence after that recovery is `coordinator.escalation.publish-failed` at exit `2` with consequence `unknown`, not a terminal silent failure. The delivered blocker module stays unchanged and keeps acquiring and releasing its own fence. The escalation is idempotent by `(coordinatorId, budgetEpochId)`: before publishing, the supervisor re-reads the verified blocker ledger and reuses an existing open owner question carrying the same coordinator ref; it publishes only when none exists. The terminal escalation record lands only after the question lands; if the question cannot be published, the supervisor returns `coordinator.escalation.publish-failed` at exit `2` with consequence `unknown`, and `coordinator status` still derives the escalation state from the restart and escalation records. A repeated tick in the exhausted state is an idempotent success with the existing escalation; it never duplicates the question or the terminal record and never returns exit `0` without an escalation receipt.

**F-7 — Wake-on-typed-question.**
On every collection cycle the supervisor performs one verified read of the blocker ledger (`readBlockerLedger`), reuses that read for the `answer` evidence class, and applies the delivered shared ranking (`rankBlockerQuestions`). It evaluates the delivered `isCoordinatorPickup` predicate strictly: the head of the ranked open set must be `rank: 1`, open (an absent `status` counts as open, matching the delivered predicate), and `audience: coordinator`. If true and the question has not already been woken, the supervisor triggers the next coordinator iteration — a live wake, a resume, or a spawn per F-2 — and, **only when the wake succeeds**, appends one durable wake record carrying the question id, rank, `askedAt` (question-lifetime identity), iteration identity, and outcome `woken`. One wake is issued per question lifetime: only a persisted `woken` record consumes that one-wake budget (dedupe on coordinator identity, question id, and the persisted `askedAt`). `already-woken` is a no-op. If the head is not an open coordinator question, the outcome is `no-pickup`. If the question is answered between ranking and wake, the outcome is `answered-before-wake` and no wake is issued. `delivery-failed`, `answered-before-wake`, and `no-pickup` are **tick results**, not durable records: they append nothing, so the next cycle can retry without ever creating a duplicate wake record. A new question that becomes rank 1 after the previous one is answered wakes normally. Wake latency is bounded by one `coordinator.collection-interval`, asserted in v1 as the next `tick` after the question qualifies (NFR-8).

**F-8 — Shared supervisor regime and single-instance lease.**
The coordinator supervisor declares a regime descriptor: state-dir scope, a single-instance lease scoped to the state dir, a unit identity derived from the state dir and the coordinator identity, a distinct process kind, and a distinct restart-budget store. The descriptor is shared in shape with the delivered `daemon install` (`SupervisorPort`/`DaemonSupervisorDescriptor`, M1-S18); a coordinator unit would require an additive explicit `command` vector in `SupervisorInstallRequest`/`renderSystemdUnit` (today they hardcode `daemon start --foreground`), and coordinator `install`/`uninstall` is out of scope. In v1 `supervisorMode` is exactly `foreground`; `detached` is a reserved closed value for a future coordinator unit and is never produced in v1; `externalUnit` is exactly `absent`. The instance lease is folded from the latest `coordinator.fence` record (EVT-7) by **ledger sequence**, which is the primary fold key for every coordinator fold (lease, stuck, last decision, last wake); `recordedAt` is descriptive only and never the tie-break, except for lease age, which is the injected now minus the acquisition record's `recordedAt` (the `acquired` or `stale-takeover` record) and is the same quantity as `fenceAgeMs`; a later `stop-requested` does not re-anchor it. The coordinator keeps this ledger lease rather than the delivered `daemon.lock` because it needs durable acquisition, takeover, and stop-request evidence, ledger-sequence folds, and per-iteration claim/release; `daemon.lock` is a heartbeat-age single-instance file lock carrying instance identity, acquisition time, and heartbeat age only, and it remains the daemon's own instance lock. The four actions are `acquired`, `released`, `stale-takeover`, and `stop-requested`, carrying `instanceId`, `holder`, `pid`, `processStartTimeMs`, `supervisorMode`, `externalUnit`, and any `previousHolder` / `fenceAgeMs`. Each record is its own append; the supervisor holds no write fence between appends. Lease liveness is decided **before** lease age, using the process port's `alive(handle)`. When the latest action is `released`, there is no holder and the lease is claimable. When the latest action is `acquired`, `stale-takeover`, or `stop-requested` and `alive=true`, the lease is held: a second `start` or `tick` is refused `coordinator.already-running` at exit `2` **regardless of lease age**, and `stop` appends `stop-requested` reporting `requested=true`, `released=false`. When the same actions have `alive=false`, the lease is takeover-eligible: a `start` or `tick` may append a **single** `stale-takeover` record that is itself the new acquisition (new `holder`/`pid`/`processStartTimeMs`, `previousHolder`, `fenceAgeMs`), with no second `acquired` record. When the declared alive capability returns no answer for the handle (`unknown`), the lease is takeover-eligible only when the lease age exceeds two `coordinator.collection-interval`s; otherwise the lease is treated as held and the claim is refused, so a possibly-live lease is never stolen. An **undeclared** alive capability at claim time is `coordinator.process.capability-gap` at exit `2` with no lease record and no takeover, never a destructive age takeover. The claim or takeover is **one fenced critical section**: `acquireFence(token)`, re-read the lease fold and liveness under the fence (that read is the tick's single verified state read, so NFR-4 stays true), decide, append one `acquired` or one `stale-takeover`, or refuse, then `releaseFence(handle)`. The supervisor holds no write fence across a cycle. Two concurrent claims over two store handles are therefore deterministic: one appends and one is refused `coordinator.already-running`. Because the delivered state write fence is non-blocking, only two interleavings exist: lock contention (the loser receives `state.lock.busy`, performs no lease re-read, and appends nothing) or serialization (the winner acquires, appends, and releases before the loser acquires and re-reads the held lease). Neither interleaving lets the loser append. Claim acquire resolves `state.lock.busy` by the **claim-acquire stale-fence rule**: read `fenceStatus()`; when `stale === true`, one `recoverFence` and one acquire retry; only a still-busy or non-stale result maps to `coordinator.already-running` at exit `2` with no lease record and no append. The remediation hint discloses the shared-fence ambiguity — retry, because a non-coordinator state writer may hold the lock — and `--live`/`degradation` reports "state write fence busy". Non-claim coordinator appends use the same one-shot recovery but map a still-busy fence to the delivered `state.lock.busy`; the lease decision never depends on the state write fence's staleness, and a stale fence can never permanently wedge `start` or `tick`. The fold over the four actions is total, including after a crash between takeover and use: the `stale-takeover` record already names the new holder, so there is no ambiguous intermediate state. A different state dir is independent. No coordinator OS autostart installer is shipped: installation stays owned by the delivered `SupervisorPort`, the additive `command` vector is a declared follow-up, and the gap is declared and tested as naming M1-S18.

**F-9 — Observation surface.**
`coordinator status` and every other subcommand return a bounded machine `data` payload (`delivery.coordinator.v1`) with the `instance` (folded from the latest lease record: `instanceId`, `pid`, `holder`, `startedAt`, `supervisorMode` — `foreground` in v1 — and `externalUnit`), regime, session, last decision, restart count and bound, last wake, escalation state, and degradation list. `data.stuck` reports the **last persisted** verdict (`stuck` or `unevaluable`) with non-null `phase`, `reason`, and `evidence`. `tickVerdict` is populated only by `coordinator tick`; `start`, `stop`, and `status` report `tickVerdict: null`, and `status` never mutates state or performs an evaluation — a caller wanting an evaluation runs `tick` (itself refused `coordinator.already-running` while a live supervisor holds the lease). Within a tick result, `tickVerdict.verdict` is `progressing`, `stuck`, or `unevaluable` and its `phase`, `reason`, and `evidence` are nullable when the verdict is `progressing`, because `progressing` is never persisted. Human output is deterministic, ANSI-free, and bounded. `--live` reports live process facts; when they are unavailable it declares `unknown` or `degraded` rather than fabricating them.

**F-10 — Closed vocabularies, config, state, and errors.**
The lifecycle decisions, restart reasons, stuck reasons, stuck verdicts, stuck record phases, evidence classes, wake outcomes, fence actions, supervisor modes, escalation states, config keys, and error identities are closed sets declared as data. The `coordinator` config branch validates six keys with declared defaults and domains; no bound or default literal lives in the decision code. The state records are additive under the delivered artifact boundary with `STATE_SCHEMA_VERSION` unchanged; no migration or derived document is created. The error table gains a `coordinator` domain kind with the declared rows; the reserved two-segment fallback namespace is unchanged, the two two-segment `coordinator.*` identities (`coordinator.already-running`, `coordinator.restart-budget-exhausted`) join the exact `RESERVED_TWO_SEGMENT_CODES` allowlist with no `coordinator.*` wildcard and no generic pattern widening, the other four coordinator identities are already three-segment, and every non-zero exit projects from the table. Capability ownership is split and never overloaded: a harness that cannot or will not spawn reuses the delivered `harness.capability.gap` / `harness.spawn.refused` at exit `1`; an undeclared or unavailable resume is a decision input (`spawn-fresh`, reason `session-interrupted`), not an error; an absent progress source is an `unknown` evidence class, not an error; and only a missing process-port alive, kill-with-grace, or start-time identity capability is `coordinator.process.capability-gap` at exit `2`. The process port is the delivered `DaemonProcessPort`, extended additively with `SIGKILL` for the grace-escalation half and an optional `startTimeMs(pid)` identity capability; a probe that returns no answer for the handle is `unknown` (the age fallback), not a gap. Claim acquire resolves a still-busy or non-stale fence after one stale-lock recovery to `coordinator.already-running` at exit `2` with no lease record and no append; a non-claim append that cannot acquire the state write fence after one stale-lock recovery returns the delivered `state.lock.busy` identity; a failed coordinator append returns the delivered `state.write.failed` identity.

## 6. USER & SYSTEM FLOWS

**Flow 1 — Supervisor start and first lifecycle decision.**
```
operator/unit -> coordinator start --foreground   (bare start -> fallback.invocation, exit 1)
  -> claim acquire: acquire state write fence
       state.lock.busy -> fenceStatus(); stale -> one recoverFence + one acquire retry
       still busy / non-stale -> refuse coordinator.already-running (exit 2, no lease record)
  -> re-read lease fold + holder liveness under the fence (the tick's single verified state read)
  -> released/none -> append coordinator.fence action=acquired
     live holder -> release fence, refuse coordinator.already-running (exit 2)
     dead holder -> append one action=stale-takeover (the new acquisition)
     alive declared but no answer -> takeover only if age > 2 x collection-interval; else refuse
     alive capability undeclared -> coordinator.process.capability-gap (exit 2, no lease record)
  -> release state write fence
  -> read coordinator session + restart records + config
  -> decide join-live | resume-context | spawn-fresh
  -> record coordinator.iteration
  -> apply the decision (attach / resume / spawn)
  -> run the declared foreground loop (Flow 9)
  -> status state=running
```

**Flow 2 — Killed mid-iteration.**
```
coordinator session killed (no completion record)
  -> next tick or start sees the session not alive
  -> tick/start claims the lease: dead holder -> one stale-takeover (the new acquisition)
  -> resume-context when context < limit and resumable
     OR spawn-fresh when context >= limit / unknown / not resumable
  -> append coordinator.restart with the next ordinal and classified reason
  -> already closed-out phase/merge/answer artifacts remain; no re-execution
```

**Flow 3 — Stuck coordinator.**
```
expectation issued (start/wake/restart/actionable digest change)
  -> tick evaluates digest-consumed / merge / answer + session progress
  -> no class advanced, no positive progress within progress-bound, window elapsed
  -> append coordinator.stuck phase=verdict, killOutcome=not-attempted, reason and bounded evidence
  -> verify pid + processStartTimeMs identity through the delivered DaemonProcessPort (startTimeMs)
  -> TERM, wait kill-grace, SIGKILL if needed
  -> append coordinator.stuck phase=outcome with the same stuckId (terminated | forced | failed)
  -> budget check -> coordinator.restart + resume/spawn
```

**Flow 4 — Restart exhaustion.**
```
restart count reaches coordinator.restart-budget
  -> no spawn/kill; coordinator.restart-budget-exhausted (exit 1)
  -> publish one owner-audience decision-needed question
       before the blocker append: fenceStatus(); stale -> one recoverFence + one retry
       still busy -> coordinator.escalation.publish-failed (exit 2, consequence unknown)
  -> append coordinator.exhaustion (terminal escalation receipt)
  -> brief blocker-questions anchor renders the question first in its section
  -> later ticks: state=exhausted-escalated, no duplicate question
  -> owner chooses restart-fresh-budget -> coordinator start --fresh-budget
```

**Flow 5 — Coordinator question wake.**
```
blocker ledger changes; a new question becomes rank 1, open, coordinator
  -> tick ranks the verified ledger
  -> isCoordinatorPickup == true and question not already woken
  -> wake live session, or resume/spawn per F-2
  -> append coordinator.wake (woken, questionId, askedAt, iterationId)
  -> next iteration answers as data; answer record is the consumption evidence
```

**Flow 6 — Delivered daemon, no coordinator unit (the M1-S18 seam).**
```
M1-S18 delivered (daemon, DaemonProcessPort, SupervisorPort)
  -> coordinator supervision runs only as coordinator start --foreground (v1)
  -> the change consumes the delivered DaemonProcessPort additively (SIGKILL, startTimeMs)
  -> the shared regime descriptor is the handoff for a future coordinator unit
  -> a coordinator unit needs an additive explicit command vector; coordinator install/uninstall is out of scope
  -> no daemon command change, control socket, lane supervision, or installer is created
```

**Flow 7 — Stop request from another process.**
```
operator -> coordinator stop (separate process)
  -> read latest coordinator.fence lease (fold by ledger sequence)
  -> latest action in {acquired, stale-takeover, stop-requested} and alive(holder)=true,
     or declared alive returns no answer and age <= 2 x interval:
     append coordinator.fence action=stop-requested
     -> report requested=true, released=false, exit 0 regardless of lease age
     -> live supervisor observes the request at the next cycle boundary
     -> supervisor stops and appends coordinator.fence action=released
  -> latest action released, or holder alive=false, or declared alive returns no answer and age > 2 x interval:
     append nothing, report not-running, exit 0
  -> alive capability undeclared -> coordinator.process.capability-gap (exit 2), never not-running
  -> stop never releases another process's state write fence handle
```

**Flow 8 — Tick claim, takeover, and quiet-cycle volume.**
```
tick starts -> claim acquire: acquire state write fence
  state.lock.busy -> fenceStatus(); stale -> one recoverFence + one acquire retry
  still busy / non-stale -> refuse coordinator.already-running (exit 2, no lease record)
  -> re-read lease fold + liveness under the fence (the tick's single verified state read)
  -> released/none -> append coordinator.fence action=acquired
  -> live holder -> release fence, refuse coordinator.already-running (exit 2)
  -> dead holder -> append one action=stale-takeover (the new acquisition)
  -> alive declared but no answer and age <= 2 x collection-interval -> refuse coordinator.already-running
  -> alive capability undeclared -> coordinator.process.capability-gap (exit 2, no lease record)
  -> release state write fence
  -> run exactly one collection cycle
  -> append coordinator.fence action=released (attempted in a finally on every exit, including non-zero)
  -> a quiet cycle grows the log by exactly this lease pair and no action record
```

**Flow 9 — Foreground supervision loop.**
```
start --foreground claims the lifetime lease (acquired or stale-takeover; Flow 1)
  -> loop: injected cycle driver waits one collection-interval (bounded cancellable wait)
  -> cycle body = claim-free evaluation cycle (the same evaluation cycle as tick minus claim/release)
  -> cycle boundary: stop-requested observed? -> append released -> exit 0
  -> fatal cycle error -> typed exit identity, released attempted in a finally
  -> SIGINT/SIGTERM -> graceful stop, released attempted -> exit 0 (released landed) or 2 (append failed)
  -> loop exit appends exactly one released for the lifetime, never a per-cycle lease record
```

## 7. SCOPE & BOUNDARIES

### 7.1 In Scope

- A new `coordinator` command family: `start --foreground [--fresh-budget]` (v1 foreground-only; a bare `start` is an invocation error), `stop`, `status [--live]`, `tick`.
- A pure coordinator-supervision decision domain: lifecycle decision, context recoverability, artifact-evidence stuck verdict, restart admission, wake evaluation, and escalation projection.
- Reuse of the delivered `DaemonProcessPort` for process signalling and liveness, extended additively with `SIGKILL` and optional `startTimeMs(pid)` capabilities, implemented in adapters beside the delivered daemon and harness session adapters and faked in tests; harness session spawn and resume are consumed from the delivered harness session port.
- A declared foreground supervision loop (`start --foreground`) with an injected cycle-driver/clock seam, one lifetime lease pair, and declared stop, fatal, and signal exits.
- Additive coordinator state records: iteration, restart, stuck, exhaustion, wake, and fence; durable reads and appends under the delivered artifact boundary.
- A `coordinator` config branch with six keys and declared defaults.
- Coordinator error identities and a `coordinator` domain kind in the internal error table.
- A shared supervisor-regime descriptor and a state-dir single-instance lease carried by `coordinator.fence` records.
- An atomic lease claim/takeover over the delivered state write fence, with liveness-first decisions, single-record takeover, and the two named state-fence rules (claim acquire vs non-claim append).
- Owner-brief escalation by publishing an owner-audience `decision-needed` question, idempotently and loudly, with the same one-shot stale-fence recovery before the blocker append.
- Wake-on-typed-question using the delivered `isCoordinatorPickup` predicate and blocker ledger.
- Deterministic text and `data` output, `{0,1,2}` exit projection, bounded evidence, and no secret/prompt/transcript material.
- Tests and documentation for the new surface, including SC-M1-25 reconciliation.

### 7.2 Out of Scope

- [OUT] Any change to the delivered `daemon` command, a daemon control socket, lane supervision, startup reconciliation, or any OS supervisor unit installer; coordinator `install`/`uninstall` is out of scope (M1-S18 owns installation).
- [OUT] A `dispatch` command, spawn loop, dual-run evidence, or per-repo handover (M1-S9).
- [OUT] Agent-prompt or lifecycle-instruction changes (M1-S20).
- [OUT] Queue scheduling, merge execution, closeout mechanics, or status-collector redesign.
- [OUT] A new status-digest section, a new brief anchor, or a new typed-question type.
- [OUT] CPU-based liveness, CPU sampling, or CPU thresholds.
- [OUT] Any model call in a deterministic decision or render path.
- [OUT] Reuse of `lane.restart-budget`, `lane.liveness-interval`, or `economics/<workItemRef>` for the coordinator.
- [OUT] Multi-coordinator, multi-host, or remote supervision.
- [OUT] Adding a second process-lifecycle port or redeclaring harness resume, spawn, or progress inside the process port; the delivered `DaemonProcessPort` is reused additively and the harness session port keeps resume.
- [OUT] Detached or background start, daemonization, or OS-unit hosting in v1 (M1-S18).
- [OUT] Automatic application of the owner's escalation answer; that is the delivered daemon/queue path (M1-S18) or the manual `--fresh-budget` operator action.

### 7.3 Deferred / Maybe-Later

- Registering the coordinator supervision loop under the delivered `daemon install` user-level unit; this requires an additive explicit `command` vector in `SupervisorInstallRequest`/`renderSystemdUnit` (M1-S18 follow-up).
- Detached supervisor mode and OS-unit hosting (M1-S18); `detached` remains a reserved closed value and is never produced in v1.
- Lease heartbeat or periodic lease-refresh records; v1 keeps the lease action-only and decides liveness from the recorded process identity.
- A coordinator section in the status digest or board once the daemon and board surfaces exist (M1-S18/M2-S4).
- Treating an audit-ledger digest invocation as a consumption signal (available now; deliberately unused in v1 because an invocation is not comprehension and a wedged coordinator can re-run the command).
- Adaptive stuck windows by phase or work type.
- Remote or container-attached coordinator supervision.
- Automatic consumption of the owner's exhaustion answer by the daemon.

Carries `exhaustionId` (`<coordinatorId>#<budgetEpochId>`), `coordinatorId`, `budgetEpochId`, `restarts`, `historyRef`, `escalationQuestionId`, the declared `options`, `terminal: true`, and `recordedAt`. |
| EVT-5 | `coordinator.wake` | One durable record per **successful** wake (`outcome` = `woken`) for a pickup predicate. Carries `wakeId`, `coordinatorId`, `questionId`, `questionRank`, `askedAt` (question-lifetime identity), `outcome`, `iterationId`, and `recordedAt`. `already-woken`, `answered-before-wake`, `delivery-failed`, and `no-pickup` are tick results that append no durable wake record; only `woken` consumes the one-wake-per-question lifetime. |
| EVT-6 | Owner escalation question | Reuses the delivered blocker question message: type `decision-needed`, audience `owner`, `ref` = `<coordinatorId>#<budgetEpochId>`, `lane` = `coordinator`, bounded question text, and the declared recovery options. The reserved slot identifies it from the payload alone — `type`, `audience`, `lane`, and the `<coordinatorId>#<budgetEpochId>` ref shape (exactly one `#`, both sides non-empty) — so the digest and brief read no coordinator state for it. The digest `typed-questions` section and the brief `blocker-questions` anchor render the reserved question **first**; the other questions follow in normal rank order, up to seven, and the lowest-ranked question is displaced and counted as omitted, within the declared eight-question bound. No new message type is introduced. |
| EVT-7 | `coordinator.fence` | One durable record per instance-lease action; this is the append-only carrier of coordinator single-instance ownership and the takeover evidence, not a hold on the state write fence. Carries `fenceId`, `instanceId`, `coordinatorId`, `action` (`acquired`, `released`, `stale-takeover`, `stop-requested`), `holder` (pid plus process start time), `pid`, `processStartTimeMs`, `supervisorMode` (`foreground` in v1; `detached` is a reserved value never produced in v1), `externalUnit` (`absent`), `previousHolder` (nullable), `fenceAgeMs` (nullable), and `recordedAt`. The current lease is folded from the latest record by ledger sequence (`recordedAt` is descriptive only); lease liveness is decided by `alive(handle)` before any age fallback, and lease age (the same quantity as `fenceAgeMs`) is the injected now minus the acquisition record's `recordedAt`, so a later `stop-requested` does not re-anchor it. An undeclared alive capability at claim time is `coordinator.process.capability-gap`, never an age takeover. A `stale-takeover` is itself the new acquisition — one record carrying the new holder, the `previousHolder`, and the `fenceAgeMs` — and is never followed by a second `acquired`. The instance's `startedAt` is the `recordedAt` of its acquisition record (`acquired` or `stale-takeover`). Each append uses the non-claim per-append state write fence rule: acquire, one stale-lock recovery and retry on `state.lock.busy`, append, release; a still-busy fence returns the delivered `state.lock.busy`. Reads validate it like every other coordinator record. No separate instance record exists. |

Record kinds are additive under `delivery.state.v1`; the schema version does not change. The record-kind set stays closed at six (EVT-1 through EVT-5 and EVT-7): `coordinator.fence` carries the instance lease and `coordinator.stuck` carries both phases under one `stuckId`. Every non-claim coordinator record append — fence records, stuck phases, restart, exhaustion, and wake — uses the non-claim state write fence rule: acquire, one stale-lock recovery and retry on `state.lock.busy`, append, release; a still-busy fence returns the delivered `state.lock.busy`. The claim acquire uses the separate claim-acquire rule (one stale recovery, then still-busy/non-stale maps to `coordinator.already-running`), and the claim's under-fence read is the tick's single verified state read. The escalation question is published through the delivered blocker append path, which acquires and releases its own fence, after the supervisor has performed the same one-shot stale recovery; no supervisor holds a write-fence handle across a cycle. Every `tick` attempts exactly one lease pair (`acquired` then `released`, or `stale-takeover` then `released`) even when the cycle is otherwise quiet, with `released` attempted in a `finally` for every claimed tick including non-zero exits; that pair is expected volume. A `no-pickup`, `already-woken`, `answered-before-wake`, or `delivery-failed` outcome is a tick result, not a persisted record, so apart from the per-tick lease pair a quiet cycle grows the log by no records and a retry cannot duplicate action records. NFR-6's idempotency claim covers action records (restart, stuck, wake, exhaustion), not the per-tick lease pair.

### 8.4 External Integrations

- **Harness adapters (opencode, Claude Code).** The process port is the delivered `DaemonProcessPort`, extended in adapters beside the delivered daemon and harness session adapters; the harness adapter supplies the stable session handle and process identity, and the process port performs signalling, liveness, and the optional start-time identity check. Capability ownership is explicit: a harness that cannot or will not spawn uses the delivered `harness.capability.gap` / `harness.spawn.refused` identity at exit `1`; an undeclared or unavailable resume selects `spawn-fresh` with reason `session-interrupted` (no error, one recovery ordinal); an absent progress source is an `unknown` evidence class and never a failure; and a missing process-port alive, kill-with-grace, or start-time identity capability is `coordinator.process.capability-gap` at exit `2` with no destructive action. The adapter maps the delivered harness liveness report's `token-delta` and `session-traffic` readings to the `newTurn` / `progressing` facts; an absent or unsupported reading maps to `unknown`, never to zero or false. TDR-0017 DC-3 records this four-way split; this specification edits no TDR.
- **Operating-system process signals.** The delivered `DaemonProcessPort.signal` is extended additively with `"SIGKILL"` for the grace-escalation half, and its optional `startTimeMs(pid)` capability carries the PID-plus-start-time identity check before TERM. TERM then SIGKILL for the coordinator process tree, with the Windows equivalent behind the same port. Before TERM, the port verifies the recorded `pid` plus `processStartTimeMs` identity against the live process; on a mismatch it sends no signal and reports `identity-mismatch`; an absent `startTimeMs` capability at kill time is `coordinator.process.capability-gap` and sends no signal. No network, no shell interpolation, and no credential value is involved.
- **Supervisor installation.** Installation stays owned by the delivered M1-S18 `SupervisorPort`/`DaemonSupervisorDescriptor`; `renderSystemdUnit` today hardcodes `ExecStart=<binary> daemon start --foreground`, so a future coordinator unit needs an additive explicit `command` vector. Coordinator `install`/`uninstall` is out of scope for this change.
- **No other external integration.** The change reads the delivered state layer, config, blocker ledger, and economics/liveness facts locally.

### 8.5 Backward Compatibility

- **Additive only.** Existing commands, envelopes, exit codes, config keys, state records, digest sections, and brief anchors are unchanged except for the declared reserved escalation slot in `typed-questions`/`blocker-questions`. The `coordinator` family is new.
- **No daemon runtime dependency.** The command works without a running resident daemon, control socket, or OS unit; it consumes the delivered `DaemonProcessPort` contract but does not require the daemon process to be running. `--live` degrades to state-only facts and declares the degradation. No delivered daemon command, installer, or unit renderer changes.
- **No lane/economics collision.** The coordinator budget and records use a distinct namespace; the delivered lane and economics surfaces are untouched.
- **No schema bump.** Coordinator records are additive within `delivery.state.v1`; no migration, backfill, or derived document is created.
- **Bash retirement unchanged.** `ceo-loop.sh` remains in place until M4-S5; this change supplies its typed replacement but does not retire or deprecate it.

## 9. NON-FUNCTIONAL REQUIREMENTS (NFRs)

| ID | Requirement | Threshold |

| NFR-1 | Determinism of decisions and rendered output | 100% identical decision and `data` for identical state, config, and injected facts; no ambient clock, randomness, or environment read outside injected ports. |
| NFR-2 | No CPU signal | 0 CPU reads or CPU-derived thresholds in the stuck-detection or lifecycle decision path. |
| NFR-3 | No model call in a deterministic path | 0 model calls in any decision, status, or render path. |
| NFR-4 | Bounded reads and records | At most one verified read per store per tick; the claim's under-fence state read is the tick's single verified state read; at most 8 ranked questions rendered; at most 64 KiB machine `data` and at most 32 human lines per command. |

| NFR-7 | Durability | Restart count, budget epoch, exhaustion receipt, and wake dedupe survive a supervisor crash and restart (100%). |

**Collection-cycle semantics (v1).** This change ships `tick` and a declared foreground loop, not a resident scheduler. NFR-8 and NFR-9 are asserted as: the next `tick` after the qualifying condition — the question becoming rank 1 for NFR-8, the window elapsing for NFR-9 — produces exactly one wake or exactly one verdict. The supervisor's own loop ticks at `coordinator.collection-interval` through an injected cycle-driver/clock seam (a bounded cancellable wait); no ambient wall clock, `setTimeout`, or wall-clock timer is read, and a caller that ticks slower than the configured interval is caller-bounded and does not violate the policy. No resident scheduler and no wall-clock timer is required, and the policy numbers are unchanged; an injected clock drives the fixtures.

## 10. TELEMETRY & OBSERVABILITY REQUIREMENTS

- **Durable evidence.** The six coordinator record kinds (EVT-1 through EVT-5 and EVT-7) are the telemetry. They carry decisions, restart ordinals, two-phase stuck verdicts with their reason and bounded evidence (with `unevaluable` producing exactly one verdict record and no outcome record), exhaustion receipts, successful wake records, and instance-lease acquisitions/releases/takeovers/stop requests. Every `tick` also attempts one lease pair (with any release failure disclosed); the foreground loop appends one lifetime acquisition/release pair and no per-cycle lease record. The per-tick pair is the expected heartbeat-free volume and carries no action semantics. No separate metrics store is introduced.
- **`coordinator status` fields.** Instance identity from the latest lease (`instanceId`, `pid`, `holder`, `startedAt`, `supervisorMode` — `foreground` in v1 — `externalUnit`), uptime (live or `unknown`), state-dir scope, lease holder and last lease action (with previous holder and fence age on a takeover), coordinator session identity and liveness, last decision and reason, restart count and bound, history reference, the last persisted stuck verdict with phase, reason, and evidence, the `tickVerdict` field (which is `null` for `start`, `stop`, and `status` and non-null only for `coordinator tick`, with `progressing | stuck | unevaluable`), last wake outcome and question, escalation state and question id, and a bounded degradation list (including "state write fence busy" when a claim is refused for a busy fence).
- **Owner escalation.** The exhaustion question is the owner-facing signal. The digest `typed-questions` section and the brief `blocker-questions` anchor render it **first** in their respective sections within the declared eight-question bound, so it is visible even at the normal cap; the other questions follow in rank order, up to seven, and the lowest-ranked is displaced and counted as omitted. The slot is selected by the payload-only predicate (type, audience, lane, ref shape) and adds no read. No new alerting channel is added.
- **Operational queries.** An operator can answer "is the coordinator running, what did it decide, how many restarts remain, was it stuck, was it woken, and is it exhausted?" from `coordinator status` alone.
- **No sensitive content.** Records and evidence carry counts, identities, references, and closed vocabulary values only.

## 12. ASSUMPTIONS

- M1-S15 (GH-235, merged `c4f6cd63`) and M1-S16 (GH-230, merged `03edcdd7`) are delivered and stable; their sourced progress signals, ranking, pickup predicate, and brief anchor are consumed as current contracts.
- The state layer supports additive record kinds under `delivery.state.v1` without a schema bump or migration. Its write fence is a short-lived, handle-scoped lock (`acquireFence` is non-blocking; `fenceStatus` exposes `held`/`stale`/`token`; `recoverFence` only clears a held-and-stale lock), so coordinator single-instance ownership uses append-only `coordinator.fence` lease records and requires no change to the delivered state contracts. Claim acquire and non-claim appends each perform the same one-shot stale-lock recovery and then diverge only in the refusal identity; the claim's under-fence state read is the tick's single verified state read. The lease decision never depends on state-fence staleness, and lease age is the injected now minus the acquisition record's `recordedAt` (the same quantity as `fenceAgeMs`, never re-anchored by a later `stop-requested`).
- The delivered `DaemonProcessPort` can be extended additively with `"SIGKILL"` and an optional `startTimeMs(pid)` identity capability; adapters beside the delivered daemon and harness session adapters implement it. The harness adapter can expose a stable session handle and process identity sufficient for alive, resume, and kill; the delivered liveness report's `token-delta` and `session-traffic` readings are the new-turn source; where it cannot, a spawn gap is `harness.capability.gap`/`harness.spawn.refused` at exit `1`, an undeclared resume selects `spawn-fresh`, an absent progress source is `unknown`, and only a missing process-port alive, kill-with-grace, or start-time identity capability is `coordinator.process.capability-gap`.
- The blocker ledger is the single escalation surface and the brief renders open owner-audience questions through the existing `blocker-questions` anchor.
- One coordinator exists per state-dir scope; multi-coordinator and multi-host supervision are out of scope.
- The supervisor runs as the same OS user as the coordinator; no privilege escalation is needed. In v1 the supervisor runs only in the foreground; a detached or OS-unit host is the M1-S18 seam.
- POSIX process signals are available on the reference host; the Windows equivalent is behind the same port.
- The operator reads `coordinator status` and the owner reads the brief; no additional notification channel is assumed.
- The delivered `daemon install` (`SupervisorPort`/`DaemonSupervisorDescriptor`) can host this process later once `SupervisorInstallRequest`/`renderSystemdUnit` gain an additive explicit `command` vector; coordinator install/uninstall is out of scope for this change and nothing here assumes the unit exists.

## 18. ROLLOUT & CHANGE MANAGEMENT (HIGH-LEVEL)

- **Delivery shape.** One change on `feat/GH-241/coordinator-supervision`, one pull request targeting `main-tools`. The change is additive: contracts, domain, state, config, adapters, CLI, tests, and docs.
- **No migration.** No schema bump, no state transformation, no backfill. Coordinator records are new keys under the existing state schema.
- **No behavioral flip.** Existing commands, digest sections, brief anchors, and lane/economics behavior are unchanged. The new family is opt-in: an operator or a future coordinator unit runs `coordinator start --foreground`.
- **Bash retirement unchanged.** `ceo-loop.sh` remains until M4-S5. This change supplies the typed replacement and the strangler evidence; it does not remove or wrap the bash entry point.
- **Adoption path.** Start with `coordinator tick` in tests and one-shot operation, then `coordinator start --foreground` in a terminal or under a future coordinator unit once the delivered M1-S18 installer gains an explicit `command` vector. The regime descriptor is the handoff point.
- **Rollback.** Stop the supervisor (`coordinator stop`), stop invoking the command, and leave the additive records in place. No data loss and no migration reversal is needed.
- **Communication.** The new command family, config keys, and owner escalation are documented in the coordinator-supervision feature spec, the CLI registry, the command page, and the operator runbook.

## 19. DATA MIGRATION / SEEDING (IF APPLICABLE)

N/A. The change adds new record kinds and a new config branch; it does not transform, backfill, or seed existing state. `STATE_SCHEMA_VERSION` stays `delivery.state.v1`. A fresh state dir starts with a verified-empty coordinator record set, which is a valid state and not an error.

## 20. PRIVACY / COMPLIANCE REVIEW

- **No prompt or transcript content.** Coordinator records carry identities, counts, closed vocabulary values, timestamps, and references only. No prompt, message, transcript, question body beyond the bounded owner question text, or model output is persisted in coordinator records.
- **No secret or credential values.** The owner question text is a bounded status sentence (coordinator id, restart count, bound, options). The process port carries session and process handles, not credentials. Error evidence is counts, identities, and references.
- **No new personal data.** The change adds no personal-data category and no new network destination.
- **Trust model unchanged.** The supervisor is same-user and local; the instance lease and filesystem permissions are the boundary. No privilege escalation and no remote transport.
- **Privacy guard impact.** None; the change adds no committed private literal and no cloud dependency.

## 21. SECURITY REVIEW HIGHLIGHTS

- **Kill is a privileged operation.** Only the supervisor holding the current instance lease can kill; the target is the recorded session and process-tree handle, never a name, pattern, or user-supplied free-form value. The delivered `DaemonProcessPort` is extended additively with `SIGKILL`, and before TERM the recorded `pid` plus `processStartTimeMs` identity is verified through the optional `startTimeMs` capability, so a reused pid is not signalled; an absent capability is `coordinator.process.capability-gap` with no signal. There is no shell interpolation on the kill path.
- **Single-instance instance lease.** A second supervisor cannot share the state dir, so two loops cannot race to kill or restart the same coordinator; `stop` is a recorded request, not a cross-process handle release. A live holder is refused regardless of lease age; only a dead holder is taken over; lease age applies only when the declared alive capability returns no answer.
- **Fail-closed on unknown state.** A torn or unreadable record set is `unevaluable`; the supervisor does not kill or restart on unknown state. A missing process-port alive, kill-with-grace, or start-time identity capability is a classified gap, not an assumed success; an undeclared alive capability at claim time fails closed with no lease record and no takeover, while a probe that returns no answer is `unknown` (the age fallback). An undeclared or unavailable harness resume is never assumed — it falls back to `spawn-fresh`.
- **No secret surface.** Records, evidence, status output, and error envelopes carry no credentials, tokens, prompts, or transcript content. The owner question is bounded and guarded by the delivered blocker content rules.
- **Denial-of-service bounds.** Reads, renders, records, and wake actions are bounded; a slow or malformed store cannot cause unbounded scanning or a wake storm.
- **Escalation integrity.** The owner question is published by the supervisor identity through the delivered blocker channel; the audience and delegation rules are unchanged, so a coordinator identity cannot answer an owner-audience escalation without the declared policy.
- **Residual risk.** The local same-user boundary is the delivered M1 trust model; a same-user process can in principle interfere with state. This change does not widen that boundary.

## 22. MAINTENANCE & OPERATIONS IMPACT

- **New operator surface.** `coordinator start`, `stop`, `status`, and `tick`; `start --fresh-budget` after an owner recovery decision.
- **Runbook.** Start the supervisor with `coordinator start --foreground` in a terminal (or under a future coordinator unit once the delivered installer gains an explicit `command` vector), or run `tick` for a bounded cycle. Check `status` for the instance (from the latest lease), session, decision, restarts, stuck verdict, last wake, and escalation; `tickVerdict` is `null` for `status` and populated only by `tick`. `stop` appends a stop request and reports `requested=true`; the live supervisor stops at the next cycle boundary and records `released`. On exhaustion, read the owner question in the brief, then either park or `stop` and run `start --fresh-budget`.
- **Configuration.** Six `coordinator.*` keys are policy data; the defaults are documented and can be tuned without code changes.
- **State growth.** Records are appended on actions (decisions, restarts, two-phase `stuck` and single-verdict `unevaluable` verdicts, exhaustion, successful wakes, instance-lease acquisitions/releases/takeovers/stop requests). A quiet `tick` attempts exactly its two lease fence records (`acquired`/`released` or `stale-takeover`/`released`) and appends no action record; the foreground loop adds one lifetime acquisition/release pair and no per-cycle lease record; failed wake attempts persist nothing. The log growth is proportional to coordinator activity plus one bounded lease pair per tick and is bounded per event.
- **Observability.** `coordinator status` is the operational query; the existing brief is the owner query. No new dashboard, metrics store, or alert channel is added.
- **Interaction with M1-S18.** The daemon and its installer are delivered; the coordinator supervisor can be registered under the same user-level installer once `SupervisorInstallRequest`/`renderSystemdUnit` gain an additive explicit `command` vector. The coordinator process, lease, and budget remain distinct.
- **Maintenance cost.** The new domain is pure and the new records are additive; the main ongoing cost is keeping the process-port adapters aligned with harness changes and keeping the six config defaults appropriate.

| Spawn-fresh | Start a new coordinator session when there is no prior session, the prior session completed cleanly, or the prior session's context is at/above the limit, unknown, absent, or not resumable; only the recovery reasons consume a restart ordinal. |
| Iteration expectation | The supervisor's record that the coordinator is expected to make progress after a start, wake, restart, or actionable digest change. |
| Digest-input fingerprint | A bounded, read-only, state-sourced identity over the state event-log cursor and the open coordinator-audience question count; no tracker/CI/network read and no question text. |

| Digest-consumed evidence | The digest-input fingerprint advanced after the expectation and the coordinator session produced a new turn. |
| Prefill-safety corroborator | Positive sourced session progress within `coordinator.progress-bound` (positive `token-delta` or `session-traffic`); it vetoes a stuck verdict so a large working session is not killed. |
| Artifact-evidence stuck detection | A stuck verdict based on the three artifact classes and session progress, never CPU. |
| Stuck record phases | The two appends under one `stuckId` for a `stuck` verdict: `verdict` (before the kill, `killOutcome=not-attempted`) and `outcome` (after the kill, with `terminated`, `forced`, or `failed`); an `unevaluable` verdict produces exactly one `verdict` phase and no `outcome` record. Reads fold to the latest per `stuckId` by ledger sequence. |
| Tick verdict | The tick result's separate `tickVerdict.verdict` field (`progressing`, `stuck`, or `unevaluable`); it is populated only by `coordinator tick` and is `null` for `start`, `stop`, and `status`. `phase`, `reason`, and `evidence` are nullable when the verdict is `progressing`, which is never persisted. |
| Stuck identity | `stuckId = iterationId`, the active expectation's iteration identity; because at most one expectation is active per coordinator, the replay guard is derivable from durable state. |
| Kill with grace | Verify the recorded pid + process start time through the delivered `DaemonProcessPort`'s optional `startTimeMs`, TERM the recorded process tree, wait `kill-grace`, then `SIGKILL` if still alive. |
| Restart budget | The durable per-epoch bound on coordinator restarts, distinct from the per-delivery lane budget. |
| Budget epoch | A durable identity that scopes the restart count; it survives supervisor restarts and is reset only by `start --fresh-budget`. |
| Exhaustion | The state where the restart count has reached the bound; it stops restarts and escalates to the owner with escalation states `not-exhausted`, `exhausted-escalated`, or `exhausted-escalation-failed`. |
| Owner-brief escalation | An owner-audience `decision-needed` typed question rendered first in the existing brief `blocker-questions` anchor. |
| Wake-on-typed-question | Triggering the next coordinator iteration when the rank-1 open question is coordinator-audience. |
| Pickup predicate (`isCoordinatorPickup`) | The delivered payload-determinable rule: rank 1, open (an absent status counts as open), audience coordinator. |
| Collection cycle | The supervisor's evaluation interval, `coordinator.collection-interval`, default 30 000 ms. |
| Ledger sequence | The append-order primary key for every coordinator fold (lease, stuck, last decision, last wake); `recordedAt` is descriptive only and never the tie-break. |
| Progress bound | `coordinator.progress-bound`, default 300 000 ms; the window in which positive sourced progress vetoes a stuck verdict. |
| Supervisor regime | The shared descriptor of state-dir scope, single-instance lease, unit identity, process kind, budget store, supervisor mode, and external unit. |
| State-dir scope | The isolation boundary: one supervisor and one coordinator per state dir. |
| Instance lease | The durable, append-only single-instance ownership folded from the latest `coordinator.fence` record (`acquired`, `released`, `stale-takeover`, `stop-requested`) by ledger sequence; it carries instance identity and holder pid + process start time. Liveness is decided by `alive(handle)` before age; lease age (the same quantity as `fenceAgeMs`) is the injected now minus the acquisition record's `recordedAt`, never re-anchored by a later `stop-requested`; a `stale-takeover` record is itself the new acquisition. It is not a hold on the state write fence and not the delivered `daemon.lock`, because it must carry durable takeover/stop evidence, ledger-sequence folds, and per-iteration claim/release. |
| State write fence | The delivered short-lived, handle-scoped lock (`acquireFence` is non-blocking; `releaseFence` needs the in-process handle). **Claim acquire** (`start`, `tick`) and **non-claim appends** each perform one stale-lock recovery (`fenceStatus` + one `recoverFence` + one acquire retry); a still-busy or non-stale claim maps to `coordinator.already-running`, while a still-busy non-claim append maps to `state.lock.busy`. `recoverFence` only clears a stale lock, so it is never used for instance takeover. |
| Supervisor mode | `foreground`, the only v1 value; `detached` is a reserved closed value for a future coordinator unit and is never produced in v1. |
| External unit | Exactly `absent` in v1; no coordinator OS unit exists, and the delivered M1-S18 installer owns future registration. |
| Reserved escalation slot | The render rule that places the reserved coordinator-exhaustion question first in `typed-questions` and `blocker-questions`, with up to seven others in rank order and the lowest-ranked displaced and counted as omitted. |
| Process-lifecycle port | The delivered `DaemonProcessPort` used for signalling and liveness (`signal` extended with `SIGKILL`, `isAlive`, optional `startTimeMs` identity); harness session spawn and resume are consumed from the delivered harness session port; the domain stays pure. |
| Foreground supervision loop | The declared loop `coordinator start --foreground` runs: the claim-free evaluation cycle (the same cycle as `tick` minus claim/release), an injected cycle-driver/clock seam, one lifetime acquisition/release pair, no per-cycle lease records, and declared stop, fatal, and signal exits. |
| TDR | Technical Decision Record; the record type for the precedent-setting decisions in this change. |

### Appendix C — SC-M1-25 reconciliation

SC-M1-25 states: **Given** a coordinator session mid-iteration, context pressure rises, and a coordinator-audience question is ranked top-of-digest; **when** supervision evaluates; **then** the join-or-resume decision is recorded and applied, a stuck coordinator (no digest consumed, no merge, no answer within the declared window) is detected by artifact evidence, killed with grace, and restarted within budget, and the typed question wakes the next iteration within one collection cycle; **assert** restart events are classified, exhaustion escalates to the owner brief, and the `ceo-loop` function map is covered.

This specification **inherits** SC-M1-25 and **extends** it without divergence:

- "Context pressure rises" is made concrete by `coordinator.resume-context-limit` and the three decision kinds (AC-F2-1..6).
- "No digest consumed" is made observable by the state-sourced digest-input fingerprint (event-log cursor plus open coordinator-audience question count) and a new turn (positive `token-delta` or `session-traffic`), with the explicit absence behavior in DEC-4 (AC-F3-1..4).
- "No merge, no answer" are the `merge` and `answer` artifact classes (AC-F3-1).
- "Killed with grace and restarted within budget" is AC-F4-1..4 and AC-F5-2..3; the kill uses the delivered `DaemonProcessPort` extended additively (AC-F4-1, AC-F10-4).
- "Supervision evaluates" is the declared foreground loop (`start --foreground`) or `tick`; the loop's lifetime lease pair and declared exits are AC-F1-5 and Flow 9.
- "Within one collection cycle" is `coordinator.collection-interval` and AC-F7-1.
- "Exhaustion escalates to the owner brief" is AC-F6-1..3.
- "The ceo-loop function map is covered" is AC-F10-5 and Appendix A.

The only **clarification** is the observable definition of "digest consumed" (DEC-4), which SC-M1-25 left implicit. It is not a divergence: the scenario's artifact-evidence intent is preserved, and the corroborator prevents a false kill.

### Appendix D — Config defaults and justification

| Key | Default | Domain | Semantics | Justification |
|---|---:|---|---|---|
| `coordinator.stuck-window` | 600 000 ms | integer > 0 | Time after an expectation before a no-progress coordinator is `stuck`. | Mirrors the `ceo-loop.sh` stalled-session baseline; long enough for a slow merge/closeout, short enough to catch a stall. |
| `coordinator.kill-grace` | 20 000 ms | integer > 0 | TERM-to-SIGKILL grace for the coordinator process tree. | Mirrors the bash TERM/SIGKILL grace; gives the session a final chance to finish without hanging the supervisor. |
| `coordinator.restart-budget` | 10 | integer ≥ 0 | Restarts per budget epoch; `0` admits no restarts. | Mirrors the `ceo-loop.sh` maximum restart count; distinct from the per-delivery lane bound. |
| `coordinator.resume-context-limit` | 100 000 tokens | integer > 0 | Context size at or above which a fresh spawn is preferred to a resume. | Mirrors the bash context-resume threshold; keeps resume economical while avoiding a huge-context re-entry. |
| `coordinator.collection-interval` | 30 000 ms | integer > 0 | One supervision collection cycle; bounds wake latency, stuck-check cadence, and the lease-age fallback (2×) used only when the declared alive capability returns no answer for the handle. | Mirrors the bash poll cadence and keeps the "within one collection cycle" promise testable; the foreground loop waits on the injected cycle driver at this interval. |
| `coordinator.progress-bound` | 300 000 ms | integer > 0 | Liveness window in which positive sourced progress (`token-delta` or `session-traffic`) vetoes a stuck verdict. | Gives a large working session a bounded window to prove progress before the stuck window can kill it; policy data only. |

The coordinator collection interval is deliberately distinct from the delivered `daemon.heartbeat-cycle` (M1-S18, default 60 s in the M1 contracts) and from `lane.liveness-interval` (M1-S15, default 30 s). When the delivered daemon hosts the supervisor, the daemon may drive the cycle, but the coordinator's own keys remain the source for its wake, stuck, and progress bounds.

Lease age (the same quantity as `fenceAgeMs`) is the injected now minus the acquisition record's `recordedAt`; a later `stop-requested` does not re-anchor it. All six records are additive under `delivery.state.v1`; the schema version does not change and no migration exists. Reads validate kind, schema, required fields, vocabularies, and ordinal contiguity before serving; the `coordinator.fence` record is the append-only instance lease and validates like the others. Every non-claim coordinator record append, including each fence record and each `released`, uses the non-claim per-append state write fence rule (acquire, one stale `recoverFence` retry, append, release); the claim acquire uses the separate claim-acquire rule (one stale recovery, then still-busy/non-stale maps to `coordinator.already-running`). The escalation question is published through the delivered blocker append path after the supervisor's one-shot stale-fence recovery; that path acquires and releases its own fence. A torn or unknown record set is `unevaluable`, never zero.

### Appendix F — Exit matrix

| Outcome | Identity | Exit | Consequence |
|---|---|---:|---|
| Supervisor started, stopped, status read, or tick completed with an actionable result | — (success `data`) | 0 | — |
| Tick observed an already-escalated exhaustion | — (success `data`, `escalation=exhausted-escalated`) | 0 | — |
| Wake outcome `already-woken`, `no-pickup`, or `answered-before-wake` | — (success `data`) | 0 | — |
| Stop request accepted for a live supervisor (no release claimed) | — (success `data`, `requested=true`, `released=false`) | 0 | — |
| Stop with no live supervisor (latest lease `released`, holder not alive, or the declared alive capability returns no answer for the handle and age > 2×interval) | — (idempotent success, `not-running`) | 0 | — |
| Foreground loop observes a `stop-requested` at the cycle boundary, or exits on SIGINT/SIGTERM, with `released` landed | — (success `data`, `released=true`) | 0 | — |
| Restart or resume attempted at/above the budget | `coordinator.restart-budget-exhausted` | 1 | `not_landed` |
| Invalid invocation grammar or argument | `fallback.invocation` | 1 | `not_landed` |
| State permission denied while reading or appending | the delivered `state.permission.denied` | 1 | `not_landed` |
| Harness cannot or will not spawn a session | `harness.capability.gap` / `harness.spawn.refused` | 1 | `not_landed` |
| Wake outcome `delivery-failed` (no record appended) | `coordinator.wake.delivery-failed` | 2 | `unknown` |
| Second supervisor or a concurrent `tick` on the same state dir, including a claim acquire that is still busy or non-stale after one stale-lock recovery | `coordinator.already-running` | 2 | `not_landed` |
| Kill could not terminate the recorded tree, or the recorded pid + process start time does not match the live process (`identity-mismatch`) | `coordinator.session.kill-failed` | 2 | `unknown` |
| Escalation question could not be published (after the publish path's one-shot stale-fence recovery) | `coordinator.escalation.publish-failed` | 2 | `unknown` |
| Missing process-port alive, kill-with-grace, or start-time identity capability | `coordinator.process.capability-gap` | 2 | `not_landed` |
| Torn, unknown, or unreadable coordinator records | the delivered `state.store.torn` / `state.store.unknown` / schema identity | 2 (per the state row) | `not_landed` |
| State write fence busy on a non-claim coordinator append after one stale-lock recovery | the delivered `state.lock.busy` | 2 (per the state row) | `not_landed` |
| Coordinator append fails to write | the delivered `state.write.failed` | 2 (per the state row) | `not_landed` |

Success outcomes that are not errors: harness resume undeclared or unavailable records `spawn-fresh` with reason `session-interrupted` at exit `0`; a stale instance lease taken over and recorded is a success `data` result carrying one `coordinator.fence` `action=stale-takeover` that is itself the new acquisition at exit `0` (no second `acquired`); a claim acquire that recovered a stale fence once and then succeeded is a success at exit `0`; an absent or unsupported progress source is the `unknown` evidence class and is not an error; an alive probe that returns no answer for the handle is `unknown` and only feeds the age fallback (an **undeclared** alive capability is `coordinator.process.capability-gap`, never `not-running`); a stop request accepted for another process is `requested=true`, `released=false` at exit `0`; an uncontended `tick` succeeds at exit `0`, and its one lease pair is expected volume rather than an idempotency violation; a foreground loop that stops on a request or signal leaves exactly one lifetime acquisition/release pair and no per-cycle lease record.

Every non-zero outcome resolves to one declared error-table identity; no outcome exits outside `{0,1,2}`.
