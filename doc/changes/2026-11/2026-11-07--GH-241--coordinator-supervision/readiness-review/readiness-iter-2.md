## New Blocking Findings

1. **[critical] cross_artifact_consistency / ac_quality / system_spec_consistency** — `chg-GH-241-spec.md` §5.1 F-1:146, F-8:181, §17.8 AC-F8-1:565, AC-F8-3:567, §17.1 AC-F1-3:499, §22:627; `chg-GH-241-test-plan.md` TC-010 step 4:481, step 5:482, TC-011 step 1, TC-015 step 2:626, §3.1 AC-F8-3 row:130; TDR-0013 DC-2:296; `chg-GH-241-plan.yaml` header:41 and Phase 6 task 6.3:501-514; `chg-GH-241-plan.md` task 6.3:280.
   Gap: takeover is `alive(handle)` absent **OR** lease age > 2×`collection-interval`, but the lease record is written once at `start` and never refreshed (§22:627 lists records per action and explicitly excludes quiet cycles). With the defaults (30 000 ms interval) every healthy supervisor's lease becomes "stale" after 60 s. Then AC-F8-3 lets a second `start` take over a live supervisor (two supervisors), and the "latest lease is stale" branch of AC-F1-3 makes `stop` report `not-running` and append nothing, so a live supervisor can no longer be stopped. AC-F8-1 ("a second start … is refused") and AC-F1-3 ("given a live supervisor … stop appends stop-requested") become unreachable in steady state. TC-010/TC-011 seed a fresh lease and TC-015 step 2 seeds a live holder with an old lease and demands takeover, so both tests pass while the contracts contradict. TDR-0013, the plan header, plan 6.3, and test plan §1.2:59 repeat the same rule, so the defect is consistent, not a typo.
   Suggested remediation target phase: specification
   Suggested fix: make age a fallback only when liveness is unknown (`alive` absent → takeover; `alive` present → refuse regardless of age; age > 2×interval → takeover only if `alive` cannot be evaluated), or add a declared per-cycle lease refresh with a new action and stable `startedAt`. Re-issue the rule in F-1/F-8/AC-F8-3/EVT-7/Appendix B, TDR-0013, plan 6.3 and test plan §1.2, and add a TC that a live holder past 2×interval is never taken over and can still be stopped.

2. **[major] system_spec_consistency / spec_completeness** — `chg-GH-241-spec.md` F-1:146, F-8:181, AC-F8-1:565, §12:405; `chg-GH-241-plan.yaml` Phase 6 task 6.3:501-514; delivered `packages/core/src/state/index.ts:604-627` (`acquireFence`) and `:426-449` (`appendRecord`).
   Gap: the lease claim is a read-fold-then-append. The spec says each write "acquires the delivered state write fence for that one append and releases it immediately" but never says the fold is re-read after the fence is acquired and before the claim/takeover append. The delivered fence serialises single appends only; reads never require it. Two concurrent `start`/`tick` processes can therefore both read the fold as free and both append `acquired`, so AC-F8-1's refusal is guaranteed only for sequential invocations. No TC exercises overlapping claims.
   Suggested remediation target phase: specification
   Suggested fix: pin the claim/takeover as one `acquireFence → re-read fold → append → releaseFence` critical section (or an equivalent declared atomic mechanism), and add a TC with two overlapping claims over two store handles asserting exactly one `acquired` and one `coordinator.already-running`.
