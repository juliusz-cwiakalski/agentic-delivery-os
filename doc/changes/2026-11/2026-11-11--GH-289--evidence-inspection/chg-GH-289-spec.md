# CHANGE SPECIFICATION

> **PURPOSE**: Make the dual-run evidence ledger inspectable and actionable from the CLI — a bounded, machine-readable attempt history per work item and a divergence resolution that declares that it ran from local evidence and reports the unresolved counts it leaves behind — so handover decisions and retros cite recorded evidence instead of reading state files by hand.

## 1. SUMMARY

The dispatch engine already records one durable attempt record per classified dispatch, carrying the result token, the pm-notes/tracker/ci corroboration triple, the comparison outcome, the divergence reference, the timestamps, the harness, and the evidence class. Nothing in the CLI reads that history: an operator who wants to know what the engine observed for a work item opens the state files, and a retro that cites dispatch evidence has no surface to cite. `dispatch dual-run resolve` likewise appends a resolution but reports neither that it ran from local evidence nor what the resolution left unresolved, so the two facts the handover decision turns on are absent from the output that records the decision.

This change delivers the missing read side as `dispatch attempts [--ref <ref>] [--limit <n>]`, a read-only subfamily of `dispatch` over the delivered ledger, with a declared `attempts.v1` envelope, a deterministic bounded text digest, repository-scoped isolation, and explicit bound declarations. It extends the resolve result additively with an unconditional `mode: "local-evidence"`, the owning repository, and the unresolved counts after the resolution, makes one declared change to the summary — its divergence block joins that same repository-scoped computation and its identifier list honours the 20-identifier bound the dispatch feature spec already documents — and points the reader at `dispatch dual-run summary` for coverage and floor instead of duplicating them.

The change adds no state record, no schema version, no configuration key, no external dependency, and **no error-table row**: the three error identities the M2 command proposal invents are resolved against the delivered `input` and `state` identities, and an empty history is a successful verified read rather than a refusal.

## 2. CONTEXT

### 2.1 Current State Snapshot

- **The durable evidence the read side needs already exists.** Every dispatch that reaches classification appends exactly one `dispatch.attempt` record (`delivery.dispatch.attempt.v1`) carrying the attempt id, the normalized repository identity, the work-item reference, the harness kind, the evidence class, the start and finish timestamps, the handover state at run, the engine outcome, the result token, the comparison record (class, token, outcome), an optional single divergence reference, the false-success flag, the tri-state corroboration record (`pmNotes`, `tracker`, `ci`), the optional resume facts, up to sixteen bounded evidence references, and the recorded time. The record schema, the fixture set, and the writer path are delivered and exercised by the dispatch truth, evidence, gate, and handover suites.
- **The bounded reader already exists.** The delivered ledger helper reads attempt records from the store in one verified pass, keeps the newest 5,000, and returns a declared truncation carrying the bound and the omitted count. A torn or unreadable store returns a classified `state.*` code rather than an empty success. Divergences have their own reader, a latest-per-identifier fold, and a four-field summary (reported, resolved, unresolved, and every open identifier) whose counts are taken from that store-wide list, with no identifier cap.
- **No CLI read surface exists.** The `dispatch` grammar accepts exactly four forms: `dispatch <ref>`, `dispatch dual-run summary --repo <repo>`, `dispatch dual-run resolve <divergence-id> --note <text>`, and `dispatch handover <repo> [--revert]`. There is no `attempts` verb, no `--ref`, and no `--limit` on the family; the family's declared flags are `--revert`, `--harness`, `--resume-prompt`, `--repo`, and `--note`, and `--json` is a global flag.
- **The summary is the gate surface.** `dispatch dual-run summary --repo <repo>` reports the evidence window and its reason, the elapsed day count, counted deliveries, counted and excluded evidence classes, incidents, the divergence block, coverage present and missing, corroboration satisfaction, the floor, the verdict, and every unmet condition, with `floor_only=true` in the text projection. Coverage and floor are its contract and are not reported anywhere else.
- **Resolve already runs from local evidence only.** It resolves no credential, performs no network call, and reads no truth source outside the local store and the divergence ledger. It appends one resolved record, leaves the original open record byte-identical, clamps the note to 240 characters before the record is built, is idempotent on replay, maps an absent identifier to `input.value.rejected` under `kind: "input"`, and keeps a genuine store fault under `kind: "state"` with that row's own projection. Its success `data` carries exactly `divergenceId`, `state`, `resolved`, `note`, and `principal`: it declares no mode and no counts.
- **Read-only dispatch surfaces resolve identity without persisting it.** Repository identity resolves from the checkout: the dispatch repository binding marker (`dispatch-identity.json` in the git common directory) when one exists, then the scheduling engine's normalized key, then the checkout's configured remote normalized to `host/owner/name`. Only a dispatching invocation creates or repairs that binding marker; the read-only `dual-run summary`, `dual-run resolve`, and `handover` surfaces read the binding when present and never persist one. The project checkout identity marker minted by the per-repository state scope is a separate artefact: any store-opening invocation, including a read, may cause it to exist once. An unresolvable identity is a clean refusal at exit `1`.
- **Delivery state is per repository.** After GH-288 a store is opened at `<host root>/projects/<project key>`, so two checkouts of different repositories hold disjoint state. The one-step migration moves a pre-migration store wholesale into one designated project's root and re-attributes nothing, so a migrated project root can hold attempt and divergence records whose `repository` field belongs to a different repository. Every record therefore carries its own repository identity, and reading a store is not the same as reading a repository.
- **The active change context has a delivered seam.** The local PM context at `.ai/local/pm-context.yaml` declares an `active_change` with `workItemRef`, `branch`, and `change_folder`; it is read by the delivery digest and by the spend read side, which refuses with `input.value.rejected` and the message "no active change context; pass `--ref <ref>`" when the context is missing, malformed, or carries no active change.
- **The error table is a closed, row-pinned registry.** `ERROR_TABLE` declares 124 identities; the `dispatch` domain kind carries exactly four rows; the result-contract spec documents exactly those 124 rows and a bidirectional sync gate keeps the two in step. Structural suites pin both numbers, and a reserved two-segment allowlist pins the exact codes of that shape.
- **The help surface is inventoried and gated.** `dispatch` is prompt-required, appears in the root listing among seventeen families, and carries exactly four help entries — the family plus `dual-run summary`, `dual-run resolve`, and `handover`. The reference-page parity gate pins that count and requires every see-also target to exist and to be registered in the coverage inventory, which names the prompt-required families and their per-command reference pages.
- **The M2 pack carries the proposed contract and its own contradiction.** The M2 contracts page declares `attempts.v1` with `divergenceRefs[]` as a list, a per-ref read side, a resolve that declares `local-evidence` mode when tracker truth is unreachable, and coverage and floor staying on the summary. The M2 `attempts(1)` page proposes three error codes (`attempts.ref-unknown`, `attempts.limit-invalid`, `attempts.ledger-unavailable`) and states both that exit `0` covers "an empty history" and that exit `1` means "the ref has no attempt history"; its envelope example names the command `dispatch attempts`; its text example prints a token (`success`) that is not in the eleven-token vocabulary.

### 2.2 Pain Points / Gaps

- **Evidence inspection is file spelunking.** The attempt ledger is durable, verified, and already carries every fact a handover decision or a retro cites, but the only way to read it is to open the state files by hand. The ticket's premise — that handover decisions and retros rest on readable evidence — has no reader.
- **The resolve output omits the two facts that make it evidence.** A resolution records a note and a principal, but the result does not say that it ran from local evidence and does not report the unresolved count it leaves behind, so a handover argument cannot cite the resolve result to show that the truth condition moved.
- **A repository's evidence is not distinguishable from a store's evidence.** After the per-repository split and the wholesale migration, one project root can contain another repository's history; no surface filters on the record's own repository, so a read would present a foreign attempt as the operator's own.
- **The proposed error identities cannot exist.** Three new `attempts.*` codes would break a closed registry that is pinned by row count, by kind count, and by the two-segment allowlist, and would require a bidirectional documentation sync for identities the delivered surfaces do not need.
- **The proposed contract overstates cardinality and contradicts itself on failure.** `divergenceRefs[]` describes a list the durable record cannot fill beyond one element, and the proposed exit table makes an empty ref history both a success and a refusal.
- **Nothing points the evidence reader at the gate.** Coverage and floor live on the summary; an operator inspecting attempts has no declared pointer to the surface that answers "is this repository eligible".
- **The pack and the product would disagree silently.** Left alone, the M2 page would describe a command that does not exist in that shape, which is exactly the mount-and-documentation drift the milestone pack records as a recurring failure mode.

## 3. PROBLEM STATEMENT

Because the dispatch engine records durable attempt and divergence evidence while the CLI exposes no reader for it and the resolve result declares neither its evidence mode nor the unresolved counts it leaves, an operator preparing a handover decision or a retro must open state files by hand, cannot show from the command output that a resolution moved the truth condition, and — because a project state root can hold history recorded by another repository after the per-repository migration — cannot tell whose evidence a record is; and because the proposed contract's three new error identities and self-contradicting exit rule cannot be satisfied by a closed error registry, the read side would either break that registry or ship undefined failure semantics.

## 4. GOALS

- **G-1**: Make a work item's attempt history readable from the CLI as a bounded, declared, machine envelope, with every field the contract names present on every row.
- **G-2**: Make the read deterministic, read-only with respect to delivery evidence, and bounded in every dimension it can grow (page, ledger, human lines, bytes), with each bound declared rather than implied.
- **G-3**: Make the read repository-scoped: only the resolved repository's attempts are returned, foreign records are excluded and counted but never named, and an invocation outside a checkout refuses instead of inventing a repository.
- **G-4**: Resolve the error-identity question inside the delivered taxonomy — no new error-table row — and give empty history a single declared meaning.
- **G-5**: Extend the resolve result additively so it declares `local-evidence` mode unconditionally, names the owning repository, and reports the unresolved counts after the resolution, while keeping replay idempotent and the note bound intact.
- **G-6**: Deliver a deterministic human digest that follows the family's existing conventions, and keep coverage and floor on the summary with an explicit pointer instead of a duplicate.
- **G-7**: Make the surface reachable and documented: family help lines, a fifth help entry, the M2 reference page registered and corrected, the dispatch feature spec reconciled, and the planning corpus advanced — with no root-family change and no prompt-required change.

### 5.1 Capability Details

- **F-1 — Read surface and ref resolution.** `dispatch attempts` is a verb of the delivered `dispatch` family with `--ref <ref>` and `--limit <n>` and the global `--json`. It is a subfamily, not a new root family: the root listing keeps its seventeen families and the prompt-required set is unchanged. Grammar is evaluated before any store is opened. `--ref` must match the canonical work-item shape (`[A-Z]+-\d+`); any other value, an unknown flag, or an unexpected positional is refused at exit `1` with `input.value.rejected`, with no state read and nothing appended, so the whole grammar-refusal family is one cell with one owner (`AC-F1-6`). When `--ref` is supplied, the read is scoped to that reference and the envelope declares `refSource: "flag"`. When `--ref` is omitted, the active reference is resolved from the local delivery context — `.ai/local/pm-context.yaml`, the file the delivery digest and the spend read side already read, through the same seam: `active_change.workItemRef` — and the envelope declares `refSource: "active-change"`. When that context is absent, unparsable, or carries no active change, the command refuses at exit `1` with `input.value.rejected` and a bounded summary that names the missing context and the `--ref` remedy, appending nothing and reading no store; the refusal is the delivered spend behaviour, reused rather than reinvented. `--limit` accepts canonical decimal notation only — digits with no sign, no surrounding whitespace, and no leading zero, so the accepted form is `[1-9][0-9]*` — with the default 20, the minimum 1, and the maximum 100; a non-integer, a non-numeric value, a missing value, a non-canonical form (`07`, `+7`, ` 7`), zero, a negative value, or a value above the maximum is refused at exit `1` with `input.value.rejected` and nothing is clamped or silently normalised, because a clamped or rewritten page tells the caller it has the whole history when it does not and `hasMore` already declares page truncation honestly. Results are ordered newest first by `startedAt`, ties broken by `recordedAt` descending and then by `attemptId` ascending, so the order is total and identical across runs. Read-only means no attempt, divergence, handover, or authority record is appended, no fence is acquired, and no credential, provider, harness, or model is touched; the surface does open a store, so it inherits exactly the effects every store-opening invocation has (§8.5).
- **F-2 — `attempts.v1` envelope and projection.** The machine `data` carries eight always-present keys — `repository` (the resolved normalized `host/owner/name` identity), `ref` (the reference the read was scoped to), `refSource` (`"flag"` or `"active-change"`), `limit` (the effective page bound), `matched` (how many records matched the filters within the bounded ledger read), `hasMore` (whether matched attempts exist beyond the returned array), `attempts[]` (newest first), and `excluded` (a count-only object: `foreignRepository`) — plus `truncation` only when a bound binds. Each `attempts[]` entry projects exactly sixteen fields from the stored record: `attemptId`, `repository`, `ref`, `harness`, `evidenceClass`, `outcome`, `token`, `startedAt`, `endedAt`, `divergenceRef`, `corroboration`, `falseSuccess`, `comparison`, `resumeMode`, `evidenceRefs`, `recordedAt` — the projection is the attempt's identity, its result, its comparison, its corroboration triple, its divergence reference, its timing, and its bounded citations, and it carries no prompt, transcript, diff, credential, or provider payload. `endedAt` is the contract name for the record's finish timestamp and the projection maps it one-to-one; no stored field is renamed and the state contract is untouched. `divergenceRef` is a singular value — one identifier or explicit `null` — because the durable record carries at most one reference and a list that can never hold two elements declares a capability the evidence cannot supply. The corroboration object carries the three named sources with their tri-state values. The `comparison` object carries the delivered class, token (or `null` when not applicable), and outcome. `resumeMode` is the recorded mode or `null`. `evidenceRefs` is the bounded identifier list the record carries (at most sixteen). `truncation`, when present, is a single object `{ scope, bound, omittedRecords }` whose scope is `"ledger"` when the newest 5,000 records were folded from a larger ledger or `"page"` when the serialized page was shortened by the 65,536-byte budget; `bound` names the bound that bound — `5000` for `"ledger"` and `65536` for `"page"` — so the two scopes are distinguishable by `scope` and by `bound` together without a third key; `omittedRecords` counts what that bound left out, which is records dropped by the ledger window for `"ledger"` and otherwise-eligible rows dropped by the byte budget for `"page"`; the ledger scope takes precedence because it is the outermost omission and `hasMore` already declares that the returned array is a prefix. The envelope adds no top-level key; `command` stays `"dispatch"`, which is the family token every dispatch subform already carries.
- **F-3 — Repository-scoped read isolation.** Two rules apply together. Physically, the store is the project state root derived from the checkout identity, so another repository's state lives elsewhere. Logically, the read filters records on their own `repository` field against the repository resolved for the invoking checkout, because the delivered migration places a pre-migration store — history of whatever repositories shared it — inside one designated project root, so a store is not a repository. Records failing the filter are excluded from `attempts[]` and counted in `excluded.foreignRepository`; the count is of attempt records **within the retained ledger read window** — the newest 5,000 records the verified read keeps — whose `repository` differs, and it is independent of `--ref`, because it is a statement about the root rather than about the query. Records in the omitted tail of a larger ledger are not counted, because the read never retained them: the count describes what was read, never what is on disk. Their identifiers never appear in the envelope, its warnings, or the text digest, because the count is an honest statement about the root while an identifier would disclose another repository's work. Repository identity resolves through the delivered resolver with persistence disabled: a read never creates or repairs the **dispatch repository binding marker** (`dispatch-identity.json` in the git common directory) and never persists a binding from an argument. The **project checkout identity marker** is a different artefact — the per-repository state scope's own marker, minted once by any store-opening invocation — and is the only marker a read may cause to exist (§8.5). An unresolvable identity refuses at exit `1` with `input.value.rejected` and a bounded summary naming the checkout; in particular an invocation outside any checkout refuses rather than reporting the host-scoped `unbound` store as some repository's history.
- **F-4 — Read-only semantics, refusals, and empty history.** Four failure cells exist and no others. A malformed request (a non-canonical ref, an invalid limit, an unknown flag, an unexpected positional) is `input.value.rejected`, exit `1`. An unresolvable active reference or repository identity is `input.value.rejected`, exit `1`, with a bounded summary that names what could not be resolved. A store that cannot be read honestly — torn, unreadable, schema-mismatched, permission-denied — keeps its own `state.*` identity under `kind: "state"` with that row's category, retryability, consequence, remediation, and exit `2`; it is never reported as an empty history. An empty history is not a failure at all: a verified read that matches no record exits `0` with `attempts: []`, `matched: 0`, and `hasMore: false`, because the ledger is keyed by attempt identifier rather than by reference, an absent reference is indistinguishable from a reference whose attempts have not been recorded yet, and refusing would make a first inspection of a freshly dispatched ticket fail. The proposed `attempts.ref-unknown`, `attempts.limit-invalid`, and `attempts.ledger-unavailable` identities do not exist: the first is the empty-history case, and the other two are the delivered `input` and `state` identities. The read's boundedness is a property of the read, not of the response: the ledger read keeps the newest 5,000 records and declares the omission, the page is bounded by `limit`, and the serialized page is bounded by 65,536 bytes with a declared page omission.
- **F-5 — Resolve result extension.** The delivered five keys keep their names and meanings. Four facts are added: `mode` is the constant `"local-evidence"` on every successful resolution — including a replay — because the delivered resolve resolves no credential, performs no network call, and reads no truth source outside the local store, so a mode that appeared only sometimes would imply a live-truth branch that does not exist; `repository` is the repository recorded on the resolved divergence, so the counts are unambiguously scoped; `divergences` is the block the summary reports — the four delivered fields `reported`, `resolved`, `unresolved`, and `unresolvedIds`, plus the declared additive key `idsTruncated` — computed by the same latest-per-identifier fold over the records of that repository after the resolution, where `unresolved` is the exact number of folded records still `open`, `unresolvedIds` lists at most 20 of them, and `idsTruncated` declares an omission exactly when identifiers were dropped; and the existing `resolved` flag keeps meaning "this call appended the resolution". The note contract is asymmetric by design: a blank or whitespace-only note is refused at exit `1` with `input.value.rejected` and nothing is appended, because a resolution without a rationale is not evidence, while a note longer than 240 characters is clamped to the bound before the record is built and reported as stored, because a long note already carries information and must never fail a write. Replay is idempotent: a second identical resolve appends nothing, reports `resolved: false`, the stored note and principal, and unchanged counts. The result reports the repository the divergence belongs to rather than the invoking checkout's, because a resolve is an action whose subject is the named divergence and the identifier is its only input; this makes a resolution of a record that a migrated root inherited from another repository visible in the output instead of silent (OQ-1).
- **F-6 — Human digest and family conventions.** The attempts digest follows the family's multi-row convention rather than the run form's four keys: one summary line, then one line per attempt, newest first, then an optional truncation key, then one pointer line. The summary line is `attempts=<n>; repository=<identity>; ref=<ref>; has_more=<true|false>`. A row is `<startedAt> <ref> <token> <corroboration> <divergenceRef|none> <harness> <evidenceClass>` with the timestamps printed exactly as stored — no reformatting, no locale, no time zone conversion, no rounding. The corroboration cell is a closed three-value derivation from the recorded triple: `corroborated` when no source is `unsatisfied` and at least one is `satisfied`, `uncorroborated` when any source is `unsatisfied`, and `vacuous` when all three are `not-applicable`. The run form's `result=`, `pr_url=`, `exit_code=`, and `last_message=` keys belong to the one-shot run and never appear here. An empty page prints the summary line, no rows, and the pointer. The digest is bounded to 40 lines and 8,192 bytes: rows are dropped from the oldest end, and when any row is dropped a `truncation=human:bound:<kept>,omitted:<dropped>` line is printed before the pointer, so at most 37 rows print alongside it. The pointer line is `next: dispatch dual-run summary --repo <repository> (coverage and floor)`. The resolve surface gains one deterministic line of its own: `divergence=<id>; state=<state>; appended=<true|false>; unresolved=<n>; mode=local-evidence; repository=<identity>`, so the counts the ticket requires are visible to a human as well as to a machine.
- **F-7 — Coverage and floor stay on the summary.** The attempts envelope carries no `coverage`, `floor`, `verdict`, `eligibility`, or `unmetConditions` key, and the attempts surface never evaluates the gate. `dispatch dual-run summary --repo <repo>` keeps its delivered report and its verdict semantics, with its divergence block changed in the declared ways of §8.5: it becomes one shared repository-scoped computation with the resolve result's block (DEC-15), so its counts are exact on an unmigrated root and cover only the declared repository's records on a migrated one; its `unresolvedIds` narrows to the declared at-most-20 list with the additive `idsTruncated` key whenever identifiers are dropped; and the human `unresolved_divergences=` line prints that same list. Its four delivered fields keep their names, types, and order, and `reported`, `resolved`, and `unresolved` keep their meanings as exact counts; no verdict changes because any open divergence already makes the count positive and the eligibility predicate reads "zero unresolved". The pointer in the text digest, the help synopsis, and the reference page are the declared route from evidence to the gate.
- **F-8 — Mount, help, inventory, and documentation coverage.** `dispatch attempts` becomes reachable through the static help inventory: the family entry gains one usage line, the `--ref` and `--limit` options, and one example; a fifth help entry is added at the path `dispatch attempts` with its own summary, usage, options, and example, and its see-also target is the M2 `attempts` page. The root listing keeps seventeen families because `attempts` is a subfamily, so no prompt-required change is made and the entrypoint composition is untouched. The reference-page parity gate's dispatch pin moves from four entries to five as a declared contract update, and the M2 attempts page is registered in the coverage inventory so the see-also target resolves. The M2 page becomes the delivered reference page: it documents `--help` and `--version`, replaces the three proposed error rows with the resolved identities, states the empty-history rule, prints `command: "dispatch"` in its envelope example, replaces `divergenceRefs[]` with `divergenceRef`, replaces the text example with the declared digest, and keeps its proposed status header per the pack's planned-until-milestone-exit semantics. The M1 `dispatch(1)` page stays byte-unchanged: it is a milestone snapshot of M1 delivery, and the subfamily documents itself in its own milestone's page root.
- **F-9 — Additive compatibility.** The run envelope, the summary envelope, the handover result, and the five delivered resolve keys keep their names, types, and order, and their meanings apart from the summary divergence block's declared changes (F-7, §8.5). The dispatch command definition gains one verb branch. The two attempts flags are declared in the published grammar — the family usage line and its options, the fifth help entry, and the reference page — while their validation belongs to the command module rather than to the shared parser: the grammar lets the flags reach the module, and the module owns value checking, canonical-form checking, and unknown-flag refusal, because the shared parser would answer `fallback.invocation` for a missing or malformed value where the attempts grammar must answer `input.value.rejected` with the accepted shape and range named (AC-F1-3, AC-F1-6). Because the definition opts the family out of the shared parser's unknown-flag branch, the four delivered forms keep their `fallback.invocation` refusal through a guard in the handler itself, which is the only remaining refusal for an undeclared flag: with the definition accepting any flag, `dispatch <ref>`, `dispatch dual-run summary --repo <repo>`, `dispatch dual-run resolve <id> --note <text>`, and `dispatch handover <repo> [--revert]` each still refuse an undeclared flag at exit `1` with `fallback.invocation` under that row's `kind: "fallback"` and no store read. That guard is proven by the unknown-flag suite cell of the delivered-form stability case (TC-ATTEMPT-034) rather than by that case's diff-review cell, and the attempts grammar's own refusals stay owned by TC-ATTEMPT-039 (AC-F9-1). The exit projection is unchanged: an attempts payload carries no `result`, `verdict`, or `operation`, so it projects as a plain success at exit `0`. The attempts payload is discriminated unambiguously by its `attempts` array, so no existing text selector can mistake it for the summary, the run form, or the handover result. No configuration key, external dependency, workspace package, state record, schema version, token, projection class, or exit literal is added.

## 10. TELEMETRY & OBSERVABILITY REQUIREMENTS

- **No new telemetry.** No event, metric, span, or diagnostic stream is added. The read side is the observability: it turns recorded evidence into a bounded, inspectable projection.
- **Declared degradation instead of silence.** Every bound that binds is declared in the envelope (`truncation`) or in the digest (`truncation=human:...`), and `hasMore` always states that the returned array is a prefix. Excluded foreign records are disclosed as a count.
- **Failure diagnosis.** Every refusal names the value that makes it actionable: a non-canonical reference names the value and the expected shape; an invalid limit names the value, the accepted range, and the canonical decimal form; an unresolvable active reference names the local context file and the `--ref` remedy; an unresolvable repository identity names the checkout; a store fault carries the `state.*` row's own remediation and names the store.
- **No unintended disclosure.** Foreign records are counted, never named. Attempt evidence references are identifiers only, and the projection carries no prompt, transcript, diff, credential, or provider payload.
- **Audit continuity.** Both invocations are recorded in the command audit ledger through the delivered mechanism, with no new audit field.

## 12. ASSUMPTIONS

- The delivered attempt record carries every field the contract names, and its reader returns a verified truncation rather than an unbounded list. Both are verified in the delivered ledger and its suites.
- A stored attempt record's `repository` is the authority for whose evidence it is, and it is rename-invariant because it is the normalized `host/owner/name` identity bound at first resolution.
- The per-repository state scope means an `attempts` invocation opens exactly one store, so the read has one physical scope and needs no directory traversal.
- The local PM context file at `.ai/local/pm-context.yaml` is the delivered source of the active change reference, and the spend read side already consumes it through a reusable seam.
- The delivered resolve performs no truth read, so a constant `local-evidence` mode is a statement of fact rather than a policy choice.
- The error table and its documentation sync are closed over the declared rows, and adding rows is a milestone-level decision rather than a story-level one.
- The help inventory, the coverage inventory, and the parity gate are the three mechanisms that make a subfamily reachable, and each needs its own update.
- The state store's read path verifies the ledger once and classifies a torn or unreadable store, so a successful read is a verified read.
- Tests can build attempt, divergence, and handover records directly through the delivered ledger helpers and can point the state-scope override at a temporary root.

## 18. ROLLOUT & CHANGE MANAGEMENT (HIGH-LEVEL)

The change is additive and ships behind no flag: the new verb, the two flags, and the three additive resolve keys are visible as soon as the build lands, and the only delivered surface whose reported fields move is `dispatch dual-run summary`, in the declared ways of §8.5. Delivery order that keeps every gate green at each step:

1. The contracts and the projection: the attempts data and projection types, the bounds, and the pure page/fold helper, with their unit tests.
2. The read runtime over the delivered store and identity seams, with the isolation, refusal, and bound tests.
3. The command branch, the flag declarations, and the text renderers, with the grammar, digest, and determinism tests.
4. The resolve enrichment and the shared count rule, with the resolve and summary agreement tests.
5. Help, inventory, and the parity-pin update as one unit, so no intermediate state leaves a gate red.
6. Specification and corpus reconciliation.

One changeset declares the fixed-group packages at `minor`, consistent with an additive command surface; a patch entry would fail the release gate.

## 19. DATA MIGRATION / SEEDING (IF APPLICABLE)

None. No record kind, schema version, key prefix, fold, or validation rule changes, and no existing record is rewritten, re-attributed, or backfilled. Records written before this change are readable as-is because the projection reads the delivered fields, and a historical record whose `repository` field names a different repository is excluded from a mismatched read and counted rather than migrated.

## 20. PRIVACY / COMPLIANCE REVIEW

No personal data is introduced. The projection carries attempt identifiers, repository identity, work-item references, harness kind, evidence class, outcome and token, timestamps, bounded evidence identifiers, and a divergence reference; it carries no prompt, transcript, diff, credential value, or provider payload, and the evidence references are identifiers by construction. Excluded foreign records are disclosed as a count, never as identifiers, so the read cannot become a cross-repository disclosure channel. The attempts digest prints no filesystem path — the repository identity stands in for the store location — and the resolve line prints the divergence's repository, which the operator already supplied an identifier for.

## 21. SECURITY REVIEW HIGHLIGHTS

- **No new input surface reaches a network or a credential.** Both surfaces are local reads; the read resolves no credential and the resolve's local-only property is preserved and asserted.
- **Identity is read, never persisted.** The read resolves repository identity with persistence disabled, so an argument or a bare read cannot create, repair, or re-bind the dispatch repository binding marker; the project checkout identity marker is a separate store-scope artefact that any store-opening invocation may mint once.
- **Foreign evidence is not readable through a scope mismatch.** The logical repository filter is the control that keeps a migrated root from serving one repository's evidence to another; the count is the only disclosure.
- **No secret can enter the output.** The projection is a fixed allowlist of fields; the text renderers print those fields only, and the shared redaction path is unchanged.
- **Failure wording cannot leak a value.** The refusals name a reference shape, a range, a context file, or a store, never a secret; the store fault keeps the delivered remediation rather than echoing content.
- **Taxonomy integrity is a security property of classification.** Reusing the delivered `input` and `state` identities keeps exact-code classification total, so no read failure can be contained by a fallback identity while looking like a domain refusal.

## 22. MAINTENANCE & OPERATIONS IMPACT

The read side is a consumer of the delivered record contract, so it needs maintenance only when the attempt record changes; the projection is the single place that maps stored fields to consumer-facing names, and the contract test that asserts the exact projection field set is the guard against an accidental widening. The page and ledger bounds are declared constants beside the delivered dispatch bounds, while the byte and line budgets are the delivered dispatch constants themselves rather than second declarations, so each bound has exactly one declaration and tuning stays a one-line change with a test that asserts the declaration rather than the number. The help entry, the coverage inventory row, and the parity pin form one unit: adding a future dispatch subform without all three leaves a gate red, which is the intended behaviour. Operators gain one durable diagnostic habit — reading attempts before arguing about a handover — and the pointer line keeps the gate surface one command away.

| Term | Definition |
|---|---|
| Attempt record | The durable `dispatch.attempt` payload appended once per classified dispatch; the only source the read side projects. |

| Foreign record | A record whose `repository` field names a repository other than the one the read resolved; excluded and counted, never named. |

| Ledger bound | The newest 5,000 attempt records the delivered verified read retains; an omission is declared. |
| Project checkout identity marker | The per-repository state scope's own checkout marker (GH-288), minted once by any store-opening invocation; its creation is a permitted inherited effect of a read. |
| Dispatch repository binding marker | The `dispatch-identity.json` file in the git common directory that binds a checkout to a repository identity; a read surface never creates, repairs, or re-persists it. |
