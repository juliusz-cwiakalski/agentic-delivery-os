## The four judgement questions

1. **Is the F-1 evidence genuinely observed through the delivered path?** Yes (iteration-1 F-1). The re-recorded observation is a different run from the withdrawn one, records the delivered wrapper’s resolver output, a recorded attempt, the delivered attribution union, the delivered extractor’s row, and a separate read-only store query. The store read independently supports the row’s version/agent/model, and the timestamps match exactly. It supports AC-F5-6 and the live half of AC-F3-1 **as written**. The only weakness is explanatory (iter-2 F-12) and stale pm-notes text (iter-2 F-10), not the evidence. One honesty caveat: the profile (`coder-seat`, `agentOverrides {coder: …}`) is the observer’s declared input, and the production `resolveProfileContext` (real config) is not exercised by the observation or any test (iter-2 F-7); the AC does not require that, but it should not be overstated as a production-config run.
2. **Does the F-2 mount make the production port resolve a caller-supplied agent, and is the role-less passthrough preserved?** Yes (iteration-1 F-2). The composed `opencode` port is wrapped, the wrapper calls `resolveBinding` once per spawn and supplies the binding, and an `undefined` agent short-circuits to the original `call(callInput)` — byte-identical, so DEC-15 is intact. Two caveats: the mount is proven by a source-text assertion rather than a composed-port test (iter-2 F-7), and the context resolver is a second config-parse path (iter-2 F-8).
3. **Are the F-3 identities in their correct homes, and is the widening safe?** Yes (iteration-1 F-3). Empty/whitespace → `config.value.invalid` field `agent`; unassigned → `provider.profile.invalid` naming agent/profile/seats, in both helpers, with oracles. The `HarnessFailure` widening leaks nothing: the closed code vocabulary is unchanged, adapters still emit `kind: "harness"`, the attempt-stage detail keeps its delivered two-value kind, and `provider.profile.invalid` keeps its delivered `user-validation` exit. The only new surface is the wrapper’s undeclared “no context” condition (iter-2 F-4), which reuses `config.value.invalid`.
4. **Did any remediation regress a delivered control, or add a duplicate/undeclared surface?** No behavioural regression found: role-less spawn, the refusal side-effect guarantees, the closed vocabulary, the exit projections, and the telemetry schema are intact; all touched suites pass. New/duplicate surfaces: the undeclared no-context refusal (iter-2 F-4), the duplicated refusal mapping and config resolution (iter-2 F-8), the second version grammar (iter-2 F-5), and the edge/domain duplicate absence projection (iter-2 F-11).
