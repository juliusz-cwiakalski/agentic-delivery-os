# CHANGE SPECIFICATION

> **PURPOSE**: Make opencode v2.x a version-gated, mode-decided, profile-propagating delivery harness whose sessions land schema-versioned per-seat telemetry in the state layer — so a harness-port spawn with a caller-supplied agent identity either runs with the resolved profile or refuses with a typed, actionable identity instead of guessing.

## 1. SUMMARY

This change delivers milestone story M3-S1. It extends the delivered harness seam additively with four things the harness cannot state today: a supported-version window evaluated before any session exists, with typed refusals instead of an unexamined pass, and a single production probe point whose output grammar and normalization are pinned; one explicitly decided integration mode for opencode dispatch, recorded as a decision and drawn from the mode surfaces the installed harness actually exposes; per-spawn propagation of the resolved seat binding on a surface the harness honours — one seat per spawn, resolved from the agent the caller supplies at the harness port (DEC-15); and per-seat telemetry attribution — seat identity, resolved model, tokens, cost, and store-sourced durations — landing in the state layer under the existing schema identity, with the version the session record itself states stamped on every row and the delivery bound by the union of the session identities the work item's recorded dispatch attempts hold and the bindings those attempts recorded. Telemetry absence, degraded capture, and extraction failure stay three distinct classifications inside the delivered envelopes; no command surface is added. The delivered conformance registry gains scenarios for the three refusal and propagation properties while its six-scenario classification floor stays as delivered. Both delivery dependencies (M1-S11, M2-S14) are delivered current truth, so this change extends a live seam rather than creating one.

## 2. CONTEXT

### 2.1 Current State Snapshot

- **The harness seam is delivered.** `HarnessInstance` carries a closed kind, an injected `observedVersion` (`null` is the explicit unknown value and always rides the `version-probe-failed` warning), and a capability declaration with explicit gaps. `HarnessSessionPort` carries spawn, deliver, resume, collect, classify, liveness, and read-only session listing; `steer` is a closed operation in the vocabulary and a steering payload on `deliver`/`resume`, not a separate port member. The opencode adapter spawns the harness, decodes its JSONL stdout line by line, acquires the handle on the first identified session line — so the dispatch holds the session identity it ran — keeps draining to process close, and resumes by session identity. The shared classifier is harness-neutral; adapters classify nothing themselves.
- **The installed harness and its store are observed, not assumed.** At intake the harness on `PATH` reported `opencode v2.2.5`; at delivery the installed harness — the `PATH` wrapper and the binary it execs alike — reports `opencode v2.3.2` on stdout, exit 0, empty stderr, and no 2.2.5 installation remains on the host. The output is a product name, a `v` prefix, and a newline-terminated bare semantic version, and the grammar is identical across the two lines. Its session store is the SQLite file in the harness's own data directory (`~/.local/share/opencode/opencode.db` on the observation host), not the harness state directory the delivered default names. Two session generations coexist: a legacy `session` table with `message`/`part` children, and a current `session_v2` table with `session_message`/`session_part` children. Every session created under v2.2.5 or v2.3.2 lands in the current generation (352 in the last day at the delivery observation; the legacy table's newest row predates it). A session row records the harness version that created it (`session.version`, a bare semver — `2.2.5`, `2.3.2`, `1.19.0`, and `1.19.3` coexist in one store), the agent, the model as a structured provider/model object, cost, the five token classes, and start/end timestamps. An assistant message records its agent, model, cost, tokens, and timestamps inside a JSON payload that also carries conversation content; agent and model switches are separate metadata events. The store has no work-item or ticket column anywhere, no separate harness-version column, and no populated tool-call table for the current generation.
- **The spawn environment is deny-by-default.** The child environment is built from the declared allowlist alone. A declared variable entry is required unless it carries the variable-only optional marker; a credential entry resolves through the credential port at use time. An optional validated data-record map from profile resolution may supply values for declared variable names: a record value takes precedence over the injected parent environment, and an undeclared record name changes nothing.
- **Per-seat model derivation exists as data, with no observed consumer.** Profile resolution derives a per-seat model environment record (`OC_<PREFIX>_AGENT_<SEAT>_MODEL`, or the seat's explicit `envName`), serialized and validated under the data-v1 record contract. The record map is derived and validated; nothing in the delivered dispatch path asserts that it reaches an opencode spawn, and no test proves the spawned session runs the resolved per-seat models. The installed harness exposes no such variable family at all: its environment surface accepts only its own `OPENCODE_*` variables, and per-agent models are selected through its configuration document (where a value may interpolate an environment variable) or per invocation. The derived name is therefore a convention with no consumer on this harness.
- **Version identity is observed but never evaluated.** The configured-kind registry resolves an instance from an injected version probe; a failed or empty probe yields `null` plus the warning. No component compares the observed version to a supported window, no component refuses on it, and the closed harness failure vocabulary carries nine identities — none for a version or a mode refusal. No production path invokes the registry resolution today, so the probe seam has no production owner and is exercised by tests only.
- **Telemetry v2 is delivered without seat attribution or durations.** `delivery.harness.telemetry.v1` rows carry work item, run, session, harness kind and version, agent, model, tree root, parent chain, the five token classes, calls, bounded tool counts, cost (null when missing, never zero), an injected capture timestamp, and closed-vocabulary warnings. Rows are captured at closeout and, per step, during the opencode stream into additive state records; bounded read-only queries only. A row has no seat identity, no resolved-versus-observed model comparison, and no duration. More seriously, the delivered extractor and the per-session totals read query a store shape that no observed store has: a work-item column and a harness-version column on the session table, token/agent/model columns on the message table, and a tool column on the part table. None of those columns exists, and current sessions live in a different table generation, so a capture against a real store fails as extraction failure and lands zero rows while the fixture-built tests stay green.
- **Integration mode is implicit.** The delivered adapter starts one harness process per spawn and reads the harness session store read-only for telemetry. That behavior is a mode in fact, but no mode is declared, configured, refused, or recorded as a decision, and `doc/decisions/` contains no integration-mode record.
- **Conformance is a six-scenario classification floor.** The registry registers exactly the two shipped harness kinds and fails a harness that misses a floor scenario. There is no version-window scenario, no mode scenario, and no profile-propagation scenario.
- **Planning truth.** Backlog M3-S1 and milestone pack EC-1 define goal, tasks, and AC; `m3/contracts.md` declares the extended harness port and three typed refusals; `m3/test-scenarios.md` pins TC-M3-HARNESS-001 and TC-M3-HARNESS-002. Open question Q-06 in GH-342 (opencode version window) is unanswered, so its stated default applies.

### 2.2 Pain Points / Gaps

- **G1 — No supported-window evaluation and no typed refusal.** `m3/contracts.md` declares `harness.version.unsupported`, but the closed failure vocabulary has no such identity and no code path compares an observed version to a window. An out-of-window or unknown harness today proceeds as if compatible.
- **G2 — Per-spawn profile propagation is unproven and mis-targeted.** The per-seat record derivation exists, but the dispatch path does not state how the resolved binding reaches the spawn, that a record value beats the ambient parent environment, what happens to undeclared record names, or what is refused when a required seat model cannot be expressed. The installed harness exposes no per-seat model variable family, so the delivered convention has no consumer on this harness.
- **G3 — Integration mode is undecided and unrecorded.** A per-invocation private server, the managed background service, and a client to a running server are all exposed by the installed opencode v2.x line (`v2.3.2` at delivery); no spike, no decision record, no configuration expression, and no refusal for an unavailable mode exist.
- **G4 — Telemetry carries no seat, no resolved-model comparison, and no durations.** The ticket AC requires per-seat models and durations beside schema version, tokens, and cost; the delivered row shape expresses none of the first two and only the second conditionally.
- **G5 — Conformance cannot see the new properties.** The registry's scenarios cover classification outcomes only, so a regression in version gating, mode refusal, or profile propagation would pass the suite.
- **G6 — An adapter-contract change without its governing record.** The repository rule (TDR-0016, TDR-0021 precedent) is that a harness adapter-contract change is governed by a recorded decision; neither the mode decision nor the contract refinements have one.
- **G7 — The telemetry path reads a store shape that does not exist.** The delivered extractor and per-session totals read assume work-item, harness-version, per-message token/agent/model, and tool columns; the observed store has none of them and keeps current sessions in a different table generation. A capture therefore cannot land a row, and the failure is indistinguishable from a genuinely empty delivery unless the store contract and the absence taxonomy are stated.

## 3. PROBLEM STATEMENT

Because the harness port observes a version without evaluating it, propagates the resolved profile through a surface the installed harness does not consume, and captures telemetry through a store shape no observed store has, a dispatch cannot state that it ran the resolved per-seat models on a compatible harness — so an incompatible or unknown harness proceeds unannounced, a profile can be silently ignored, and the statistics the learning plane consumes cannot attribute cost and time to the seat that produced them. The current fixtures hide this because they encode the inferred shape rather than the observed one.

## 4. GOALS

- **G-1**: A supported-version window is evaluated for every dispatch before any session exists, and versions outside it refuse with the declared typed identity.
- **G-2**: An undeterminable version stays an explicit unknown and refuses distinctly — never a fabricated version, never a silently permissive pass.
- **G-3**: Exactly one integration mode is the delivered default for `delivery-os`/`jaiship` dispatch, expressed through configuration, decided by an in-change spike, recorded in a decision record, and refused with a typed identity when an unavailable mode is requested.
- **G-4**: The resolved profile's seat binding for the agent a spawn names reaches that spawn through a surface the harness actually honours — for opencode, the observed per-invocation agent/model selection — as exactly one seat per spawn (N seats are N spawns); it wins over the ambient parent environment for declared names, changes nothing for undeclared names, and refuses with a typed identity when a required seat model cannot be expressed on that surface or the named agent has no assigned seat.
- **G-5**: Resume and attach continue an existing session identity under the same propagation contract, without forking the tree root.
- **G-6**: Telemetry rows land in the state layer, sourced from the store's own session and message facts and attributed to the delivery by the union of the session identities the work item's recorded dispatch attempts hold (DM-8), with the recorded binding supplying the seat, the schema identity, the version the session record itself states, the resolved per-seat model, the five token classes, cost, and store-sourced durations — additively within the existing schema identity. A capture that lands zero rows for a session the dispatch ran and the store can read is a failure, not a pass.
- **G-7**: Conformance against the harness port gains the version-window, mode-refusal, and profile-propagation properties without altering the delivered six-scenario classification floor.
- **G-8**: The adapter-contract refinements and the integration-mode selection are recorded as decision records and reconciled into the harness feature spec.
- **G-9**: Telemetry absence, degraded capture, and extraction failure stay three distinct classifications inside the delivered capture and read envelopes, with no new command surface and no change to a delivery's exit code.

### 5.1 Capability Details

- **F-1 Supported-version evaluation and typed refusal.** A supported window is declared as data: the current minor line at delivery time plus one previous minor — at delivery, the `2.3.x` line plus `2.2.x`, derived from the installed `v2.3.2` (the same rule at intake named `2.2.x` plus `2.1.x`, derived from the then-installed `v2.2.5`). The rule is the contract and the literal is its application: the value is re-evaluated whenever the harness minor advances, so `2.1.x` is now outside the window and `2.3.x` is inside it. The window is evaluated once per dispatch at harness resolution, before any session-bearing child process exists, and the evaluation result is carried on the instance so every consumer reads one verdict. An observed version inside the window proceeds; an observed version outside it refuses with `harness.version.unsupported`, naming the observed version and the supported window; a version that cannot be determined refuses with `harness.version.unknown` (DEC-3), never with a fabricated version and never as a permissive pass. There is exactly one production probe point: the dispatch path's harness resolution. Today no production code invokes that resolution, so this change makes the dispatch path its owner and no other production path probes the harness. The accepted probe output is the harness's version line, normalized to a bare semantic version — the observed `opencode v2.3.2` normalizes to `2.3.2`, and the same grammar normalizes an in-window `opencode v2.2.5` to `2.2.5` — and the raw line is retained only as diagnostic, never as the stamped version. Empty output, a non-zero exit, a timeout, multiple lines, or any line outside the accepted grammar is an indeterminate version: never a substring match, never a partial version, and never a permissive pass. The probe is one bounded, shell-free invocation per dispatch; it completes within its bound and is reaped, and a probe that cannot answer within the bound is an indeterminate version, never a retry loop. No configurable window ships in this change and no configuration key widens or narrows it; should a configurable window be introduced later, an absent, malformed, or unsupported configured value degrades to this pinned default — never to an unbounded or silently wider window.
- **F-2 Explicit integration mode with a recorded decision.** The spike chooses among the mode surfaces the installed harness actually exposes: a per-invocation private server (the `--standalone` flag — the observed default on the observation host, where the harness on `PATH` is a wrapper that prepends it), the managed background service (`service start|restart|status|stop`), and a client to a running server (`--server`, `api`; the harness's `serve` starts that server). The spike records its outcome as a decision record, including the read-only direct-store access the telemetry path needs. Exactly one mode is the delivered default for `delivery-os`/`jaiship` dispatch; the others are declared and refuse with `harness.mode.unavailable`, naming the requested and the available mode. The mode is expressed as a declared value on the harness configuration branch (absent → the delivered default with a `defaults` origin) and is never inferred from ambient state. A dispatch never falls back from one mode to another: a fallback would make the decision unobservable and double the tested surface (DEC-2).
- **F-3 Per-spawn profile model propagation.** For every spawn for which the caller supplies an agent identity, the resolved profile's seat binding is carried into the spawn as data and expressed on a surface the harness honours; one spawn binds exactly one seat. **Scope boundary (DEC-15).** The contract binds at the harness port and for a caller-supplied agent identity only. No shipped invocation supplies an agent identity on that port today: the shipped generic `dispatch` path supplies none, so this change states and proves the contract at the port boundary for a spawn whose caller names an agent, and makes no claim that the shipped dispatch runs a resolved profile — a spawn with no agent supplied binds nothing and is disclosed `unresolved-seat` (see Resolution input), and adding an agent-naming surface to `dispatch` is out of scope for this change. The contract is harness-neutral and surface-mapped: the binding record is the contract (DM-4), and each adapter maps it onto the surface its harness honours — for opencode the per-invocation agent/model selection (one `--agent` and one `--model` per invocation), for a harness that consumes declared variables the declared variable name (`envName`, or the derived name). The per-spawn binding is supplied as data on the spawn call, never through process-global state, and the environment build receives the per-spawn record map alongside the descriptor. A declared record value wins over the injected parent environment for a declared name; an undeclared record name changes nothing and never widens the deny-by-default allowlist.
  - **Cardinality.** One spawn ⇔ one seat. The binding is the resolver's output and is a single-seat record, not a seat map, so no caller can make one invocation carry two seats even by mistake: the caller supplies one agent identity and the resolver returns the one seat it resolves for that identity. A profile's N seats are exercised by N spawns — each its own session, its own held session identity, and its own row set. A resume continues the seat its spawn declared; it never adds one.
  - **Resolution input and outcomes.** The seat is resolved from the agent identity the spawn names — the value the harness receives as `--agent` and records as the session agent — never from ambient state. **Carrier.** The agent identity reaches the port as contract data, not as an ad-hoc convention: the spawn input and the resume input each gain an additive optional agent-identity member — its own member, distinct from the additive optional binding member — and the composition passes the supplied agent identity together with the descriptor to the pure resolution function, which returns the binding, an `unassigned` refusal, or — for a present value that is not a name at all — an invalid-identity refusal (DEC-17). The member's absence is the `no-agent` state (never an empty string, never an inferred value); the identity is never taken from an environment variable, a process-global value, or ambient state, and it is expressed on the invocation as `--agent` only as the resolved binding's carrier. Both members are added in the same contract phase, so the resolution rule has a declared production call site instead of being provable only from a fixture the test itself built. The shipped generic `dispatch` sets neither member (DEC-15). Resolution is a pure lookup over the resolved profile: `agentOverrides[agent]`, else the seat whose name equals the agent, else the profile's single declared seat; the seat-named step and the single-seat step both presuppose a **non-empty** agent identity, since neither an override key nor a seat name can be empty. For a spawn whose agent-identity member is present there are exactly three outcomes: a **binding** (the seat, the agent identity it was resolved for, and that seat's resolved model — the pacing-applied model where pacing applied, else the seat's declared model), an **`unassigned` refusal** — a spawn naming an agent that a multi-seat profile assigns no seat refuses before any session exists with the delivered `provider.profile.invalid` identity (no new identity, no attempt record, no telemetry row), naming the agent, the profile, and the declared seats in the bounded error summary, with the remediation "declare `agentOverrides` for this agent, or run a single-seat profile" (`detail.harness` stays reserved for the four new pre-session harness identities, TDR-0037), or an **invalid-identity refusal** — a present value that is empty or whitespace-only is not a name: it is **not** the `no-agent` state (that state is the member's absence alone) and is never silently read as absence, and because it is invalid input rather than an absent one it refuses before any session exists with the delivered `config.value.invalid` identity, naming the agent-identity field, with no session, no lease claim, no attempt record, and no telemetry row, and never as `--agent ""` (DEC-17). **Unresolvable profile context.** Stated separately because it is a precondition, not a resolution: a spawn, deliver, or resume that supplies an agent identity while the composition resolves no profile context to resolve it against refuses before any session exists with the delivered `config.value.invalid` identity, naming the agent-identity field and the reason — no profile resolved for the supplied agent — in the bounded error summary, with no session, no lease claim, no attempt record, no telemetry row, and no invocation. It is a pre-resolution input failure, never a fourth resolution outcome: the resolution function is not called when there is nothing to resolve against, so the closed outcome set stays at the three above and no delivered vocabulary changes — counted as dispositions of a present agent identity this path has four, and any statement of the count says which set it counts (DEC-18). The invalid-identity check precedes it, so a present value that is not a name reports that refusal even where no context resolves; a role-less call never reaches either check, so it needs no profile context and stays an unchanged passthrough (DEC-15). A spawn whose agent-identity member is absent is the unasked state, not a resolution: it binds nothing (`no-agent`), no `--agent`/`--model` is sent, the harness default runs, and the run is recorded and disclosed as `unresolved-seat` with a null seat — never an inferred seat, and never a first-declared fallback presented as the run's seat.
  - **Carrier map (opencode).** The opencode harness exposes no per-seat model variable family, so the per-invocation selection is what carries the binding there. Agent identity → `--agent <agent>`, exactly once: the harness agent name, and never the seat name when the two differ. Resolved model → `--model <provider>/<model>[#<variant>]`, exactly once, with `#<variant>` appended only when the model declares one. Seat identity → no invocation carrier: it is recorded on the run (DM-4) and stamped on the row (DM-5); sending a seat name as `--agent` would send a value the harness may not know.
  - **Refusal.** A resolved model that cannot be expressed as `provider/model[#variant]` — an empty provider or model segment, a missing separator, whitespace or control characters that would corrupt the argument, or a value beyond the adapter's declared bound — refuses with `harness.profile.model-unrepresentable` naming the seat, before any session exists; never a silenced seat, never a guessed value. An agent or model the harness does not recognise is not a pre-session refusal (DEC-14): it is the harness's own classified spawn failure, and any disagreement between the recorded binding and the harness report is disclosed as a divergence rather than reconciled. The propagation contract is identical for spawn, deliver, and resume so a resumed session keeps the profile its spawn declared.
- **F-4 Resume and attach under the same profile contract.** A resume continues the caller's session identity and preserves the tree root; an attach resolves an existing session from the read-only, bounded session listing before resuming, and spawns nothing. A resume that identifies a different or absent session keeps the delivered `harness.session.unknown` semantics and kills its stream idempotently. Where a resumed session's original descriptor is available, its propagation contract is reused rather than re-derived.
- **F-5 Per-seat telemetry rows from the observed store contract, with version and durations.** Every landed row is bound to the delivery by the union of the session identities the work item's recorded dispatch attempts hold — one per spawn/resume, the identities the adapter acquired when it spawned or resumed — together with each attempt's recorded binding for the seat claim, and never by a store column that names a work item; the store supplies the session tree below each held identity through its parent links. **Capture scope for a work item.** The attribution capture runs at closeout, whose run id is the closeout run and not a dispatch attempt, so the scope is the union of the held session identities and the recorded bindings across every dispatch attempt recorded for the work item, resolved at capture time from the state layer's attempt records (DM-8). An attempt that recorded no session identity contributes nothing to the union — no identity is inferred for it from the store, a title, or a directory — and its loss is disclosed as a counted unattributed attempt, never hidden. **Bounded attempt read.** The attempts are read through the delivered bounded attempt read (the newest `DISPATCH_MAX_ATTEMPT_RECORDS` records), so a truncated attempt ledger is disclosed as a counted truncation and is never silently narrowed: when truncation occurs, the capture claims only the seats and session identities the attempts it read hold, reports the counted omission, and never presents the narrowed union as the work item's complete attempt history. An empty union yields the delivered `skipped-gap` outcome with `session-attribution-unavailable`, no rows, and no fabricated session list, exactly as the delivered compaction checkpoint does; when several attempts exist, that checkpoint reports the union's sorted session-identity set (with the delivered counted truncation at the cap) and never one attempt's set presented as the work item's. A recorded binding attaches only to the identities of the attempt that recorded it. Rows stamp the schema identity; the harness version the session record itself states, normalized, with a null and a warning when the record states none; the seat and the resolved model from the recording attempt's binding (DM-4, DM-8); the harness-reported agent and observed model from the session row and per-message metadata, with the session row as the baseline and the switch events as the transitions, and an axis the per-message metadata and the session row both leave unstated carried as a declared absence on that axis — the row lands with the declared absence marker (`absentObservedAxes`, a closed two-axis vocabulary: `agent`, `model`) naming exactly that axis, the delivered non-null field holding the delivered empty-string placeholder rather than a widened nullable member, and the delivered `optional-field-absent` warning naming the same axis; never fabricated and never classified `invalid-session-identity` (F-6), and a group whose observed agent is unstated never asserts the binding's seat — it carries a null seat with the `unresolved-seat` warning; the five token classes and calls; the store-reported cost; and durations taken from the store's own start/end timestamp pairs. Divergence is disclosed on both axes with both values kept — never reconciled by overwriting: model divergence (resolved ≠ observed) and agent divergence (the binding's agent ≠ the observed agent, the signal that the harness did not run the named agent). The binding's seat attaches only to the group whose observed agent equals the binding's agent; any other group of that session carries a null seat with the `unresolved-seat` warning, and a run that bound no seat carries a null seat with the same warning — never a guessed or re-derived seat. A divergence between the dispatch-probed installed version and the session's stored version is disclosed the same way; neither is overwritten. A cost the store reports as zero is recorded as the reported zero (free models are observed to report zero cost with non-zero tokens); a store that exposes no cost source yields null with the delivered cost warning — a missing cost is never replaced by zero. A duration the store's timestamp pair cannot express is explicitly absent with a warning and is never derived from the capture timestamp or estimated. Tool-call counts are carried only where the store exposes a populated tool source; where it does not, they are absent with a warning and are never recovered by reading conversation content. A capture that lands zero rows for a session the dispatch ran and the store can read is a capture failure, never a clean pass and never a silent absence. Ingestion remains bounded and read-only, riding the delivered extraction and per-step ingest seams.
- **F-6 Classified telemetry absence and degradation inside delivered envelopes.** Telemetry absence is a classification, not an error and not a zero: a session the dispatch ran for which the store yields no rows is disclosed as absence with its reason, inside the delivered capture and read envelopes. A readable store that yields zero rows for such a session is a capture failure, not absence. An unreadable or unopenable store keeps the delivered `harness.telemetry.extraction-failed` identity and is never re-projected as absence. Optional-field drift continues to degrade with a warning and never hard-fails. **Supersession of `invalid-session-identity`.** A drift on the observed agent or model axis is exactly this case: a group the store holds whose mandatory usage fact is present and whose agent or model it does not state must **land** with the declared absence marker naming that axis, the delivered empty-string placeholder in the non-null field it cannot populate (which is not widened to nullable), and the delivered `optional-field-absent` warning, and the delivered `invalid-session-identity` classification is not emitted for it (AC-F5-7). `invalid-session-identity` keeps only its literal meaning — a group whose session identity is genuinely unusable and cannot be attributed — and never stands for a merely missing agent or model (OQ-3). On the read side, the delivered `spend.telemetry-absent` meaning is the work-item-scoped absence identity and is untouched. The change adds no command, verb, or exit projection for telemetry (NG-9), and closeout capture stays non-gating: a failed or absent capture writes no zero-valued record and changes no other closeout effect.
- **F-7 Harness-port conformance extension.** The registry's six-scenario classification floor for exactly the two registered kinds stays as delivered and keeps passing. New scenarios are registered per harness: version refusal inside and outside the window, unknown version, mode unavailable, and profile propagation (the resolved binding is carried on the honoured surface and the session's reported model is compared where the harness reports one). A registered harness missing a newly declared scenario fails the suite; a new refusal identity with no scenario fails the suite. The extension is data on the registry, not a forked conformance path.

## 6. USER & SYSTEM FLOWS

```
Flow 1: Dispatch resolution, version probe, and mode
  dispatch resolves harness settings (kind, mode, stores, allowlist)
  → the single production probe point runs one bounded, shell-free version
    probe and normalizes its output (opencode v2.3.2 → 2.3.2)
  → window evaluation:
      inside window   → instance carries the verdict, continue
      outside window  → refuse harness.version.unsupported (exit 1), no session
      indeterminate   → refuse harness.version.unknown (exit 1), no session
    (the probe is the only child a refusal allows; it completes and is reaped)
  → mode resolution: declared or delivered default; unavailable → harness.mode.unavailable

Flow 2: Spawn with the resolved profile
  the caller supplies an agent identity (the value sent as --agent)
  → profile resolution yields the seat assigned to that agent → that seat's
    resolved model; the binding carries exactly one seat (its agent identity,
    its seat, its resolved model)
  → binding carried on the spawn call as data
  → expressed on the surface the harness honours: one --agent, one --model;
    environment built: record value wins, undeclared names change nothing
  → agent named, no seat assigned  → provider.profile.invalid (no spawn)
  → agent identity present but empty or whitespace-only
                                   → config.value.invalid, naming the field
                                     (no spawn, no attempt, no row) — DEC-17
  → agent identity supplied, but the composition resolves no profile context
                                   → config.value.invalid, naming the field and
                                     the reason (no spawn, no attempt, no row)
                                     — DEC-18
  → seat model inexpressible       → harness.profile.model-unrepresentable
                                     (no spawn)
  → no agent supplied              → nothing bound; run recorded and
                                     disclosed as unresolved-seat, harness
                                     default runs
  → session spawns, handle acquired on the first identified line, stream drains
  → a further seat is a further spawn: its own session, its own rows

Flow 3: Resume / attach
  existing handle or bounded read-only session listing → resume the same identity
  → same descriptor and propagation contract, tree root preserved
  → unknown/different session → harness.session.unknown, idempotent kill

Flow 4: Telemetry landing
  the work item's recorded dispatch attempts hold every session identity they
  spawned or resumed; the capture scope is the union across all of them (DM-8)
  → bounded read-only store read of each held session and its tree (current or
    legacy generation), projecting only non-content fields
  → rows with schema identity, the session's own version, the seat and resolved
    model from the recording attempt's binding, the observed agent and model,
    tokens, cost, store-timestamp durations; a group whose observed agent
    differs from the binding's agent carries no seat and warns
  → divergence or missing field → closed-vocabulary warning, value kept or absent
  → seat the run never declared (role-less run) → null seat, unresolved-seat
  → an attempt that recorded no identity → counted unattributed, nothing inferred
  → fenced verified append to the state ledger (non-gating)
  → zero rows for a session the dispatch ran → capture failure, never a pass
  → no rows for a session the store does not hold → classified absence
  → empty union → skipped-gap / session-attribution-unavailable, no rows
  → unreadable store → extraction-failed; the spend read side says spend.telemetry-absent

Flow 5: Conformance
  registry → six delivered classification scenarios + new version/mode/profile scenarios
  → simulated harness I/O only → missing scenario or undeclared identity fails the suite
```

## 7. SCOPE & BOUNDARIES

### 7.1 In Scope

- The supported-version window as data, evaluated once per dispatch at a single production probe point, with the probe output grammar and normalization pinned, and `harness.version.unsupported` and `harness.version.unknown` refusals before any session exists.
- The integration-mode spike over the mode surfaces the installed harness exposes (per-invocation private server, managed background service, client to a running server, including read-only direct-store access for token/usage analytics) plus its recorded decision.
- Exactly one delivered default mode, its configuration expression, and `harness.mode.unavailable` for any other requested mode.
- Per-spawn propagation of the resolved seat binding on a surface the harness honours — one seat per spawn, resolved from the agent the caller supplies on the spawn input's agent-identity member (a contract member, not an environment or argv convention), with a further seat being a further spawn — precedence over the ambient parent environment, undeclared-name neutrality, and the two pre-session profile refusals: `harness.profile.model-unrepresentable` for a seat model that cannot be expressed on that surface, and the delivered `provider.profile.invalid` for a named agent the profile assigns no seat.
- Resume and attach under the same propagation contract, with the delivered `harness.session.unknown` semantics preserved.
- Per-seat telemetry attribution sourced from the observed store contract: the seat and resolved model from each recording attempt's binding beside the harness-reported agent and model, with divergence disclosed on both axes, store-sourced durations with explicit absence, and the session's own harness version on every row — additive within `delivery.harness.telemetry.v1`, attributed by the union of the session identities the work item's recorded dispatch attempts hold (F-5, DM-8).
- Reconciliation of the configured opencode store location with the harness's own declared data directory and its documented store override, with a classified outcome when the resolved path is absent.
- Classified telemetry absence, degraded capture, and extraction failure disclosed inside the delivered capture and read envelopes — with no new command surface — and the delivered non-gating closeout semantics preserved.
- Error-table rows for every new identity with a stable code, exit projection, and remediation hint; `HARNESS_FAILURE_CODES` extended additively.
- Conformance registry extension covering the version-window, mode, and profile scenarios, with the delivered six-scenario floor unchanged.
- Decision records for the adapters-contract refinements and the integration mode, linked from this change and the harness feature spec.
- Tests proving TC-M3-HARNESS-001, TC-M3-HARNESS-002, and every acceptance criterion that is provable offline, against simulated harness I/O and fixture stores derived from the observed store contract; the human-gated live observation is recorded separately and is never a CI oracle.

### 7.2 Out of Scope

- [OUT] Claude Code adapter extension or parity: it stays a registered generated-artifact surface, not a delivery harness (OQ-M3-01).
- [OUT] Concurrent multi-mode operation, runtime mode fallback, or mode auto-detection from ambient state.
- [OUT] Harness-side configuration mutation to force model selection (writes to the harness's own configuration or store).
- [OUT] A telemetry schema bump, structural re-shape, or field removal (OQ-M3-07).
- [OUT] Backfill of seat or duration facts onto pre-change sessions.
- [OUT] Provider profile resolution, model nomination, pacing, and cost normalization — consumed as input only.
- [OUT] Tracker adapters (M3-S2/S3/S4), the parity and trap-catalog suite (M3-S5), and multi-tracker routing (M3-S6).
- [OUT] Background-service supervision, daemonization, or health management of the harness process.
- [OUT] A new CLI command surface; existing dispatch and configuration paths are extended.
- [OUT] Introducing or requiring a per-seat model environment-variable family in the harness; propagation is expressed only on surfaces the harness honours (NG-10).
- [OUT] Attributing store sessions to a delivery by a store column, a title heuristic, or a store-wide scan (NG-11).
- [OUT] Recovering any telemetry field by reading conversation content, message bodies, part payloads, or tool output (NG-11, NFR-5).
- [OUT] Currency conversion, re-pricing, or cross-model cost normalization.
- [OUT] An agent-naming surface on the generic `dispatch` path (a value flag or a declared harness-agent default): the propagation contract binds a caller-supplied agent at the harness port only, and the shipped role-less dispatch stays disclosed as `unresolved-seat` (DEC-15, OQ-4).

### 7.3 Deferred / Maybe-Later

- A configurable supported-version window once a second harness or a second delivery line exists.
- Any mode not selected as the default, if a later story needs it (would need its own decision and test surface).
- Background-service lifecycle management for a long-lived harness instance.
- Telemetry v3 if a future harness cannot express seat or duration facts as fields.
- Claude Code per-seat propagation if it ever becomes a delivery harness.

## 9. NON-FUNCTIONAL REQUIREMENTS (NFRs)

| ID | Requirement | Threshold |
|----|-------------|-----------|
| NFR-1 | Refusal before side effects | A version, mode, or profile refusal occurs before any session-bearing child process exists: zero sessions started, zero orphan processes, zero telemetry rows written, zero store writes. The single bounded version probe is the declared exception; it completes and is reaped |
| NFR-2 | Version-probe bound | The probe resolves within 5 s in the reference environment, at most once per dispatch; a probe that cannot answer within the bound is an explicit indeterminate version, never a retried loop and never a fabricated version; the probe process is reaped before the verdict is published |
| NFR-3 | Bounded store reads | Read-only open, query-only pragma before the first read, bounded indexed queries only, no full-table message/part scans, and no content projection; caps unchanged (64 sessions, 16 agents, 16 models, 24 tools per agent where a populated tool source exists) with explicit truncation marks; per-message reads are scoped by session and message type |
| NFR-4 | Bounded output | Machine payload ≤ 65 536 UTF-8 bytes; human disclosure ≤ 4 096 bytes and ≤ 24 lines; truncation deterministic, tail-ordered, and marked; refusal identities and remediation hints are never truncated |
| NFR-5 | Telemetry privacy | Rows, warnings, and refusals carry identity references, counts, costs, and durations only — never prompt text, message bodies, transcripts, diffs, tool output, credential material, or harness configuration values. Store reads project only non-content fields; conversation content is never selected, parsed, or emitted |
| NFR-6 | Non-fabrication | No figure is invented: a cost source the store does not expose is null, a missing token class is null with a warning, a duration the store's timestamps cannot express is explicitly absent, a missing or unparseable version is the explicit unknown; a value the store reports — including a reported zero cost — is recorded as reported. Zero is never a substitute for absence, and absence is never a substitute for a reported zero |
| NFR-7 | Determinism | Byte-identical output for identical injected harness facts, probe result, resolved profile, and clock; zero model calls and zero network on any evaluation, refusal, or render path |
| NFR-8 | Spawn non-interference | Version evaluation, mode resolution, and profile propagation add no blocking work to the delivered stream drain, handle acquisition, or output-bound behavior |

## 10. TELEMETRY & OBSERVABILITY REQUIREMENTS

- Every version, mode, and profile refusal is a classified outcome on the result envelope with its identity, the observed or requested value, the supported or available alternative, and a remediation hint — never a bare exit status.
- Every dispatch discloses the evaluated version verdict (with the normalized observed version and the raw probe line as diagnostic) and the selected mode, so a later reader can tell which harness line and mode produced the delivery. On the success path the disclosure rides the attempt record and the dispatch envelope. On the pre-session refusal path no attempt record exists, so the disclosure rides the failure envelope, and the channel is scoped precisely: the declared `detail.harness` member is the channel for the four new pre-session harness refusals — `harness.version.unsupported`, `harness.version.unknown`, `harness.mode.unavailable`, and `harness.profile.model-unrepresentable` (TDR-0037); the unassigned-agent refusal, which reuses the delivered `provider.profile.invalid` identity, discloses its agent, profile, and seat facts through the bounded `error.summary` plus that identity's remediation hint and adds no envelope member (TDR-0036 A-2); the invalid agent-identity refusal (DEC-17) likewise reuses the delivered `config.value.invalid` identity, disclosing the agent-identity field name through that identity's bounded `error.summary` and remediation hint and adding no envelope member; the unresolvable-profile-context refusal (DEC-18) does the same on that same delivered identity — the agent-identity field and the reason ride the bounded `error.summary` and remediation hint, with no envelope member and no interpolated caller value in the summary; and the scripted projection stays exactly `{error, runId}` and carries no `detail` at all, so in scripted mode the verdict and mode are not disclosed there, while the interactive envelope carries the member. The member is never a fabricated record.
- The version stamped on a captured row is the version the session record itself states; the dispatch-probed installed version is disclosed separately, and a divergence between them is warned — neither is overwritten.
- Telemetry capture stays non-gating: a capture degradation is classified with counts and closed-vocabulary warnings and never changes a delivery's outcome, phase, summary, or verdict.
- Absence, degraded capture, and extraction failure are three distinct classifications inside the delivered capture and read envelopes. None is projected as a zero-valued row; a zero-row capture for a session the dispatch ran is a failure; the work-item read side keeps the delivered `spend.telemetry-absent` absence identity. No command, verb, or exit projection is added for telemetry.
- Per-seat attribution discloses unresolved seats, model divergence, agent divergence, and version divergence with counts and reasons — never silently dropped and never reconciled by overwrite.
- Every invocation lands its delivered command-audit record; an audit-write failure is a diagnostic and never changes the outcome.

## 12. ASSUMPTIONS

- The installed harness exposes its version through one bounded, shell-free invocation as `opencode v2.3.2` at delivery (`opencode v2.2.5` at intake); the accepted grammar is pinned and identical for both, so probe failure modes stay distinguishable from a version outside the window.
- The resolved profile's seat models are available at spawn time as validated data, so the binding for the agent a run names can be resolved without a new data source; profile resolution itself remains delivered behavior.
- The profile plane already declares the agent→seat relation (`agentOverrides` and the seat-named lookup), so seat resolution for a binding needs no new mapping authored anywhere.
- The store's session agent equals the `--agent` value the invocation carried; a divergence surfaces as an agent-divergence warning, and the recording attempt's binding stays authoritative for the seat.
- No shipped invocation supplies an agent identity on the harness port for the life of this change: the generic `dispatch` path supplies none, so the propagation claim stays a port-level contract proven for a caller-supplied agent (DEC-15), and adding an agent-naming surface to `dispatch` is out of scope.
- Operator profiles declare their seat models in `provider/model[#variant]` form in practice; a value that does not is refused with `harness.profile.model-unrepresentable` rather than coerced.
- The observed store generation (`session_v2` with `session_message`) remains the generation the in-window harness writes, and its fields expose per-session version, agent, model, cost, tokens, and timestamps, plus per-message agent/model/cost/tokens/timestamps; where a store does not, the absence is explicit and classified.
- The observed per-invocation selection surfaces (`run --agent`, `run --model provider/model#variant`) remain available across the supported window; a harness that drops them is out of window or needs a new decision.
- The delivered telemetry row grouping (per session/agent/model) is the right coarse grain; seat identity is added as a dimension, not a re-shape.
- Exactly one mode can be the delivered default because a solo-operator delivery path needs one tested transport, not a matrix.
- Decision records follow `.ai/agent/decision-instructions.md`; the adapter-contract record stays `Proposed` until a human decides where rigor requires it.

The change adds no command surface and no new product-name coupling; the store location stays resolved from configuration and the harness's own declared data directory.

## 22. MAINTENANCE & OPERATIONS IMPACT

- The supported window is a maintained value of a fixed rule — the current minor line at delivery time plus one previous minor — with a declared revisit trigger: every harness minor release re-evaluates the value, and the value is the only place acceptance widens. This change has already applied the rule once (`2.2.x` + `2.1.x` at intake, `2.3.x` + `2.2.x` at delivery). A stale value shows up as an explicit refusal, not as a silent compatibility claim (RSK-2).
- The propagation contract is a surface mapping, not a variable family: if the harness changes how it accepts a model selection, the adapter mapping — not the profile resolution — is what changes (RSK-1, DEC-8).
- The seat rule is operational as well as contractual: a delivery that needs several seats is several spawns, one per named role, not one spawn carrying a profile. Operators declaring a multi-seat profile must assign each role its seat through `agentOverrides` (or name a seat exactly as the role), and an unassigned named agent refuses rather than borrowing a seat (DEC-13, OQ-5).
- The observed store contract is maintained like the window: the generation and field set are re-observed on each harness minor release, and a drift is a classified outcome rather than a silent zero-row capture (RSK-9, NFR-11).
- Any future telemetry addition follows the same rule as this change: fields only, identity unchanged, absence explicit.
- New refusal identities are cheap to add but expensive to fork; the rule is one identity per condition, with the delivered meanings untouched (RSK-5).
- Operators should expect an out-of-window harness to block delivery deliberately; the remediation hint names the supported lines so the fix is an upgrade, not a workaround.

**C.3 What the observation settles**

- OQ-2 is closed: there is no per-seat model variable family; the honoured surface is per-invocation selection, with configuration-document interpolation as an alternative carrier (DEC-8).
- The store contract in DM-10 is pinned, and every extraction fixture must derive from it (DEC-9). The `v2.2.5` → `v2.3.2` upgrade left that contract's shape unchanged: the same `session`/`session_v2` generations, byte-identical `message`/`session_message`/`part` shapes, the same JSON key vocabulary, and every column a row sources from present under the same name — only the version distribution, the row counts, and the null counts drift (484 → 503 null models across the passes), and those counts are observations, never fixture constants.
- The version stamp has a real source (`session_v2.version`) and a real normalization (`opencode v2.3.2` → `2.3.2`, and `opencode v2.2.5` → `2.2.5` under the same grammar) (DEC-11).
- The supported window's value at delivery is `2.3.x` plus `2.2.x` under DEC-1's own time-relative rule, so the installed harness is in-window and the `2.3.2` store rows are in-window rows.
- The per-session telemetry-request surface that AC-F6-1/AC-F6-2 previously assumed does not exist and is not added (DEC-10).
