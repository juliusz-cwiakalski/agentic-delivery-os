# CHANGE SPECIFICATION

> **PURPOSE**: Turn the daemon's delivered two-topic snapshot stream into a published, versioned event taxonomy — six topics, four of them carrying a seven-change-field envelope plus the taxonomy version stamp (eight `data` keys) — with a machine-readable reference surface whose version, kind sets, payload fields, ordering rule, and overflow policy are pinned per topic by contract tests, so a watch command, a script, and a board consume one declared contract instead of each reading state files.

## 1. SUMMARY

Publish **event taxonomy v1** on the resident daemon's subscribe surface and mount its reference command. The taxonomy declares six topics: the delivered `queue` and `lanes` snapshot topics (which declare no kind), plus four event topics — `queue.graph` (extends `queue`), `dispatch.attempt`, `phase.state`, and `blockers.state` — each with a declared kind set, per-kind payload field list, one ordering rule, and one overflow policy. Every event on an event topic carries `topic`, `kind`, `lane`, `ref`, `sequence`, `occurredAt`, a topic-specific `payload`, and the taxonomy version, inside the delivered open event `data` body; `lane` is always a non-empty string, and `ref` is nullable only on `blockers.state`, where the source record's own `ref` is nullable. The two snapshot topics keep their delivered `{topic, cursor, snapshot}` frames byte-for-byte. A consumer that overflows keeps the delivered outcome — exactly one `degraded` event carrying `subscriber-overflow`, only that subscription dropped, then a repoll — now additively stamped `overflow: "repoll"` so the same value a client reads from the reference surface is the value it reads on the wire.

`<binary> events list` and `<binary> events describe <topic>` mount as one unit: prompt-set entry, edge composition, help entries, an M2 reference page, a coverage-inventory row, and the page root the help gates resolve. The taxonomy declaration is the single authored source of the contract: the six topics, each topic's shape and kind set, each kind's payload field list, the lane and `ref` rules, the ordering value, the overflow value, and the version. The reference surface is generated from it, its integrity validator reads it, and a named test asserts that the rendered surface equals the declaration, so a drift in the surface cannot pass. The daemon's emission projection is **hand-authored**: it imports only the taxonomy version constant and assembles each kind's frame itself, so it is a second consumer of the declaration rather than an artifact generated from it. It is pinned to the declaration by two comparisons that run against the shipped code — a bidirectional literal-set pin of the emitted kind names, where the projection's kind literals must equal the declaration's emitted set so an added, renamed, or removed name fails in either direction, and an exact per-kind emitted-payload-key comparison against the contract's declared field lists for every kind that can emit (twelve of the thirteen declared kinds; `remove` has no v1 producer, so only its declared field list is compared), where an undeclared key and a missing required key each fail — and the drift suite consumes the live `events list --json` surface and the live projector rather than fixtures built from the declaration. A version, kind, or payload-field drift in either direction therefore fails a named test; ordering and overflow, which no event frame can express, are pinned at declaration and surface level only. No frame is generated from the declaration.

The change is additive on every delivered axis. It adds no wire type, no state record kind, no payload schema version, no migration, no package dependency, and no new capability in any engine; it widens one internal topic union, adds one command family, one contract module, one event projection, and exactly three error-table rows in a new `events` domain kind.

## 2. CONTEXT

### 2.1 Current State Snapshot

The resident daemon, its control protocol, and its snapshot publish path are delivered. The taxonomy does not exist:

- **Two topics, closed — and a topic outside the pair is accepted, not refused.** `CONTROL_TOPICS = ["queue", "lanes"]`; `status` is a member of `CONTROL_WIRE_TYPES`, not a topic (`packages/core/src/contracts/control.ts:25-40`). The daemon's subscribe handler is typed over the same literal pair (`packages/cli/src/daemon-compose.ts:1164-1171`), but no layer validates the requested topic value: the codec and the session accept any string, and the projection resolves every topic other than `queue` to the `lanes` snapshot (`packages/cli/src/daemon-compose.ts:384`). A `subscribe` for a topic outside the pair therefore succeeds today and is served the `lanes` snapshot labelled with the requested topic name.
- **Events carry a snapshot revision and nothing else.** One event body is `{ topic, cursor, snapshot? }` or `{ degraded, topic? }` (`control.ts:100-103`); the session's publish builds exactly `{ topic, cursor, snapshot }` (`packages/core/src/domain/control-session.ts:195-220`). There is no `kind`, `lane`, `ref`, `sequence`, `occurredAt`, or `payload` on the wire, and therefore no change semantics a client can branch on.
- **The cursor is a per-topic snapshot revision.** `lastPublished` is keyed by topic; the cursor increments when that topic's stable-serialized snapshot changes, and an unchanged snapshot publishes nothing (`packages/core/src/app/control-server.ts:317-337`). It says "which revision of this topic's snapshot", never "which change, in which lane order".
- **The publish source is snapshot-diff and covers exactly two topics.** `createWatchState` projects the bounded `queue` and `lanes` snapshots, primes a baseline, and yields only changed topics (`packages/cli/src/daemon-compose.ts:375-411`); the resident loop calls `publishState` once per loop iteration (`packages/core/src/app/daemon-runtime.ts:243`). The first observation of a topic is a baseline, not an event.
- **Every delivered fold reads the whole store; the publish tick reads it twice and a heartbeat iteration twice more.** The state port exposes one whole-store read — `readRecords(): StateResult<{ records, evidence }>` takes no prefix, page, or limit (`packages/core/src/contracts/state.ts:338-341`) — and each queue fold calls it once (`packages/core/src/app/queue.ts:409-410`). One publish tick (`publishState` → `stateChanges`) performs two such reads, one per snapshot topic (`readQueueEntries` and `readDaemonLanes`, `packages/cli/src/daemon-compose.ts:336-355,384`). On a heartbeat loop iteration the loop first calls `writeHeartbeat`, which folds the same two ledgers before the publish runs, so that iteration reads the store twice again (`packages/core/src/app/daemon-runtime.ts:172-175,208-213,243`). `readChangeTransitions` is not a single read either: it probes the store and then reads the change's phase artifact through the boundary, which is itself one whole-store read, so it costs two reads per change and offers no index over changes (`packages/core/src/state/registry.ts:292,303`; `packages/core/src/state/artifact-boundary.ts:111`). There is no per-ledger read and no change index; any bound on a publish tick's store reads is a property of that tick, not of the port.
- **Overflow is delivered and uniform.** Each subscription has a bounded buffer; overflowing deletes only that subscription and emits exactly one `degraded` event carrying `subscriber-overflow` for that topic (`control-session.ts:195-220`); the same capacity bound also caps the per-connection subscription count, refusing with `daemon.subscriber-degraded` (`control-session.ts:186-194`); the value is `daemon.subscription-buffer` with default `256` (`packages/core/src/contracts/daemon.ts:22`, `control-server.ts:284`). The CLI watch degrades to a repoll on that marker (`packages/core/src/app/watch.ts:153-158`) and its projection renders `degraded: "subscriber-overflow"` (`packages/core/src/domain/watch-stream.ts:71-79`).
- **The event `data` body is open on the wire.** The codec validates the protocol version, frame kind, wire type, principal, exactly-one-of `payload`/`data`/`error`, and the absence of `id` on events; it does not whitelist fields inside `data`, and it does not validate a topic value at all (`packages/core/src/domain/control-codec.ts:79-120`). Additive fields inside `data` are therefore wire-compatible with v0 and v1 peers.
- **The four source planes exist as durable ledgers, not as events.** `queue.entry` (`delivery.queue.entry.v1`: `ref`, `repository?`, `repositoryRoot?`, `priority`, `recordedAt`), `queue.dependency` (`delivery.queue.dependency.v1`: `ref`, `edges[]`, `recordedAt`), `queue.lease` (`delivery.queue.lease.v1` with the closed `operation` set `acquired|renewed|released|taken-over`), and `queue.park` are declared together with the five queue record kinds and their key prefixes (`packages/core/src/contracts/queue.ts:293-342`), and each has a fold read side (`readQueueEntries`, `readQueueDependencies`, `readQueueLeases`, `readQueueParks`). One attempt record per classified dispatch carries `attemptId`, `repository`, `ref`, `harness`, `evidenceClass`, `startedAt`, `finishedAt`, `handoverState`, `outcome`, `token`, `comparison`, `falseSuccess`, `corroboration`, `evidenceRefs` (`packages/core/src/contracts/dispatch.ts:189-211`), and `HARNESS_OUTCOMES` includes `refused` (`packages/core/src/contracts/harness.ts:159-167`). Phase landings are `phase.transition` records with `changeRef`, `phaseId`, `operation` (`complete|reopen`), `timestamp`, `outcome`, reopen-only `reason`, and completion-only commit intent (`packages/core/src/contracts/registry.ts:39-49`), folded per change by `foldPhaseState`. Blockers are `blocker.question` (`id`, `type`, `audience`, `lane`, `ref`, `question`, `options[]`, `askedAt`) and `blocker.answer` (`questionId`, `answeringAudience`, `choice?`, `text?`, `answeredAt`, `applied: false`, `laneResume`) records (`packages/core/src/contracts/blockers.ts:200-239`), and the daemon records `resumeIntent` on the matching delivering lane when it consumes an answer (`packages/core/src/app/daemon-runtime.ts:219-225`; `packages/cli/src/daemon-compose.ts:426-464`). Lanes are `daemon.lane` records with `ref`, `state`, `harnessKind?`, `sessionId?`, `spawnOrdinal`, `liveness?` (`packages/core/src/contracts/daemon.ts:163-177`). A blocker question's `lane` is a required non-empty string while its `ref` is `string | null` (`packages/core/src/contracts/blockers.ts:205-206`; `packages/core/src/state/blockers.ts:66,269`), and the shipped `blockers publish` path passes no `ref`, so every CLI-published question records `ref: null` (`packages/cli/src/commands/blockers.ts:139-141`). A queue lease record carries its own fields — `leaseId`, `scope`, `repository`, `holder`, `ref`, `runner`, `weightClass`, `operation`, `acquiredAt`, `heartbeatAt`, `ttlMs`, `recordedAt`, and optional takeover evidence — and no park cause (`packages/core/src/contracts/queue.ts:42-57`); a `queue release --park` writes a separate `queue.park` record.
- **Two delivered gaps between the source planes and the contract's kind sets.** No delivered path removes a queue entry — the queue verbs are `ready`, `list`, `plan`, `add`, `prioritize`, `dep`, `claim`, `release` (`packages/cli/src/commands/queue.ts:359-432`) — and no delivered path records a phase *begin*: `phase.transition` records landings only, and the fold records `started` at the first completion (`packages/core/src/state/registry.ts:377-397`). Both gaps are handled explicitly in this specification (§5.1 F-3, DM-8, DEC-J).
- **Nothing describes the subscribe contract.** There is no `events` command, no taxonomy declaration, no reference page for the subscribe surface, and no `events` member in `PROMPT_REQUIRED_COMMANDS`, which today holds eighteen commands ending in `daemon` and `projects` (`packages/cli/src/help/prompt-required-commands.ts:11-30`).
- **The planning pack contradicts itself on the kind sets.** `m2/contracts.md` §Event taxonomy v1 enumerates four `queue.graph` kinds and three `dispatch.attempt` kinds and assigns the stop, parked, resumed, and park-edge shapes to M2-S17 (`doc/planning/oss-tooling/milestones/m2/contracts.md:62-88,170-179`), while `m2/commands/events.md` prints `queue.graph` with 6 kinds and `dispatch.attempt` with 4 and gives `dispatch.attempt` the stop/parked/resumed kinds (`doc/planning/oss-tooling/milestones/m2/commands/events.md:26-30,69-76`). `TDR-0025` records the contract section as the authority and the page as pre-contract text (`doc/decisions/TDR-0025-public-event-taxonomy-v1-subscribe-surface.md`).
- **The test scenarios assert the observable.** SC-M2-S13-01 asserts a monotonic `sequence` on `queue.graph` events and a pinned `data.taxonomyVersion`; SC-M2-S13-02 asserts `data.overflow == "repoll"` for each of the four new topics (`doc/planning/oss-tooling/milestones/m2/test-scenarios.md:215-230`).

**Users and current impact.** A watch command, a script, or a board that wants delivery-state changes has exactly one option: poll `queue list`, `lanes`, `blockers list`, `phase list`, and the attempt ledger on its own cadence and diff the results itself. Each consumer therefore invents its own reading of the same state files, the daemon's own subscribe surface answers "a snapshot changed" rather than "an entry was added", and no client can state which contract version it speaks.

### 2.2 Pain Points / Gaps

- **No change semantics on the wire.** The subscribe surface answers delivery (a bounded, deduplicated snapshot) and not change (what happened, about what, in what order). A client cannot branch on an event kind because there is no kind.
- **Four delivery-state planes are unobservable.** Queue graph changes, dispatch attempts, phase transitions, and blocker state changes exist durably and have no published projection, so every consumer re-derives them.
- **The contract cannot be cited.** No client can name a taxonomy version, and no test can pin one, because nothing publishes the topic set, the kind sets, the payload fields, the ordering rule, or the overflow policy.
- **A wrong topic is accepted and mislabelled.** A `subscribe` for a topic outside the closed set is decoded successfully, accepted, and answered with the `lanes` snapshot whose frames carry the requested topic name, so the client reads another topic's data under its own label. The mistake is neither refused nor diagnosed, and the wrong-data path is the defect — not only the absence of an error identity.
- **The publish tick has no read budget.** The delivered publish path takes two whole-store reads and each fold takes its own, so every new topic projection adds reads unless the publish tick is restructured to share one view; the port offers no per-ledger read to bound them. A heartbeat loop iteration adds two more reads of its own, which no publish-path bound covers.
- **Two planning pages disagree, and neither is executable.** The kind counts and the stop/park/resume prose in the reference page contradict the contract section, and neither page can fail a test.
- **The overflow instruction is implicit.** The delivered degraded frame names `subscriber-overflow`; the remedy a client must take — repoll — is stated in prose in the system spec and asserted by the test scenario, never declared per topic on a surface a client reads.

## 3. PROBLEM STATEMENT

Because the daemon's subscribe surface carries a per-topic snapshot revision and no event kind, publishes only `queue` and `lanes`, and declares nothing about topics, payloads, ordering, or the overflow remedy, a watch command, a script, or a board cannot consume delivery-state changes from one contract: it must poll and diff five command surfaces on its own cadence, cannot state the contract version it speaks, cannot tell a slow-consumer drop from a quiet period without reading prose, and is served another topic's snapshot when it asks for a topic that does not exist — which blocks every M2 consumer that presumes one published subscribe contract.

**Who is affected.** The operator and the owner lose a single integration surface for scripts and dashboards; the M2 board, attempts read side, and engine-first operations stories have no declared contract to consume; agents that stream delivery state keep re-implementing snapshot diffing; and S17 has no declared landing place for the kinds it owns, so its delivery would silently edit a shipped kind set.

## 4. GOALS

- **G-1** Declare event taxonomy v1 as one authored source: six topics, each topic's shape, kind set, per-kind payload fields, lane selection, ordering rule, and overflow policy, plus the taxonomy version.
- **G-2** Publish the four event topics from durable records, so a subscriber to `queue.graph` observes entry and dependency changes it can act on (ticket AC1).
- **G-3** Put a change envelope on every event of an event topic — `topic`, `kind`, `lane`, `ref`, `sequence`, `occurredAt`, `payload` — and the taxonomy version, without changing the delivered snapshot topics' frames.
- **G-4** Guarantee per-`(topic, lane)` monotonic `sequence` and nothing else; state that a gap requires a repoll and that the delivered `cursor` is not an ordering signal.
- **G-5** Preserve the delivered overflow behaviour for every topic and carry `overflow: "repoll"` on the degraded frame and on the reference surface, so the declared remedy and the wire remedy are the same value.
- **G-6** Mount `events list` / `events describe <topic>` as one unit — prompt-required entry, edge composition, help family and verb entries, M2 reference page, coverage-inventory row, page root — so the family is reachable from root `--help` only when it is complete.
- **G-7** Pin the taxonomy version with per-topic contract tests: the reference surface is generated from the declaration, the hand-authored emission projection is pinned to it by bidirectional emitted-kind-set pinning and an exact per-kind emitted-payload-key comparison for every kind that can emit (twelve of the thirteen declared kinds; `remove` is `emitted: false` and only its declared field list is compared), and ordering and overflow — which no event frame can express — are pinned at declaration and surface level, so a version, kind, or payload-field drift in either direction fails a named test.
- **G-8** Keep the change additive: no new wire type, state record kind, payload schema version, migration, engine capability, or package dependency, and exactly three named error rows.

### 5.1 Capability Details

**F-1 — One authored taxonomy declaration.**
The declaration is runtime-neutral data: the taxonomy version `v1`, and one record per topic carrying `name`, `version`, `shape` (`snapshot` | `event`), `parent` (only `queue.graph` has one: `queue`), `frame` (the ordered field list of the frames that topic emits), `lane` (the lane-selection rule), `ordering`, `overflow`, `kinds[]` (empty on a snapshot topic), and `payloadFields[]`. The topic set is closed at six: `queue`, `lanes`, `queue.graph`, `dispatch.attempt`, `phase.state`, `blockers.state`. `status` stays a wire type and is not a topic.

| Topic | Shape | Parent | Lane rule | Declared kinds (order) | Ordering | Overflow |
|---|---|---|---|---|---|---|
| `queue` | snapshot | — | none (`lane` never appears) | none (`kinds: []`) | `snapshot-revision` | `repoll` |
| `lanes` | snapshot | — | none (`lane` never appears) | none (`kinds: []`) | `snapshot-revision` | `repoll` |
| `queue.graph` | event | `queue` | the entry `ref` | `entry`, `dependency-edge`, `release`, `remove` | `sequence-per-lane` | `repoll` |
| `dispatch.attempt` | event | — | the delivery `ref` | `started`, `refused`, `completed` | `sequence-per-lane` | `repoll` |
| `phase.state` | event | — | the `changeRef` | `began`, `completed`, `reopened` | `sequence-per-lane` | `repoll` |
| `blockers.state` | event | — | the question record's `lane` (required, non-empty) | `published`, `updated`, `cleared` | `sequence-per-lane` | `repoll` |

`ordering` and `overflow` are closed values, not prose: `ORDERING_VALUES = ["sequence-per-lane", "snapshot-revision"]` and `OVERFLOW_VALUES = ["repoll"]`. A snapshot topic's `snapshot-revision` value states what the delivered `cursor` is and is explicitly *not* an ordering guarantee (DEC-D). A kind's identity is the pair `(topic, kind)`; `kind` is scoped to its topic and is not globally unique — `completed` exists on both `dispatch.attempt` and `phase.state`, and `published`/`updated`/`cleared` are not shared with any other topic. A snapshot topic declares no kind, because it emits no `kind` on the wire; `kinds: []` on `queue` and `lanes` is the honest declaration, and the emitted-set comparison is scoped to event topics (DEC-B, DEC-K).

**Envelope nullability is declared per topic, not globally.** `lane` is present and a non-empty string on every v1 event topic: each of the four lane rules names one (the entry ref, the delivery ref, the `changeRef`, and the question record's required `lane`), so v1 has no lane-less witness and no nullable lane. A future topic whose source can lack a lane must declare a nullable `lane` in its own taxonomy version. `ref` is present and nullable only where its source is nullable, declared per topic:

| Topic | `lane` | `ref` |
|---|---|---|
| `queue.graph` | the entry `ref` from the source record | the same record's `ref`, a non-empty string |
| `dispatch.attempt` | the delivery `ref` from the source record | the same record's `ref`, a non-empty string |
| `phase.state` | the `changeRef` | the same `changeRef`, a non-empty string |
| `blockers.state` | the question record's `lane` (required non-empty) | the question record's `ref`: a string or explicit `null` — `null` for a question published without one, which is what the shipped publish path records |

**F-2 — Reference surface.**
`<binary> events list [--json]` and `<binary> events describe <topic> [--json]` are pure data rendering: no store, configuration, git, network, or filesystem read, and no write.

```
<binary> events list
queue             v1  shape=snapshot  kinds=0  ordered by snapshot revision  overflow=repoll
lanes             v1  shape=snapshot  kinds=0  ordered by snapshot revision  overflow=repoll
queue.graph       v1  shape=event     kinds=4  parent=queue  ordered per lane  overflow=repoll
dispatch.attempt  v1  shape=event     kinds=3  ordered per lane  overflow=repoll
phase.state       v1  shape=event     kinds=3  ordered per lane  overflow=repoll
blockers.state    v1  shape=event     kinds=3  ordered per lane  overflow=repoll
```

The machine envelope is the delivered `CommandResult` shape, unchanged and not re-invented: `{ schemaVersion, runId, exitCode, timing, data }` on success or `{ schemaVersion, runId, exitCode, timing, error }` on a refusal — exactly one of `data`/`error`, no top-level `ok`, `command`, or `warnings` key. Command identity lives inside `data`: `data.command` is `events list` or `events describe`. `data` also carries `taxonomyVersion` (`"v1"`), `envelope[]` (the eight event-frame fields, in order), and `topics[]` (one record per topic for `list`, exactly one for `describe`). Because `data.command` is inside `data`, the scripted machine projection — a success line of `data` alone, without `schemaVersion`, `exitCode`, or `timing` — still carries the command identity. A topic record carries:

| Key | Contract |
|---|---|
| `name` | the topic name, a member of the closed topic set |
| `version` | `"v1"` |
| `shape` | `snapshot` or `event` |
| `parent` | present only on `queue.graph`, value `queue` |
| `frame` | the ordered frame field list: `["topic","cursor","snapshot"]` for a snapshot topic, `["topic","kind","lane","ref","sequence","occurredAt","payload","taxonomyVersion"]` for an event topic |
| `lane` | the lane-selection rule: `none`, `ref`, `change-ref`, or `blocker-lane` |
| `kinds` | one record per declared kind: `name`, `emitted` (boolean), `payloadFields[]`; ordered as declared; an empty list on a snapshot topic, which declares no kind |
| `payloadFields` | the derived union of the topic's per-kind payload fields, never authored separately; empty on a snapshot topic |
| `ordering` | `sequence-per-lane` or `snapshot-revision` |
| `overflow` | `repoll` |

`events describe <topic>` adds nothing to the machine shape (it returns the same `data` with one topic record) and renders, in text, the kinds with their `emitted` state, the per-kind payload fields, the lane rule, the ordering sentence, the overflow sentence, and the frame field list — within the delivered human bounds (≤ 40 lines, ≤ 8 192 bytes). `emitted: false` appears exactly once in v1: `queue.graph` kind `remove` (§5.1 F-3, DEC-J).

Exit codes follow the delivered projection: `0` the reference was produced; `1` the request was refused (`events.topic-unknown` for a topic outside the set, including `status`; `events.verb-unknown` for an absent or unknown verb); `2` `events.taxonomy-unavailable` when the declaration fails its own integrity check (DEC-M).

**F-3 — Event envelope and per-kind emission.**
An event-topic frame carries `data` with eight fields, in this order: `topic`, `kind`, `lane`, `ref`, `sequence`, `occurredAt`, `payload`, `taxonomyVersion`. **Counting convention:** the frame carries **seven change fields** — `topic`, `kind`, `lane`, `ref`, `sequence`, `occurredAt`, `payload` — plus the `taxonomyVersion` stamp, which is eight `data` keys in total. A count of "seven" always means the change fields and a count of "eight" always means the full `data` key set; the two counts describe the same frame and are never in conflict. `lane` is always present and a non-empty string, per the per-topic rule in §5.1 F-1; v1 declares no nullable `lane`. `ref` is always present and nullable only where its source is nullable, per the same table: a non-empty string on `queue.graph`, `dispatch.attempt`, and `phase.state`, and the question record's `string | null` on `blockers.state`. `occurredAt` is the source record's own timestamp, never the publish time and never an injected clock: the record's `recordedAt` on `queue.entry`, `queue.dependency`, `queue.lease`, `daemon.lane`, and `dispatch.attempt`, `askedAt` on `blocker.question`, `answeredAt` on `blocker.answer`, and `timestamp` on `phase.transition` — so a re-observation of the same record yields the same value. `sequence` is allocated at emission by the publishing process, per the ordering rule in F-4. `payload` is the topic-specific object. An event frame carries no `cursor`.

**Payload derivations, declared.** Several payload fields are named differently from the record field they come from, and one payload `ref` repeats the envelope `ref`; each derivation below is declared so a client and a test can tell a rename from a missing field:

- `queue.graph` payloads repeat the source record's own `ref` field; it equals the envelope `ref` by construction and is declared for record symmetry, not as a second identity.
- `queue.graph.release.operation` is the lease record's `operation` field. The closed set is `acquired|renewed|released|taken-over`; this kind is emitted only for `released`, so the payload value is always `released`.
- `dispatch.attempt.completed.comparisonClass` is the attempt record's `comparison.class` (the nested comparison record is flattened; its `outcome`, `reason`, `token`, and `urlResolved` are not projected).
- `dispatch.attempt.refused.token` and `dispatch.attempt.completed.token` are the attempt record's own `token` value, projected verbatim: the closed-vocabulary delivery result token, which is the attempt's corroboration identifier and a declared, non-secret field (NFR-10). The nested comparison record's separate `token` is not projected — the two are different fields and only the attempt's is published.
- `dispatch.attempt.started.recordedAt` is the lane record's `recordedAt`; `dispatch.attempt` payload fields are the attempt record's own fields.
- `blockers.state.updated.id` is the answer record's `questionId`; `updated.resumeMode` is the answer record's `laneResume.mode`.
- `blockers.state.cleared.id` is the lane record's `resumeIntent.questionId`; `cleared.resumeMode` is `resumeIntent.mode`; `cleared.lane` is the question record's `lane` for that id; `cleared.clearedAt` is the `recordedAt` of the lane record that carries the `resumeIntent`. The question record is the one the blocker ledger read already holds, so no second ledger is joined.
- The `blockers.state` envelope `lane` and `ref` are the question record's own fields for all three kinds, including `updated` (the question identified by the answer's `questionId`) and `cleared` (the question identified by `resumeIntent.questionId`); the payloads do not repeat them.
- Nothing else is renamed, flattened, or synthesised: every other payload field is the same-named field of the declared source record.

**Park facts are not projected in v1.** A `queue release --park` writes a separate `queue.park` record carrying its own cause, condition, and recheck delay. No v1 kind consumes that record, the `release` payload carries no park cause, and no kind joins two ledgers to produce a payload; park publication belongs to M2-S17.

**Payload bounds — v1 has no truncation marker and exactly one declared presentation bound.** Every declared payload is bounded below `DAEMON_MAX_FRAME_BYTES` (65 536) by caps the delivered contracts enforce: `QUEUE_MAX_REF_CHARS` (64) on every ref and edge, `QUEUE_MAX_EDGES_PER_ENTRY` (32) on `edges`, `added`, and `removed`, `DISPATCH_MAX_EVIDENCE_REFS` (16) on `evidenceRefs`, `BLOCKER_MAX_QUESTION_CHARS` (120), `BLOCKER_MAX_OPTIONS` (4) with `BLOCKER_MAX_OPTION_CHARS` (60) per option, and `BLOCKER_MAX_ANSWER_CHARS` (160) — plus one bound no delivered contract carries, which the projection enforces itself: **each `dispatch.attempt.refused.evidenceRefs` entry is bounded to 256 characters by the projection.** That bound is a **presentation bound, not a contract cap**: `DispatchEvidenceReference` stays a `string` with no declared maximum, so the bound widens no contract, adds no field, and changes no record shape. An over-length reference is **cut to its first 256 characters, not dropped**: the entry keeps its list position, the count cap stays `DISPATCH_MAX_EVIDENCE_REFS` (16), and a reference at or under 256 characters is copied unchanged — so every shipped producer, whose refs are `attempt:<id>`, `daemon:lane`, `window:<ts>`, `handover:<ts>`, `harness:spawn-failed`-shaped identifiers, is unaffected and the cut is unreachable from them. Every other projected field is a fixed-shape identifier, a closed vocabulary value, an integer, or an ISO-8601 timestamp.

The worst case is unchanged by that bound: a `dependency-edge` payload — three lists of at most 32 refs of at most 64 characters, under 7 KB serialized — is still the largest, and the next-largest case, a `refused` payload with 16 evidence refs, is now provable at 16 × 256 = 4 096 characters of ref content, under 5 KB serialized, because of the per-entry bound. Both are an order of magnitude below the frame bound. v1 therefore declares no truncation marker — `truncated`/`truncationReason` is not a member of any kind's `payloadFields` — and no cut order over payload fields; the one cut this version declares is the per-`evidenceRefs`-entry presentation bound named above, which shortens an over-length reference instead of removing it. A future kind whose payload cannot be bounded this way must declare its marker and its cut order in the version that adds it.

Three declarations make the mapping honest rather than aspirational:

1. **`completed` is not a success claim.** The attempt record's `outcome` may be `completed`, `premature-end`, `failed`, or `timed-out`; the kind names "the attempt ended and was recorded", and the payload's `outcome` names what happened. A refusal is the one outcome that gets its own kind, because a refused attempt never ran.
2. **`began` is derived, not recorded.** No delivered path writes a begin record: `phase.transition` records landings only and the fold records `started` at the first completion. `began` is therefore emitted when a completion is first observed for a phase with no prior `started`, in the same observation as that phase's first `completed`, and the two carry ascending `sequence` values on the same lane. The alternative — claiming a begin time the record set does not hold — is rejected; adding a begin record is new persistence and is out of scope (NG-3).
3. **`remove` is declared and not emitted.** The contract section enumerates it and this change declares it, so a client can write the `switch` case once and be ready for S15; `emitted: false` on the reference surface says truthfully that v1 never produces it, and no `remove` event is emitted by any v1 path. Declaring it silently as emitted would be a lie a contract test cannot catch.

A `queue.graph` event is emitted one per observed durable change, so a subscriber that adds an entry and then a dependency receives an `entry` event followed by a `dependency-edge` event carrying `added`/`removed` deltas it can act on (ticket AC1). A `dependency-edge` event is emitted only when a dependency record's folded edge set differs from the previous record for the same `ref`, so a re-written identical record publishes nothing.

**F-4 — Ordering.**
`sequence` is a positive integer allocated once per emitted event, per `(topic, lane)`, increasing by exactly 1 per emitted event for that pair; every subscriber of the topic receives the same value for the same event. The value is allocated at emission by the publishing process — it is neither seeded from a ledger nor allocated from the durable state revision. The guarantee is scoped: within one `(topic, lane)` pair, `sequence` is monotonic; there is no cross-topic and no cross-lane ordering promise, because subscriptions are per topic and the daemon holds no cross-topic sequencer.

`occurredAt` is the source record's own timestamp and carries no ordering guarantee: two events on one lane may carry descending `occurredAt` values while their `sequence` ascends, and no client may sort by it.

A client's rule: its baseline is the first value it observes for a lane; a non-contiguous successor (a jump forward or any value at or below the last observed) means the stream is discontinuous, and the client repolls instead of inferring order. The counters are process-scoped, so a daemon restart is a declared discontinuity that a client detects the same way — the sequence is a wire ordering value, not a durable revision (DEC-I). The delivered `cursor` keeps its per-topic snapshot-revision meaning on snapshot topics, is absent from event frames, and is never an ordering signal (DEC-D).

**F-5 — Overflow.**
The delivered mechanism is unchanged for all six topics: a subscription's bounded buffer overflows, that subscription receives exactly one `degraded` event carrying `degraded: "subscriber-overflow"`, only that subscription is dropped, every other subscription keeps receiving, and the client repolls. The single capacity bound `daemon.subscription-buffer` (default `256`) still caps both the per-subscription buffer and the per-connection subscription count, which still refuses with `daemon.subscriber-degraded`.

Additively, that degraded frame's `data` also carries `overflow: "repoll"` and `taxonomyVersion: "v1"`, for every topic including the two snapshot topics; the delivered `degraded` field, its reason vocabulary, and the dropped-subscription behaviour are untouched. The reference surface declares `overflow: "repoll"` on every topic, generated from the same declaration constant the degradation path renders the frame from, and a named test pins that constant and the absence of a second literal in the degradation path, so the two values cannot diverge unnoticed (DEC-C).

**F-6 — Snapshot topics preserved.**
`queue` and `lanes` keep their delivered frames exactly: `{ topic, cursor, snapshot }` on publish, `{ degraded, topic }` plus the additive overflow stamp on a degraded frame, and the delivered initial-subscribe baseline whose frame carries `cursor: 0`. No `kind`, `lane`, `ref`, `sequence`, `occurredAt`, or `payload` is added to them, and their `data` field set is unchanged. The taxonomy declares them as snapshot topics that carry **no kind at all** — `kinds: []` and `payloadFields: []` — rather than inventing a kind set from the planning page's example counts or fabricating a `snapshot` kind the wire never carries (DEC-B); their `ordering` is declared as the snapshot revision they actually carry.

**F-7 — Mounted reference command.**
`events` joins `PROMPT_REQUIRED_COMMANDS` (18 → 19) and is composed by the production entrypoint unconditionally, because program selection is strict: a missing prompt-required command throws and is contained as `fallback.internal`. The mount cannot degrade, because the runtime is the taxonomy declaration itself — no store, no configuration, no transport, no entry path — so `daemon`-style unavailable-runtime handling is unnecessary.

The help inventory gains one family entry (`events`) and one entry per verb (`events list`, `events describe`), each pointing at the M2 reference page `doc/planning/oss-tooling/milestones/m2/commands/events.md` through the per-command page-root mapping; the coverage inventory gains `events` in `commands` and the M2 page in `referencePages`; the page-root mapping gains the `events` row beside the `projects` row; and the reference page carries the `--help`/`--version` section the coverage guard requires. Root `--help` lists nineteen families.

**F-8 — Additive contracts and the error table.**
`CONTROL_TOPICS` widens from two to six members; `ControlEventData` gains an additive member for the event envelope; the server's subscribe accept shape accepts a topic with no snapshot; the daemon's subscribe handler widens its topic literal pair; and the publish projection learns four event topics. No wire type, no frame field outside `data`, no codec rule, no protocol version, and no subscription bound changes.

The error table gains a new `events` domain kind and exactly three rows: `events.topic-unknown` (`user`, non-retryable, `not_landed`, `user-validation` → exit `1`), `events.verb-unknown` (same class), `events.taxonomy-unavailable` (`platform`, non-retryable, `not_landed`, `platform-provider` → exit `2`). No existing row is added, removed, or reworded. The daemon refuses a `subscribe` for a topic outside the six with `events.topic-unknown` before any store read, matching the reference surface's identity for the same mistake (DEC-L). This replaces the delivered behaviour, which accepted such a subscribe and answered it with the `lanes` snapshot labelled with the requested topic: the change is an acceptance becoming a refusal, and it also removes a wrong-data path.

## 6. USER & SYSTEM FLOWS

**Flow 1 — A client reads the contract and subscribes to `queue.graph`.**
```
client  -> <binary> events describe queue.graph --json
        <- data.taxonomyVersion=v1, one topic record: shape=event, kinds[4], payloadFields, ordering, overflow
client  -> daemon socket: subscribe { topic: "queue.graph" }
        <- response { ok: true, subscriptionId }
        <- (no synthetic baseline; the first frame is the next observed change)
operator-> <binary> queue add GH-999
        <- event { topic:"queue.graph", kind:"entry", lane:"GH-999", ref:"GH-999",
                   sequence:1, occurredAt, payload:{ref,priority,recordedAt}, taxonomyVersion:"v1" }
operator-> <binary> queue dep GH-999 GH-777
        <- event { kind:"dependency-edge", lane:"GH-999", sequence:2, payload:{edges,added,removed} }
client  -> acts on the entry and on the new edge (ticket AC1)
```

**Flow 2 — A slow consumer overflows on any topic.**
```
subscriber stops reading -> its bounded buffer fills
daemon -> exactly one event { type:"degraded", topic:<t>,
                              data:{ degraded:"subscriber-overflow", overflow:"repoll", taxonomyVersion:"v1" } }
       -> that subscription is removed; every other subscription keeps its stream
subscriber -> repolls current state (the declared remedy, same value the reference surface declares)
```

**Flow 3 — Snapshot topics are untouched.**
```
client -> subscribe { topic: "lanes" }
       <- response { ok:true, subscriptionId }
       <- { topic:"lanes", cursor:0, snapshot:{...} }        (delivered baseline frame)
       <- { topic:"lanes", cursor:4, snapshot:{...} }        (delivered change frame, byte-identical shape)
```

**Flow 4 — Phase and blocker planes.**
```
operator -> <binary> phase complete GH-290 specification
         -> phase.transition { operation: complete } appended
         <- events: kind:"began" (first completion of that phase), then kind:"completed", same lane GH-290
operator -> <binary> blockers publish ...
         <- kind:"published"   (question record)
operator -> <binary> blockers answer ...
         <- kind:"updated"     (answer record)
daemon consumes the answer, records resumeIntent on the delivering lane
         <- kind:"cleared"     (the lane is no longer blocked)
```

**Flow 5 — A wrong topic, a wrong verb, and a broken declaration.**
```
<binary> events describe status   -> events.topic-unknown, exit 1   ("status is a wire type, not a topic")

<binary> events                   -> events.verb-unknown,  exit 1

                                    before this change the same request returned ok and the lanes snapshot under topic "status")

```

```

```

## 7. SCOPE & BOUNDARIES

### 7.1 In Scope

- The taxonomy declaration: version, six topics, per-topic shape, parent, frame fields, lane rule, kind records with `emitted`, derived payload-field unions, ordering, and overflow — as runtime-neutral data in the contracts tier, re-exported from the contract index.
- The four event topics' emission from existing durable ledgers, with the per-kind source mapping in §5.1 F-3, a per-`(topic, lane)` sequence, the eight-field envelope inside the delivered open `data` body, `occurredAt` from the source record, and bounded payloads.
- The delivered publish tick restructured to **one shared store read per publish tick — one `readRecords()` view per `publishState` invocation** — one view folded once for the snapshot projection and once for the event projection, replacing the delivered two-whole-store-read publish shape — and extended to project the four event topics from that view; the per-`(topic, lane, source family)` watermark that keeps an unemitted delta pending rather than dropped or buffered. The heartbeat branch is outside this count and unchanged: `writeHeartbeat` folds `readQueueEntries` and `readDaemonLanes` on its own interval before the publish runs, and this change neither moves nor bounds those reads.
- `CONTROL_TOPICS` widened to six; the additive `ControlEventData` member; the internal subscribe-accept shape; the daemon subscribe handler's topic widening; the unknown-topic refusal mapped to `events.topic-unknown` before any store read (an acceptance becomes a refusal; the delivered handler served any unknown topic the `lanes` snapshot).
- The additive `overflow: "repoll"` and `taxonomyVersion` on every degraded frame, for all six topics, with the delivered marker and drop behaviour unchanged.
- The `events list` / `events describe <topic>` command family: grammar, machine envelope, text rendering within the delivered human bounds, the three error identities, and the exit projection.
- The mount as one unit: prompt-required set (18 → 19), edge composition and production wiring, help family and verb entries, coverage-inventory `commands` and `referencePages` rows, the `events` page-root mapping, and the M2 reference page's `--help`/`--version` section.
- The three new error-table rows and the `events` domain kind, and their rows in the documented result-contract table.
- The per-topic contract tests over the generated reference surface and over daemon-emitted frames, with the hand-authored projection pinned to the declaration by the emitted-kind-set pin and the exact per-kind payload-key comparison, plus the guard updates named in §8.5.

### 7.2 Out of Scope

- [OUT] Any S17 shape: the stop, parked, resumed, and park-edge kinds, their payloads, their bounded-grace deadlines, and the park fields on `status` and `brief`. They are the recorded v2 extension path (DEC-A).
- [OUT] Queue or lane mutation of any kind: entry removal with a reason, the `dep add`/`dep remove` grammar, automatic removal on merge and closeout, and stale reconciliation. M2-S15 owns them; this change only observes what those paths will append.
- [OUT] A `remove` event from any v1 path. The kind is declared, marked `emitted: false`, and emitted by no production path.
- [OUT] A phase *begin* record, or any new record kind, payload schema, key prefix, or state schema version. `began` stays a derived projection (§5.1 F-3).
- [OUT] Changing the control protocol: no new wire type, no protocol version or floor change, no frame field outside `data`, no codec rule, no subscription-buffer semantics, no at-most-once semantics, no `subscriber-overflow` vocabulary change.
- [OUT] Re-keying, re-wrapping, or enriching the delivered `queue` and `lanes` frames (DEC-B).
- [OUT] New `--watch` topic flags on `queue` or `lanes`, and any new watch command.
- [OUT] `board`, `spend` v2, telemetry attribution, `attempts` read side, `projects` changes, and cross-repository group scoping.
- [OUT] A second served taxonomy version, per-client version negotiation, or a version field on frames that do not carry the envelope.
- [OUT] Any prompt, agent, or lifecycle-instruction change; any `.opencode/**` edit.
- [OUT] Any new package dependency, network listener, provider call, credential read, or filesystem location.
- [OUT] A payload truncation marker or cut order. Every v1 payload is bounded below the frame bound by delivered caps plus the projection's declared 256-character per-`evidenceRefs`-entry presentation bound, so no `truncated`/`truncationReason` field and no partial-payload path is declared.

### 7.3 Deferred / Maybe-Later

- A `remove` emitter once M2-S15 delivers reason-bearing entry removal and automatic landed removal.
- A served v2 carrying S17's stop/park/resume and park-edge kinds, with their payload requirements.
- A durable sequence (seeded from the ledger) so a sequence survives a daemon restart, if a client demonstrates a need beyond the repoll remedy.
- Per-lane `since` resumption for event topics, once a durable sequence exists (`since` has no meaning for an event topic in v1, DEC-H).
- A `queue.graph` park-edge projection once S17 declares the kind and its payload.
- Batching several deltas of one lane into one frame, if a burst-heavy store shows per-event overhead that matters.

One authored source for the declaration, the generated surface, and the validator; the surface tests compare the rendered surface against it, and the hand-authored emission projection is compared against the contract's declared field lists. The projection imports only the taxonomy version constant and assembles each kind's frame itself; it is pinned to the declaration by bidirectional emitted-kind-set pinning and an exact per-kind emitted-payload-key comparison, so drift in either direction fails a named test, and the frames are not generated from the declaration. |
| DM-2 | Event frame data | Eight fields in declared order. `lane` is a non-empty string on every v1 event topic; `ref` is a non-empty string on `queue.graph`, `dispatch.attempt`, and `phase.state`, and `string \| null` on `blockers.state` — the only nullable envelope field in v1. `taxonomyVersion` is the frame's version stamp and sits outside `payload`; the seven change fields carry the change, so the frame is seven change fields plus the stamp = the eight `data` keys of §5.1 F-3's counting convention. Additive inside the delivered open `data` body; no truncation marker. |
| DM-3 | Snapshot frame data (unchanged) | `{ topic, cursor, snapshot? }` exactly as delivered, for `queue` and `lanes` only; no `kind`. |
| DM-4 | Degraded frame data | Delivered `{ degraded, topic? }` plus `overflow: "repoll"` and `taxonomyVersion: "v1"`. Additive; the marker and the drop behaviour are unchanged. |
| DM-5 | Sequence semantics | Per-event, per-`(topic, lane)`, positive integer, shared across subscribers of the topic, allocated once per emitted event at emission by the publishing process, process-scoped (a restart is a declared discontinuity), incremented by exactly 1. Not durable, not persisted, not seeded from a ledger, not allocated from the durable state revision. |
| DM-6 | Topic-set widening | `CONTROL_TOPICS` = `["queue","lanes","queue.graph","dispatch.attempt","phase.state","blockers.state"]`; the event body union gains the envelope member; the server's subscribe accept accepts a topic whose snapshot is absent; the daemon's subscribe handler widens its literal pair and refuses a topic outside the six with `events.topic-unknown` before any ledger read. No wire type, codec rule, or protocol version changes. |
| DM-7 | Events envelope and topic record | The delivered `CommandResult` envelope, unchanged: on success `{ schemaVersion, runId, exitCode, timing, data }` with `data = { command, taxonomyVersion, envelope[], topics[] }`, and on a refusal `{ schemaVersion, runId, exitCode, timing, error }`; the command family adds no envelope key and no top-level `ok`/`command`/`warnings` field, and success is read as `exitCode: 0` plus `data`. | DM-8 | No state-schema change | `STATE_SCHEMA_VERSION` unchanged; no record kind, payload schema, key prefix, migration, backfill, or seed. The one contract addition outside the taxonomy is three error rows in a new `events` domain kind (§8.5). |
| DM-9 | Emission watermark | Per observed `(topic, lane, source family)`, the identity of the last emitted source record. For a family whose records are one per change, the identity is the record's `key` paired with its `sequence` position in the `readRecords()` view. The `phase.state` family is the declared exception: its source record is the change's **cumulative verified artifact** — one record per change carries the whole transition history and is rewritten on each append (`packages/core/src/state/registry.ts:401-404,445-459`) — so its identity is the artifact record's `key` paired with the **index of the last emitted transition inside** that record's transition list; a later append yields the same `key` with a longer list, and the unemitted tail is the positions past the stored index. A same-tick burst within one change is therefore diffed inside one artifact payload, not by new record keys, and the per-tick cap applies to the transitions derived from that payload. Source families are the record families that feed the topic (at most three: `blockers.state` reads `blocker.question`, `blocker.answer`, and the lane's `resumeIntent`). One entry per observed pair, replaced by a later record of the same family; bounded by 4 event topics × observed distinct lanes × 3 families, independent of record count, event count, and subscriber count. Initialised to the store's current tail on the projection's first observation, so a populated store is a baseline and not a replay. The unemitted remainder stays pending because the watermark does not advance past it; nothing is queued. `began` needs no entry: whether a phase has a prior `started` is folded from the `phase.transition` records the tick already read. |

### 8.4 External Integrations

- **Local unix control socket (delivered).** The taxonomy is served over the existing subscribe surface at the existing socket path with the existing principal model. No new transport, no remote transport, no authentication change.
- **No tracker, provider, credential, or network surface is touched.** The reference surface performs no I/O at all, and the event projection reads only the local durable store the daemon already reads.
- **No consumer outside the repository is required to change.** A v0 or v1 peer that ignores the added `data` fields keeps interoperating; a peer that subscribes to `queue` or `lanes` receives byte-identical frames.

### 8.5 Backward Compatibility

- **Wire compatibility.** The event `data` body is open in the delivered codec, so additive fields inside `data` are wire-compatible with v0 and v1 peers. No new wire type, no new frame kind, no field moved outside `data`, no `id` on events, no protocol version change. The closed `CONTROL_TOPICS` union widens additively: an existing subscriber's topics are unchanged, and a subscription for a topic outside the six is now refused rather than accepted (next bullet).
- **Delivered snapshot topics are byte-stable.** `queue` and `lanes` publish, baseline, dedupe, and degrade exactly as delivered, with the one additive degraded-frame stamp named in EVT-2. No delivered consumer of those frames must change.
- **One delivered acceptance becomes a refusal (v0/v1 compatibility note).** A `subscribe` for a topic outside the closed set was decoded, accepted, and answered with the `lanes` snapshot whose frames carried the requested topic name: no layer validated the topic value, and the projection resolved every non-`queue` topic to the `lanes` snapshot (`daemon-compose.ts:384,1164-1171`). It is now refused with `events.topic-unknown`, a user-validation identity, before any store read. Client-visible consequence: an existing client that subscribed to an undeclared topic loses a stream whose data belonged to `lanes` under a name that was never a topic, and gains a classified refusal it can act on. No conforming client loses its own data, because the frames it received were never the topic it asked for; a client that relied on the wrong-label path was relying on a defect. This is the single intentional behaviour change on the delivered control plane, and removing the wrong-data path is part of it.
- **Unchanged identities and schema.** No existing error-table row is added, removed, or reworded; `STATE_SCHEMA_VERSION` and every closed vocabulary this change reads are unchanged; `{0,1,2}` remains the only exit set.
- **Guards that must be updated as part of the mount.** The prompt-required command enumeration in the help-coverage suite (18 → 19); the help coverage fixture (`commands` gains `events`, `referencePages` gains the M2 events page); the `events` row in the page-root mapping the help-guide coverage check applies; the two contract-surface inventories (the file set gains the new contract module and the new command/projection modules; the v1 contract inventory gains the new exports); and the executable-export allowances for the new files. The root-family membership assertion in the entrypoint help suite is a hand list that already omits `dispatch`, `coordinator`, and `projects` (fifteen of the eighteen delivered names), so it needs no edit to stay green; `events` may be added to it as documentation of the mount, and the equality that matters (inventory versus prompt-required set) is carried by the coverage suite. The permitted-edit set is **derived, not enumerated**, and the derivation must cover counts as well as names: every suite or check that contains the prompt-required enumeration, a family list derived from it, **or a literal count of either** is in the set. A bare count is not a command-name literal, so a search for names alone misses it: `tests/structure/daemon-production-composition.test.ts` asserts the prompt-required length three times (18 for the full set, 18 in the composition with every optional input absent, and 17 for the daemon-omission mutant), and those become 19, 19, and 18. Every inventory or coverage count that grows with the mount (`commands`, `referencePages`, root-family counts) is in the same set. Naming the set is the plan's job and editing the files is delivery's; the rule this specification pins is that a count assertion affected by this change is part of the edit set and must be declared, not discovered at the quality gate.
- **Delivered suites that must keep passing without semantic change**: the control codec, control conformance, control session, control connection, control transport, daemon lifecycle, daemon degradation (both), daemon heartbeat, daemon lane supervision, daemon crash/restart, daemon effects, daemon foreground lifetime, queue CLI, queue scheduling contract, blockers, error classification and error-table sync, port contract inventory, content inventory, entrypoint help and help coverage, and reference-page parity suites. `tests/structure/daemon-production-composition.test.ts` is the one delivered suite in the edit set for its three count assertions (above) and is otherwise unchanged.
- **The doc-conformance page list is not extended.** That hand list already omits `dispatch`, `coordinator`, and `projects`; adding `events` alone would leave the omission set incoherent, and the assertion it protects (every listed reference page documents `--help`) is already covered for `events` by the help-coverage guard. This follows the precedent set when `daemon` and `projects` were mounted (GH-286 DEC-13, GH-288).

## 9. NON-FUNCTIONAL REQUIREMENTS (NFRs)

| ID | Requirement | Threshold |
|---|---|---|
| NFR-1 | Reference-surface purity and latency | `events list` / `events describe` perform 0 state, configuration, git, network, or filesystem reads, 0 writes, and 0 command-composer invocations; p95 ≤ 100 ms; output ≤ 40 lines and ≤ 8 192 bytes on the human page |
| NFR-2 | Publish-tick cost and read model | Exactly one whole-store `readRecords()` **per publish tick** — one `publishState`/`stateChanges()` invocation — serves all six topics and all subscribers through both projections; the read count is independent of subscriber count, subscribed-topic count, and store size; no per-topic read and no per-subscriber read is issued on the publish path; 0 socket connects, 0 process probes, 0 sleeps on the publish path; added p95 publish-tick latency ≤ 25 ms over the delivered publish tick on the reference store. **Heartbeat ticks are outside this count:** on a heartbeat loop iteration `writeHeartbeat` folds `readQueueEntries` and `readDaemonLanes` (two whole-store reads) before `publishState` runs; that fold is a delivered consumer this change does not touch and is not a publish read, so the guarantee is exactly one read per publish tick, not one read per loop iteration. |
| NFR-3 | Burst handling, no silent loss | ≤ 64 events per topic per publish tick; an unemitted delta stays pending through the per-`(topic, lane, source family)` watermark (DM-9) and is emitted on a later publish tick; 0 dropped events; the watermark holds at most one entry per observed `(topic, lane, source family)` — ≤ 4 event topics × observed lanes × 3 source families, with the `phase.state` entry carrying a position inside the change's cumulative artifact — independent of record, event, and subscriber count, with no unbounded in-memory event queue |
| NFR-4 | Envelope conformance | 100% of emitted events on all four event topics carry all eight fields; `lane` is present and a non-empty string, never absent and never `null`; `ref` is present, a non-empty string on `queue.graph`/`dispatch.attempt`/`phase.state`, and a string or explicit `null` on `blockers.state`; `kind` is always a member of its topic's declared set |
| NFR-5 | Frame bound | Every event frame ≤ `DAEMON_MAX_FRAME_BYTES` (65 536), provable from the declared payload caps plus the projection's declared 256-character per-`evidenceRefs`-entry presentation bound; no payload field is truncated, no `truncated`/`truncationReason` field exists in v1, and the only cut is that declared per-entry bound, which shortens an over-length reference instead of dropping it; no frame is shortened by anything undeclared |
| NFR-6 | Ordering determinism | 0 non-monotonic `sequence` values per `(topic, lane)` within a daemon incarnation; 100% of discontinuities (gap, decrease, restart) route the client to a repoll; 0 orderings inferred from `occurredAt` or `cursor` |

| NFR-8 | Additivity | 0 new wire types, 0 new state record kinds, 0 payload schema versions, 0 migrations, 0 new package dependencies, 3 new error rows and 0 changed existing rows |
| NFR-9 | Non-blocking publication | No publish path awaits a subscriber write; a subscriber that stops reading cannot delay the publish tick or another subscription beyond its own buffer |
| NFR-10 | Privacy and content safety | No credential or secret material (an auth token, a lock token, a provider payload, or a resolved credential), no prompt, transcript, or model output, no diff, and no repository content in any payload; evidence is bounded to identifiers, counts, closed vocabulary values, and declared caps; a queue entry's `repositoryRoot` is never projected. **The `token` payload field is not an exception to any of that, because it is not a credential:** `dispatch.attempt`'s `token` is the attempt record's closed-vocabulary delivery result token (`merged`, `blocked`, `pr-open`, `pr-open-unverified`, `failed`, `finished`, `max-restarts`, `state-unverified`, `partial`, `noop-lane-permission`, `noop-lane-nothing-to-do`) — the attempt's corroboration identifier, already durable in the attempt record and already readable on the `attempts` read side — so it is a declared, non-secret field, and the words "token", "credential", and "secret" in this requirement are read as excluding credential-bearing tokens only |

**How NFR-2 is counted, and the restructure it implies.** The counting seam is the state port itself: the composition takes an injected `StateStorePort`, and the test wraps its `readRecords` in a counter, so every call made between the entry and the return of one `publishState` invocation — one publish tick — is counted directly, with no wall-clock inference and no log parsing. **The counted interval is the publish call, not the loop iteration.** The resident loop's `tick()` also calls `writeHeartbeat` on the heartbeat interval, and that fold performs two whole-store reads of its own (`readQueueEntries` and `readDaemonLanes`, `packages/core/src/app/daemon-runtime.ts:172-175,208-213`) before `publishState` runs at `:243`. Those two reads belong to the heartbeat, are delivered behaviour this change adds none of and moves none of, and are excluded from NFR-2 by construction: a count that included them would measure the daemon loop rather than the publish path this specification restructures. The delivered publish tick cannot meet a one-read bound: `stateChanges()` calls `readQueueEntries` and `readDaemonLanes`, and each of those folds calls whole-store `readRecords()` on its own (`packages/cli/src/daemon-compose.ts:336-355,384`; `packages/core/src/app/queue.ts:409-410`). The phase topic's source is worse than one read: `readChangeTransitions` is a per-change fold with no change index over the store, and one call performs two store reads — a store probe plus the artifact-boundary read, which is itself one `readRecords()` (`packages/core/src/state/registry.ts:292,303`; `packages/core/src/state/artifact-boundary.ts:111`) — so a per-change loop over the phase topic's lanes would cost two store reads per change, one of them whole-store. The change therefore takes one `readRecords()` view per publish tick and folds it once for the snapshot projection and once for the event projection: the projections share the view, the phase transitions are derived from that view's `phase.transition` records instead of from a per-change call, the snapshot dedupe and the event watermark stay per topic, and no fold performs its own read. This is a distinct restructure of the publish tick's read model, not an incidental edit, and §18 declares it as its own plan phase.

## 10. TELEMETRY & OBSERVABILITY REQUIREMENTS

- **Durable evidence is the telemetry.** Every emitted event maps to exactly one existing durable record (§5.1 F-3), so "what did clients see" is answerable from the store plus the published contract. No new metric, trace, log line, or event store is added (NG-8).
- **One operational query.** `<binary> events list --json` answers "which topics does this binary speak, at which version, with which kinds, payload fields, ordering, and overflow policy, and which kinds are declared but not emitted?"
- **A client can prove its own health.** A subscriber compares its last observed `sequence` per lane against the next value; a gap or a decrease is its own observable and its declared action is a repoll. No server-side counter, gauge, or log is required for that proof.
- **Overflow is already observable and stays so.** Each overflow yields exactly one degraded frame on the affected subscription, carrying the same `overflow: "repoll"` value the reference surface declares: both read one declaration constant, a named test pins that constant and the absence of a second literal in the degradation path, and a divergence therefore fails a test.
- **No sensitive content.** Every reported value is an identity, a path-free identifier, a count, a duration, a closed vocabulary value, or bounded question/answer text the blocker plane already publishes at exit `0`.

## 12. ASSUMPTIONS

- The delivered control protocol — codec, session, server, transports, bounded buffer, at-most-once control actions, and the open event `data` body — is a stable current contract this change consumes additively.
- The event `data` body stays open to additive fields in v0 and v1, so a peer that ignores the new fields keeps interoperating; no external consumer decodes `data` strictly enough to reject them (§14 OQ-1).
- The daemon is the only publisher: every topic is served by the resident process over one local socket, and a client's subscription lives within one daemon incarnation, which is what makes the process-scoped sequence sufficient.
- Every event kind maps to an existing durable record the daemon already reads on its own cadence, with the two declared exceptions (`began` derived from the first completion, `remove` declared and not emitted).
- A phase's first `complete` transition is the only available evidence of its begin, because no begin record exists and none is added.
- An answer record plus the consuming daemon's `resumeIntent` on the delivering lane is sufficient evidence that a blocker cleared, because the lane is the thing that was blocked.
- A blocker question's `ref` is nullable and the shipped publish path always records `null`, so `blockers.state` declares the only nullable envelope field in v1 and derives it from the question record; every other v1 topic's source always names a `ref` and a `lane`.
- Envelope nullability is a per-version declaration, not a global escape hatch: a v1 event frame never carries an absent or `null` `lane`, and a future topic whose source can lack one must declare it in its own version.
- The taxonomy declaration is a compiled constant, so "the taxonomy cannot be read" can only mean a broken declaration, not an unreadable file (DEC-M).
- Mounting the family is trivially safe in production because the runtime is the declaration: no store, configuration, transport, entry path, or supervisor input is involved.
- A client that wants current state reads a command surface (`queue list`, `blockers list`, `phase list`, `lanes`); the event topics promise changes, not a baseline.
- The delivered human-output bounds (40 lines, 8 192 bytes) are the right bounds for a reference page.

## 18. ROLLOUT & CHANGE MANAGEMENT (HIGH-LEVEL)

- **Delivery shape.** One change on `feat/GH-290/event-taxonomy`, one pull request targeting `main-tools`, delivered through the full eleven-phase lifecycle with its plan phases declared in the plan artifact and commits routed through the `commit` primitive.
- **No migration and no schema change.** Nothing is transformed, backfilled, or seeded; no existing record is rewritten.
- **Ordering inside the change.** The declaration and the error rows are independent of the mount; the mount, the prompt-set entry, the help inventory, the coverage inventory, and the page-root mapping must land together because the strict program selection and the two help gates fail in both directions otherwise. The `queue`/`lanes` preservation proof and the overflow parity proof land with the envelope, because a regression there is only visible once the publish path is touched. The shared-read restructure of the publish tick is a declared plan phase of its own: it changes the delivered `stateChanges`/`publishState` seam from two whole-store reads per publish tick to one shared view per publish tick, and the event projection consumes the view that phase produces; the heartbeat branch keeps its own reads and is untouched.
- **Adoption path.** A client calls `events list` once, pins `taxonomyVersion: v1`, subscribes to the topics it needs, switches on `(topic, kind)`, and repolls on a sequence discontinuity or on `overflow: "repoll"`. Nothing changes for a client that keeps polling command surfaces, and nothing changes for an existing `queue` or `lanes` subscriber.
- **Disclosed behaviour change.** A `subscribe` for a topic outside the six was accepted and answered with the `lanes` snapshot labelled with the requested topic; it is now refused with `events.topic-unknown` before any store read. An existing client that subscribed to an undeclared topic loses a stream that was never its topic's data and gains a classified refusal it can act on. A degraded frame also carries two additive fields. Both changes are named in §8.5 and must be stated in the reconciled pages, including the removal of the wrong-label path.
- **Rollback.** Revert the change. The taxonomy adds no persisted state, so no record is invalidated and no reversal migration exists; a client that spoke v1 returns to snapshot-diffing or polling.
- **Communication.** The taxonomy, the shape split, the ordering scope, and the overflow carriage are recorded in the canonical taxonomy page (`feature-event-taxonomy.md`, reachable through its `doc/00-index.md` row), the resident-daemon page summary and its pointer, the result-contract page, the M2 reference page, the entrypoint delta, and the glossary.

## 19. DATA MIGRATION / SEEDING (IF APPLICABLE)

N/A. No record kind, payload schema, or schema version changes, and no record is transformed, backfilled, or seeded. The event projection reads existing ledgers from its declared per-`(topic, lane, source family)` watermark (DM-9), initialised to the store's current tail on the first observation, so a daemon that starts against a fully populated store baselines and publishes only subsequent changes; nothing is replayed and no historical event is synthesized.

## 20. PRIVACY / COMPLIANCE REVIEW

- **No personal data or content.** Payloads carry identifiers, counts, closed vocabulary values, timestamps, and the bounded question/answer text the blocker plane already publishes at exit `0` under its own caps. No prompt, transcript, diff, diff hunk, or model output is projected.
- **Internal-only fields stay internal.** A queue entry's `repositoryRoot` exists for producer deploy-expectation discovery and is never serialized; the taxonomy's `entry` payload declares `ref`, `repository?`, `priority`, and `recordedAt` and excludes it (NFR-10).
- **No secret material.** The provenance surface reads no configuration and no credentials; the daemon's payloads carry no lock token, credential, or provider payload. The one field named `token` in the taxonomy is the attempt's closed-vocabulary delivery result token — a corroboration identifier, not a credential, and not a secret (NFR-10). The event projection adds no new read of a secret-bearing store.
- **Trust model unchanged.** Same-user local socket, the delivered principal model, no privilege escalation, no remote transport, no new write location.
- **Privacy guard impact.** None; the change adds no committed private literal and no cloud dependency.

## 21. SECURITY REVIEW HIGHLIGHTS

- **The attack surface is a read-only projection.** The taxonomy is compiled data plus reads of ledgers the daemon already reads; no new listener, path, credential read, or execution path is added.
- **An unknown topic is refused before any read.** The subscribe refusal for a topic outside the six is decided from the declaration, so a hostile or mistaken topic string never reaches a ledger read — and it can no longer be answered with another topic's snapshot.
- **Bounded output is a safety property.** Every event payload is bounded by its declared field list and by the delivered caps that bound each variable-length field plus the projection's declared 256-character per-`evidenceRefs`-entry presentation bound (NFR-5), every frame by the delivered frame bound, and the reference page by the delivered human bounds; unbounded or free-form prose is not projected, and the only cut is that declared per-entry bound on an over-length evidence reference — which shortens the reference rather than removing a payload field, and is declared rather than silent.
- **No injection into a client's decision.** `kind` is scoped to its topic and always a member of the declared set, so a client that switches on `(topic, kind)` cannot be fed an undeclared kind, and a payload field outside the declared list is additive by rule and ignorable by a v1 client.
- **Fail closed on a broken contract.** A malformed declaration yields `events.taxonomy-unavailable` at exit `2` rather than a partial taxonomy, so a client never receives a page that under-describes the served topics.
- **Residual risk.** A same-user process can interfere with durable state, as in the delivered trust model; and a client that never repolls on a discontinuity builds on an ordering it was not promised — a client defect the contract names explicitly.

## 22. MAINTENANCE & OPERATIONS IMPACT

- **New operator and integrator surface.** `<binary> events list [--json]` and `<binary> events describe <topic> [--json]`, with help for the family and both verbs.
- **Runbook.** Read `events list` once per integration to pin the version and the topic set; read `events describe <topic>` to write the handler for one topic; treat a sequence discontinuity or `overflow: "repoll"` as "repoll and continue from a fresh baseline".
- **Operational interpretation.** A quiet event topic means no durable change was observed, not that the daemon is down; a degraded frame means this subscription overflowed and this client must repoll; `emitted: false` means the kind is declared for a later producer and will not appear in v1.
- **Maintenance cost.** One authored declaration, one generated surface, one hand-authored emission projection pinned to the declaration by named comparisons, and one test suite per topic. Adding, renaming, or removing a kind, changing an ordering rule, an overflow policy, or a parentage is a taxonomy version change with its own tests; adding a payload field is additive inside v1. Changing envelope nullability — adding a nullable `lane`, or a nullable `ref` on a topic where v1 declares none — is likewise a version change, never a v1 edit: v1's envelope nullability is fixed per topic. That friction is the point of the pin.
- **State growth.** None. The classification projects; it persists nothing, and the per-`(topic, lane, source family)` watermark (DM-9) lives in the daemon's memory, not in the store, bounded by lanes × source families rather than by records.
- **Cost model.** One whole-store read per publish tick, shared by the snapshot and event projections, so adding a topic or a subscriber adds no read. The heartbeat's own two-ledger fold is outside that count and unchanged: a heartbeat loop iteration still reads the store for its heartbeat facts before the publish runs, and an operator sizing daemon cost must count both. The added cost is the taxonomy's fold over the view the tick already holds, bounded by the declared added-latency budget (NFR-2).
- **Failure handling.** A broken declaration fails closed at exit `2` and renders nothing; an unreadable source ledger degrades that topic's projection for that publish tick (no event, retried on the next publish tick) rather than failing the daemon loop or publishing a partial event.

## 23. GLOSSARY

| Term | Definition |
|---|---|
| Event taxonomy | The published contract this change delivers: the six-topic set, each topic's shape, kinds, payload fields, lane rule, ordering, overflow policy, and the taxonomy version. |
| Snapshot topic | A delivered topic whose frame is `{topic, cursor, snapshot}` and whose publish rule is snapshot-diff: `queue` and `lanes`. Declares no kind (`kinds: []`) and the ordering value `snapshot-revision`. |
| Event topic | A topic whose frame carries the change envelope: `queue.graph`, `dispatch.attempt`, `phase.state`, `blockers.state`. Declares its kinds, payload fields, and `sequence-per-lane`. |
| Event envelope | The eight `data` fields on every event-topic frame: the seven change fields (`topic`, `kind`, `lane`, `ref`, `sequence`, `occurredAt`, `payload`) plus the `taxonomyVersion` stamp. `lane` is always a non-empty string; `ref` is nullable only on `blockers.state`. |
| Kind | The change class within a topic. Its identity is `(topic, kind)`; `kind` is not globally unique. |
| Emitted kind | A declared kind a v1 path can produce. `queue.graph.remove` is declared and not emitted in v1. |
| Attempt token | The `token` field of the `dispatch.attempt` `refused` and `completed` payloads: the attempt record's closed-vocabulary delivery result token (`merged`, `blocked`, `pr-open`, `pr-open-unverified`, `failed`, `finished`, `max-restarts`, `state-unverified`, `partial`, `noop-lane-permission`, `noop-lane-nothing-to-do`), already durable in the attempt record and readable on the `attempts` read side. A corroboration identifier — the only `token` the taxonomy publishes, and never a credential (NFR-10). |
| Sequence | A positive integer, allocated once per emitted event per `(topic, lane)` at emission, shared by every subscriber, increasing by one per event, process-scoped. The only ordering guarantee. |
| Lane | The ordering group of a subject: the entry ref, the delivery ref, the change ref, or the question record's lane. Always a non-empty string on a v1 event topic; a future topic whose source can lack one must declare a nullable `lane` in its own version. |
| Ref (envelope) | The subject identity. Present on every event frame; a non-empty string on `queue.graph`, `dispatch.attempt`, and `phase.state`, and the question record's `string \| null` on `blockers.state`, where the shipped publish path records `null`. |
| Emission watermark | The per-`(topic, lane, source family)` identity of the last emitted source record: a record key plus its position in the view, or — for `phase.state`, whose record is one cumulative artifact per change — the artifact key plus the position of the last emitted transition inside that artifact's history. It keeps an unemitted delta pending instead of dropping or buffering it, and its size is bounded by lanes × source families, not by records. |
| Gap | A non-contiguous successor sequence for a lane (a jump, a decrease, or a restart). The only correct response is a repoll. |
| Overflow-to-repoll | The delivered slow-consumer outcome: one `degraded` event carrying `subscriber-overflow` and `overflow: "repoll"`, that subscription dropped, the client repolls. |
| Snapshot revision (`cursor`) | The delivered per-topic counter that advances when a snapshot topic's content changes. Not an ordering signal and absent from event frames. |
| Taxonomy version | `v1`. Pinned per topic: the reference surface is generated from the declaration, the hand-authored emission projection is pinned to it by the bidirectional emitted-kind-set pin and an exact per-kind emitted-payload-key comparison, and ordering and overflow are pinned at declaration and surface level because no event frame carries them. The pin is a comparison a named test runs: drift in either direction fails a named test rather than being impossible by construction. A kind, ordering, overflow, envelope, or parentage change is a new version. |
| Reference surface | `events list` / `events describe <topic>`, generated from the declaration, readable as text or as the machine envelope. |
| Extension path | S17's stop, parked, resumed, and park-edge shapes, which arrive as a taxonomy version change, not as an in-place edit. |

- **Approach.** The ticket's three acceptance criteria are turned into capabilities and 38 acceptance criteria, each with an observable (a frame field, a reference-surface key, a declared value, an identity, an exit code, or a guard result). `TDR-0025`'s DC-1..DC-5 are adopted as DEC-A..DEC-E and mapped one-to-one in Appendix B. The decisions the record leaves open are resolved rather than deferred: the snapshot-topic kind treatment (DEC-B), the overflow carriage (DEC-C), the sequence scope and restart behaviour (DEC-D, DEC-I), the version-stamp carriage (DEC-G), event-topic subscription semantics (DEC-H), the per-kind source mapping with its two declared gaps (DEC-J), the reference-record key set (DEC-K), the unknown-topic identity and the acceptance-to-refusal change (DEC-L), the taxonomy-integrity rule (DEC-M), the shared tick read (DEC-N), and the payload bound in place of a truncation marker (DEC-O).
- **Contradictions resolved in this specification.** (1) The planning reference page prints `queue.graph` with 6 kinds and `dispatch.attempt` with 4 and gives `dispatch.attempt` the stop/parked/resumed kinds, while the contract section enumerates 4 and 3 and assigns those shapes to S17; DEC-A names the contract section the authority, the page's example counts are recorded as non-governing, and the reconciliation is scheduled in §16. (2) The same page shows `queue` with 4 kinds and `lanes` with 3, which would require inventing kind sets for two delivered snapshot topics; DEC-B declares them snapshot topics with no kind (`kinds: []`) and records the page's counts as pre-contract text. (3) SC-M2-S13-02 asserts `data.overflow == "repoll"` while the delivered degraded frame carries only `degraded: "subscriber-overflow"`; DEC-C keeps the delivered marker and adds the value, so both assertions hold. (4) SC-M2-S13-01 asserts a pinned `data.taxonomyVersion` on received events while the contract's envelope names seven fields and no version; DEC-G stamps the version on the frame outside `payload`, so the scenario's literal reading holds without changing the seven contract fields. (5) The contract enumerates a `remove` kind while no delivered path removes a queue entry; DEC-J declares the kind and marks it `emitted: false` rather than silently claiming a producer. (6) The contract enumerates a `began` kind while no delivered path records a phase begin; DEC-J derives it from the first completion and states the derivation, rather than adding a record kind. (7) The delivered subscribe handler accepts a topic outside the closed set and serves the `lanes` snapshot under the requested name; DEC-L turns that into a classified refusal with one identity across both surfaces, and §8.5 and §18 disclose the client-visible consequence. (8) The record's DC-2 names an injected-clock `occurredAt` and a durable-revision `sequence`, and its Problem Frame excludes new error identities while DC-4 declares three; DEC-D, DEC-I and the §15 closing note state the governing semantics and route the amendment to `@decision-advisor`.
