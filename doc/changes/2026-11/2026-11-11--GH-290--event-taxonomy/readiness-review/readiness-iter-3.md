## New blocking findings

Both are `test_planning` findings of the same class — an NFR bound applied to an output NFR-1 does not cover — and both are pre-existing, not introduced by the iteration-2 remediation. They are blocking because each sits in a phase gate and no implementation can make the assertion true as written.

### RF-14 [major] — TC-EVT-011 asserts the 40-line / 8 192-byte human bound on pretty-printed JSON, which no six-topic envelope can meet

**Facet:** cross_artifact_consistency
**Artifacts:** `chg-GH-290-test-plan.md` TC-EVT-011 step 6 (`:501`); contradicts `chg-GH-290-spec.md` NFR-1 (`:445`) and AC-F2-2 (`:598`), and contradicts TC-EVT-080 step 3 (`:1484`) inside the same document.

**Gap:** TC-EVT-011 is the `events list --json` case. Step 6 says "Assert the out-of-band bounds: ≤ 40 lines / 8 192 bytes when pretty-printed with `--pretty`". `--pretty` is the delivered global flag that indents machine output (`packages/cli/src/help.ts:45`, `index.ts:236,349`), so the assertion applies to a pretty-printed six-topic envelope carrying 13 kind records and their `payloadFields` — an order of magnitude more than 40 lines. NFR-1 and AC-F2-2 scope that bound to "the human page"; TC-EVT-080 step 3 already states the correct split ("text ≤ 40 lines and ≤ 8 192 bytes … `--json` … ≤ 65 536 when pretty-printed"). Two cases therefore demand incompatible ceilings for the same output.

**Suggested remediation target phase:** `test_planning`
**Suggested fix:** delete the 40-line/8 192-byte claim from TC-EVT-011 step 6 and assert only the machine-envelope bound TC-EVT-080 step 3 already declares (compact ≤ 8 192 bytes, pretty ≤ 65 536 bytes), or drop the bound from the `--json` case entirely because NFR-1 does not cover it.

### RF-15 [major] — TC-EVT-061 asserts "every page ≤ 40 lines", which the delivered root `--help` already violates at 45 lines

**Facet:** cross_artifact_consistency
**Artifacts:** `chg-GH-290-test-plan.md` TC-EVT-061 step 6 (`:1186`) and step 1 (`:1181`); contradicts `chg-GH-290-spec.md` NFR-1 (`:445`) and the delivered tree.

**Gap:** TC-EVT-061 step 1 renders root `--help`; step 6 then asserts "**every** page is ≤ 40 lines / 8 192 bytes". Measured on this tree, root `--help` renders **45 lines** with the delivered 18 family rows (and will render 46 after the mount), so the assertion fails before `events` exists. NFR-1 bounds the *reference surface* output (`events list` / `events describe`), not root help or family help pages, and the delivered mount precedent for a family help page is a different bound: `tests/behaviour/daemon-mount-help.test.ts:181-188` asserts `≤ 4 000` bytes and `≤ 120` lines for every `daemon` help entry. As written the Phase-5 gate cannot go green, and the only in-delivery escape is the assertion change the plan's own escalation trigger reserves ("a delivered suite needs a semantic assertion change outside the mount rows").

**Suggested remediation target phase:** `test_planning`
**Suggested fix:** scope the bound explicitly — assert root `--help` by content (nineteen rows, no reorder/removal of the delivered eighteen) and apply the delivered family-page convention (`≤ 120` lines / `≤ 4 000` bytes, GH-286 precedent) to `events --help`/verb pages; keep the 40-line/8 192-byte bound only where NFR-1 declares it (`events list` / `events describe` text output).

**Owning author:** `@test-plan-writer` (both). **Do not reopen `delivery`.**

## Independent judgement — the M2 page's unguarded items (the residual the plan author flagged)

**Question:** the reference-record key set and the `Delivered (M2-S13)` status line are Phase-5 page obligations with **no token scan** (the plan binds only `event-taxonomy-conformance` for the counts, the S17 heading, and the `restart`/`repoll` tokens). Is that a blocking gap, a recorded advisory, or acceptable under GAP-T6?

**Judgement: acceptable under GAP-T6, as a recorded advisory — not a blocker.** Four reasons:

1. **The obligation is declared, not implicit.** Plan Phase 5 names the exact key set, the exact status line, the exact heading, and the review item (`plan.yaml:576-604`); spec §16 (`:570`) carries the same content. RF-13's defect was that these two items were missing from the plan; that is fixed. What remains is only the *proof mechanism*.
2. **GAP-T6 is the change's declared boundary, and it names owners.** `test-plan.md:58` states that the page's every sentence is not proved mechanically, that the reconciliation claim is review-attested by `@doc-syncer` and `@reviewer`, and TC-EVT-002's Notes (`:323`) repeat it. Prose truth of a planning-corpus page is a review property in this system's test strategy (`.ai/rules/testing-strategy.md` assigns diff-shape/prose claims to review), not a permanent-suite property.
3. **The machine contract the page describes is mechanically pinned.** The key set is asserted on the *surface itself* (TC-EVT-011 step 4 key-set equality, TC-EVT-013 list/describe equality, TC-EVT-016 per-kind payload/union derivation, TC-EVT-051 snapshot-record shape), and the counts/S17 boundary/ordering tokens are asserted on the page (TC-EVT-002, TC-EVT-032). A page that advertises a surface the code does not serve therefore contradicts tests that already exist — the residual risk is a **stale page**, not an unverified contract.
4. **The harm is bounded and reversible.** A wrong page misleads a reader; it cannot change a frame, a topic, an exit code, or a stored record, and Phase 8's doc corpus pass and the PR review read the same page again.

**Residual risk (named):** the page could ship with the old `topics[]` table or the `Proposed (M2)` line while every automated gate is green. That is a documentation-truth risk, and it is the one item in this change whose only guard is a human reading it.

**Recommended cheap hardening (optional, not a gate):** add to `tests/checks/event-taxonomy-conformance.test.ts` (Phase 6, already owned by TC-EVT-002/032) two exact-token assertions — `Delivered (M2-S13)` present and `Proposed (M2)` absent, and the `OUTPUT` table naming `shape`, `frame`, and per-kind `emitted`. That is six lines against tokens the plan already pins, with no brittleness, and it converts the last review-attested item into a mechanical one. If `@pm` prefers to carry it as an accepted residual, record it in `pm-notes` with `@doc-syncer`/`@reviewer` as owners; either way it does not reopen `delivery_planning`.
