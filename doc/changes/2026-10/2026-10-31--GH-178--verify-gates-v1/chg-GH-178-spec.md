# CHANGE SPECIFICATION

> **PURPOSE**: Replace the manual merge checklist with one read-only command that evaluates the five M0 merge gates, gives every verdict a bounded citation, and makes a red pipeline, a missing CI job, a vacuous green pipeline, a stale local head, an unanswered owner ask, or an unsafe squash preflight fail loudly instead of slipping through a near-miss.

## 1. SUMMARY

This change delivers M0-S9 `verify gates v1`: one read-only command that answers whether a delivered change is merge-ready under the M0 gate battery. The command is `verify gates <changeRef>`. The change ref selects the committed pm-notes ledger and the tracker work item; the current checkout identifies the delivery branch. There is no PR-number argument in v1. The command evaluates exactly five gates in a fixed order: `lifecycle-finalization`, `ci-green`, `push-parity`, `owner-gate`, and `squash-preflight`.

Each gate returns one verdict from `pass`, `fail`, and `unknown`, plus a bounded citation naming its source, outcome, identity (change ref, branch, work item, delivery request, SHA), and counts or job names. The overall result passes only when all five gates pass. A gate never passes on a failed, absent, unresolved, or unattempted read. A red pipeline, a missing expected job, a pipeline with zero runs or only skipped runs, a local/remote SHA mismatch, an owner-attention label, a wrong integration base, a draft or closed PR, a conflicting or unknown mergeability, or an empty commit/change surface fails the relevant gate. The three ticket acceptance cases — red pipeline, missing job, and vacuous green — are explicit gates and explicit fixtures, not side effects.

The command composes the delivered `verify change` ledger verifier rather than duplicating it, reuses the status digest's owner-attention contract and CI result semantics, and reuses the provider client read slice. It adds two additive `verify` error rows: `verify.gates.failed` (user-validation, exit `1`) and `verify.gates.unavailable` (platform-provider, exit `2`). It adds optional gate facts to the `DeliveryRequest` primitive — source head SHA, mergeability, commit count, and changed-file count — with absence meaning unknown, never mergeable and never non-empty. It performs no write, fence, mutation, merge, auto-merge, or child process, and reads at most one bounded page per provider source. Target resolution is one deterministic open-PR rule shared by push parity and squash, and a definitive HTTP 404 absence is distinguished from a read failure: an absent work item or open-PR list is a gate failure, a resolved PR whose detail read returns 404 is `head-unresolved` for every detail-consuming gate, and a check-run 404 is `unknown` `read-failed` with source outcome `absent`.

### 2.2 Pain Points / Gaps

- **Manual merge checklist:** the coordinator inspects lifecycle state, CI, local/remote head equality, owner labels, and PR base/draft/mergeability by hand, costing roughly ten minutes per merge and producing inconsistent evidence.
- **Near-miss classes:** a red pipeline can be read from the wrong commit; a green-looking check-run set can omit a required job; a pipeline with zero jobs or only skipped jobs can look green; a stale local checkout can be merged over; an owner question can be missed; and a PR can target the wrong base, be a draft, conflict, or carry no real change.
- **Vacuous green:** the current status classifier already treats no runs and all-skipped as `none`, not green, but there is no merge gate that turns that classification into a merge decision. The retrospective concept names this exact class.
- **No cited verdict:** `verify change` is ledger-only; status is a digest, not a verdict; the manual checklist leaves no deterministic, machine-readable citation per gate.
- **No expected job set:** a green check-run page cannot reveal a job that never reported. Without a declared expected set, a missing job is invisible.
- **No push-parity fact:** `DeliveryRequest` has no source head SHA, so local HEAD cannot be compared with the pushed branch head.
- **No squash-preflight fact:** `DeliveryRequest` has no mergeability or commit/change counts, so unknown mergeability can be mistaken for mergeable and an empty commit surface can pass.
- **No combined exit:** a partial manual checklist cannot produce one non-zero result with a stable failure identity and a per-gate evidence chain.
- **Ambiguous open-PR resolution:** a lone open request on a different branch can look like no PR, and a full page cannot prove that the matching request is unique, so push parity and squash can disagree or pass on an ambiguous branch.
- **Absence flattened into read failure:** the read surface cannot distinguish a definitive HTTP 404 from a transport failure, so an absent work item or pull request can be misreported as `unknown`.
- **Lifecycle failure evidence is summary-only:** `classifyVerifyChange` exposes structured counts and missing phases only on success, so a gate that needs them on failure would have to parse a summary or duplicate the ledger rules.
- **Comment-based owner asks:** the GitHub read slice omits comment sets, so unanswered-comment detection cannot be delivered in this change. The owner-gate scan is label-based and has a declared limitation.

## 3. PROBLEM STATEMENT

Because merge readiness is assembled by hand from the ledger, CI, the local checkout, tracker labels, and PR metadata, and because those sources disagree about identity (checkout HEAD vs pushed head), completeness (a green page with a missing job), and vacuity (zero jobs or all-skipped), a coordinator cannot produce one trustworthy merge verdict: `verify change` is ledger-only and explicitly not sufficient for merge, status is a digest rather than a gate decision, and `DeliveryRequest` lacks the head/mergeability/change-surface facts the manual checklist uses. The result is a near-miss class in which a red pipeline, a missing job, a vacuous green, a stale local head, an unanswered owner ask, or an unsafe squash preflight can reach a merge, at a cost of roughly ten minutes of manual checking per merge and with no per-gate citation.

## 4. GOALS

- **G-1**: One read-only command, `verify gates <changeRef>`, that evaluates every M0 merge gate and returns one verdict.
- **G-2**: Exactly five gates in a fixed order: `lifecycle-finalization`, `ci-green`, `push-parity`, `owner-gate`, `squash-preflight`.
- **G-3**: Non-vacuous pass guarantee: no gate passes on a failed, absent, unresolved, unattempted, zero-run, all-skipped, missing-job, missing-SHA, missing-PR, or unknown-mergeability input.
- **G-4**: A citation layer: every gate verdict names its evidence source, outcome, identity/ref/SHA, and counts or job names.
- **G-5**: Consume one pure structured ledger evaluation for lifecycle finalization against the declared full or LITE variant, with `classifyVerifyChange` retained as a behavior-preserving wrapper, rather than duplicating the ledger verifier or parsing a summary.
- **G-6**: CI green on the pushed commit, with a declared expected job set and explicit red, pending, canceled, no-run, all-skipped, missing-job, invalid-expected-set, and truncated-page outcomes.
- **G-7**: Push parity between the local checkout HEAD and the delivery request head SHA for the same branch, using one deterministic open-PR resolution rule that fails closed on ambiguity.
- **G-8**: Owner-gate scan over the owner-attention contract on the work item, matching status-digest semantics.
- **G-9**: Squash preflight over the integration base, open/non-draft state, mergeability, and non-vacuous commit/change surface.
- **G-10**: One overall verdict and one exit contract: all-pass `0`; definitive gate failure `1`; platform/provider evidence failure `2`; user-category credential failure `1`.
- **G-11**: Read-only, bounded, deterministic, tier-compliant, brand-neutral execution with no new package, subpath, runtime-API location, or dependency.
- **G-12**: Current-truth documentation that makes the gate battery, its limitations, and its failure semantics durable.

### 5.1 Capability Details

- **F-1 — Command surface and target resolution.** `verify` remains a top-level command. Its subcommand set becomes exactly `change` and `gates`; each takes exactly one non-empty change ref, and there are no command-specific flags. Both subcommands are exposed by one `verify` command definition: `createVerifyCommandDefinition` accepts a combined runtime in which `VerifyCommandRuntime` gains an optional `gates` member (or an equivalent combined runtime type) holding the gates reads, and dispatches on the first positional (`change` or `gates`) after grammar validation; `ConfigProgramOptions.verify` remains the single option and is typed to that combined runtime, and the CLI edge composes the existing change runtime plus the gates runtime. `verify gates <changeRef>` validates grammar before any read; a wrong subcommand or a missing/empty ref is a handler grammar failure (`input.value.rejected`), while a third positional or an unknown flag is a parser failure (`fallback.invocation`); neither reads a source. The change ref selects the committed pm-notes ledger, the verified phase registry, and the tracker work item. The current checkout selects the delivery branch: an attached HEAD branch is the branch under test; a detached HEAD is a gate failure for every branch-dependent gate, never a vacuous pass. The open delivery request is resolved by the one deterministic open-PR resolution rule declared in F-5 and DM-13, shared verbatim by push parity and squash preflight; no PR number is accepted in v1. All five gates are evaluated independently in the fixed order, with no short-circuit, so the report is complete and every gate carries a citation.
- **F-2 — Lifecycle-finalization gate.** The gate consumes one pure structured ledger evaluation over the same pm-notes declaration and verified `phase.transition` history, including the full/LITE variant required set and per-phase registry-over-declaration precedence. The evaluation contract is `EvaluateVerifyChange` → `VerifyLedgerEvaluation` (DM-15): it returns the effective variant, outcome, required/completed/missing phase ids, declaration counts, and registry evidence whenever the document was classified (finished, partial, or state-unverified), and the empty/zero phase shape with a document-failure identity when a terminal document failure prevents phase evaluation, derived from the same rules as `classifyVerifyChange`. `classifyVerifyChange` keeps its existing success/failure shape by wrapping that evaluator, so `verify change` is behaviorally unchanged and the ledger rules live in one place. `finished` maps to `pass`; `partial`, malformed notes, and a missing target map to `fail` with the underlying `verify.ledger.incomplete` or `lint.*` code; a platform- or user-category registry/store failure maps to `unknown` with the underlying `state.*` code; the overall unknown reuses that code. The citation carries the effective variant, required/completed/missing counts from the evaluator, bounded missing phase ids in required-set order, unique registry record/transition/overlay counts from the same evaluation, and the underlying code when present. The gate never derives any count or phase id by parsing the human-readable summary.
- **F-3 — CI-green gate.** The target is the delivery request's source head SHA (the pushed commit), not the local checkout. The gate reads one bounded check-runs page for that SHA at `VERIFY_GATES_CI_RUN_LIMIT` (100) with no pagination, and combines it with the expected job set (F-4). It passes only when the expected set is valid, the page was read, the page is not at the read limit, at least one run is present, at least one expected job's effective state is `succeeded`, no run failed/canceled/is running/queued, and every expected job is present. It fails on a red run (`ci-failed`), pending run (`ci-pending`), canceled run (`ci-canceled`), zero runs or zero jobs (`ci-no-runs`), every expected job skipped with no expected job succeeded (`ci-all-skipped`), one or more missing expected jobs (`ci-missing-jobs`), an unreadable/empty/duplicate/over-cap expected set (`ci-expected-jobs-invalid`), or an unresolved head SHA (`head-unresolved`). A page returned at the declared read limit is `unknown` (`ci-truncated`), because a hidden failing run or a hidden missing job cannot be excluded. The check-run classification aligns with the status digest's `STATUS_CI_RESULTS` semantics: `none` is never green, and all-skipped is never green. The gate depends on the resolved delivery request detail for its head SHA. When the open-PR list resolves a match but the detail read then returns HTTP 404 (`provider.not-found`), the detail source outcome is `absent` and the gate is `fail` `head-unresolved`, because the pushed head can no longer be resolved; a detail 404 is never a generic `unknown`. Any non-404 detail read failure (transport, non-404 non-2xx, credential, or binding) is `unknown` (`read-failed`, `credential-unavailable`, or `address-unresolved`). A check-run read that returns HTTP 404 is a definitive absence for that read: source outcome `absent`, gate verdict `unknown`, reason `read-failed`, because the commit may not be pushed to the remote yet; it is neither `failed` nor `ci-no-runs` and never passes. Any other check-run read failure is `unknown` (`read-failed`, `credential-unavailable`, or `address-unresolved`).
- **F-4 — Expected-job-set read.** The runtime edge reads the repository's declared CI workflow at `VERIFY_GATES_CI_WORKFLOW_PATH` (default `.github/workflows/ci.yml`) with a bounded YAML read, extracts the top-level `jobs` map in declaration order, and uses each job's display `name` when present, otherwise the job id, as the expected check-run name. The set must be non-empty, unique by exact name, at most `VERIFY_GATES_MAX_EXPECTED_JOBS` (200), and each name at most `VERIFY_GATES_MAX_EXPECTED_JOB_NAME_CHARS` (120). A missing, unreadable, malformed, empty, duplicate, over-cap, or over-long set fails the CI gate (`ci-expected-jobs-invalid`); the gate never falls back to the observed run names, because that would make a missing job undetectable. This is job presence, not suite-to-job mapping: matrix-expanded names and job-level `if` conditions are not evaluated; a job that does not report a check run is reported missing (a safe false fail, never a false pass), while a job that reports a skipped check run is present but not a success. The expected set is read from the checkout; a local/pushed divergence is caught independently by push parity, so it cannot turn the overall result into a pass.
- **F-5 — Push-parity gate.** The gate compares the current checkout HEAD SHA with the delivery request's source head SHA for the same branch. Target resolution is one deterministic open-PR rule shared verbatim with F-7: a detached HEAD is `branch-unresolved` before any PR read; otherwise the gate reads exactly one bounded open-PR page at `VERIFY_GATES_OPEN_PR_LIMIT` (100) with no pagination; if the raw page size is at that limit, the result is `ambiguous-open-pr` regardless of whether a match is present, because uniqueness cannot be proven; otherwise count the open requests and the requests whose `sourceRef` exactly equals the checkout branch; exactly one match is the target; more than one match is `ambiguous-open-pr`; zero matches with zero open requests is `no-open-pr`; and zero matches with at least one open request is `branch-mismatch`. It passes only when HEAD is attached to a non-empty branch, exactly one open delivery request matches that branch, the request's `sourceRef` equals the branch, the request's `sourceHeadSha` is a full 40- or 64-hex SHA, and the two SHAs are equal (case-insensitive hex comparison). A detached HEAD (`branch-unresolved`), a page at the limit (`ambiguous-open-pr`), multiple matching requests (`ambiguous-open-pr`), zero open requests (`no-open-pr`), zero matches among one or more open requests (`branch-mismatch`), a missing/invalid remote head (`head-unresolved`), or a SHA mismatch (`parity-mismatched`) is `fail`. A PR list/detail read failure other than a definitive HTTP 404 is `unknown` (`read-failed`, `credential-unavailable`, or `address-unresolved`). A 404 is definitive absence: an absent list is `fail` `no-open-pr`; a detail 404 after a resolved match is `fail` `head-unresolved` with source outcome `absent`, because the pushed head can no longer be resolved; neither is a generic `unknown`. The citation carries the branch, both full SHAs, and the PR number; the human line shows short SHAs.
- **F-6 — Owner-gate scan.** The gate reads the work item for the change ref and matches its labels against `STATUS_OWNER_ATTENTION_LABELS` (`hand-back`, `human-input-needed`), case-insensitively, reusing the delivered status-digest contract rather than declaring a second label set. No matching label is `pass` (`owner-gate-absent`); one or more matching labels is `fail` (`owner-gate-present`) with the matched labels cited in contract order. A malformed or non-numeric work-item identity (for example, `GH-abc`) is a `fail` (`ticket-unresolved`) with source outcome `unresolved`, never `read-failed`; a valid numeric identity whose read receives HTTP 404 (`provider.not-found`) is definitively absent and is also a `fail` (`ticket-unresolved`) with source outcome `absent`. Absence is not a read failure; transport failures, non-404 non-2xx responses, credential failures, and an unresolved repository binding are `unknown` (`read-failed`, `credential-unavailable`, or `address-unresolved`), with `failed` or `not-attempted` source outcome as applicable. The gate's declared signal is labels; it does not add a work-item delivery-status condition in v1, and unanswered comments are not read (ADR-0006), so comment-based asks are a declared limitation and a residual risk, not an implicit pass claim.
- **F-7 — Squash-preflight gate.** The gate uses the same resolved delivery request detail as F-5, including the same deterministic open-PR resolution rule (DM-13): a raw open-PR page at `VERIFY_GATES_OPEN_PR_LIMIT` is `ambiguous-open-pr` even when a match is present; zero matches among one or more open requests is `branch-mismatch`; zero open requests is `no-open-pr`. It passes only when the request is open (review state `open`, `approved`, or `changes-requested`), not draft, targets `VERIFY_GATES_INTEGRATION_BASE` (`main-tools`), reports `mergeableState: "mergeable"`, and carries a non-vacuous change surface: `commitCount > 0` and `changedFileCount > 0`. It fails on `merged`/`closed` (`squash-not-open`), `draft` (`squash-draft`), a different base (`squash-target-mismatch`), `conflicting` (`squash-conflicting`), `not-mergeable` (`squash-not-mergeable`), `unknown`/absent mergeability (`squash-mergeability-unknown`), zero commits (`squash-no-commits`), zero changed files (`squash-no-changes`), absent counts (`squash-surface-unknown`), or a failed open-PR resolution (`branch-unresolved`, `no-open-pr`, `branch-mismatch`, `ambiguous-open-pr`). A PR list/detail read failure other than a definitive HTTP 404 is `unknown` (`read-failed`, `credential-unavailable`, or `address-unresolved`). A 404 is definitive absence: an absent list is `fail` `no-open-pr`; a detail 404 after a resolved match is `fail` `head-unresolved` with source outcome `absent`, because the pushed head can no longer be resolved and the detail carries the mergeability/surface facts; neither is a generic `unknown`. Unknown mergeability is never mergeable. Every squash citation on pass and on every condition failure where the detail was read successfully carries a `squash-signals` name list with exactly two distinct, ordered tokens: `draft=<true|false>` then `mergeable=<mergeable|conflicting|not-mergeable|unknown>`, derived from the same request detail used for the verdict; the reason still names the failed condition. Where no usable delivery-request detail was read — a resolution failure such as `branch-unresolved`, `no-open-pr`, `branch-mismatch`, or `ambiguous-open-pr`; a detail 404 (source outcome `absent`); or a failed detail read (source outcome `failed`) — the list is empty rather than fabricated or defaulted, the `commits`/`changedFiles` counts are omitted as unknown (never zero), and the citation's source outcome and reason name the cause. Whenever a detail was read successfully, the list is always present with its two ordered tokens, including on every condition failure. Emptiness on these unread/unusable-detail paths is not a citation-completeness violation because the citation still carries at least one source and at least one reason. Review approval is not part of v1; human review and branch protection remain external.
- **F-8 — Citation layer.** Every gate emits a citation with up to three ordered sources, an identity record, ordered counts, up to three bounded name lists with omitted counts, and up to four closed reasons. Sources are drawn from `pm-notes`, `delivery-registry`, `repository-ci-workflow`, `github-check-runs`, `repository-head`, `github-work-item`, `github-delivery-request-list`, and `github-delivery-request-detail`. Source outcomes are `read`, `observed-empty`, `failed`, `absent`, `unresolved`, and `not-attempted`; a failed source may carry an existing error-table `failureCode`. `failureClass` is optional and, when present, is one of the declared read-result codes (`provider.payload.invalid`, `provider.not-found`), never free-form provider text; a read that carries an error-table code uses `failureCode` and omits `failureClass`. A definitive HTTP 404 on any read is cited as source outcome `absent`, not `failed`, whatever the gate verdict: an absent work item or pull request fails, while a check-run 404 is `unknown` `read-failed` with source outcome `absent`. Counts and names are contract-defined per gate; name kinds are the closed set `missing-phases`, `missing-jobs`, `failed-jobs`, `pending-jobs`, `owner-labels`, and `squash-signals`; names are de-duplicated, ordered (missing jobs and missing phases in expected-set order, failed/pending jobs lexicographically, owner labels in contract order, squash signals `draft` then `mergeable` in fixed order), capped at `VERIFY_GATES_MAX_CITATION_NAMES` (8) per list with an `omitted` count, and clamped to `VERIFY_GATES_MAX_NAME_CHARS` (120). A `squash-signals` value is a `key=value` token in the fixed order and value domain declared for that kind. A citation never carries raw provider payloads, response bodies, titles, comment bodies, commit messages, file contents, credentials, or arbitrary messages. Every citation always has at least one source and at least one closed reason; an empty citation (no source or no reason) is a contract violation, never a valid degenerate case. A gate with no usable evidence still carries a citation whose source outcome is `failed`, `absent`, `unresolved`, or `not-attempted` and whose reason names why the gate did not pass. Counts and name lists may be empty when the gate could not obtain usable evidence for them — when the dependent source outcome is `failed`, `absent`, or `not-attempted`, or when no detail was read; the reason names that cause, and such an empty counts/names set is not a citation-completeness violation. A squash `squash-signals` list is empty only when no usable delivery-request detail was read (`failed`, `absent`, or `not-attempted`); a detail 404 is `absent` and a failed detail read is `failed`, and on both paths the list and the `commits`/`changedFiles` counts are empty (unknown, not zero) while the citation's source and reason satisfy completeness. Whenever a detail was read successfully, the list always carries the two ordered tokens.
- **F-9 — Overall verdict, identities, and exits.** The overall result is `pass` only when all five gates are `pass`; `fail` when any gate is `fail`; `unknown` when no gate is `fail` and at least one is `unknown`. Unknown never passes. A success envelope is emitted only for `pass`, with the structured report as `data` and exit `0`. An overall `fail` emits an error-only envelope with the new `verify.gates.failed` identity, exit `1`, regardless of any coexisting `unknown` gate. An overall `unknown` emits an error-only envelope: if the first unknown gate in fixed order carries a `failureCode` that resolves to an error-table entry, that entry is reused with its declared domain kind and code (preserving its projection class and exit, for example `config.credential.missing` → `1` or `state.store.torn` → `2`); otherwise the new `verify.gates.unavailable` identity is used with exit `2`. Handler grammar uses `input.value.rejected`; parser failures use `fallback.invocation`. Envelope exclusivity is preserved: no failure carries `data`, no success carries `error`, and no exit leaves `{0, 1, 2}`.
- **F-10 — Machine and human output.** On success, `--json` returns exactly one `CommandResult` envelope whose `data` is the full `delivery.verify-gates.v1` report: schema version, change ref, target `gates`, overall `pass`, summary counts, and exactly five gate records in fixed order, each with `id`, `verdict`, `reason`, and `citation`. The `CommandDefinition.humanText` hook contract is widened additively to return `string | undefined`, where `undefined` means "no custom human text — fall through to the existing `humanSuccess`/`humanJson` path". The single `verify` command definition gains one `humanText` hook that dispatches on the success payload's `target`: when `data.target === "gates"` it returns the deterministic six-line gates report (header plus one line per gate) with the key identities, sources, and counts; for every other target it returns `undefined`, so `runCli` falls through to the delivered `humanSuccess`/`humanJson` path. `verify change` therefore does not use `humanText`: it keeps the pre-change redact-then-serialize pipeline, where the data object is redacted before it is serialized, so its output stays byte-identical to today, including for secrets whose raw form is not a contiguous substring of their JSON-escaped form. Gates uses `humanText` — and therefore string redaction of the rendered report — because its six-line report carries no raw payloads, titles, or free-form provider text. `humanSuccess: true` may remain on the definition, and a defined `humanText` result takes precedence; only `verify gates` renders the six-line report. On failure, the envelope carries no `data`; the error `summary` is a deterministic, bounded, multi-line citation block with one header line and exactly one line per gate, preserving each gate's verdict, reason, source outcome(s), identity/ref, and the `counts` and `names` segments. This is the failure-mode machine evidence channel and does not change the envelope shape. No timestamps, LLM prose, raw payloads, titles, or secrets appear in either mode.
- **F-11 — Read-only composition and credential/network semantics.** The command performs zero writes, fences, state mutations, merge attempts, auto-merge attempts, network writes, and child processes. An unresolved repository binding makes every provider-backed gate `unknown` with `address-unresolved` before any client call. The runtime composition admits only a GitHub VCS instance whose auth mechanism is `credential-reference`; an anonymous or otherwise configured instance withholds the GitHub reads and makes every provider-backed gate `unknown` with `credential-unavailable` and `failureCode: config.credential.missing`, while the local lifecycle gate is still evaluated. A credential-resolution failure reuses `config.credential.missing` (user-validation, exit `1`). A transport failure or a non-404 non-2xx response makes the affected gate `unknown` with `failureClass: provider.payload.invalid`; an HTTP 404 surfaces as the additive adapter-local `provider.not-found` and maps per the read-failure table in Section 8.3: work-item and PR-list absence are definitive gate failures, a resolved PR whose detail read 404s is `fail` `head-unresolved` for every detail-consuming gate, and check-run absence is `unknown` `read-failed` with source outcome `absent` because the commit may not be pushed yet. If no classified identity applies, the overall `unknown` uses `verify.gates.unavailable` (platform-provider, exit `2`). There are no retries and no pagination: one bounded read per source. A failed read is never a pass, and an unattempted dependent read is `not-attempted`, never a pass.
- **F-12 — Additive delivery-request gate facts.** `DeliveryRequest` gains four optional fields: `sourceHeadSha` (the full source-ref commit SHA at read time), `mergeableState` (`mergeable`, `conflicting`, `not-mergeable`, or `unknown`), `commitCount` (provider-asserted commits), and `changedFileCount` (provider-asserted changed files). The GitHub detail read populates them from the pull-request payload; the list read may populate `sourceHeadSha` but is not required to. The GitHub mapping is deterministic, in this precedence order: (1) `mergeable === false` (with a clean or dirty `mergeable_state`) or `mergeable_state === "dirty"` → `conflicting`; (2) `mergeable_state` in `blocked`, `behind`, `unstable`, or `draft` → `not-mergeable`, even when `mergeable === true`; (3) `mergeable_state` is `null`, absent, `computing`, or any unrecognized state and `mergeable !== true` → `unknown`; (4) `mergeable === true` with `mergeable_state` `clean` or absent → `mergeable`; (5) any remaining combination → `unknown`. Absence of any field means unknown, never mergeable and never a non-zero surface. A non-finite or negative `commitCount`/`changedFileCount` is treated as absent (unknown), never as a fabricated count. Other provider seeds may omit the fields; a gate over an omitting provider reports `unknown` or `fail` (`squash-surface-unknown`), never a fabricated value. The closed adapter-operation set, capability declaration, and GitHub subpath exports are unchanged.
- **F-13 — Deterministic contract, tier, and boundary placement.** Gate ids, order, verdicts, reasons, sources, outcomes, count names, name kinds, constants, and bounds are declared once as `as const` data in `core ./contracts`. The pure evaluator lives in `core ./domain`, imports contracts and the existing verify-change classifier only, and performs no I/O, clock, randomness, or ambient environment access. Runtime I/O stays in the already-admitted `adapters ./github`, `adapters ./repo`, and `adapters ./file` subpaths and the CLI edge. No new package, subpath, declared entrypoint, workspace edge, runtime-API location, or dependency is introduced. Ordering comes from contract arrays, never map iteration; identical injected facts produce identical report, summary, human text, and exit.
- **F-14 — Fixture and live evidence model.** The default suite uses a committed fixture corpus covering every gate, verdict, reason, the three ticket negative cases, push mismatch, owner-label presence, bad squash preflight, open-PR at-limit with and without a match, branch mismatch, 404 absence, credential/network failure, detached HEAD, no PR, invalid expected set, and truncation. A completeness meta-check requires every gate and every reason to have at least one fixture and fails by case name when a case is missing, stale, or asserts the wrong verdict. Trap payloads and catalog entries live under the existing catalog's required `tests/fixtures/providers/` location; behavioural fixtures live under `tests/fixtures/verify-gates/providers/...`. The default suite is fixture-driven with zero live calls; an opt-in live smoke asserts only structural invariants (five gates in order, citations present, bounds, no secrets, exit semantics) and never pins volatile counts.

## 6. USER & SYSTEM FLOWS

1. **All-pass flow.** The coordinator runs `verify gates GH-178`. The edge reads pm-notes and the verified registry, resolves the checkout branch and HEAD, reads the CI workflow job names, lists open delivery requests, reads the matching request detail, reads check runs for its head SHA, and reads the work item. All five gates pass; the success report cites each source and count; the command exits `0`.
2. **Red pipeline flow.** CI runs for the pushed head include a failed run. The CI gate fails `ci-failed`, cites the failed job names and counts, and the overall result is `fail` with `verify.gates.failed`, exit `1`. The other four gates still report their verdicts.
3. **Missing-job flow.** The check-run page is green but omits one expected workflow job. The CI gate fails `ci-missing-jobs`, cites the missing expected job names, and the overall result is `fail`, exit `1`. A green page alone never passes.
4. **Vacuous-green flow.** The check-runs read succeeds but reports zero runs, or no expected job succeeded while every expected job is skipped (including the case where an extra non-expected run succeeded). The CI gate fails `ci-no-runs` or `ci-all-skipped`, cites zero succeeded expected jobs and the observed/skipped counts, and the overall result is `fail`, exit `1`. A pipeline with zero jobs never ran and is never green.
5. **Push-mismatch flow.** The local HEAD differs from the delivery request head SHA. Push parity fails `parity-mismatched`, cites both SHAs and the branch, and the overall result is `fail`, exit `1`. CI may still be green on the pushed commit; the report shows both facts.
6. **Owner-gate flow.** The work item carries `hand-back` or `human-input-needed`. The owner gate fails `owner-gate-present`, cites the matched labels, and the overall result is `fail`, exit `1`.
7. **Bad-squash flow.** The PR targets `main`, is a draft, is closed, conflicts, reports unknown mergeability, or has zero commits/changed files. The squash gate fails with the matching reason and citation; the overall result is `fail`, exit `1`.
8. **Lifecycle-failure flow.** The declared variant's ledger is incomplete or the pm-notes document is malformed. The lifecycle gate fails with the reused `verify change` code; an incomplete ledger cites the ordered missing phases, while a malformed document or missing target cites empty phase arrays and zero declaration counts with the document failure identity. The overall result is `fail` with `verify.gates.failed`, exit `1`.
9. **Unavailable-evidence flow.** The GitHub credential is missing, the provider read fails, or the repository binding is unresolved. The provider-backed gates are `unknown`; the local lifecycle gate is still evaluated. With no definitive fail, the overall result is `unknown`; a credential failure reuses `config.credential.missing` (exit `1`) and an unclassified provider failure uses `verify.gates.unavailable` (exit `2`). No gate passes.
10. **Detached/no-match flow.** The checkout is detached, the open-PR page is empty, or it contains only non-matching requests. Branch-dependent gates fail (`branch-unresolved` without a PR read, or `no-open-pr`/`branch-mismatch` after the bounded list read); a page at `VERIFY_GATES_OPEN_PR_LIMIT` fails `ambiguous-open-pr`; the lifecycle and owner gates still run, and the overall result is `fail`, exit `1`.
11. **Invalid invocation flow.** `verify gates` with no ref, a third positional, an unknown flag, or an unknown subcommand is rejected before any read (`input.value.rejected` or `fallback.invocation`) with exit `1`; the report is not attempted.

## 7. SCOPE & BOUNDARIES

### 7.1 In Scope

- The `verify gates <changeRef>` command grammar, handler, and runtime composition.
- The five gate ids, fixed order, `pass`/`fail`/`unknown` verdict vocabulary, closed reason set, and per-gate evaluation rules.
- The `delivery.verify-gates.v1` report contract: overall result, summary counts, gate records, citation shape, bounds, and deterministic ordering.
- Lifecycle finalization by the pure structured `EvaluateVerifyChange`/`VerifyLedgerEvaluation`, with `classifyVerifyChange` retained as a behavior-preserving wrapper and registry overlay.
- CI green on the pushed commit, including the expected-job-set read, red/pending/canceled/no-run/all-skipped/missing-job/invalid-set/truncated outcomes, and bounded check-run reads.
- One deterministic open-PR resolution rule shared by push parity and squash, including the at-limit ambiguity and `branch-mismatch`.
- Push parity between the local checkout HEAD and the delivery request head SHA for the branch.
- Owner-gate scan over `STATUS_OWNER_ATTENTION_LABELS` on the open work item.
- Squash preflight over `main-tools`, open/non-draft state, mergeability, and commit/change surface.
- The citation layer, bounded failure summary, and human success report.
- Two additive `verify` error rows and their documented two-way table rows.
- The additive internal `provider.not-found` (HTTP 404) read-result kind and the read-specific absence mapping; no error-table row.
- The optional `DeliveryRequest` gate facts and the GitHub normalization/trap-catalog extension.
- One bounded CI-workflow read at the runtime edge and the repository HEAD facts reuse.
- Tests at structure, behaviour, golden, corpus, boundary, and check levels; an opt-in live smoke.
- The new current-truth feature spec, the documentation-impact reconciliation, and one minor changeset.

### 7.2 Out of Scope

- [OUT] Suite-to-job mapping, matrix expansion, reusable-workflow mapping, job-level `if` awareness, or a suite-level pass/fail roll-up (M2-S7).
- [OUT] Merge execution, squash execution, auto-merge, a merge-transaction command, or any post-merge verification (M1-S4).
- [OUT] Dispatch, watchdog, deploy verification, closeout, queue/lane engines, or a board/brief surface.
- [OUT] GitLab or Jira gate reads, a second provider binding, or new tracker/VCS/CI operations.
- [OUT] Any write: comments, labels, reviews, checks, merges, ticket creation, ticket transitions, state appends, fences, projection rebuilds, pm-notes writes.
- [OUT] PR-number, arbitrary-ref, `--gate`, `--watch`, cached-evidence, or stale-evidence arguments.
- [OUT] Unanswered-comment detection, comment-set reads, or comment-based owner asks.
- [OUT] Review approval, approval counts, unresolved review threads, or branch-protection rules as gate conditions.
- [OUT] Worktree cleanliness or uncommitted-change detection.
- [OUT] Multiple CI workflows or a configurable workflow path.
- [OUT] Embedded-metadata provenance consumption or metadata-based citation enrichment.
- [OUT] Envelope-shape changes, new domain kinds, new configuration keys, state-schema changes, new packages/subpaths, or new runtime-API locations.
- [OUT] Bash-stack changes, agent prompt adoption, MCP/OpenCode surfaces, fleet/board views, or telemetry exporters.

### 7.3 Deferred / Maybe-Later

- A PR-number or arbitrary ref argument, once the delivery model supports out-of-checkout verification.
- GitLab/Jira gate reads behind the same gate vocabulary, once a named consumer binds them.
- Suite-to-job mapping and matrix/condition awareness (M2-S7), which would make `ci-green` stricter and reduce false missing-job failures.
- A bounded re-read for GitHub's asynchronous mergeability when the provider returns `unknown`; v1 fails closed on one read.
- Review approval and unresolved-thread conditions in squash preflight, if product policy makes them part of the battery.
- Comment-based unanswered owner asks, once the comment-set read lands.
- A configurable expected-workflow path or multi-workflow expected set.
- Worktree cleanliness as a separate gate.
- Embedded-metadata provenance as an optional citation source, aligned with the embedded-metadata concept.
- A structured failure report on the envelope (rather than the bounded summary), if a consumer needs the full report on failure; this would be an envelope change.
- A `--gate <id>` filter for focused reruns.

## 8. INTERFACES & INTEGRATION CONTRACTS

### 8.1 REST / HTTP Endpoints

None. `verify gates` is an in-process CLI command; it starts no listener and exposes no HTTP endpoint. It performs only outbound read-only GitHub REST requests through the delivered client (Section 8.4).

None. The report is invocation-scoped result data. The command emits no event, message, announcement, telemetry record, or state record, and writes no GitHub artifact.

A run is counted in at most one state bucket, so the five state counts sum to `runs` minus observed runs with no recognized state; an unrecognized state contributes only to `runs` and is treated as a failed observation (`ci-failed`), so the gate never passes on it. Names `missing-jobs`, `failed-jobs`, `pending-jobs`. Parity: `matched` (0/1), `compared` (0/1); no names. Owner: `labels`, `ownerLabels`; names `owner-labels`. Squash: `commits`, `changedFiles`; names `squash-signals` with exactly two distinct, ordered values — `draft=<true\|false>` then `mergeable=<mergeable\|conflicting\|not-mergeable\|unknown>` — emitted whenever any delivery-request detail was read successfully, on pass and on every condition failure; where no usable detail was read (a resolution failure, a detail 404 with source outcome `absent`, or a failed detail read with source outcome `failed`) the list is empty, the `commits`/`changedFiles` counts are empty (unknown, never zero), and the citation's source outcome and reason name the cause; no value is fabricated or defaulted. When a successful delivery-request detail read omits `commits`/`changedFiles`, those counts are omitted as unknown (never zero) while the citation may still carry `squash-signals`. Counts that depend on an unread or unusable source are omitted rather than fabricated as zero; the declared lifecycle terminal-failure zeros in this row and DM-15 are the only deliberate zero counts on a failure path. The citation remains complete on every such path because it always carries at least one source and at least one reason. All lists are capped and ordered as declared. |

| DM-13 | Open-PR resolution rule | `OpenPrResolution = { outcome: "resolved" \| "no-open-pr" \| "branch-mismatch" \| "ambiguous-open-pr" \| "branch-unresolved", branch?, deliveryRequest?, openCount, matchCount }`. **Source-outcome semantics.** `read` means the source returned usable data. `observed-empty` means a successful read with no matching item (for example, zero open requests). `failed` means a classified read or parse failure. `absent` means the source does not exist (for example, no pm-notes target or a definitive HTTP 404). `unresolved` means an identity or SHA could not be resolved (for example, a malformed/non-numeric tracker identity or a remote head SHA). `not-attempted` means a dependent read was not issued because a prerequisite was unresolved; it is never a pass and always carries the prerequisite reason.

**Open-PR resolution rule (shared by `push-parity` and `squash-preflight`).**

| Step | Condition | Resolution |
|---|---|---|
| 1 | HEAD detached | `branch-unresolved`; no PR read |
| 2 | Raw open-PR page size equals `VERIFY_GATES_OPEN_PR_LIMIT` | `ambiguous-open-pr`, regardless of matches (uniqueness cannot be proven) |
| 3 | Exactly one open request with `sourceRef === branch` | `resolved`; that request is the target |
| 4 | More than one such match | `ambiguous-open-pr` |
| 5 | Zero matches and zero open requests | `no-open-pr` |
| 6 | Zero matches and at least one open request | `branch-mismatch` |

No other resolution path exists. Both gates use the same resolution and the same reasons; a page at the limit is a definitive `fail`, not `unknown`.

**Read-failure mapping (HTTP 404 vs other failures).**

| Read | HTTP 404 (`provider.not-found`) | Other transport / non-2xx / credential / binding failure |
|---|---|---|
| Open delivery-request list | `push-parity`: `fail` `no-open-pr`; `squash-preflight`: `fail` `no-open-pr`; source outcome `absent` | `unknown` `read-failed`/`credential-unavailable`/`address-unresolved` |
| Delivery-request detail for the resolved request | One rule for every detail-consuming gate (`ci-green`, `push-parity`, `squash-preflight`): `fail` `head-unresolved`, source outcome `absent` (the pushed head can no longer be resolved) | `unknown` `read-failed`/`credential-unavailable`/`address-unresolved` |
| Check runs for the resolved head SHA | `unknown` `read-failed`, source outcome `absent` (the commit may not be pushed yet); never `failed` and never `ci-no-runs` | `unknown` `read-failed`/`credential-unavailable`/`address-unresolved`, source outcome `failed` |
| Work item for the change ref | `fail` `ticket-unresolved`, source outcome `absent` | `unknown` `read-failed`/`credential-unavailable`/`address-unresolved`, source outcome `failed`/`not-attempted` as applicable |

A 404 is definitive absence for a work item or a pull request and is never projected as a generic `unknown`. A detail 404 after a resolved match is `head-unresolved` for `ci-green`, `push-parity`, and `squash-preflight` alike, because the detail carries the head/mergeability/surface facts and the pushed head can no longer be resolved. Non-404 detail failures remain `unknown` (`read-failed`/`credential-unavailable`/`address-unresolved`). A check-run 404 is a definitive absence for that read but keeps the gate `unknown` `read-failed` with source outcome `absent`, because the commit may not yet exist on the remote; it is not `failed` and not `ci-no-runs`. The same emptiness rule applies to every gate: when a count or name list depends on a source outcome of `failed`, `absent`, or `not-attempted` (or on a detail that was not read), the count/list is omitted as unknown rather than fabricated as zero, and the reason names the cause; the citation still has at least one source and at least one reason.

**Failure-identity precedence.**

1. Any gate `fail` → `verify.gates.failed`, exit `1`.
2. No gate `fail`, at least one `unknown` → use the first `unknown` gate in DM-2 order. If its citation carries a `failureCode` that resolves to an error-table entry, reuse that entry (and its projection class/exit); otherwise use `verify.gates.unavailable`, exit `2`.
3. All pass → success, exit `0`.
4. Handler grammar → `input.value.rejected`, exit `1`; parser shape/flags → `fallback.invocation`, exit `1`.

## 10. TELEMETRY & OBSERVABILITY REQUIREMENTS

No product telemetry, metric exporter, trace span, event sink, or background process is added. The report is the observability surface: the envelope's `runId` and `timing`, the five gate records with verdicts and citations, the summary counts, the deterministic failure summary, and the human success report. Every failure names the gate, reason, source(s)/outcomes, identity/ref, and both the `counts` and `names` segments (each `-` when empty). No raw provider payload, secret, title, comment body, commit message, or file content enters a diagnostic. The command's cost is one bounded read per source and a pure evaluation linear in the capped input.

## 12. ASSUMPTIONS

- The repository CI workflow is at the declared path `.github/workflows/ci.yml`; its job display names are unique and match the check-run names GitHub reports. The current topology has 23 jobs.
- The workflow's jobs all run on `pull_request`; job-level `if` conditions and matrix expansion are not evaluated in v1.
- The delivery request is opened from a branch in the same repository; fork PRs and cross-repository heads are not supported in v1.
- At most one open delivery request matches the checkout branch when the open-request page is below `VERIFY_GATES_OPEN_PR_LIMIT` (100). A page exactly at the limit is an ambiguous resolution that must fail closed, not an assumption of uniqueness.
- The change ref's numeric suffix maps to the GitHub issue number for the owner gate (`GH-178` → `178`).
- The checkout is on the delivery branch and its HEAD SHA is readable through the repository adapter; a detached HEAD is a gate failure, not a success.
- A credential-reference GitHub instance is supplied for live provider reads; a missing credential is `unknown` evidence, not a pass.
- The GitHub pull-request detail read supplies `head.sha`, `mergeable`/`mergeable_state`, `commits`, and `changed_files` after the additive normalization; absence of any field is unknown.
- `main-tools` is the integration base for this release (AGENTS.md); a different base requires a deliberate contract/edge change.
- The delivered `verify change` classifier, pm-notes parser, registry reader, state layer, status owner-attention labels, and result contract remain behaviorally unchanged.
- The M0 battery is exactly the five gates; suite-to-job mapping, merge execution, review approval, and comment reads are later stories.

**Data flow.**

1. The CLI edge resolves the brand, the repository binding from `origin`, and the credential-reference GitHub instance.
2. The edge reads the repository facts (branch/HEAD/detached), the pm-notes document, the verified registry history, and the bounded CI workflow job set.
3. The edge resolves the target through the deterministic open-PR rule (DM-13), reads the resolved request detail, and reads check runs for its head SHA; it reads the work item for the change ref. A 404 on the work item, the open-PR list, or a resolved detail is passed through as definitive absence, not as a generic read failure: a list 404 is `no-open-pr`, a resolved detail 404 is `head-unresolved` for every detail-consuming gate, and a check-run 404 is `unknown` `read-failed` with source outcome `absent`.
4. The pure evaluator consumes `VerifyLedgerEvaluation` for lifecycle, applies the CI/parity/owner/squash rules over the injected facts, and assembles the five citations and overall verdict; lifecycle counts and missing phases always come from the evaluation, never from a summary.
5. The CLI renders the success report or the failure summary, projects the exit, and applies the existing redaction/output path.

**Tier and boundary rules.**

- Contracts carry types and `as const` data only; the pure evaluator imports contracts and the existing verify-change domain module only.
- The domain performs no file, network, clock, randomness, or ambient environment access; every fact is injected.
- The GitHub, repository, and file I/O stay in their already-admitted adapter subpaths; the CLI edge composes them.
- No new package, subpath, declared entrypoint, workspace edge, runtime-API location, or dependency is introduced. The package-root re-export is an additive named export on the existing `core` entrypoint, not a new subpath or runtime-API location.
- Gate order, source order, count order, and name order come from contract arrays, not map iteration; identical facts produce identical bytes.

## 20. PRIVACY / COMPLIANCE REVIEW

- The command is read-only and collects no telemetry. It sends only the read-only GitHub requests required for open pull requests, pull-request detail, check runs, and work-item labels.
- Credentials resolve only through `CredentialPort`; resolved material never enters the report, citation, summary, human text, logs, or diagnostics. The serialization redaction chokepoint covers both success and failure output.
- Citations carry counts, ids, branches, SHAs, labels, job names, and reasons only. They carry no raw provider payload, response body, title, comment body, commit message, file content, or arbitrary message.
- The work-item read exposes labels only for the owner gate; the report does not copy the work-item title or body.
- The CI-workflow read exposes job display names only; it does not copy workflow steps, environment values, or secrets.
- The report is local to the invocation; the command publishes nothing. The opt-in live evidence artifact must be bounded, secret-free, and reviewed before attachment.
- No privacy or compliance regime beyond the existing repository rules is implicated; no personal data is stored.

## 21. SECURITY REVIEW HIGHLIGHTS

- **Read-only by construction:** the gates call no write/fence API, no tracker/PR/CI write, no merge, and no auto-merge. They cannot mutate a repository artifact, pull request, check, label, or state store.
- **Credential centralization:** the only credential access is `CredentialPort.resolve`; gate code reads no ambient environment. No new secret-read allowlist entry, credential-material path, or environment prefix is added.
- **Composition guard:** only a credential-reference GitHub instance is admitted; an anonymous or otherwise configured instance is refused before any GitHub read, and the refusal makes the provider-backed gates unknown rather than green.
- **No shell or spawn:** repository facts come from the existing bounded `.git` reads; the workflow is read through the bounded file adapter; the command spawns no process and executes no shell.
- **Bounded addressing:** only the `origin` remote is used; only `github.com` is accepted; userinfo and credentials in the remote URL are discarded; non-GitHub hosts are unavailable, not attempted.
- **Bounded parsing and reads:** one bounded YAML workflow read, one bounded page per provider collection, one detail read, one work-item read, no pagination, no retries, and a declared byte cap on the report/summary.
- **No secret or raw payload leakage:** citations carry codes/classes/counts/names only; the single serialization redaction path and planted-secret canaries apply; adapter failures surface as adapter-local classes (`provider.payload.invalid`, `provider.not-found`), never raw bodies or HTTP status text.
- **Denial-of-service:** the pure evaluator is linear over the capped input; no recursion over unbounded provider graphs; no arbitrary URL construction beyond the bound repository and the declared read endpoints.
- **Brand neutrality:** no product or binary literal is committed; the human header uses the injected brand binary name. Provider-specific literals are limited to the declared GitHub host and credential key.

## 22. MAINTENANCE & OPERATIONS IMPACT

- Adding a gate is a contract change (gate id/order, verdict/reason surface, source/count/name declarations, fixture, and output line). The five-gate set is not extended silently.
- Changing the integration base, CI workflow path, expected-job cap, open-PR page limit, check-run page limit, mergeability precedence, or citation bounds updates the contract, tests, and docs without changing the evaluator architecture. The open-PR limit is `VERIFY_GATES_OPEN_PR_LIMIT`; a page at it always fails `ambiguous-open-pr`.
- A new provider binding must supply the normalized `DeliveryRequest` gate facts and the check-run/work-item reads; the gate rules stay provider-agnostic. A provider that omits a fact produces `unknown`/fail, never a fabricated value. A provider that cannot signal definitive absence must map it to the declared reason or treat the gate as `unknown`, never as a pass.
- The GitHub trap catalog is the early-warning surface for PR head/mergeability/change-surface quirks, check-run emptiness/truncation, issue-comment absence, and 404 absence. Every new quirk joins as a four-field entry with a trap payload and a matching assertion; the existing catalog's bidirectional coverage remains binding. Trap payloads stay in the catalog's required `tests/fixtures/providers/` location and are not mixed with behavioural `tests/fixtures/verify-gates/` fixtures.
- The lifecycle gate consumes `VerifyLedgerEvaluation`; a change to the ledger rules must update that evaluator, the `classifyVerifyChange` wrapper, and this gate's citation mapping together. The gate never parses a summary.
- The shared `verify` definition's `humanText` must return `undefined` for `verify change` so that path stays on redact-then-serialize; a new subcommand with human output adds an explicit target branch returning a string, not a new definition, and must not route output through string redaction when it can carry raw payloads.
- The owner gate consumes the status owner-attention label set; changing the label set is a shared contract change.
- The CI gate consumes the status CI result semantics; a change to `none`/all-skipped meaning must update both surfaces.
- Docs to keep current: the new verify-gates feature spec, verify-change (subcommand/consumer), status (shared owner/CI semantics), provider client seeds (additive PR facts and traps), adapter ports (`DeliveryRequest` fields), result contract (three verify rows), pm-notes (read-only consumer), monorepo (modules/tests, no new location), delivery lifecycle, change-lifecycle/DoD guides, glossary, and index.
- Operational surface stays small: one read-only command, at most four outbound reads, one bounded workflow read, no daemon, no background process, and no new configuration knob.

| CI green | Every expected job is present, at least one run succeeded, no run failed/canceled/is pending, the page is not truncated, and the run set is not zero/all-skipped. |
| Vacuous green | A pipeline with zero jobs, zero runs, or only skipped runs that appears green but never performed effective work; explicitly not a pass. |
| Expected job set | The repository CI workflow's job display names, read at the edge, used to detect a missing job; an unreadable/empty set is a gate failure, never green. |
| Push parity | Equality between the local checkout HEAD SHA and the delivery request's source head SHA for the same branch. |
| Open-PR resolution | The one deterministic rule that selects the target delivery request from one bounded open-PR page: detached → `branch-unresolved`; page at the limit → `ambiguous-open-pr`; exactly one `sourceRef === branch` match → target; multiple matches → `ambiguous-open-pr`; zero matches with zero open PRs → `no-open-pr`; zero matches with at least one open PR → `branch-mismatch`. |
| `branch-mismatch` | A definitive failure in which the open-PR page contains one or more open requests but none has a `sourceRef` equal to the checkout branch. |
| `provider.not-found` | An additive adapter-local read-result code for HTTP 404. It is not an error-table code; work-item and PR-list 404s are definitive `fail`, a resolved PR whose detail read 404s is `head-unresolved` for every detail-consuming gate, and a check-run 404 is source outcome `absent` while the gate stays `unknown` `read-failed` because the commit may not be pushed. |
| Structured ledger evaluation | `EvaluateVerifyChange` → `VerifyLedgerEvaluation`, the pure evaluation that returns variant, outcome, required/completed/missing phases, declaration counts, and registry evidence on every outcome; a terminal document failure yields empty phase arrays, zero declaration counts, and the failure identity. |
| Owner gate | The absence of owner-attention labels (`hand-back`, `human-input-needed`) on the work item; the declared v1 signal is labels, not comments. |
| Squash preflight | The pre-merge check that the request targets `main-tools`, is open/non-draft, is `mergeable`, and has a non-vacuous commit/change surface. |
| Non-vacuous surface | At least one commit and at least one changed file reported by the delivery request; absent counts are unknown, never non-empty. |
| Unknown mergeability | The provider has not supplied a known mergeable/conflicting/not-mergeable state; it is never treated as mergeable. |
| Squash signals | The squash citation's ordered `squash-signals` name list: `draft=<true\|false>` then `mergeable=<mergeable\|conflicting\|not-mergeable\|unknown>`, carried whenever a delivery-request detail was read successfully, on pass and on every condition failure; empty only when no usable detail was read (`failed`, `absent`, or `not-attempted`), in which case the `commits`/`changedFiles` counts are also omitted as unknown (never zero). |
| Delivery request | The merged-request primitive (pull request/merge request) behind the provider ports; the gate reads its detail view. |
| `not-attempted` | A dependent source read that was not issued because a prerequisite was unresolved; it is never a pass. |
| Failure summary | The deterministic, bounded multi-line block in the error summary that preserves one citation line per gate on failure. |
| Live smoke | The opt-in, credentialed structural test against a real repository; not a default-CI network test. |
| Integration base | The branch a delivery request targets for integration; `main-tools` in this release. |

### Appendix A — Gate evaluation matrix (normative)

| Gate | Pass | Fail | Unknown |
|---|---|---|---|
| `lifecycle-finalization` | `VerifyLedgerEvaluation` yields `finished` for the declared variant; counts and missing set come from the evaluation. | `partial` (missing phases or declared-but-incomplete), malformed notes, or missing target; underlying `verify.ledger.incomplete`/`lint.*` cited; counts and ordered missing phases still come from the evaluation (empty arrays and zero declaration counts on a terminal document failure, with the failure identity naming why). | Platform- or user-category registry/store failure (`state.*`); evidence untrustworthy, and the overall unknown reuses the classified code. |
| `ci-green` | Head SHA resolved; expected set valid; page read; page < 100; ≥1 run; ≥1 expected job succeeded; no failed/pending/canceled run; every expected job present. | Head unresolved (including a resolved PR whose detail read 404s → `head-unresolved`, source `absent`); expected set invalid; zero runs/jobs; any failed/canceled/pending; no expected job succeeded and every expected job skipped; missing expected jobs. | Page at the 100-run limit; check-run 404 (`unknown` `read-failed`, source `absent`); other provider/credential read failure. |
| `push-parity` | Attached branch; open-PR page below `VERIFY_GATES_OPEN_PR_LIMIT`; exactly one `sourceRef === branch` match; full remote head SHA; local HEAD equals remote head. | Detached HEAD; raw page at the limit (even with a match); zero open PRs (`no-open-pr`); only non-matching open PRs (`branch-mismatch`); multiple matches; list 404 (`no-open-pr`); resolved-detail 404 (`head-unresolved`, source `absent`); missing/invalid remote head; SHA mismatch. | Other PR list/detail/provider read failure; unresolved binding. |
| `owner-gate` | Work item read; no owner-attention label. | Owner-attention label present; malformed/non-numeric identity (`unresolved`) or a work-item HTTP 404 (`ticket-unresolved`, source outcome `absent`, never `read-failed`). | Transport failure, non-404 non-2xx response, credential failure, or unresolved repository binding. |
| `squash-preflight` | Resolved request; open (not merged/closed), non-draft; base `main-tools`; `mergeableState: mergeable`; commits > 0; changed files > 0; citation carries `squash-signals` (`draft=false`, `mergeable=mergeable`). | Not open; draft; wrong base; conflicting; `not-mergeable`; unknown/absent mergeability; zero/absent commits or changed files; failed open-PR resolution (`branch-mismatch`, `no-open-pr`, `ambiguous-open-pr`, `branch-unresolved`); list 404 (`no-open-pr`); resolved-detail 404 (`head-unresolved`, source `absent`); when the detail was read the citation still carries `squash-signals` (`draft`/`mergeable`) and the reason names the failed condition. | Other PR list/detail/provider read failure; where no detail was read, `squash-signals` is empty rather than fabricated. |

**Primary-reason precedence within a gate.** A gate reports one primary reason; the citation still carries secondary facts (for example, missing jobs alongside a red run). CI precedence: invalid expected set → head unresolved (including a resolved-detail 404) → read failure (including check-run 404) → truncation → zero runs → any failed → any canceled → any pending → all skipped → missing expected jobs → pass. Squash precedence: open-PR resolution failure (`branch-unresolved` → at-limit/ambiguous → no-open-pr → branch-mismatch) → resolved-detail 404 (`head-unresolved`) → not open → draft → wrong base → conflicting → not-mergeable → unknown mergeability → absent surface → zero commits → zero changed files → pass. Parity precedence: detached HEAD → open-PR resolution failure (at-limit/ambiguous → no-open-pr → branch-mismatch) → resolved-detail 404 (`head-unresolved`) → missing/invalid head → SHA mismatch → pass. Lifecycle precedence: document/missing-target failure → incomplete → platform unknown → pass.

**Mergeability precedence.** `mergeable === false` (clean or dirty state) or `mergeable_state === "dirty"` → `conflicting`; `mergeable_state` in blocked/behind/unstable/draft → `not-mergeable` even when `mergeable === true`; null/absent/computing/unrecognized with `mergeable !== true` → `unknown`; `mergeable === true` with clean/absent state → `mergeable`; any remaining combination → `unknown`. The mapping never defaults to `mergeable`.

### Appendix D — Failure summary grammar and example

```text
result=<fail|unknown>; gates=<passed>/5 passed, <failed> failed, <unknown> unknown
<gate-id> <verdict> reason=<reason> source=<name>:<outcome>[+<name>:<outcome>...] ref=<changeRef|branch|PR|SHA|-> counts=<k=v[,k=v...]|-> names=<names-spec>
<names-spec> := - | <kind>=<json-array>[+<n>][ <kind>=<json-array>[+<n>]]...
... exactly one line per gate, in fixed order ...
```

Rules:

- The header is always one line. Exactly five gate lines follow, in `VERIFY_GATES_GATE_ORDER`; the block is at most 6 lines and 4096 bytes.
- `result` is `fail` when any gate fails, otherwise `unknown`; a success never produces this block.
- `source` is the ordered source list joined by `+`, and every source token carries `name:outcome`; the outcome set is `read`, `observed-empty`, `failed`, `absent`, `unresolved`, or `not-attempted`.
- `ref` is the strongest resolved identity for the gate: change ref, branch, PR number, SHA, or `-`, clamped to `VERIFY_GATES_MAX_REF_CHARS`.
- The `counts` segment is always present. It is the gate's declared count subset, in contract order, with non-negative integer values; when the gate's count subset is empty (the value is unknown, never zero), the segment is the literal `counts=-`. An empty set is never rendered as a bare `counts=` and is never replaced by a zero alias.
- The `names` segment is always present. When the gate has at least one non-empty bounded name list, each list is rendered as `<kind>=<json-array>` in contract order separated by a single space; the JSON array is compact and clamped, and `omitted` is not printed when zero, otherwise `+<n>` follows the array. When all name lists for the gate are empty, the segment is the literal `names=-`. A name list is never dropped segment-wise.
- Both segments therefore appear on every gate line in the fixed order `counts=... names=...`; `-` is the only empty-set marker (never `0`, never `[]`, never an omitted segment).
- For `squash-signals`, `values` is exactly `draft=<true|false>` then `mergeable=<mergeable|conflicting|not-mergeable|unknown>` in fixed order; when the delivery-request detail was read successfully the list is present with both tokens, including on every squash condition failure. It is empty only when no usable detail was read: a resolution failure or `not-attempted` read, a detail 404 (source outcome `absent`), or a failed detail read (source outcome `failed`). On those paths no value is fabricated or defaulted, the `commits`/`changedFiles` counts are also omitted as unknown (never zero) and render as `counts=-`, and the reason names the cause.
- Every citation always has at least one source and at least one reason; a citation missing either fails the contract and is never emitted. `counts` and `names` may be empty when the gate could not obtain usable evidence for them — when the dependent source outcome is `failed`, `absent`, or `not-attempted`, or when no detail was read; the reason names that cause, and this is not a citation-completeness violation. Empty counts are unknown, never zero (the declared lifecycle terminal-failure zeros are a distinct defined shape). When a successful delivery-request detail read omits `commits`/`changedFiles`, those counts are omitted as unknown (never zero) while the citation may still carry `squash-signals`. A condition failure after a successful read still carries the gate's declared counts and name lists.
- Values are single-line, deterministic, and escaped with JSON string quoting when they contain characters outside the safe set; no raw payload, title, comment body, or secret enters.
- Replay over identical facts produces identical bytes.

Illustrative example (values not pinned): `result=fail; gates=2/5 passed, 3 failed, 0 unknown` followed by `lifecycle-finalization pass reason=lifecycle-complete source=pm-notes:read+delivery-registry:read ref=GH-178 counts=required=11,completed=11,missing=0`, `ci-green fail reason=ci-missing-jobs source=repository-ci-workflow:read+github-delivery-request-detail:read+github-check-runs:read ref=abc1234 counts=expected=23,runs=22,missing=1 names=missing-jobs=["TS tests"]`, `push-parity pass reason=parity-matched source=repository-head:read+github-delivery-request-list:read+github-delivery-request-detail:read ref=abc1234 counts=compared=1,matched=1`, `owner-gate pass reason=owner-gate-absent source=github-work-item:read ref=GH-178 counts=labels=4,ownerLabels=0`, and `squash-preflight fail reason=squash-target-mismatch source=github-delivery-request-list:read+github-delivery-request-detail:read ref=178 counts=commits=3,changedFiles=7 names=squash-signals=["draft=false","mergeable=mergeable"]`.

Empty-set rendering example: a squash gate whose matched detail read returned HTTP 404 has no usable detail, so its line is `squash-preflight fail reason=head-unresolved source=github-delivery-request-list:read+github-delivery-request-detail:absent ref=178 counts=- names=-` — both segments are present and both use the single `-` marker, never a zero alias, a bare `counts=`, or an omitted segment.

### Appendix E — Human success grammar and example

```text
<binary> verify gates <changeRef>  pass  5/5
lifecycle-finalization  pass  [pm-notes+delivery-registry]  variant=<full|lite> required=<n> completed=<n> missing=<ids|->
ci-green                pass  [repository-ci-workflow+github-delivery-request-detail+github-check-runs]  sha=<sha7> expected=<n> runs=<n> failed=0 missing=<names|->
push-parity             pass  [repository-head+github-delivery-request-list+github-delivery-request-detail]  branch=<branch> local=<sha7> remote=<sha7>
owner-gate              pass  [github-work-item]  work-item=<ref> owner-labels=<names|->
squash-preflight        pass  [github-delivery-request-list+github-delivery-request-detail]  pr=<n> base=main-tools draft=no mergeable=mergeable commits=<n> files=<n>
```

Rules: exactly six lines (header plus five gates), fixed order, no timestamps, no LLM prose, no raw payloads/titles/comment bodies/secrets; each line names the gate verdict and its key evidence; the squash line's `draft`/`mergeable` facts are the same `squash-signals` facts carried by the machine citation; the full structured citations are available under `--json`; the block is at most 6 lines and 4096 bytes. This grammar applies only when the success payload's `target` is `gates`; for every other target `humanText` returns `undefined` and `runCli` uses the existing `humanSuccess`/`humanJson` path (redact-then-serialize), preserving today's `verify change` bytes. On failure, no success text is printed; the deterministic failure summary is the diagnostic.

### Appendix F — Expected job set and CI comparison rules

- **Read:** one bounded YAML read at `VERIFY_GATES_CI_WORKFLOW_PATH`; extract the top-level `jobs` map in declaration order; each expected name is the job's non-empty display `name`, otherwise the job id.
- **Validate:** non-empty, exact-unique, ≤200 names, each ≤120 chars. Any failure is `ci-expected-jobs-invalid`; the gate never substitutes the observed run names.
- **Compare:** exact case-sensitive match between an expected name and the normalized check-run `pipelineName` (the GitHub check-run `name`). Extra observed runs do not fail by themselves; a failed/canceled/pending extra run does.
- **Duplicate observed names:** if several runs share an expected name, the effective state is the worst by `failed > canceled > pending > skipped > succeeded`; a failed duplicate can never hide behind a passed duplicate.
- **Counts:** `expected` counts the declared expected names and `missing` counts expected names not observed; `runs` is the observed normalized check-run count (the raw page size); `succeeded`/`failed`/`pending`/`skipped`/`canceled` are observed run counts by normalized state. A run is counted in at most one state bucket, and `runs` may exceed their sum only when an observed run has no recognized state; such a run is treated as a failed observation (`ci-failed`) and never lets the gate pass.
- **Vacuous rules:** zero runs/jobs → `ci-no-runs`; no expected job succeeded and every expected job is skipped → `ci-all-skipped` (even when an extra non-expected run succeeded); at least one expected job succeeded and the rest of the expected jobs succeeded/skipped → not vacuous. A page at the 100-run limit is `unknown` (`ci-truncated`), not pass.
- **Read failure:** a check-run read that returns HTTP 404 (`provider.not-found`) is a definitive absence for that read: source outcome `absent` and gate `unknown` `read-failed`, because the commit may not be pushed to the remote yet; it is neither `failed` nor `ci-no-runs`, and any other transport/non-2xx failure is also `unknown`, never a pass.
- **Known limits:** matrix-expanded check-run names and job-level `if` conditions are not evaluated; a job that does not report a check run is reported missing (safe false fail), while a job that reports a skipped check run is present but not a success. Suite-to-job mapping is M2-S7.

**Test-plan-facing fixture expectations (normative).** The test plan and its fixtures must encode these cases without changing the rule: (a) an open-PR page at `VERIFY_GATES_OPEN_PR_LIMIT` with a matching PR → `ambiguous-open-pr`; (b) the same at-limit page without a match → `ambiguous-open-pr`, not `no-open-pr`; (c) one open PR with a non-matching `sourceRef` → `branch-mismatch`; (d) zero open PRs → `no-open-pr`; (e) PR list 404 → `no-open-pr`; (f) matched PR detail 404 → `head-unresolved` with source outcome `absent` for `ci-green`, `push-parity`, and `squash-preflight` (never `no-open-pr` for squash and never a generic `unknown`); (g) work-item 404 → `ticket-unresolved` outcome `absent`; (h) check-run 404 → `unknown` `read-failed` with source outcome `absent`, not `failed` and not `ci-no-runs`; (i) incomplete ledger → lifecycle counts and ordered missing phases from `VerifyLedgerEvaluation`; (j) `verify change` human success output byte-identical to the pre-change rendering, with `humanText` returning `undefined` so the redact-then-serialize path runs, including a JSON-escaping-sensitive secret; (k) CI counts use the declared denominators (`expected`/`missing` over the expected set, `runs` observed, state counts per observed run) and an unrecognized run state keeps the gate from passing; (l) a squash citation carries the two ordered `squash-signals` tokens whenever a detail was read successfully and an empty list with omitted (unknown, not zero) `commits`/`changedFiles` counts when no usable detail was read (`failed`, `absent`, or `not-attempted`), and a successful detail read that omits `commits`/`changedFiles` omits those counts as unknown while still carrying `squash-signals`; (m) `failureClass` values are drawn only from the declared read-result codes; (n) the CLI imports the new evaluator/renderers from the `@delivery-os/core` package root, not a new subpath; (o) a failure-summary gate with no counts and no names renders `counts=- names=-` — never a zero alias, a bare `counts=`, or an omitted segment — and TC-VGATES-042's line-shape expectation covers a no-usable-detail squash line. Behavioural fixtures for these cases live under `tests/fixtures/verify-gates/providers/...`; trap payloads and catalog entries stay under `tests/fixtures/providers/traps/` and `tests/fixtures/providers/github/**`.

**Plan-facing note (non-normative, for `@plan-writer`).** The delivery plan must add a task that introduces the pure `EvaluateVerifyChange`/`VerifyLedgerEvaluation` contract, makes `classifyVerifyChange` a wrapper, and consumes the structured evaluation in the lifecycle gate. The plan must include the additive package-root re-export in `packages/core/src/index.ts`, and every phase's file list must name every new or exported module: the package root, the domain barrel, the CLI command barrel, and the inventory/allowance files. The plan writer formalizes the exact task wording and file list; this spec fixes only the contract.
