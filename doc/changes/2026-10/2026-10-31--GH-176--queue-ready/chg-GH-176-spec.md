# CHANGE SPECIFICATION

> **PURPOSE**: Give the coordinator a read-only, evidence-backed answer to "what can start now?" for an explicit set of candidate work items — naming every condition that blocks a candidate and ranking close items above new starts — so idle lanes beside a full queue become visible and closing beats opening, without a queue engine, provider-engine call, or any write.

## 1. SUMMARY

This change delivers M0-S7 `queue ready`: a read-only command that evaluates one or more candidate work items against six closed readiness conditions and returns a ranked ready set. The command surface is `queue` with the subcommand positional `ready`, accepting one or more `<workItemRef>` positionals and only the global `--json` switch. Every candidate carries exactly six conditions in fixed order — `deps-satisfied`, `repo-free`, `tier-known`, `no-owner-gate`, `ci-healthy`, `provider-available` — each with a tri-state result (`satisfied`, `unsatisfied`, `unknown`) plus bounded evidence. A candidate is ready only when all six conditions are satisfied; any unsatisfied or unknown condition is named in the output and makes the candidate not-ready.

The command also classifies each candidate as a close item or a new start. A close item is an open pull request associated with the candidate by the repository branch convention. `merge-ready` requires an observed approval on a non-draft pull request; `review-pending` covers every other associated open pull request, including an unknown review signal. Rank order is `merge-ready`, `review-pending`, ready new start, unknown close association, not-ready, with numeric-aware work-item ref ties. This makes closing visible ahead of opening even when the candidate is not itself ready to start.

The change adds no error-table rows, no configuration keys, no state-schema change, no new package or subpath, and no new adapter read. It reuses the delivered status collector inputs and classification for CI, provider availability, work items, pull requests, and the local PM context. Source read failures become condition evidence, never command failures; only the existing `input.value.rejected` grammar identity and `fallback.internal` containment can fail the command handler (the global parser keeps its existing `fallback.invocation` path for malformed invocations). The machine payload is a new bounded `delivery.queue-ready.v1` structure in the standard `CommandResult` envelope, with a deterministic, byte-bounded human digest rendered from the same data that never fails a legal invocation.

### 2.2 Pain Points / Gaps

- The coordinator decides what to start next by manually cross-checking dependencies, repository activity, tier labels, owner hand-backs, CI, and provider parks. This is slow, inconsistent, and easy to skip under pressure.
- A full queue hides idle lanes: without a ready-set answer, a coordinator keeps feeding new starts while merge-ready and review-pending work sits unclosed.
- The delivered GitHub slice identifies an item by its provider-native number (`176`) while the caller names candidates canonically (`GH-176`). Without an explicit matching rule a naive comparison observes no candidate, and every label- and dependency-derived condition silently degrades to `unknown` on the live slice even though the labels and items are observable.
- Manual checks collapse distinct evidence states. "No dependencies found", "dependency source unavailable", "ticket not on the observed page", and "all dependencies done" all look the same, so a blocker is missed or a candidate is started prematurely.
- Provider availability is easy to overclaim. A declared chain with an active park can look like available capacity when the engine was never run.
- CI health is easy to overclaim. A commit with no runs, pending runs, or a failed read can look green.
- Tier is easy to fabricate. An untriaged ticket can be started with an invented default tier instead of being excluded from the ready set.
- Close items are invisible in a new-start-only view. A branch-associated open pull request that is approved or awaiting review is not surfaced as work that should be closed first.
- The current GitHub slice cannot observe structured dependency relations, done/canceled dependency targets outside the open page, or an approval signal on the pull-request list. A naive readiness command would turn those gaps into false satisfaction.
- `queue ready` has no command, no contract, no evaluator, no close classifier, and no tests. The registry row exists; the behavior does not.

**Story cross-check and in-spec resolutions.** The M0-S7 story is terse in seven places; each is resolved in this spec rather than left to implementation: (1) "for one ticket" vs "across candidates" → one-or-more explicit refs, capped at eight (F-2, DEC-1, DEC-14); (2) "repo free" → local PM context active change, because per-repo single-flight is M2-S1 (F-5, DEC-4); (3) "tier known" → exactly one recognized `priority:*` triage label, because no current per-ticket delivery-tier source exists (F-6, DEC-3); (4) "provider available" → declared chain plus verified park fold, never the engine (F-9, DEC-8); (5) "CI healthy" → current checkout HEAD check-runs, only `succeeded` (F-8, DEC-7); (6) "deps satisfied" → normalized `blocked-by` relations with unavailable/unobserved = unknown (F-4, DEC-5); (7) "close items (merge-ready, review-pending)" → branch-convention association with observed-approval-only merge-ready (F-10, DEC-9). Journey 2.2's "gates" is read as the ticket's owner-gate, CI-health, and readiness checks; a full merge-gate battery is `verify gates` (M0-S9) and is not duplicated here. The story does not contradict the current system spec: status already declares the queue/lane section `not-delivered` until M2-S1 and explicitly leaves `queue ready` to this story, so the two commands do not duplicate each other; the provider, state, config, and result contracts already expose the read-only surfaces this command consumes. Residual uncertainty is captured as non-blocking OQ-1..OQ-8.

## 3. PROBLEM STATEMENT

Because the coordinator has no bounded, evidence-backed ready-set answer for an explicit set of candidate work items, it must manually re-derive dependency, repository, tier, owner-gate, CI, and provider readiness every time — and manual checks cannot distinguish an observed clear condition from an absent, failed, unobserved, or unavailable source — so idle lanes beside a full queue stay invisible, close items wait behind new starts, and candidates are either started with unmet or unknown conditions or blocked by evidence the coordinator cannot name.

### 5.1 Capability Details

- **F-1 — Command surface.** The command is `queue` with the subcommand positional `ready`, composed where `status`, `verify`, `lint`, `phase`, `provider`, and `config` are composed. Grammar is validated in the handler before any source read: the first positional must be exactly `ready`; at least one and at most `QUEUE_READY_MAX_CANDIDATES` work-item refs must follow; each ref must match the declared work-item-ref shape and, after canonicalization, be at most `QUEUE_READY_MAX_WORK_ITEM_REF_CHARS` (64) characters. A zero-ref, too-many-ref, over-length-ref, wrong-subcommand, or malformed-ref invocation fails as `input.value.rejected` (kind `input`, exit `1`) before any read. The global parser still rejects unknown flags, unknown command names, and invocations beyond the declared positional bound as `fallback.invocation` (exit `1`), unchanged. `--json` is the only output switch and adds no command behavior. The handler performs no stream writes and chooses no exit code; it returns data or a classified failure, and the CLI edge renders and projects. The command is read-only.
- **F-2 — Candidate set.** The candidate set is the canonicalized work-item refs supplied by the caller, in caller order before ranking; duplicates are detected after canonicalization and rejected, never silently merged. **(a) Input grammar — caller-ref validation, canonicalization, and length check before any read.** Each caller-supplied ref must match `QUEUE_READY_WORK_ITEM_REF_PATTERN` exactly. Pattern validation is a whole-value match against the caller's ref, not a substring or prefix match: the ASCII alphabetic prefix is compared case-insensitively while the hyphen and the digit substring are exact. No surrounding or interior whitespace is accepted or trimmed, and a whitespace-bearing ref is malformed. This step validates and canonicalizes only the caller's ref and checks its length; it never matches a ref to provider data. Canonical emission uppercases the ASCII alphabetic prefix and preserves the hyphen and the digit substring exactly as supplied, including leading zeros (`gh-176` → `GH-176`; `Gh-007` → `GH-007`; `GH-007` and `GH-7` remain distinct refs). After canonicalization the canonical ref must be at most `QUEUE_READY_MAX_WORK_ITEM_REF_CHARS` (64) characters; a canonical ref of exactly 64 characters is accepted, and a canonical ref of 65 or more characters is rejected as `input.value.rejected` before any read. The length check runs after canonicalization and before duplicate detection and any source read. Two refs are duplicates iff their canonical strings are equal; a duplicate pair is rejected as `input.value.rejected` before any read and is never silently merged into a single candidate. Condition evaluation is independent per candidate over the same shared facts: one candidate's condition states, evidence, rank, and close class never change another candidate's condition verdicts. Identity observation is candidate-set-scoped, however, through the §8.3 unique-suffix bridge: when a bare all-ASCII-digit `identity.entityId` matches the numeric suffix of more than one requested candidate, the item is unobserved for every sharing candidate, with no precedence and no dependence on caller order; a candidate never gains or loses observation because of another candidate's conditions, only through this deterministic shared-suffix rule. **(b) Observed-identity matching — validated ref to observed provider data.** After grammar validation, a validated candidate ref is matched against an observed work item's full normalized `identity.entityId` by the §8.3 provider-agnostic rule: exact case-insensitive full-value equality first, then an all-ASCII-digit provider id bridged to the candidate's canonical numeric suffix only when exactly one requested candidate carries that suffix; never a substring, prefix-only, or numeric-coercion match, and always over the full value before any output clamp (DM-11). A wrong number, a non-digit provider id that is not the canonical ref, or a suffix shared by two requested candidates leaves the item unobserved. `blocked-by` targets have no caller-grammar step — they are provider-supplied — and are resolved only by the same §8.3 observed-identity rule over the observed work-item set: exact full-value match first, then the unique bare-digit suffix bridge whose uniqueness domain is the observed work-item set. The command does not enumerate open issues to invent candidates, does not infer a candidate from the active change, and does not accept a repository, path, label, or filter argument.
- **F-3 — Six conditions and tri-state.** Every candidate carries exactly six conditions in the fixed order `deps-satisfied`, `repo-free`, `tier-known`, `no-owner-gate`, `ci-healthy`, `provider-available`. Each condition carries exactly one state from `satisfied`, `unsatisfied`, `unknown` and bounded evidence. `ready` is true only when all six are `satisfied`; otherwise the candidate is not-ready and `blockingConditions` lists every non-satisfied condition in fixed order with its state. A condition that cannot be observed is `unknown`, never `satisfied`; a condition observed to be unmet is `unsatisfied`.
- **F-4 — `deps-satisfied`.** Evaluation order is candidate observation, then relation-signal availability, then the target predicate. If the candidate work item is not observed — the tracker read failed or was not attempted, or the successful page contains no item that the §8.3 identity rule matches to the candidate — the condition is `unknown` with `work-item-unobserved`, evaluated before any relation-signal check. Otherwise, if the tracker source declares blocked-dependency relations unavailable, the condition is `unknown` with `signal-unavailable` — even when the candidate appears to have no relations, because absence of a relation signal is not evidence of no dependencies. Otherwise, with relations available: zero `blocked-by` relations is `satisfied` (`no-blocked-dependencies`); every target observed `done` or `canceled` is `satisfied` (`dependencies-done`); any target observed with a non-done, non-canceled delivery state is `unsatisfied` (`dependency-open`); otherwise (at least one target unobserved and none known open) the condition is `unknown` (`dependency-unobserved`). A done target outside the observed page remains unobserved, never assumed done. A `blocked-by` target is resolved against the observed work-item set with the §8.3 target rule (exact full-value identity first, then a bare all-ASCII-digit target `entityId` bridged only when exactly one observed work item carries that numeric suffix); a target that resolves to no observed item, or whose digit string is shared by more than one observed work item with no exact match, is unobserved (`dependency-unobserved`), never assumed done, and a canonical-shaped target that matches no observed item stays unobserved even when its ref equals a requested candidate. The condition carries exactly one evidence record from source `tracker`; for the target-derived reasons `dependencies-done`, `dependency-open`, and `dependency-unobserved` the detail is the bounded state-count summary `done:<n>; open:<n>; unknown:<n>`, whose three counts sum to the total number of `blocked-by` relation targets (observed plus unobserved), with no target-ref list, no comma-joined refs, and no per-target record. `no-blocked-dependencies`, `signal-unavailable`, and `work-item-unobserved` carry no detail.
- **F-5 — `repo-free`.** The condition reads the git-ignored local PM context through the same bounded projection status uses. Missing context is `unknown` with `local-context-missing`; malformed YAML or wrong shape is `unknown` with `local-context-malformed`; an observed context with no `active_change` is `satisfied` with `no-active-change` and detail `repo:local-context`; an observed active change whose `workItemRef` equals the candidate (case-insensitive) is `satisfied` with `candidate-is-active` and detail `repo:local-context; candidate-is-active`; an observed active change for a different ref is `unsatisfied` with `other-active-change` and detail `repo:local-context; active-change:<ref>`. Missing and malformed contexts carry no detail. The condition never writes the context and never infers "free" from a missing file. **Proxy caveat:** `repo-free` reflects only the local PM context and cannot see another machine's active change; per-repo single-flight is M2-S1. The evidence detail names the proxy source `repo:local-context` so the caveat is visible in machine and human output.
- **F-6 — `tier-known`.** Labels are read from the candidate work item. If the work item is unobserved, the condition is `unknown` with `work-item-unobserved`, evaluated before label-signal availability. Otherwise, if the label signal is unavailable, the condition is `unknown` with `signal-unavailable`. With labels observed: exactly one distinct recognized label from `priority:high`, `priority:medium`, `priority:low` (case-insensitive) is `satisfied` with `tier-label` and detail `tier:priority-label; label:<label>`; zero recognized labels is `unknown` with `tier-absent` and detail `tier:priority-label; none`; more than one distinct recognized label is `unsatisfied` with `tier-conflict` and detail `tier:priority-label; labels:<sorted labels>`. Unrecognized labels do not satisfy or conflict. No default tier is invented. **Proxy caveat:** `tier-known` uses the `priority:*` triage label as the only current triage signal; a documented per-ticket `DeliveryTier` intake policy is M2. The evidence detail names the proxy source `tier:priority-label` so the caveat is visible in machine and human output.
- **F-7 — `no-owner-gate`.** Labels are read from the candidate work item. If the work item is unobserved, the condition is `unknown` with `work-item-unobserved`, evaluated before label-signal availability. Otherwise, if the label signal is unavailable, the condition is `unknown` with `signal-unavailable`. With labels observed: none of `hand-back` or `human-input-needed` (case-insensitive) is `satisfied` with `no-owner-labels`; any one or more is `unsatisfied` with `owner-labels:<sorted labels>`. `assignee` is not used because the normalized field is optional and absence means the provider did not supply it (ADR-0006).
- **F-8 — `ci-healthy`.** The condition reuses the delivered status CI classification on the current checkout HEAD. The commit is unresolved when HEAD carries no SHA; the check-runs read is one bounded page at `QUEUE_READY_SOURCE_PIPELINE_LIMIT` (20) with no pagination and no retry; the classified result is one of `failed`, `pending`, `succeeded`, `canceled`, `none`, `unknown`. Only `succeeded` is `satisfied` (`ci-succeeded`). `failed`, `pending`, `canceled`, and `none` are `unsatisfied` with `ci-failed`, `ci-pending`, `ci-canceled`, or `ci-none` respectively. Each `unknown` mode maps to exactly one reason: an unresolved SHA is `commit-unresolved`; a read not attempted because the repository binding is unavailable is `addressing-unresolved` (or `remote-unsupported` for an unsupported host); a read not attempted because no credential is resolvable is `credential-unavailable`; a read attempted and failed is `read-failed` with a bounded `failureCode`/`failureClass` detail from the existing result contract. A raw check-runs page of exactly 20 runs never changes the classification, the condition state, the evidence records, or `blockingConditions`; it raises `source-truncated` in the payload-level `reasons` only (DM-1, DM-11). No run is never green; an all-skipped page is never `succeeded`.
- **F-9 — `provider-available`.** The condition reads the resolved provider configuration and the verified active park views; it never calls the provider engine, `provider resolve`, `provider quota`, or any quota transport. A provider park matches an entry when its `subjectKind` is `provider` and its `subjectName` equals the entry name; a chain park matches the declared chain when its `subjectKind` is `chain` and its `subjectName` equals the chain name. A provider-config read failure is mapped by the `StatusProviderConfigRead.reason`, never blanket-mapped: `{ ok: false, reason: "config-invalid" }` is `unknown` with `config-invalid`; `{ ok: false, reason: "provider-chain-unresolved" }` is `unknown` with `provider-chain-unresolved`; and a verified park-fold failure is `unknown` with `state-unreadable` from source `provider-parks`. No declared default chain is `unknown` with `provider-chain-not-declared`; a declared default chain that the resolved configuration does not resolve to declared entries — including the defensive `ok: true` view whose declared default chain is absent from `chains` — is `unknown` with `provider-chain-unresolved`. With a resolved chain: an active chain park for the declared chain is `unsatisfied` with `chain-parked` and bounded cause/expiry; zero enabled entries among the chain's entries is `unsatisfied` with `no-enabled-entry`; otherwise at least one enabled chain entry with no active provider park is `satisfied` with `no-active-park`; otherwise every enabled chain entry is parked and the condition is `unsatisfied` with `all-entries-parked`. Every `provider-available` condition carries exactly two evidence records in fixed order: the case record first, then the companion record `{ source: "provider-config", reason: "engine-not-run" }` with no detail. The case record is `{ source: "provider-parks", reason: "no-active-park", detail: "chain:<chainName>" }` when satisfied; `{ source: "provider-parks", reason: "chain-parked", detail: "chain:<chainName>; until:<expiry|none>; cause:<cause|none>" }` for an active chain park; `{ source: "provider-config", reason: "no-enabled-entry", detail: "chain:<chainName>" }` for no enabled entry; `{ source: "provider-parks", reason: "all-entries-parked", detail: "chain:<chainName>" }` for all parked; `{ source: "provider-config", reason: "provider-chain-not-declared" }` for no declared default chain; `{ source: "provider-config", reason: "config-invalid" }` for a config read failure, and `{ source: "provider-config", reason: "provider-chain-unresolved" }` for either the defensive `ok: true` view or a command-level config read failure; and `{ source: "provider-parks", reason: "state-unreadable" }` for a park-fold failure. A config or park failure record carries the read's bounded failure identity in the pinned form `failureCode:<code>` when a `failureCode` is supplied (the delivered command-level config and park reads supply one), `failureClass:<class>` when only a `failureClass` is supplied, or both joined by `; ` when both are supplied; the defensive `ok: true` view and `provider-chain-not-declared` have no read failure identity and therefore carry no `detail`; a record never carries a free-form message. Apart from this pinned failure identity, a condition evidence `detail` is only one of the pinned state/count/case tokens enumerated in F-4..F-10 and DM-4 (for example `tier:priority-label; label:<label>`, `repo:local-context; active-change:<ref>`, `owner-labels:<sorted labels>`, `done:<n>; open:<n>; unknown:<n>`, `chain:<chainName>`, `result:pending`), and is never free-form. Evaluation precedence for the case record is config resolution, then chain declaration/resolution, then the verified park fold, then the per-entry predicate, so the case record is deterministic when more than one source fails; the single invocation-scoped park-fold read still occurs per NFR-5 and a park-fold failure is still reported in the payload-level `reasons`. No provider evidence record and no availability claim uses `available` as a claim or state, and none claims engine verification. The pinned condition id `provider-available`, the `QUEUE_READY_CONDITION_ORDER` id list, and `blockingConditions`/human `blocking:` references to that id are explicitly exempt from this rule; every negative `available` scan is scoped to provider evidence records/details and the provider human-text segment, never the whole payload or digest. `engine-not-run` is always a `reason` record, never a `detail`.
- **F-10 — Close classification.** The delivered open pull-request read is the same bounded status read (`?state=open`), bound to the `origin`-derived target repository, so command-level association observes open pull requests only; a merged or closed request cannot appear in that read. A candidate is associated with an open pull request when the pull request's `sourceRef` follows the repository branch convention `<type>/<workItemRef>/<slug>`: split the ref on `/`, require at least three non-empty segments, and require any segment to equal the candidate ref case-insensitively. A matching PR is selected deterministically within one close class: the merge-ready set is preferred when it is non-empty (non-draft, review-state signal observed, and observed `approved`); otherwise the full associated set is used. Within the selected set — whether several merge-ready PRs or several review-pending PRs (the associated set when no merge-ready one exists) — select by `entityId` ascending with a numeric-aware comparison: when both values are all-ASCII-digit, compare their unsigned integer values and treat equal numeric values as a tie at this key (so `7` and `007` tie); otherwise compare the values lexically. A tie proceeds to `sourceRef` ascending, then `targetRef` ascending, then — only if all three keys are equal — the lexically smaller raw `entityId` string. Selection never depends on API return order. The class rank order is unchanged. `closeClass` is `merge-ready` when that condition holds; otherwise `review-pending` when an associated open pull request exists; otherwise `new-start` when the candidate is ready and the association is observed absent; otherwise `unknown` when the candidate is ready and the association could not be observed; otherwise `not-ready`. Association is `unknown` when the repository binding is unavailable, the pull-request read failed, or the read succeeded at its declared page limit and no open match was found; association is `not-associated` only when the read succeeded below its limit and no open match exists. At command level, a below-limit open-only page with no open match carries `pr-not-associated` and never `pr-not-open`. **Evaluator-input invariant:** when an evaluator-injected normalized view contains a matching pull-request object whose delivery state is `merged` or `closed`, that object is never an associated open close item — never selected, never counted in `associatedCount`, and never yields `merge-ready` or `review-pending`. In such an injected view, below the page limit with no open match, `close.reason` is `pr-not-associated` when no matching object of any state is present and `pr-not-open` when at least one matching merged/closed object is present; the close class follows the not-associated row (`new-start` when the candidate is ready, otherwise `not-ready`), and `pr-not-open` never appears for an open match. The at-limit rule wins in both layers: at the page limit with no open match, association is `unknown` with `pr-association-unknown`, even when matching merged/closed objects were injected. `associatedCount` is the number of open matching pull requests observed on the single page: a non-negative integer bounded by the page (`0..QUEUE_READY_SOURCE_ITEM_LIMIT`), exact below the limit, a page-bounded lower bound at the limit, and 0 when the read failed or the binding is unavailable; it is not separately capped.
- **F-11 — Ranking.** Candidates are ranked by class first: `merge-ready`, `review-pending`, `new-start`, `unknown`, `not-ready`. Within a class, ties break on the numeric suffix of the work-item ref ascending, then the canonical ref text ascending. `rank` is the 1-based position after sorting. A close item therefore always ranks above a ready new start, and a not-ready candidate never outranks a close item.
- **F-12 — Machine payload.** `--json` returns exactly one standard `CommandResult` envelope whose `data` is the full bounded `delivery.queue-ready.v1` payload: `schemaVersion`, `generatedAt`, `repository`, `head`, `candidates`, `summary`, `reasons`, and `truncated`. Each candidate carries `workItemRef`, `rank`, `ready`, `closeClass`, `workItem` observation, `close` classification, six `conditions`, and `blockingConditions`. Each condition carries `id`, `state`, and up to two bounded evidence records. Provider-derived values are projected only within the declared caps (DM-11): a clamp is output-only, marks the payload `truncated` with `value-clamped`, and never changes a condition verdict. The payload is deterministic and contains no raw provider payload, response body, credential, or free-form message.
- **F-13 — Human digest.** Human mode renders a deterministic digest from the same payload: an optional header, exactly one summary line, and exactly one line per rendered candidate in rank order. Each line names the candidate ref, its close class, its close evidence when associated, and the blocking conditions with states when the candidate is not ready; a close item that is also not-ready prints both its close evidence and its blocking conditions. Each line also ends with the fixed proxy-source suffix `[repo:local-context; tier:priority-label]`. The digest is at most 16 lines and `QUEUE_READY_MAX_HUMAN_BYTES` (4 096) UTF-8 bytes for every legal payload, performs no extra reads, uses no LLM, and prints no titles, timestamps, raw payloads, or secrets. The renderer is byte-aware: each per-candidate provider segment (`PR #<entityId>` and the source ref) is rendered to at most `QUEUE_READY_MAX_HUMAN_SEGMENT_BYTES` (32) UTF-8 bytes including a trailing `+` when shortened, with the `+` counting toward the 32-byte cap and no code point split; the header renders owner and name to at most 128 UTF-8 bytes each and branch to at most 256 UTF-8 bytes, each marked with a trailing `+` when shortened. These are renderer rules only: they change no payload field and are not `value-clamped` clamps. If a legal payload would still render above `QUEUE_READY_MAX_HUMAN_BYTES` after every renderer cap, the renderer drops trailing candidate lines in reverse rank order (last-ranked candidate first), keeps the header (when present) and the summary line, and marks the drop with `+more` after the summary; it never throws, never exits non-zero, and never emits an unbounded digest. The line drop is renderer-only: it changes no payload field, does not set the payload `truncated` flag, and adds no reason token; the summary line continues to report the payload-level counts. Payload truncation and a defensive line drop are both marked `+more`.
- **F-14 — Evidence and non-verdict rules.** A condition is `satisfied` only when its required source read succeeded and the observed value meets the predicate. A failed, absent, unattempted, unavailable, unobserved, or unresolved source yields `unknown`; a source that is observed to be unmet yields `unsatisfied`. Unknown is never rendered as ready, satisfied, or zero. The negative-control matrix in AC-F14-1 is exhaustive for the delivered sources. Evidence reasons come from a closed set; details are bounded and safe.
- **F-15 — Reuse and GitHub degradation.** The command composition reuses the delivered status runtime seams and normalized read results: one open-issues page, one open-pull-request page, one check-runs page for the current HEAD, the resolved provider branch, the verified park fold, the repository binding and HEAD facts, and the local PM context. It introduces no new adapter operation, no closed-issue read, no per-issue detail read, no GraphQL review read, and no provider-engine call. On the current GitHub slice this means `deps-satisfied` is `unknown` (relations unavailable), `merge-ready` is unreachable (review state unavailable), and `no-owner-gate`/`tier-known` are observable from labels. Those are truthful declared gaps, not failures.
- **F-16 — Read-only, tier/brand-neutral, error reuse.** The evaluator, ranker, and renderer are pure over injected facts: no I/O, clock, randomness, or ambient environment. All reads stay in the existing adapter subpaths and the CLI edge. The command performs zero writes, fences, state mutations, network writes, and child processes. No new package, subpath, runtime-API location, secret-read allowlist entry, or error-table row is added. The human header uses the injected brand binary name; no product literal is committed. The command handler's own failures are only `input.value.rejected` (grammar) and `fallback.internal` (containment); source failures are evidence, and the existing global parser `fallback.invocation` path is unchanged.
- **F-17 — Evidence model.** Default CI uses a committed fixture corpus for every condition state, close class, ranking rule, bound, and negative control, with zero live network calls. An opt-in live smoke runs against this repository with a credential and asserts structural invariants only: one valid payload, six conditions per candidate, at least one known candidate observed through the §8.3 identity rule, no ready candidate with a non-satisfied condition, no merge-ready without observed approval, no provider evidence record or availability claim using `available` (the pinned condition id is exempt), bounds, and no secrets. It never pins volatile item counts. The opt-in live smoke is enabled only by the test-harness literal environment variable `ADOS_QUEUE_READY_LIVE`, read only under `tests/**` and enabled only when its value is exactly `1`. That literal is never declared as a production or contract constant (it is not exported from `core ./contracts` and does not appear in Appendix C), is not a configuration key, is not a payload or evidence field, and never appears in the human digest. It is read only by the test harness and is absent from every production edge.

## 6. USER & SYSTEM FLOWS

1. **Ready-set flow.** The coordinator runs `ados queue ready GH-175 GH-179 GH-170` (human) or with `--json` (agent). The CLI edge resolves the brand, the repository binding, the checkout HEAD, and the injected read sources. The pure evaluator classifies each candidate's six conditions, derives close class and rank, assembles bounded evidence, and returns one payload. Human mode renders the digest; machine mode wraps it in the envelope.
2. **Zero-ref flow.** The coordinator runs `ados queue ready` with no refs. The handler rejects the grammar as `input.value.rejected` before any source read; the command exits `1` and no GitHub, state, config, or file read occurs.
3. **Not-ready flow.** A candidate has an observed tier conflict and an unavailable dependency source. Its conditions are `tier-known: unsatisfied`, `deps-satisfied: unknown`, and the remaining conditions as observed. `ready` is false, `blockingConditions` names both, and the human line prints `blocking: tier-known=unsatisfied, deps-satisfied=unknown`. The command still exits `0`.
4. **Close-first flow.** A candidate is not ready because CI is pending, but its branch has an associated open pull request with an unobserved review signal. It is `review-pending` and ranks above a fully ready candidate with no associated pull request. The coordinator sees that closing it is the better next action.
5. **Merge-ready flow.** A candidate has an associated non-draft open pull request whose source declares review state available and the observed state is `approved`. Its `closeClass` is `merge-ready` and it ranks first. On the current GitHub slice, review state is declared unavailable, so this flow is exercised by fixtures and by a future review-capable source, not by the GitHub slice.
6. **Degraded-source flow.** The repository binding is unavailable, or the PR read fails, or the check-runs read fails. The affected conditions become `unknown` with named evidence; the unaffected conditions remain as observed (for example `repo-free` from the local PM context). Every candidate is still rendered, and the command exits `0`.
7. **Provider-park flow.** The provider config declares a chain and the park fold reports an active provider or chain park. `provider-available` is `unsatisfied` with the bounded cause and expiry; the evidence says the engine was not run. The command never fetches quota and never writes a park.
8. **Live-repository flow.** In an opt-in live smoke with a credential, the command runs against this repository and truthfully reports deps unknown, merge-ready unreachable, and any other declared gap. Structural assertions pass without pinning counts.

## 7. SCOPE & BOUNDARIES

### 7.1 In Scope

- The `queue ready` command definition, grammar, runtime composition, and human/machine rendering.
- The `delivery.queue-ready.v1` contract vocabulary: condition ids and order, tri-state states, evidence sources/reasons, close classes, candidate shape, summary, bounds, and reasons.
- The pure readiness evaluator, close classifier, ranker, and human renderer in the runtime-neutral core domain tier.
- `deps-satisfied`, `repo-free`, `tier-known`, `no-owner-gate`, `ci-healthy`, and `provider-available` predicates over the delivered status inputs.
- Close association by the repository branch convention, `merge-ready`/`review-pending` classification, and deterministic ranking.
- Input, candidate, condition, evidence, provider-derived field and collection, machine-byte, and human-byte bounds with explicit truncation and clamp marking.
- Reuse of the delivered status read results and classification; no new adapter read.
- Tests at structure, behaviour, boundary, golden, and fixture-corpus levels, plus an opt-in live smoke.
- A minor changeset and the new current-truth feature spec; phase 7 reconciles the surrounding docs.

### 7.2 Out of Scope

- [OUT] Any queue, lane, dispatch, supervision, board, brief, merge, deploy, closeout, or scheduling engine; per-repo single-flight, preemption, and build-weight planning (M2-S1).
- [OUT] Automatic candidate discovery, open-issue enumeration as a candidate source, or fleet-wide ready-set computation.
- [OUT] Provider-engine execution, chain resolution by the engine, quota evaluation/fetch, announcements, park writes/clears, provider telemetry, or spawn selection.
- [OUT] Any mutation: tracker/PR/CI writes, state appends, fences, park clears, projection rebuilds, pm-notes writes, or PM-context writes.
- [OUT] New GitHub reads, closed-issue pages, GraphQL review decisions/threads, structured issue-dependency reads, open-PR-head CI, or a full GitHub adapter.
- [OUT] New configuration keys or branches for queue readiness, tier labels, candidate caps, repository addressing, or thresholds.
- [OUT] A per-ticket `DeliveryTier` record or pm-notes-variant-derived tier; M2 owns the intake policy.
- [OUT] LLM summarization, semantic ranking, recommendations, prose generation, or agent-prompt adoption.
- [OUT] MCP/OpenCode surfaces, shared board state, cross-repository/fleet status, or replacing `status`/`verify`/`lint`.
- [OUT] New error-table rows or identities, result-envelope changes, state-schema changes, new packages/subpaths, or new runtime-API locations.
- [OUT] Reading pm-notes phase ledgers or duplicating `verify change`/`status`.

- MCP/OpenCode exposure of the ready-set (M1-S7/M3-S2).

## 8. INTERFACES & INTEGRATION CONTRACTS

### 8.1 REST / HTTP Endpoints

None. `ados queue ready` is an in-process CLI command; it starts no listener and exposes no HTTP endpoint. It performs only the outbound read-only GitHub REST requests already declared by the status collector (Section 8.4).

None. The payload and its evidence are invocation-scoped result data. The command emits no event, message, announcement, telemetry record, or state record, and writes no provider park or announcement.

**Readiness and close matrix (normative).**

| Candidate observation | Conditions | `ready` | `closeClass` |
|---|---|---|---|
| Associated open PR, non-draft, review signal observed `approved` | any combination (close beats start) | true only if all six satisfied | `merge-ready` |
| Associated open PR, any other state (draft, open, changes-requested, unknown approval) | any combination | true only if all six satisfied | `review-pending` |
| No associated PR, association observed absent | all six satisfied | true | `new-start` |
| No associated PR, association observed absent | at least one not satisfied | false | `not-ready` |
| Association unknown | all six satisfied | true | `unknown` |
| Association unknown | at least one not satisfied | false | `not-ready` |

**Normative non-verdict rule.** A condition may be `satisfied` only when its required source read succeeded and the observed value meets the predicate. A failed, absent, unattempted, unavailable, unobserved, or unresolved source yields `unknown`; it never yields `satisfied`, never contributes to `ready`, and never prints as zero. `merge-ready` may be claimed only from an observed approval on a non-draft open pull request; an unavailable review signal can at most produce `review-pending`. No provider evidence record or availability claim uses `available` as a claim or state — the pinned condition id `provider-available`, the condition-id list, and `blockingConditions` references are exempt — every `provider-available` condition carries the `engine-not-run` reason, and no provider condition claims engine verification. No-run CI is never healthy. A source-at-limit marker is a coverage caveat, not a verdict: `source-truncated` never changes a condition state. The delivered open-only command read never returns a merged or closed matching pull request; when an evaluator-injected view contains one, it is never a close item, and `pr-not-open` explains the absent open association in that view but never yields `review-pending` or `merge-ready`.

**Deterministic rank keys.** Class rank, then numeric suffix ascending, then canonical ref text ascending. Numeric-aware comparison parses the digits after the final hyphen as a base-10 integer; refs with equal numeric values compare by canonical text. The caller's order is not a tie-breaker.

**Identity resolution (normative).** This is the observed-identity matching step (F-2 step (b)), separate from the caller-ref grammar validation in F-2 step (a): a validated requested candidate ref and a provider-supplied `blocked-by` relation target are each compared with an observed work item by one provider-agnostic match rule over the full normalized value, before any output clamp (DM-11); the uniqueness domain of the numeric bridge is role-specific (the requested candidate set for candidate observation, the observed work-item set for `blocked-by` targets). For a requested candidate and an observed work item:

1. **Exact canonical match wins.** The observed full `identity.entityId` equals the candidate's canonical ref, compared case-insensitively.
2. **Numeric bridge.** Otherwise, if the observed full `identity.entityId` is a non-empty all-ASCII-digit string `d` (full-value match of `QUEUE_READY_NUMERIC_ENTITY_ID_PATTERN`), it matches the requested candidate whose canonical numeric suffix — the digits after the final hyphen, leading zeros preserved as text — equals `d` exactly, and only when exactly one requested candidate carries that suffix. If two or more requested candidates carry `d`, the bridge is ambiguous: the item is unobserved for each of those candidates (`work-item-unobserved`), and none of them wins by precedence or caller order.
3. **No other match.** There is no substring, prefix-only, or numeric-coercion match: `0176` does not match suffix `176`, suffix `007` does not match `7`, and a provider id that is not all-ASCII-digit never bridges.

Candidate matching is evaluated per candidate over the same observed page, but its uniqueness domain is the requested candidate set: a shared suffix leaves the item unobserved for every sharing candidate rather than assigning it to one of them, and caller order or any other precedence never resolves the ambiguity. Condition evaluation otherwise remains independent per candidate (F-2).

`blocked-by` relation targets resolve against the observed work-item set, not the requested candidate set. An exact full-value identity match against an observed work item wins. Otherwise, a bare all-ASCII-digit target `entityId` `d` bridges only when exactly one observed work item carries a canonical-shaped `identity.entityId` whose numeric suffix — the digits after the final hyphen, leading zeros preserved as text — equals `d` exactly; if two or more observed work items share that suffix, or none does, the target is unobserved (`dependency-unobserved`) and is never assumed done. A canonical-shaped target that no observed work item matches stays unobserved (`dependency-unobserved`), even when its ref equals a requested candidate. The uniqueness domain therefore differs by role: candidate observation uses the requested candidate set (the three steps above), while `blocked-by` target resolution uses the observed work-item set. Matching always uses the full normalized value before any output clamp. On the delivered GitHub slice both sides of the target comparison are provider-native numbers (`176`), so the exact match resolves them directly. The bridge applies only to a bare all-ASCII-digit target `entityId` compared against the observed work-item set; a canonical-shaped target is resolved only by the exact case-insensitive full-value rule, and a canonical-shaped target that is not observed stays `dependency-unobserved` and never bridges on its numeric suffix.

## 12. ASSUMPTIONS

- The repository is a git checkout with an `origin` remote pointing at a GitHub repository. If not, the repository binding is unavailable and the affected conditions are `unknown`; the command still returns a payload.
- A GitHub credential is resolvable through the injected `CredentialPort` for live reads. If absent or rejected, the affected reads fail and the conditions are `unknown`; no anonymous fallback is attempted.
- The GitHub list endpoints return the declared fields (state, labels, relations when available, updated_at for issues; state/draft/head/base for pull requests) and check runs for a SHA. The minimal slice does not supply trusted review decisions or structured issue links.
- The candidate work item appears in the single bounded open-issues page and is matched by the §8.3 identity rule: an observed `identity.entityId` equal to the canonical ref, or an all-ASCII-digit provider id equal to the unique requested candidate's numeric suffix. If not, its label/dependency conditions are `unknown`; the command never invents an open item or reads a second page.
- All relevant open pull requests appear in the single bounded page. If the page is at its limit and no match is found, association is `unknown`.
- `.ai/local/pm-context.yaml` is the canonical local PM coordination file and is git-ignored. Its absence in a clean checkout or CI is normal and must not become "repo free".
- The provider configuration branch resolves; `provider.defaultChain` is absent in shipped defaults and `provider.chains` ships empty; an absent default chain is `unknown`, not a failure.
- The state layer's verified park fold is the park evidence; the derived `provider-parks.json` projection is not read as truth.
- The queue/lane engine does not exist until M2-S1; the provider engine is not executed by this command.
- The current checkout HEAD is the commit under CI observation; open-PR-head CI is deferred.
- The delivered status read results and pure classifications are reusable without changing the status payload or the GitHub surface.
- Default CI has no live network or live credential; the live smoke is opt-in and structural.
- The injected brand binary name is a short token (well under 276 UTF-8 bytes), so the optional human header renders within the digest byte bound (DM-12).

## 15. DECISION LOG

| ID | Decision | Rationale | Rejected alternatives |
|----|----------|-----------|-----------------------|
| DEC-1 | **PM D1 — grammar.** The command is `queue` with the subcommand positional `ready`, accepting 1..8 `<workItemRef>` positionals and only the global `--json`. Zero refs, a wrong subcommand, too many refs, an over-length ref (canonical length 65 or more), or a malformed ref fails as `input.value.rejected` before any read. An unknown flag or an invocation beyond the parser's declared positional bound remains `fallback.invocation` from the existing global parser. | Matches the registry (`queue ready`) and the `verify change <ref>` subcommand precedent; one-or-more satisfies both "one ticket" and "across candidates" without fleet enumeration. | One ref only (cannot build a ready set); a top-level `queue-ready` command (breaks the locked family grammar); a filter/limit flag. |
| DEC-2 | **PM D2 — truthful readiness.** Six closed conditions per candidate, tri-state (`satisfied`/`unsatisfied`/`unknown`) with bounded evidence. Ready iff all six are satisfied; any unsatisfied or unknown condition makes the candidate not-ready and is named. Unknown is never ready and never a clear zero. | A boolean would conflate absent, failed, and observed-unmet evidence; the ticket requires naming the missing condition. | Boolean ready flag; one aggregate score; silently defaulting unknown to satisfied. |
| DEC-3 | **PM D3 — tier source, no refinement.** `tier-known` requires exactly one recognized label from `priority:high`, `priority:medium`, `priority:low`; absent is `unknown`; conflicting is `unsatisfied`. The spec searched for a documented per-ticket tier source and found none that is current: `.ai/agent/pm-instructions.md` declares the priority labels as the selection/triage set; `doc/planning/concepts/primitive-catalogue.md` records `DeliveryTier` as an M2 intake policy; the pm-notes `variant` exists only after a change artifact. Therefore the source is not refined. | The priority labels are the only current machine-checkable per-ticket tier signal; defaulting an untriaged ticket would fabricate a tier. The refinement clause was checked and is not triggered. | A default tier; pm-notes `variant` (not available for an open ticket); the M2 `DeliveryTier` field (not delivered); label heuristics such as `bug`/`feature`. |
| DEC-4 | **PM D4 — repo-free.** `repo-free` is satisfied when the local PM context is observed and either has no `active_change` or records the candidate itself; unsatisfied when another active change is recorded; unknown when the context is missing or malformed. | Per-repo single-flight is M2-S1; the local active change is the only current truthful read-only signal, and a candidate already in flight does not block itself. | A remote lock (not delivered); a branch scan (heuristic); treating a missing context as free (false all-clear). |
| DEC-5 | **PM D5 — deps-satisfied.** Evaluation order is candidate observation, then relation-signal availability, then the target predicate: an unobserved candidate is unknown with `work-item-unobserved` before any relation-signal check; an observed candidate whose source declares relations unavailable is unknown with `signal-unavailable`; with relations available, all targets observed done/canceled is satisfied, an observed non-done target is unsatisfied, and an unobserved target (with no known open target) is unknown. | Mirrors the status blocked-dependencies family and ADR-0004/ADR-0006 absence discipline; absence of relations is not evidence of no dependencies. | Treating an absent relation source as "no deps"; requiring every target to be observed before any verdict; reading a second page speculatively. |
| DEC-6 | **PM D6 — no-owner-gate.** Satisfied when the open work item carries none of `hand-back`/`human-input-needed`; unsatisfied when it carries one or more; unknown with `work-item-unobserved` when the work item is unobserved (evaluated first), and unknown with `signal-unavailable` when the observed work item's label signal is unavailable. | Labels are available on the GitHub slice; owner-attention labels are the declared gate. `assignee` is not used because absence means unknown (ADR-0006). | Using `assignee`; treating an unobserved item as ungated. |
| DEC-7 | **PM D7 — ci-healthy.** Evaluated on the current checkout HEAD's single bounded check-runs page; only `succeeded` satisfies. `none`, `pending`, `canceled`, `failed`, an unresolved commit, or a failed read never satisfy; unresolved/failed read is unknown. | Reuses the status CI classification, where no-run is never green; the checkout HEAD is the available commit signal. | Treating `none` as green; reading all branches; open-PR-head CI (no head signal). |
| DEC-8 | **PM D8 — provider-available, refined for an active chain park.** Satisfied when the declared default chain resolves and at least one enabled entry has no active provider park; unsatisfied when every enabled entry is parked or no enabled entry exists; unknown when no default chain is declared, the chain does not resolve, or the verified park fold fails; a provider-config read failure is mapped by its read reason (`config-invalid` or `provider-chain-unresolved`) and is never blanket-mapped to `config-invalid`. **Refinement:** an active chain park for the declared chain is evaluated as `unsatisfied` (the chain-level pause is active) with cause/expiry, rather than being forced through the per-entry predicate; this preserves D8's "no active park" intent without claiming that every enabled entry is individually parked. Evidence always states that the engine was not run, and no provider evidence record or availability claim uses `available` as a claim or state (the pinned condition id and its `blocking:`/condition references are exempt). **Evidence pin:** every `provider-available` condition carries exactly two records — the case record pinned in F-9, then `{ source: "provider-config", reason: "engine-not-run" }`; the satisfied case record is `{ source: "provider-parks", reason: "no-active-park", detail: "chain:<name>" }` and the chain-park case record is `{ source: "provider-parks", reason: "chain-parked", detail: "chain:<name>; until:<expiry|none>; cause:<cause|none>" }`. | The ticket explicitly sources provider availability from the declared chain and park states, as in the M0-S6 collector; the engine must not run. The chain-park case is a real state the status vocabulary exposes and must not be reported as available. Pin the pairing so an implementation cannot put `engine-not-run` in a detail, omit it, or attach the park record to the wrong source. | Calling `provider resolve`/`quota` (mutating/network); marking unparked entries `available`; ignoring a chain park. |
| DEC-9 | **PM D9 — close ranking, refined for unknown association.** A candidate is a close item when an open pull request's source branch follows `<type>/<workItemRef>/<slug>` (at least three segments; any segment equals the canonical candidate ref case-insensitively); candidate and `blocked-by` target identities are matched by the §8.3 rule, not by substring or numeric coercion. `merge-ready` requires an observed approved review state on a non-draft PR; `review-pending` covers any other associated open PR, including unknown review state. Rank: merge-ready, review-pending, ready new start, unknown close association, not-ready; ties by numeric-aware ref ascending. **Refinement:** a ready candidate whose association is unknown (binding unavailable, PR read failed, or page at limit with no match) is `unknown` and ranks between new-start and not-ready, never `new-start`; a not-ready candidate with an unknown association is `not-ready`. **Merged/closed pin (evaluator-injected view only):** the delivered open-only pull read cannot observe a merged/closed object, so a below-limit page with no open match yields `not-associated` with `pr-not-associated`; when an injected normalized view contains only merged/closed matches below the limit, it yields `not-associated` with `pr-not-open` and the normal not-associated fallback class (`new-start` when ready, else `not-ready`); at the page limit with no open match the at-limit rule wins (`unknown`/`pr-association-unknown`) in both layers. `associatedCount` counts open matches only, is exact below the limit, and is bounded by `0..QUEUE_READY_SOURCE_ITEM_LIMIT` without a separate cap. | Closing beats opening, and a close item must never hide behind a new start. The GitHub slice makes association occasionally unobservable, so the unknown class is necessary to avoid fabricating a new start. A merged/closed match is not an open close item but is worth naming so the absence of an open association is explained rather than misread. | Substring/prefix ref matching; treating unknown association as no association; ranking unknown below not-ready (hides a possible close item); treating a merged/closed match as an open close item or as `review-pending`. |
| DEC-10 | **PM D10 — output and boundaries.** Machine output is a new bounded `delivery.queue-ready.v1` payload in the standard `CommandResult` envelope (candidates, per-condition state and evidence, close class, rank, summary counts) plus a deterministic human digest; `--json` is the only flag. No new error-table rows, configuration keys, state-schema change, provider-engine call, or write/fence/child process. Source read failures are condition evidence. Only `input.value.rejected` (grammar) and `fallback.internal` (containment) can fail the command. | The ready-set is a report, not a mutation; the existing envelope and identities are sufficient; a queue-specific error identity would add a surface with no consumer. | A new `queue.*` error row; a boolean payload; failing the command on a source read failure. |
| DEC-11 | An unobserved candidate work item makes every label- and relation-derived condition (`deps-satisfied`, `tier-known`, `no-owner-gate`) `unknown`; it is never treated as an open, untriaged, ungated, or dep-free ticket. | The single bounded open page may not contain the candidate; absence is unknown, not a fabricated open item. | A second per-issue read; defaulting labels/relations to empty; failing the candidate. |
| DEC-12 | Association is `unknown` when the PR source is unavailable, the binding is unavailable, or the page is at its limit and no match exists; `not-associated` only when the read succeeded below the limit. | The bounded page can under-report associations; absence is not proof, and a false `new-start` hides a possible close item. | Treating an at-limit page as complete; treating a failed read as no association. |
| DEC-13 | The command reuses the delivered status read results and classification and adds no adapter read; the GitHub slice's declared gaps (`deps` unknown, `merge-ready` unreachable) are surfaced truthfully. | The ticket depends on M0-S6 and says provider availability is "as in the M0-S6 collector"; a new read would duplicate status and widen scope. | New list/detail/GraphQL reads; a second issues page; a closed-issue page. |
| DEC-14 | Candidates are explicit refs; no automatic discovery or implicit active-change candidate. | The story is a ready-set answer, not a scheduler; explicit refs keep the result deterministic and the read cost bounded. | Enumerating all open issues; inferring candidates from the active change or parked work. |
| DEC-15 | Input refs over the candidate cap (but within the parser's hard positional bound) fail as `input.value.rejected`; the parser's hard bound and unknown-flag rules remain `fallback.invocation`. Duplicate refs (case-insensitive) fail as `input.value.rejected`. **Canonicalization pin:** input matching is case-insensitive with no whitespace trimming or acceptance; output uppercases the ASCII alphabetic prefix and preserves the digit substring exactly, including leading zeros; after canonicalization the ref must be at most `QUEUE_READY_MAX_WORK_ITEM_REF_CHARS` (64) characters — a 64-character ref is accepted and 65 or more is rejected as `input.value.rejected` before any read; the candidate set is the canonicalized refs supplied by the caller; duplicates are detected after canonicalization and the length check and are rejected, never silently merged. | Honors D10's command-failure set at the handler level while keeping the existing global parser behavior unchanged; duplicates would make ranking ambiguous. A single canonical spelling keeps the payload, ranking tie-break, and duplicate check deterministic. | Silent truncation of the candidate set; parser-level rejection for 9-32 refs; deduplicating silently; trimming whitespace; stripping leading zeros. |
| DEC-16 | Evidence reasons are a closed queue-ready vocabulary (reusing status reasons where they fit); they are condition evidence, not error-table identities. **Ordering pin:** top-level `reasons` follows `QUEUE_READY_REASON_ORDER` (six groups: binding, payload bounding markers, provider-config, park-fold, condition-source failures, close association); group 2 is `source-truncated` then `value-clamped`; group 5 rolls up only `QUEUE_READY_SOURCE_FAILURE_REASONS`, so `read-failed` and `credential-unavailable` are group-5 only and never appear in group 6; group 6 is exactly `pr-association-unknown` and is the last group. | DEC-17 | **Deterministic truncation and live-switch pins.** Evidence-cap overflow retains the first two records and sets both the affected candidate and the payload `truncated`; reason-cap overflow retains the first six and sets the payload `truncated` only; source-at-limit sets the payload `truncated` only; a raw 20-run check-runs page raises payload-level `source-truncated` without changing the `ci-healthy` classification, state, evidence, or blocking list. The opt-in live smoke is enabled only by the test-harness literal `ADOS_QUEUE_READY_LIVE`, read only under `tests/**`, enabled only when its value is exactly `1`, and never a production or contract constant, configuration key, payload field, or human-text token. The human digest's reverse-rank line-drop fallback marks `+more` only and adds no reason token. | A single flag rule per drop cause keeps the two output surfaces consistent and bounded; a source-at-limit caveat must not silently rewrite a verdict; the live smoke must stay opt-in and outside the production surface. | Candidate-only flags for reason overflow; payload-only flags for evidence overflow; a CI `source-truncated` that changes the verdict; a production live switch or a config key. |
| DEC-18 | **Provider-agnostic identity resolution.** A requested canonical ref is matched to an observed item by (1) exact case-insensitive equality with the full normalized `identity.entityId`, then (2) an all-ASCII-digit provider id bridged to the candidate's canonical numeric suffix only when exactly one requested candidate carries that suffix, with an ambiguous suffix leaving the item unobserved; there is no substring, prefix-only, or numeric-coercion match. `blocked-by` targets resolve against the observed work-item set: the bare-numeric target bridge requires exactly one observed work item with that numeric suffix, ambiguity or no match is `dependency-unobserved`, and a canonical-shaped target that is not observed stays `dependency-unobserved`; target-suffix uniqueness is therefore over observed work items, while candidate-suffix uniqueness remains over requested candidates. Matching always uses the full value, before any output clamp. | The delivered GitHub normalization uses the provider-native issue number (`176`) for both item and relation-target identities, while the command takes canonical refs (`GH-176`); without a pinned bridge the live slice would observe no candidate and silently degrade every label- and dependency-derived condition to `unknown`. | DEC-19 | **Output-only provider-derived clamps.** The payload projection caps identity (128), provider refs (128), labels (128 characters, 16 items), `blocked-by` relations (16; other kinds filtered out entirely), owner (128), repository name (128), head branch (256), and provider `updatedAt` (40); any clamp sets the payload `truncated` and adds `value-clamped` in group 2 after `source-truncated`. If the capped payload would still exceed 65 536 bytes, trailing relations then labels are dropped in a fixed order with the same markers. Clamping never changes a condition verdict, close class, rank, `associatedCount`, or summary, because matching and predicates use full values. The human digest bound is met by the DM-12 byte budgets and the reverse-rank line-drop fallback, never by failing a legal command. | The normalized views declare no length or count bounds, so a legal view could otherwise exceed the declared 64 KiB machine and 4 096-byte human bounds; the reviewable and testable posture is an explicit, marked, verdict-neutral projection cap rather than an unguarded contract failure. | An unguarded contract failure on legal provider data; silently dropping a condition or evidence record; sorting labels/relations (provider order is the deterministic, source-faithful order); changing a verdict from a clamped value. |
| DEC-20 | **F-9 human-bound correction.** The human digest is byte-aware: `QUEUE_READY_MAX_HUMAN_SEGMENT_BYTES` (32) caps each per-candidate provider segment (`PR #<entityId>`, source ref) including a trailing `+`; header owner/name render at most 128 UTF-8 bytes each and branch at most 256 UTF-8 bytes; a candidate line is at most 400 UTF-8 bytes and header plus summary at most 620 UTF-8 bytes, so eight candidate lines plus header/summary stay within 4 096 bytes. If a legal payload still renders over `QUEUE_READY_MAX_HUMAN_BYTES`, the renderer drops trailing candidate lines in reverse rank order, keeps the header and summary, and marks `+more`; it never throws, exits non-zero, or emits an unbounded digest, and adds no reason token. The machine 65 536-byte bound remains UTF-8 bytes and is unaffected. | A 32-character cap is up to 128 UTF-8 bytes and an astral branch cap is up to four times its character count, so the former ASCII-only 400/620 derivation let a legal payload exceed 4 096 bytes and throw `fallback.internal`; byte accounting plus a defensive bounded fallback keeps the command total without changing any verdict, condition, rank, close class, error identity, or boundary. | Raising or removing the 4 096-byte cap; turning `fallback.internal` into a contract error for a legal payload; leaving the header or provider segments character-capped; dropping the header or summary instead of trailing candidate lines. |

## 20. PRIVACY / COMPLIANCE REVIEW

- The command is read-only and collects no telemetry. It performs no network writes and sends no repository data to a vendor other than the read-only GitHub API requests already required by the status collector.
- GitHub credentials resolve only through `CredentialPort`; resolved material never enters the payload, evidence, human text, logs, or diagnostics. The serialization redaction chokepoint covers the envelope and human output.
- Evidence is bounded to source ids, closed reasons, counts, work-item refs, label names, pull-request refs/identity, safe failure codes/classes, and safe bounded details. It carries no raw provider payload, response body, comment text, commit message, or repository file content.
- The candidate observation carries only the `blocked-by` relations the conditions consume (at most 16), and each relation target is projected as `entityId` only — `systemName` never enters the payload — with that `entityId` at most 128 characters, so the whole projected target identity object is bounded; every other relation kind is filtered out, so unrelated provider relationship data never enters the payload. Provider-derived identity, provider ref, label, owner, repository-name, head-branch, and timestamp values are projected only within their declared caps (DM-11), so provider data cannot enlarge the payload, and every clamp is visible as `value-clamped` plus `truncated`.
- The local PM context is read with the existing bounded projection: only `active_change` and `parked_changes` fields. Free-form `notes` and unrelated fields are never read into the payload.
- The human digest prints work-item refs, close classes, pull-request refs, and blocking condition ids only; no candidate title, body, comment, or free-form text appears in either output. Private-repository data remains local; no artifact is published by the command.
- The opt-in live evidence artifact must be bounded, secret-free, and reviewed before attachment; it is not committed by default.

## 21. SECURITY REVIEW HIGHLIGHTS

- **Read-only by construction:** the command calls no write/fence API, no tracker/PR/CI write, no provider engine, and no quota endpoint. It cannot mutate an artifact or provider state.
- **Credential centralization:** the only credential access is the credential port resolving the declared GitHub credential reference; command code reads no ambient environment and adds no secret-read allowlist entry.
- **No shell or spawn:** repository binding and HEAD facts come from the delivered bounded git metadata reads through the repository adapter; the command spawns no child process and executes no shell.
- **Bounded addressing:** only the `origin` remote is read; only `host: github.com` is accepted; userinfo and credentials in a remote URL are discarded; non-GitHub hosts are unavailable, not attempted.
- **Bounded parsing:** the local PM context uses the existing bounded YAML 1.2 core parse; parse failures are classified as evidence, never raw parser output.
- **Bounded input/output:** candidate refs (each at most 64 canonical characters), conditions, evidence records, detail characters, provider-derived identity/ref/label/relation/owner/name/branch/timestamp values, machine bytes, and human bytes are capped, with explicit truncation and `value-clamped` marking. No unbounded loop, retry storm, or pagination crawl.
- **No secret or raw payload leakage:** evidence carries closed reasons and bounded details only; the single serialization redaction path and planted-secret canaries apply. Provider payload failures surface as adapter-local classes, never raw bodies.
- **Brand neutrality:** no product or binary literal is committed; the human header uses the injected brand binary name. The only provider-specific literals are the declared credential key and the GitHub host, both declared provider data.
- **Denial-of-service:** the pure evaluator is linear over the capped candidate × condition × evidence space; no recursion over unbounded provider graphs; no arbitrary URL construction beyond the bound repository and the declared read endpoints.

## 22. MAINTENANCE & OPERATIONS IMPACT

- Adding a readiness condition is a contract change (condition id/order, derivation matrix, renderer line, tests); adding a close class or rank bucket is likewise a contract change.
- Changing the tier-label set, owner-attention label set, candidate cap, evidence cap, provider-derived projection caps, identity rule, or byte bounds updates the contract, tests, and docs without changing the evaluator architecture.
- A review-capable VCS source makes `merge-ready` reachable without a command change; a relation-capable tracker source makes `deps-satisfied` achievable without a command change.
- The command is provider-agnostic over normalized views; adding a tracker/VCS/CI provider is an addressing/config story owned elsewhere.
- Condition reasons are evidence vocabulary, not error-table identities; promoting one to an error row requires a named consumer and a reviewed change.
- The human renderer is pure, byte-aware, and bounded; a new condition or candidate line must fit the line/byte caps, and a legal payload that would still exceed the digest byte cap is reduced by the DM-12 reverse-rank line-drop fallback, never a runtime throw.
- Docs to keep current: the new queue-ready feature spec, the status digest (queue gap and shared inputs), provider engine/state/config consumer notes, the result contract (no new rows), the monorepo module/test inventory, the command registry (M0-S7 row and the `queue ready`-before-`queue` note), the glossary, and the index.
- Operational surface stays small: one read-only command, at most three outbound read calls bounded by one page each, one logical park-fold read, one config resolve, one local-context read, no daemon, no background process, and no new configuration knob.

| Provider availability | `parked` when an active provider or chain park exists, otherwise "no active park, engine not run"; never engine-verified. |
| Identity resolution | The §8.3 rule that matches a requested canonical ref to an observed normalized identity: exact canonical match first, then an unambiguous all-ASCII-digit suffix bridge, never substring, prefix-only, or numeric coercion. |
| Value clamp | Output-only shortening or count reduction of a provider-derived payload value to its declared cap; verdict-neutral, marked `value-clamped` and payload `truncated`. |
| Engine not run | The fixed evidence phrase for `provider-available`: the command read config and parks but never executed the provider engine. |
| Source at limit | The raw source page returned exactly its declared read limit, so more items or matches may exist. |
| Truncation | An explicit marker that evidence records, source coverage, or rendered human candidate lines were bounded; machine `truncated`, human `+more`. |

The `provider-available` rows list the case record only; every instance also carries the fixed companion record `{ source: "provider-config", reason: "engine-not-run" }` (F-9/DM-3/DM-10). `deps-satisfied` carries exactly one record; target-derived details are the state counts `done:<n>; open:<n>; unknown:<n>` whose counts sum to the total number of `blocked-by` relation targets (observed plus unobserved), with no target-ref list or per-target record. A raw page at a declared limit raises the payload-level `source-truncated` reason without changing any cell above. Candidate and target identities are resolved by the §8.3 rule before any cell is decided: candidate observation uses the requested candidate set, so an item whose provider id matches no candidate or whose suffix is ambiguous among the requested candidates is unobserved (`work-item-unobserved`); `blocked-by` target resolution uses the observed work-item set, so a target that matches no observed item, whose digit suffix is ambiguous among the observed work items, or whose canonical shape is not observed is unobserved (`dependency-unobserved`). The candidate observation projects only `blocked-by` relations (at most 16), each target projected as `entityId` only (at most 128 characters, never `systemName`); other relation kinds never reach the payload or any cell above.

Every `provider-available` condition carries `engine-not-run` as its second evidence record with source `provider-config` and no detail; the table lists the case record for each state. The `no-active-park`, `no-enabled-entry`, `all-entries-parked`, and `chain-parked` case records carry `detail: "chain:<name>"`, with `chain-parked` appending `; until:<expiry|none>; cause:<cause|none>`. A provider-config read failure is selected by the read's reason and is never blanket-mapped to `config-invalid`: `{ ok: false, reason: "config-invalid" }` uses `config-invalid` and `{ ok: false, reason: "provider-chain-unresolved" }` uses `provider-chain-unresolved`. A config or park failure record carries the read's bounded failure identity in the pinned `failureCode:<code>`, `failureClass:<class>`, or both joined by `; ` detail form, and carries no `detail` when the read supplies neither; the defensive `ok: true` declared-chain-missing view and `provider-chain-not-declared` carry no failure detail. `source-truncated` is a payload-level reason only (DM-1/DM-11) and never a condition or close evidence record.

`value-clamped` is a payload-level reason only (group 2, after `source-truncated` when both appear) and never a condition or close evidence record: it marks that a provider-derived payload identity, ref, label, label count, relation count, owner, repository name, head branch, or timestamp was clamped or reduced to its declared cap (DM-11). ### Appendix E — Close classification and rank matrix

| Association | Review signal | PR draft | Close class | Class rank (0-4) |
|---|---|---|---|---|
| Associated | Observed `approved` | Non-draft | `merge-ready` | 0 |
| Associated | Observed `changes-requested`/`open` or unavailable | Any | `review-pending` | 1 |
| Associated | Any | Draft | `review-pending` | 1 |
| Not associated | — | — | `new-start` if ready, else `not-ready` | 2 or 4 |
| Not associated, only matching merged/closed objects below the limit (evaluator-injected view only) | — | merged or closed | `new-start` if ready, else `not-ready` | 2 or 4 |
| Unknown | — | — | `unknown` if ready, else `not-ready` | 3 or 4 |

Association rules: at least three source-ref segments; any segment equals the candidate ref case-insensitively; only open, non-merged, non-closed pull requests are associated close items; the selected PR is chosen within one close class: the merge-ready set when it is non-empty, otherwise the full associated set, then by `entityId` ascending with a numeric-aware comparison (equal numeric all-ASCII-digit values are a tie at this key, otherwise lexical), then `sourceRef` ascending, then `targetRef` ascending, then the lexically smaller raw `entityId` string only when all three keys are equal; API return order never decides. The class rank order is unchanged. The delivered open-only command read cannot return a merged/closed object, so the merged/closed exclusion and `pr-not-open` are evaluator-input rules: when an injected normalized view contains a matching merged/closed object, it is never selected or counted. In such a view, below the page limit with no open match, `reason` is `pr-not-open` when a matching merged/closed object is present and `pr-not-associated` otherwise; the delivered open-only read always yields `pr-not-associated` below the limit with no open match. At the page limit with no open match, association is `unknown` with `pr-association-unknown` in both layers, even when merged/closed matches were injected. `associatedCount` counts open matches only, is exact below the page limit, is a page-bounded lower bound at the limit, is `0` when the read failed or the binding is unavailable, and is bounded by `0..QUEUE_READY_SOURCE_ITEM_LIMIT` (100) without a separate cap. The class rank column is the 0-4 bucket from DM-7; the payload `rank` field is the 1-based position after sorting. Candidate refs are matched to observed work items by the §8.3 identity rule before association, and `blocked-by` targets are matched by the same rule; the association segment comparison always uses the canonical candidate ref.

### Appendix F — Human digest grammar and example

```
<binary> queue ready <owner>/<name> @ <branch|detached> <sha7>
ready <n> | not-ready <n> | merge-ready <n> | review-pending <n> | unknown-close <n>
<rank>. <ref>  <closeClass>  <detail>  [repo:local-context; tier:priority-label]
...
```

Rules: the header is optional and appears only when the repository binding is observed and the SHA is resolved; exactly one summary line; exactly one line per rendered candidate in rank order; `<detail>` is `PR #<entityId> <sourceRef>` for an associated close item, `all six readiness conditions satisfied` for a new start, `close association unknown` for the unknown class, and `blocking: <id>=<state>, ...` for a not-ready candidate; every candidate line ends with the fixed proxy-source suffix `[repo:local-context; tier:priority-label]` after its detail and any `blocking:` segment, so the local-context and priority-label proxies are visible; when an associated close item is also not-ready, its line carries the close evidence followed by ` | blocking: <id>=<state>, ...`; `+more` follows the summary when the payload-level `truncated` is true (evidence-cap overflow, reason-cap overflow, source-at-limit, provider-derived value clamp, or byte-budget reduction; a candidate-local evidence drop always sets it too) or when the defensive reverse-rank line drop removed candidate lines; no titles, timestamps, raw payloads, secrets, or LLM prose; at most 16 lines and 4 096 UTF-8 bytes. Each per-candidate provider segment — `PR #<entityId>` and `<sourceRef>` — is rendered to at most `QUEUE_READY_MAX_HUMAN_SEGMENT_BYTES` (32) UTF-8 bytes including a trailing `+` when shortened; the `+` counts toward the 32-byte cap, no code point is split, and the payload keeps the clamped full values, so the digest never renders a provider value beyond its payload cap. The header renders owner and name to at most 128 UTF-8 bytes each and branch to at most 256 UTF-8 bytes, each with a trailing `+` when shortened; these are renderer rules only. Bound: a candidate line is at most 400 UTF-8 bytes (3-byte rank prefix, 64-byte ref, 14-byte close class, up to a 238-byte detail built from the two 32-byte segments and six `id=state` pairs, fixed ASCII separators, and the 41-byte proxy suffix; worst case 366 bytes), the header (excluding the injected binary name) plus the summary line at most 620 UTF-8 bytes (header fixed fields 537 bytes, summary 80 bytes including `+more`), so the maximum 10-line digest is at most 3 820 bytes plus the injected binary-name length (within 4 096 bytes for a binary name of at most 276 UTF-8 bytes). **Defensive fallback:** if a legal payload still renders above 4 096 UTF-8 bytes after every renderer cap, trailing candidate lines are dropped in reverse rank order (last-ranked candidate first), the header (when present) and summary line are kept, and the drop is marked `+more` after the summary; the renderer never throws, never exits non-zero, and never emits an unbounded digest, and `+more` is the existing truncation marker with no new reason token; the line drop is renderer-only and changes no payload field, including the payload `truncated` flag, while the summary line continues to report the payload-level counts.
