# TDR-0071: Change-Branch Resolution from the Change Record Read at the Delivery Request's Head, and That Request's Head as the Verified Head

> **Traceability.** Spec §15 **DEC-1** (one declared branch source, no derived fallback) and **DEC-2** (the resolved request's asserted head is the resolved head); §24-C reserves this record; §5.1 F-1; §8.1 API-1/API-2; §8.3 DM-1/DM-2; §9 NFR-2/NFR-6/NFR-10; §17.1 AC-F1-1…AC-F1-5, AC-F5-1/AC-F5-2, AC-F3-2; §19 seeding; §24-A the normative resolution order. Sibling records own the adjacent decisions: TDR-0072 (required-check authority and default gate membership) and TDR-0073 (refusal diagnostics contract and emitted-identity totality).
>
> **Amendment (2026-11-20, DoR gate finding).** The readiness gate found that the source this record originally chose — the `branch` key read through the invocation's working-tree pm-notes read — cannot deliver AC-F1-1: the change folder exists only on the change branch, so a run from the integration base finds no record and can only refuse. The declaration is now read **at the delivery request's asserted head** through one bounded local tree read (C-9 below), and the two items the gate left open are decided here: the branch-value cap is `MERGE_BRANCH_DECLARATION_MAX_CHARS = 256`, and an absent, unreadable, or malformed change record is the same refusal row as an absent declaration with a distinct closed reason. The head binding, exact equality, convergence by ref, and dry-run agreement are unchanged. No challenge verdict and no acceptance is claimed by this amendment. **Count note (2026-11-20, spec v2.0):** the specification's acceptance-criteria inventory moved to **24** ids — the 22 previously carried plus `AC-F2-8` (the merged report renders the merge-applicable projection the run evaluated) and `AC-F4-2` (the runtime-declaration negative control). Both new criteria belong to F-2 and F-4 and are therefore outside this record's causes; the binding subset in C-5 is unchanged, and only the count and the §17 enumeration are restated.

## Context

`merge` is the lifecycle landing path: it consumes a gate-verification record, enforces a freshness envelope, probes the tracker and CI, and lands through exactly one provider-side call. Every one of those steps needs two identities — *which change branch* and *which head commit* — and today both identities come from the operator's checkout rather than from the change.

- **FACT:** The production composition assigns the merge branch from the checkout's own git facts: `const mergeBranch = resolvedRepositoryFacts.head.branch;` under the doc comment "The checkout's own current branch, read from its git facts" (`packages/cli/src/production.ts:2477-2478`, read 2026-11-20). The merge composition holds no change-record branch source at all; the only change-record read in that composition obtains the pm-notes `milestone` (`production.ts:2703-2708`).
- **FACT:** The delivered pm-notes read is rooted at the **working tree**: `changesDirectory = \`${cwd}/doc/changes\`` (`production.ts:1897`), and `readPmNotesText` locates a folder under it through the injected filesystem port (`packages/adapters/src/file/pm-notes-parser.ts:198-210`). An in-flight change's folder exists only on the change branch: `git ls-tree origin/main-tools -- doc/changes/2026-11` contains no GH-366 folder, and carried no GH-350 folder before that change merged (verified 2026-11-20). A base-checkout run therefore answers `{ ok: false, reason: "missing" }` for an in-flight change, so the working-tree read cannot be the declaration's source in the scenario AC-F1-1 names.
- **FACT:** The transaction's only head source is the `readHead` port (`packages/core/src/domain/merge-transaction.ts:135`), wired to the checkout: `readHead: () => composition.git.head()` (`packages/cli/src/edge.ts:1590`, read 2026-11-20). One value feeds the freshness comparison (`merge-transaction.ts:575-587`), the check-run page read (`:596`), the landing's expected head (`:870`), the checks posture comparison (`:993`), the dry run's head (`:1200`) and its appended verification record's identity (`:1272`); this change's API contract adds the reported resolved head as one more consumer.
- **FACT:** Request identity is resolved by listing open requests with gate facts (`production.ts:2579-2581`) and taking the first entry whose `sourceRef` equals that checkout branch (`:2583-2586`); the bounded list page doubles as the request-detail read (`:2587-2591`). When no entry matches, the composition recovers a change ref by parsing the branch name (`changeRefInBranch`, `:488`, called at `:2593`) and looks for a merged request (`:2594-2599`); otherwise it returns `merge.transaction-aborted` (`:2601`).
- **FACT:** The delivered open-request entry carries the provider-asserted `sourceRef` and the asserted head commit (`packages/core/src/contracts/ports.ts:173`; `packages/core/src/contracts/closeout.ts:611`), and the list read is bounded by `TRUTH_PROVIDER_LIMIT` (`production.ts:492`). No provider operation is needed to obtain either value.
- **FACT:** The merge path performs no fetch. `merge-transaction.ts:541-542` states it as a design property ("no fetch puts the provider's merge commit in the checkout"), the git merge seam's operations are local (`head`, `rev-parse`, `merge-base`, `checkout`, `rebase`, `merge --squash`, `branch -D`: `packages/adapters/src/git/merge.ts:59-88`), and no typed path runs `git fetch` (repository grep, read 2026-11-20).
- **FACT:** The merge seam already performs bounded, fixed-argv, local object reads at a commit through an injected child runner — `treeOf(sha)` runs `rev-parse <sha>^{tree}` (`packages/adapters/src/git/merge.ts:66,242-247`). A local tree/blob read at a commit is the same class of operation: no shell, no network, no credential, and offline-testable through the seam's child-runner injection.
- **FACT:** The repository declares a branch convention for a change ref: `<type>/<workItemRef>/<slug>` (`doc/guides/unified-change-convention-tracker-agnostic-specification.md:177,203,347`), implemented as a delivered predicate in two places — `branchConvention` (`packages/adapters/src/git/index.ts:216-217`) and its copy in `packages/core/src/domain/closeout.ts:313-314`, where `selectMatchingBranch` uses it to find a change's branch from local refs. The merge resolution can reuse that declared convention instead of inventing a second one.
- **FACT:** The delivered `branch` value reaches the transaction only as `MergeTransactionConfig.branch` (`merge-transaction.ts:162`), passed conditionally from the composition (`production.ts:2665`), and its sole consumer is post-landing branch deletion, which first restores the checkout to the base and then deletes that branch (`merge-transaction.ts:884-887`; `edge.ts:1571-1578`). A merge invoked from the integration base therefore names the integration base for deletion after a successful landing.
- **FACT:** The pm-notes document has no closed key set: "Every extra top-level key, phase key, or entry key is opaque: it is preserved and never inspected" (`doc/spec/features/feature-pm-notes-lint-and-phase-transitions.md:36`), and every document-writing branch preserves extras value-faithfully (`:77`).
- **FACT:** The committed change record is already read by a production composition, and its parse is delivered: `readPmNotesText({ changeRef, changesDirectory, fs })` returns the located path, the text, and the parsed value (`packages/adapters/src/file/pm-notes-parser.ts:198-210`), and the closeout composition consumes the `milestone` key from it (`production.ts:2703-2708`). The parse itself is separable from acquisition — `parsePmNotesText(text, file)` takes text and a path (`pm-notes-parser.ts:167-195`) — so text obtained from a commit can be parsed by the delivered parser with no new parser. An absent record answers `{ ok: false, reason: "missing" }`; an unreadable or malformed one carries the located path.
- **FACT:** An exact-equality resolution rule with a bounded page already exists on the battery side: `resolveOpenPr` filters `item.sourceRef === branch` with no prefix or substring matching, treats a saturated bounded page as ambiguous, and answers `branch-unresolved`, `no-open-pr`, `branch-mismatch`, `ambiguous-open-pr`, or `resolved` (`packages/core/src/domain/verify-gates.ts:186-229`; page saturation at `:98-99`; open-request limit 100 at `packages/core/src/contracts/verify-gates.ts:146`). It keys on the checkout branch and a detached-HEAD fact, which is exactly what the merge path may not do.
- **FACT:** The merge error table carries no branch-resolution or request-resolution row today (`grep "branch-unresolved|request-unresolved"` over `packages/core/src` finds only battery-side gate reasons), and `merge.transaction-aborted` declares `retryable: true` with the remediation "Clear the named pre-mutation condition and retry" while receiving request and work-item not-found reads (`packages/core/src/contracts/error-table.ts:960-968`; `production.ts:2456-2460`).
- **FACT:** GH-366 authors its own declaration so the change is mergeable by its own contract: `branch: fix/GH-366/merge-command-conformance` (`chg-GH-366-pm-notes.yaml:5-8`).
- **Why now:** The observed failures are one defect seen twice. A run started from the integration base reproduced evidence about the base tip and could report `result=verified` for a head unrelated to the change; and a run whose request could not be matched from that branch surfaced as an opaque abort. Both follow from the same root cause: the merge path's identity inputs are ambient checkout facts, so the verified object and the merged object can differ without any code being "wrong" relative to its own contract. That contract is written down and has to move with the behaviour: the merge feature spec states the branch comes "from the checkout's git facts" (`doc/spec/features/feature-merge-verify-deploy.md:36-45`) and that the recorded head must equal "the current head" (`:160-165`).
- **Why this amendment:** Declaring the branch on the change record is necessary but not sufficient. The record lives on the change branch, and the delivered read is rooted at the invocation's working tree, so the declaration is invisible precisely where the verdict is needed. A declaration that the run cannot read is a refusal, not a capability. The amendment therefore keeps the declaration as the single authority and moves only *where it is read from*: the commit the run is about — the delivery request's asserted head — obtained from one bounded local tree read. This is the same principle the record already applies to the head: the object that lands supplies the facts that govern it.

## Problem Framing (Clarified)

The symptom is "a merge run verified the base". The cause is that `merge` resolves the two identities that decide what it verifies and what it lands from the invocation's environment:

1. **Which branch is the change branch?** Today: whichever branch the checkout happens to be on. That value then selects the delivery request. So the selection is circular — the request is chosen to match the checkout rather than to match the change.
2. **Which head is the verified head?** Today: the checkout's `HEAD`. The freshness envelope compares a record against it, the check-run page is read for it, and the landing's expected head is it. If the checkout is on the base, all three are about the base — and the run is internally consistent while being externally wrong.
3. **What happens when the environment cannot answer?** Today: a name parse guesses a change ref, and when the guess also fails the operator receives a generic abort that names no condition.

Stated as decision questions:

- **Q1 — Authority.** Which committed artifact is the one place a change declares its branch, and *where is that artifact read from* so the declaration is reachable from any checkout? *(A declaration that governs and is readable where it lives, or a value that is inferred or merely visible from one directory?)*
- **Q2 — Identity.** How does one declared branch become exactly one delivery request, and what happens when it becomes zero or several? *(Exact match with a refusal, or a ranking/heuristic?)*
- **Q3 — Binding.** How far does the matched request's head reach? *(Only the report, or the freshness comparison, the probe, the expected head, and the dry run as well?)*

**The non-obvious part, stated because it is the whole decision.** Q1 and Q3 are one question wearing two hats. Removing the checkout branch assignment while leaving `readHead` on the checkout head changes the *label* on the verdict and nothing else: the run would resolve the right request, then compare the record to the checkout's `HEAD`, read the check-run page for the checkout's `HEAD`, and land with the checkout's `HEAD` as the expected head. That is the same defect with a better-looking report. Deciding the branch source without binding the head is a partial delivery that is worse than neither, because the report now claims the change while the evidence is still about the base. This record therefore decides them together, and §Implementation Plan forbids a mixed state.

**The second non-obvious part (added by the 2026-11-20 amendment).** Q1 has a sub-question the original framing missed: a declaration is only an authority if the run can read it. The change record lives on the change branch; a working-tree read is rooted at the invocation's `cwd`, so from the integration base it finds nothing. A mechanism that names the record as the authority but reads it from one directory is a refusal generator in the scenario the capability exists for. The fix is not a second source and not a fallback: it is to read the declaration **at the commit the run is about** — the delivery request's asserted head — so the declaration that governs is the one that ships with the head that lands. The authority does not move; only the read's address does. That is also why the candidate request is identified by the repository's declared branch convention and then *confirmed* by exact equality with the record's own declaration: the convention narrows where to look, and the declaration still decides.

**Deliberately out of scope, so the boundary is reviewable.** No required-check authority or gate membership (TDR-0072). No refusal-diagnostics contract, retryability rule, or `merge.work-item-unresolved` row (TDR-0073); this record decides only the two rows its own causes reach, plus the closed reason vocabulary those two rows carry. No automatic writer for the declaration (spec NG-5, OQ-1). No battery-side resolution (OQ-3): `verify gates` keeps its delivered resolution, so a base-checkout dry run produces a record about the *request* head while the battery's own records still describe the checkout it ran in. No fetch policy for an absent head object (the amendment refuses instead; see DC-2 and the revisit trigger). No branch-name grammar validated on the declaration's value: the candidate filter reuses the repository's already-declared `<type>/<REF>/<slug>` convention and is not a second grammar.

## Constraints (Hard Requirements)

These are the gates an alternative must pass to be *eligible*. Each is independently sourced from the change's acceptance criteria, NFRs, and non-goals; requirements that merely restate this record's chosen design are stated later as decision-derived rules and are **not** used to eliminate alternatives.

### C-1: No new configuration key, state record kind, schema version, or provider capability

- **Statement:** The branch declaration is an additive top-level key on the existing committed change artifact. The configuration key set is unchanged (no `merge.<something>` key names a branch), no state record kind or payload schema version is added, and no new provider operation, capability, scope, or credential reference appears. The two new refusal rows introduce no capability. A **local git object read** at a commit is not a provider capability: it adds no network call, no credential, no provider operation, and no adapter operation on any provider contract.
- **Source:** AC (spec §8.5, §7.1, NFR-2/NFR-6, DEC-9, DM-1; NG-1, NG-3)
- **Verification:** test (configuration key-set equality with its pin; record-kind and schema-version inventories equal their pins; adapter capability and operation sets equal their pins) + code review
- **Negotiable:** no

### C-2: Fail closed, never fall back to ambient state

- **Statement:** A change whose record is absent, unreadable or malformed at its request head, or whose record declares no branch or an unusable value (empty, whitespace-bearing, control-character-bearing, or over `MERGE_BRANCH_DECLARATION_MAX_CHARS = 256`), refuses `merge.branch-unresolved` naming the candidate's source ref, the change-record tree path or the search path, the `branch` key, and exactly one closed reason, with zero landing calls, zero retries, and no provider read beyond the single bounded open-request list read that locates the record. A declaration that does not equal its own request's source ref refuses rather than being accepted. The checkout's branch is never a candidate, the checkout's head is never the verified head, no fetch is attempted to make a head readable, and no run-time derivation (change-folder slug, spec `change.type`, ref arithmetic, provider list as authority) supplies a substitute.
- **Source:** AC (spec F-1 steps 1–2, AC-F1-1, AC-F1-3, AC-F5-2, NFR-6; DEC-1)
- **Verification:** test (each closed reason is observed against a provider double that fails the test if any provider read beyond the one list read occurs, and against a git double for the unreadable case; a production-source scan for the checkout branch, checkout head, working-tree change-record, and fetch reads on the merge path, with a mandatory failing control) + code review
- **Negotiable:** no

### C-3: Additive within v1, and exactly the two error rows this decision owns

- **Statement:** `merge.branch-unresolved` and `merge.request-unresolved` are the only identities this record adds, and both are additive: no existing code changes identity, exit, category, consequence, or projection. `merge.work-item-unresolved` is the sibling record's scope and is not decided here. `merge.transaction-aborted` no longer receives the two causes these rows now carry, while its code, category, consequence, and projection are unchanged.
- **Source:** AC (spec §7.1, §8.5, AC-F1-3, AC-F1-4, Appendix B; DEC-6; §24-C)
- **Verification:** test (the error-row inventory delta equals exactly these two codes; every pre-existing merge row's fields are byte-identical to their pin; the machine and documented tables move together) + code review
- **Negotiable:** no

### C-4: Bounded reads, no retry, no pagination

- **Statement:** Per invocation the resolution uses exactly one provider read — the delivered bounded open-request list read, which is also the request-detail read (`production.ts:2587-2591`) — plus at most `MERGE_BRANCH_CANDIDATE_MAX = 3` bounded change-record reads at candidate heads. A change-record read is one port call implemented as at most two fixed-argv local git invocations (`ls-tree -r --name-only <sha> -- <pathspec>`, then one blob read) with a byte bound of `MERGE_CHANGE_RECORD_MAX_BYTES = 262_144`, so the worst case is six local git invocations and zero network calls. Zero retries and zero pagination anywhere on the path. The branch refusal performs zero landing calls and no provider read beyond that one list read. The invocation's total stays within the spec's read budget.
- **Source:** AC (spec NFR-2, NFR-10, AC-F1-3)
- **Verification:** test (per-invocation read counts on the success, branch-refusal, request-refusal, and stale paths; a counting git double asserting the candidate cap and the per-candidate invocation bound; the branch-refusal path asserts one provider read and no additional provider read) + code review
- **Negotiable:** no

### C-5: The verification surface is the spec's 24 acceptance criteria (v2.0)

- **Statement:** The change's acceptance criteria (spec §17, **24 ids in spec v2.0**: AC-F1-1…AC-F1-5, AC-F2-1…AC-F2-8, AC-F3-1…AC-F3-6, AC-F4-1, AC-F4-2, AC-F5-1…AC-F5-3) are the verification surface. **This decision binds:** AC-F1-1, AC-F1-2, AC-F1-3, AC-F1-4, AC-F1-5, AC-F5-1, AC-F5-2, and AC-F3-2 (the credential refusal reached on the resolution's request-list read names the reference, the environment variable, and the operation). It touches AC-F3-1 and AC-F3-6 only to the extent that the two rows it owns must name their cause and must not overstate retryability; their wording and the row-level honesty rule are TDR-0073's. The two criteria added at v2.0 — AC-F2-8 (merged-report projection) and AC-F4-2 (runtime-declaration negative control) — belong to F-2 and F-4 and are not bound by this record.
- **Source:** AC (spec §17.1, §17.5, §17.3)
- **Verification:** test (the planned cases for those criteria, including the prefix-collision control and the both-SHAs stale refusal) + review
- **Negotiable:** no

### C-6: The branch is a declared change fact, not invocation state

- **Statement:** The value is authored with the change and committed with it, so it is reviewed in the change's diff and read from the artifact at run time. It is read **at the delivery request's asserted head** — the commit that will land — never from an arbitrary working tree, and never from the invocation's checkout. It is not derived, not inferred from a naming convention, and not taken from the provider's list: the provider's list supplies the candidate *address* (a source ref that follows the repository's convention, and its head), and the record's declaration supplies the *value*, which must equal that source ref exactly. The declaration carries no schema version and no other surface may read it.
- **Source:** internal standard (the system's declared-sources rule) + AC (spec §8.5, DEC-1, DM-1)
- **Verification:** code review (the only reader is the merge resolution) + test (a changed declaration changes the resolved branch; a stale, absent, or disagreeing one refuses; a record read at a candidate head governs over a different record in the checkout's working tree)
- **Negotiable:** no

### C-7: Exact equality only for request identity

- **Statement:** Exactly one candidate is accepted, and only when its change record — read at that candidate's own asserted head — declares a usable `branch` value that equals the candidate's provider-asserted source ref as an exact string. No prefix, suffix, glob, or change-ref-substring matching exists. The candidate set is the open entries whose source ref follows the repository's declared `<type>/<REF>/<slug>` convention for the invocation's change ref; that convention narrows where to look and never decides the value. A bounded list page that saturates cannot establish uniqueness and is therefore ambiguous. A candidate whose asserted head is absent or not a full hex SHA is a head-unresolved condition and is never read. No branch-name grammar is validated beyond usability.
- **Source:** AC (spec F-1 steps 3–4, AC-F1-4, AC-F2-4 delivered full-SHA rule)
- **Verification:** test (a prefix-colliding branch does not match; a saturated page refuses as ambiguous; a candidate whose record disagrees with its own source ref refuses; a short or absent head refuses `head-unresolved` before any record read; a valid full-SHA head with a matching declaration resolves) + code review
- **Negotiable:** no

### C-8: One resolution for the dry run and the real merge

- **Statement:** Both invocations resolve the branch, the request, and the head through the same resolution and report the same resolved object (branch, resolution source, request identity, resolved head). The dry run's appended verification record carries the resolved head as its identity; the dry run still writes no waiver, no transaction, no git mutation, and never reports `result=merged` or `squash=`.
- **Source:** AC (spec F-5, AC-F5-1, AC-F5-2, API-2)
- **Verification:** test (one fixture, one context: the two reports' resolved objects are equal; the dry run's record head equals the resolved head; zero mutation assertions stay green) + code review
- **Negotiable:** no

### C-9: The declaration resolves from the integration-base checkout

- **Statement:** The branch declaration is resolvable by a `merge` invocation that runs **from the integration base**, whose working tree contains no change folder for the change being merged (AC-F1-1's given). A mechanism whose declaration source exists only on the change branch does not satisfy this, however faithfully it refuses.
- **Source:** AC (spec **AC-F1-1** at `chg-GH-366-spec.md:693`, AC-F5-2, §6 Flow 1 at `:409-412`; the owner's acceptance item 1 / regression (a)) — this is the gate the original matrix missed, and every alternative below is re-scored against it.
- **Verification:** test (a fixture whose worktree has **no** change folder and whose HEAD is the base tip; the resolution must resolve the declaration and the request head — a fixture that writes the record into the checkout does not satisfy this) + code review
- **Negotiable:** no

**Table stakes.** Every alternative below keeps the delivered determinism and offline guarantees (NFR-1, NFR-4), the declared output bounds (NFR-3), secret hygiene (NFR-9), the unchanged effective gate-set identity (NFR-8), and zero landing calls on any refusal. None of these eliminates an alternative.

## Decision Drivers

1. **The verdict must describe the object that lands.** This is the change's reason to exist; a pre-flight or verification verdict about a different object is actively worse than no verdict.
2. **One declared authority, reviewable before the run.** A branch that appears in the change's diff can be reviewed, blamed, and corrected; a value inferred at run time can only be explained.
3. **Fail closed over convenience.** A named refusal that says "this change declares no branch" costs one authoring act; a fallback silently reintroduces exactly the ambient coupling being removed.
4. **No new surface.** The cheapest correct mechanism adds no configuration key, no schema, no record kind, no provider capability, and at most one bounded local read.
5. **Paved road.** Reuse the delivered pm-notes parse, the delivered exact-match resolution shape, the delivered request list/detail read, the delivered branch convention, the delivered local git seam, and the delivered error table rather than inventing a parallel mechanism.
6. **Determinism and offline provability.** A local object read at a commit plus a pure exact match is testable with no provider and no clock; the ambient checkout is a hidden input that makes the same fixture behave differently in two directories. The same provider state must resolve the same way from any checkout — a verdict that depends on which clone ran it is the defect wearing a new label.
7. **Operator legibility.** The refusal names the path, the key, the branch, its resolution source, the candidates observed, and the closed cause, so the repair is obvious and the run is diagnosable.
8. **The pre-flight must be true.** A dry run is worth running only if it describes the object the merge would land.
9. **Adopter cost is stated, not hidden.** The new obligation is one line per change; it must be documented where a change is authored, not discovered at merge time.
10. **Reachability.** A declaration the run cannot read is not an authority. The mechanism must resolve the declaration from the integration base, because that is where a coordinator runs the landing — otherwise the change ships a refusal where the capability was promised.

## Mental Models & Techniques Used

- **First principles:** What must be true for "the verdict is about the object that lands" to hold? (i) one branch identity, (ii) one head identity, (iii) one equality that ties the evidence to that head, (iv) one landing at that head, (v) an honest refusal at every join, and (vi) a declaration the run can actually read from where it runs. Six requirements produce one declared key read at one address (the request head), one exact match that confirms it, and one head value — and rule out every mechanism that buys convenience by re-admitting ambient state.
- **Inversion:** How could this change make the system worse than before? Reintroduce a fallback "just for this one case"; match on a prefix so a same-family branch resolves; bind the branch but not the head; let a bounded, saturated page prove a negative; name a refusal whose remediation does not apply to it; **accept a request on the convention because the declaration was inconvenient to read** — which makes the same provider state resolve differently in two clones, the very ambient coupling being removed; **fetch inside the resolution** to make an absent object readable, turning a local fail-closed refusal into a network operation with its own credential and failure surface. Each inversion is answered by a gate or a decision-derived rule below.
- **Second-order thinking:** Three consequences are not obvious from the goal. First, removing the branch read while keeping the head port leaves the defect intact behind a better report — which is why the two bindings are decided and delivered together. Second, the `branch` value already feeds post-landing deletion, so a base-checkout run names the *base* for deletion after a successful landing; the same declaration that fixes verification also fixes what gets deleted. Third, naming the change record as the authority without asking where it is readable produces a refusal where the capability was promised; the amendment's read-at-the-head rule is the second-order fix, and it incidentally makes the declaration a property of the commit that lands rather than of whatever is checked out.
- **Systems thinking:** The chain is: change ref → bounded open-request list → candidate source refs (by the declared convention) → record text at the candidate's asserted head → delivered parse → declaration → exact equality → asserted head → freshness comparison → check-run page → gate verdicts → expected head → landing → report. Each join is a place where an ambient fact can be substituted for a declared one. The decision pins every join, and the read budget pins the cost of doing so.
- **Opportunity cost:** A fallback buys a run that succeeds from a badly-authored change and costs the property the change exists to establish: that a merge verdict is about the change. A configuration key buys per-repository convenience and costs the correct semantics, because a change branch is per change.
- **OODA / KISS:** Observe the declared record, orient on one exact match, decide on one head, act at most once. One authority, one comparison, one refusal per join, no retry, no pagination.

### Alternative 0 — Baseline: Keep the Checkout-Branch Resolution and Document It

- **Eligibility:** Not eligible (fails C-2, C-5, C-6, C-8, C-9).
- **Summary:** Change nothing; state plainly in the reference page and the feature spec that `merge` must be run from the change branch, and that a run from the integration base verifies the base.
- **Constraint compliance:** Passes C-1, C-3, C-4, C-7 trivially. Fails C-2: the checkout branch and head remain the identity inputs, so a run that cannot answer falls back to whatever directory it is in. Fails C-6: no declared fact exists. Fails C-8: a dry run and a merge from different directories describe different objects. Fails C-9: from the base checkout there is no declaration to resolve. Fails C-5: AC-F1-1, AC-F1-2, AC-F1-5, AC-F5-2 are unsatisfiable by documentation.
- **Driver fit:** Fails drivers 1, 2, 3, 6, 8, 10; serves only "no authoring obligation".
- **Pros:** Zero change; zero new obligation; no adopter cost.
- **Cons:** The observed defect stays: a base-checkout run verifies the base tip and reports a vacuous all-pass; the opaque abort stays; the dry run keeps describing a different object from the merge; and the feature spec would be documenting a known-wrong contract as intended.
- **Why rejected:** Documentation cannot make a verdict about an object the run did not examine. This is the defect the change exists to remove.

### Alternative 1 — Derive the Branch from the Change-Folder Slug and the Spec's `change.type`

- **Eligibility:** Not eligible (fails C-2, C-5, C-6, C-9).
- **Summary:** Read the change folder name and the spec front matter's `change.type`, and compose `<type>/<ref>/<slug>` as the branch.
- **Constraint compliance:** Fails C-2: the value is derived at run time, so a naming-convention change silently re-points the merge and no artifact states which branch was intended. Fails C-6: nothing declares the branch. Fails C-9: the folder and the spec live on the change branch, so the derivation has no input in the base checkout — the same defect the amendment fixes for ALT-5. Fails C-5: with no declaration, AC-F1-3's "declares no usable branch" refusal has no subject. C-4 at risk: it adds a second change-artifact parse (markdown front matter) beyond the one bounded change-record read.
- **Driver fit:** Fails drivers 2, 3, 5, 6, 10; the derivation is testable but its correctness depends on an unwritten convention, and it is unreadable where it is needed.
- **Pros:** No authoring obligation; the branch "already follows" a convention in practice.
- **Cons:** Adds a parser for a document the merge path does not otherwise read; assumes a branch-prefix convention that the repository never declared; a change whose branch deviates from the convention resolves to the wrong branch and then refuses `no-open-request` with a true-but-useless message; the authority for the branch becomes a filename; nothing to read from the base.
- **Why rejected:** It swaps an ambient fact (the checkout) for an inferred one (the folder name) and calls that a fix. Both fail the same gates.

### Alternative 2 — Add a Configuration Key

- **Eligibility:** Not eligible (fails C-1, C-5, C-6).
- **Summary:** Add a `merge.branch`-style key (or a per-change mapping in the configuration document) and resolve the branch from it.
- **Constraint compliance:** Fails C-1 outright: no new configuration key is admissible. Fails C-6: a configuration document is repository-scoped, so a per-change branch cannot be truthfully expressed there without a mapping table — which is a second source of change facts. Fails C-5: AC-F1-3's premise is a change record that declares no branch, so a mechanism without a change-record declaration satisfies neither the refusal nor the AC. C-9 is the one gate it would pass — the configuration document is on the base — and that is precisely the trap it sets: it buys reachability with the wrong scope.
- **Driver fit:** Fails drivers 2, 4, 6; serves "one obvious place to look" at the cost of the wrong scope.
- **Pros:** Familiar mechanism; validated at configuration resolution; one place for an operator to edit; readable from any checkout.
- **Cons:** Makes a per-change fact a per-repository setting; every change's branch would collide in one document or need a map keyed by ref, which is a change artifact inside a config file; adds a key to a pinned key set and a validation surface.
- **Why rejected:** The change branch is a property of the change, not of the repository. Encoding it as configuration is a category error with a permanent schema cost.

### Alternative 3 — Resolve the Branch Purely from the Open-Request List

- **Eligibility:** Not eligible (fails C-2, C-5, C-6, C-7).
- **Summary:** Read the bounded open-request list and choose the request that belongs to the invocation's change ref — by title, by head position, or by the sole open request — and take its source ref as the branch.
- **Constraint compliance:** Fails C-6: the provider list becomes the branch authority. Fails C-2: with no declared expectation there is no way to detect the absent or ambiguous case — "the only open request" is a fallback dressed as a rule. Fails C-7: relating a request to a ref without an exact declared value requires substring, title, or ordering inference. Fails C-5: AC-F1-3 and AC-F1-4 have no declared branch to be absent or to count matches against. It passes C-9, which is why the selected alternative keeps its *reachability* (the list read) and discards its *authority*.
- **Driver fit:** Fails drivers 1, 2, 3, 6, 7, 10; it inverts the authority, so the run cannot say which object it intended to merge, only which one it found.
- **Pros:** No authoring obligation; no local object read; one provider read.
- **Cons:** With two open requests the selection is arbitrary or needs a heuristic; a base-checkout run would confidently merge whichever request the heuristic picked; the operator cannot pre-declare intent; the ambiguity that the change exists to name becomes undetectable by construction.
- **Why rejected:** It removes the declaration and therefore removes the ability to be wrong out loud — the opposite of a fail-closed contract.

### Alternative 4 — Declare the Branch on the Change Spec's Front Matter

- **Eligibility:** Not eligible (fails C-9).
- **Summary:** Add the declaration to the change specification's YAML front matter (`change.branch`) and read it from there.
- **Constraint compliance:** Passes C-1…C-3 and C-5…C-8. C-4 is at risk, not failed: the spec is a markdown document with a front-matter block, so reading it needs a parse the merge path does not have today. **Fails C-9:** the spec, like the pm-notes, exists only on the change branch, so a base checkout cannot read it. The move of the *surface* does not move the *address*. C-9 is exactly the distinction the original record missed, and it is why the amendment changes the read's address rather than the declaration's home.
- **Driver fit:** Satisfies drivers 1, 2, 3, 4, 7, 8; fails drivers 6 and 10 — unreadable from the base, and a new artifact parse.
- **Pros:** The spec is the change's most-read document; the declaration would sit beside the change's type and title where an author already works.
- **Cons:** New front-matter parsing on the merge path; the spec document's extra-key tolerance is not a declared contract (the pm-notes one is); the closeout composition would still read the pm-notes, so a change's facts stay split across two documents read by two parsers; still invisible from the base.
- **Why rejected:** It is correct in the change-branch checkout and silent in the base checkout — the same reachability failure as ALT-5, with an additional parser.

- **Eligibility:** Not eligible against the amended gate set (fails **C-5 and C-9**).
- **Summary:** This is the alternative the record originally selected: one additive top-level `branch` key on the committed pm-notes document, read through the delivered working-tree text read, then one exact-match request resolution with the head bound as this record still decides it (DC-4, DC-5).
- **Constraint compliance:** Passes C-1…C-4 and C-6…C-8 as originally scored, and every part of it that this record still adopts is unchanged. **Fails C-9:** the read is rooted at `${cwd}/doc/changes` (`production.ts:1897`) and an in-flight change's folder exists only on the change branch, so the base-checkout run answers `missing`. **Fails C-5** for the same reason: AC-F1-1 cannot be satisfied by it.
- **Driver fit:** Satisfies drivers 1–3 and 5–9 when the record is readable; fails driver 10 (reachability) and driver 6 (the verdict would depend on which directory ran it).
- **Pros:** Everything this record still adopts — the declared key, the delivered parse, exact matching, the head binding, the dry run's agreement, no new provider surface.
- **Cons:** It delivers a refusal, not a capability, in the scenario the change exists for. The DoR gate found this by checking the tree: `origin/main-tools` has no GH-366 folder, and had none for GH-350 before that change merged.
- **Why rejected (what the amendment keeps and what it changes):** The declaration's home, the parse, the exact-equality rule, the head binding, convergence by ref, and the two refusal rows are kept. Only the read's *address* changes: from the invocation's working tree to the delivery request's asserted head. No new authority is introduced, and no fallback is added.

### Alternative 6 — Selected: Read the Declaration at the Delivery Request's Asserted Head

- **Eligibility:** Eligible.
- **Summary:** One additive top-level `branch` key on the committed pm-notes document stays the authority. The resolution first takes the one delivered bounded open-request list read, narrows the candidates to the open requests whose provider-asserted source ref follows the repository's declared `<type>/<REF>/<slug>` convention for the change ref (at most `MERGE_BRANCH_CANDIDATE_MAX = 3`), reads each candidate's record **at that candidate's asserted head** through one bounded local git tree read, and accepts exactly one candidate whose record declares a usable value equal to that candidate's own source ref. The accepted request's asserted head binds the envelope, the probe, the expected head, the report, and the dry run. Anything else refuses by name.
- **Constraint compliance:** Passes C-1…C-9 (matrix above). Table stakes satisfied. The decision-derived rules below are the consequences it commits to.
- **Driver fit:** Best on net across every driver: the verdict is about the merged object (1); the authority is the record's declaration, reviewable in the change's diff (2); a missing, unreadable or disagreeing declaration refuses rather than falling back (3); no key/schema/record/provider capability is added and the only new read is one bounded local object read (4); the delivered parse, list read, branch convention, exact-match shape, git seam, and error table are reused (5); a local object read plus a pure match is offline-deterministic **and resolves the same way from any checkout** (6); the refusal names the path, the candidate, the branch and the closed cause (7); the dry run is true (8); the adopter obligation is still one documented line (9); and the declaration resolves from the integration base (10).
- **Pros:** The declared authority reaches where the run happens; the declaration that governs is the one at the commit that lands; the provider list supplies an address and never a value; a copied or stale record is caught by `declaration-disagrees` instead of being silently accepted; exact matching with no inference; one head value everywhere; the base-checkout merge becomes safe, including the deletion target; the branch-name parse is deleted with its failure mode; no schema, record kind, provider capability, credential, or configuration change; the new read is local, fixed-argv, bounded, and offline-testable through the seam's existing child-runner injection.
- **Cons:** Every in-flight change and every adopter must author one line before merging; the declaration is opaque to lint, so a typo is caught at merge time; exact equality is brittle for fork-origin requests; the resolution must precede the freshness envelope, reordering the transaction's reads; the branch refusal can no longer claim zero provider reads, because locating the record costs the one list read the request resolution needs anyway; a clone that lacks the request head's object refuses `record-unreadable` instead of resolving; a branch that does not follow the repository's convention is invisible to the candidate filter and refuses `no-open-request`.
- **Why chosen:** It is the only eligible alternative that satisfies every independently sourced gate — including the one the original matrix was missing — while keeping one declared authority and a fail-closed refusal. Among the reachable options it is the only one where the declaration still decides: ALT-3 removes it, ALT-7 and ALT-8 demote it to an optional cross-check, and ALT-9 moves it away from the artifact the owner asked for. Its cost is stated rather than hidden: one bounded local read, one restated read-count claim, and an explicit refusal when the object is not local.

### Alternative 7 — Request-First with Record Confirmation when Readable (the gate's ALT-B)

- **Eligibility:** Not eligible (fails C-2, C-5, C-6).
- **Summary:** Resolve the branch by convention over the open-request list. If the change folder happens to be readable in the invocation checkout, require agreement (disagreement refuses); if it is not, accept the request as the authority and report `resolution=request-convention`.
- **Constraint compliance:** Fails C-6: in the base-checkout case — the case that matters — the provider's source ref plus a convention is the authority, and the declaration is never read. Fails C-2: with no declared expectation there is nothing to be absent, so AC-F1-3's refusal has no subject in exactly the scenario it is tested in. Fails C-5: AC-F1-3 becomes unenforceable where AC-F1-1 applies. C-7 is at risk: acceptance without a declared value is a convention match, not an equality.
- **Driver fit:** Fails drivers 2, 3, 6, 7, 10; serves only "cheapest and always resolves".
- **Pros:** No new read; resolves in every clone; no provider operation added.
- **Cons:** The declaration stops being the authority precisely where it is inconvenient to read; a change whose record names another branch merges anyway; the rule reported as `request-convention` is a different rule from the one the record claims, and the same provider state can resolve differently in two clones (record present vs absent).
- **Why rejected:** It buys availability by giving up the property the change exists to establish. A verdict that is right in one clone and unverifiable in another is not one authority; it is two rules with one name.

### Alternative 8 — Hybrid: Head Read when Resolvable, Convention Otherwise (the gate's ALT-D)

- **Eligibility:** Not eligible (fails C-2, C-6, C-8).
- **Summary:** ALT-6 when the head object is locally resolvable; ALT-7 otherwise; report the resolution source so the operator can see which answered.
- **Constraint compliance:** Fails C-2 and C-6 for the same reasons as ALT-7 in its fallback branch. **Fails C-8**, which is the decisive one: the same provider state produces a *different acceptance decision* depending on whether the running clone happens to hold the object. Clone A (record readable, declaration wrong) refuses; clone B (record absent) accepts by convention. A dry run in one clone and a merge in another can therefore disagree about the same object — the exact ambient coupling this record removes, reintroduced as a feature.
- **Driver fit:** Fails drivers 3 and 6; the reported resolution source makes the divergence visible but not absent.
- **Pros:** Resolves in every clone; keeps the declaration authoritative when readable; no silent divergence.
- **Cons:** Two authorities with a switch between them; a change can merge in one clone and stall in another; the "which rule answered" report is an admission that the contract has two rules.
- **Why rejected:** Fail-closed divergence is acceptable; **verdict** divergence is not. ALT-6 refuses in both clones (with different reasons); ALT-8 accepts in one and refuses in the other.

### Alternative 9 — Move the Declaration to a Base-Readable Surface (the gate's ALT-C)

- **Eligibility:** Not eligible (fails C-1 and C-9; C-5/C-6 at risk).
- **Summary:** Two variants. (a) Declare the branch on the work item (ticket body or label). (b) Keep a committed index on the integration base mapping change ref → branch, and read the index.
- **Constraint compliance:** Variant (a) fails C-1: writing the declaration to the tracker adds a new provider write operation, scope, and credential surface to a read-only resolution path — the one thing C-1 forbids outright. Variant (b) fails C-9 in the only form a change can author: an index entry committed **in the change's own PR** reaches the base only when the change merges, so the base checkout cannot see it for the change it is merging. Making it visible earlier requires a direct write to the integration base outside the change's PR — a workflow change with a shared-file conflict hotspot, and a second artifact to keep in sync with the record (C-5, C-6 at risk).
- **Driver fit:** Fails drivers 2, 4, 5, 9; it buys reachability with a new write surface or a duplicated fact.
- **Pros:** Truly base-readable; no new read at merge time (variant b).
- **Cons:** A tracker write on the resolution path, or a base-branch artifact every change must edit outside its own review; two places state the branch, so the declaration is no longer one authority.
- **Why rejected:** Reachability is a property of the read's address, not a reason to duplicate the fact or to add a write capability. The owner asked for the change record, and ALT-6 delivers the change record where it actually exists.

## Decision

- **Decision:** Adopt **ALT-6**.

  1. **DC-1 — One authority: the change record's `branch` declaration, read at the request head.** The change branch is read from one additive top-level `branch` key on the change's committed pm-notes document. The document is read at the **delivery request's asserted head** — the commit the merge will land — through the delivered parser (`parsePmNotesText`) applied to text obtained by one bounded, fixed-argv, local git tree read owned by the merge composition; no working-tree change-record read is an authority on this path. The declaration is a change fact: authored with the change, reviewed in its diff, preserved value-faithfully by every document-writing branch, and opaque to lint. It is not configuration, carries no schema version, is read by no other surface, and its tree path is the refusal's evidence. Reading at the head is the point, not an optimisation: the declaration that governs a landing is the one at the commit that lands, and that commit is reachable from any checkout that holds the object. (Spec DM-1, F-1 step 1, DEC-1, DEC-9; C-9.)
  2. **DC-2 — No fallback; a bounded meaning for "unusable"; a closed cause set; a pinned cap.** The branch refusal is `merge.branch-unresolved` at exit 1 with `domainKind: merge`, `consequence: not_landed`, `retryable: false` (every cause requires an operator act before a re-run can converge), naming the command, the change ref, the candidate source ref, the change-record path or the search path, the `branch` key, and exactly one closed reason:
     - `declaration-missing` — the record is a mapping and declares no `branch` key, or a non-string or empty value.
     - `declaration-unusable` — the value is a string containing whitespace or a control character, or longer than `MERGE_BRANCH_DECLARATION_MAX_CHARS = 256` (measured in characters; never truncated).
     - `declaration-disagrees` — the value is usable but is not an exact string match for that candidate's own provider-asserted source ref.
     - `record-missing` — no `doc/changes/**/chg-<REF>-pm-notes.yaml` exists at that candidate's asserted head.
     - `record-invalid` — the file exists at that head but does not parse, is not a mapping, or fails the delivered parse's own health rules.
     - `record-unreadable` — the head object is not in the invocation's object database, or the local read failed, so the record's content cannot be observed.

      The last three are the same row as the first three on purpose: they are one condition class — *the declaration could not be established* — with different repairs (commit the record, fix the YAML, fetch the object, or correct the value), and AC-F3-1/AC-F3-5 forbid a remediation that does not name the condition it clears. When several candidates fail, the reported reason follows this declared precedence — `declaration-disagrees` > `record-invalid` > `record-unreadable` > `record-missing` > `declaration-missing` > `declaration-unusable` — and the evidence carries each read candidate's own cause (at most three), so one run diagnoses all of them. A "malformed" record is therefore **not** a separate case from an absent one: same row, same class, distinct reason. The refusal performs zero landing calls, zero retries, no fetch, and no provider read beyond the single bounded list read of DC-3. The checkout's branch is never a candidate; the folder-slug plus `change.type` composition and every other run-time derivation are rejected. No branch-naming grammar is validated on the value: a value that is otherwise unusual is compared exactly, because a grammar would assume the convention this record refuses to rely on. (Spec F-1 step 2, AC-F1-3, §24-A steps 1–2; DR-3.)
  3. **DC-3 — Candidate set by the declared convention, acceptance by exact equality, closed request reasons.** One bounded open-request list read (the delivered read, with gate facts, which is also the request-detail read) is performed first. Its **candidate set** is the open entries whose provider-asserted source ref matches the repository's declared branch convention for the invocation's change ref (`^[a-z][a-z0-9-]*/<REF>/.+$`, the delivered predicate used by closeout), capped at `MERGE_BRANCH_CANDIDATE_MAX = 3`: zero candidates refuse `merge.request-unresolved` with `no-open-request` (naming the convention, the ref, and the observed open count); more than three refuse it with `ambiguous-open-request` (a bounded window cannot rank). A candidate whose asserted head is absent or not a full hex SHA is never read and refuses `head-unresolved` (DR-4), and a saturated bounded page refuses `ambiguous-open-request` (DR-2). Each remaining candidate's record is read at its own head (DC-1) and accepted only when its declaration equals its own source ref exactly. Exactly one accepted candidate is the delivery request, and its resolution source is reported as `declared-at-head`; two or more accepted candidates refuse `ambiguous-open-request` (a declared guard: distinct source refs make it unreachable in a well-formed list). No prefix, suffix, glob, or ref-substring matching exists anywhere, and the convention narrows *where to look* without ever supplying the value. Every instance is exit 1, `domainKind: merge`, `consequence: not_landed`, `retryable: false`, and names the observed open-request count, the candidate count, and the closed reason. An absent token at this read refuses the delivered `config.credential.missing` naming the credential reference, the environment variable, and the operation — never `merge.transaction-aborted` (AC-F3-2). (Spec F-1 steps 3–4, AC-F1-4, Appendix B.)
  4. **DC-4 — Head binding: one head value, five consumers.** The matched request's asserted head is the **resolved head**, and it is the value of the transaction's head port for the whole run: the freshness envelope's current head, the check-run page read, the landing's expected head, every reported head, and the dry run's appended record identity. A verification record whose head differs — the integration base, for instance — refuses `merge.gates-stale` at exit 1 recording both SHAs, with zero landing calls; this is the only guard that catches a base-tip record, because such a record can be age-fresh and gate-set-identical. The checkout head is never read on this path, and the absence is proven by the extended source scan (DR-5). Because the resolved head replaces the checkout head everywhere, no second head notion exists for a consumer to disagree with. (Spec F-1 step 5, AC-F1-1, AC-F1-2, AC-F1-5, DEC-2.)
  5. **DC-5 — One resolution for both surfaces.** The dry run and the real merge call the same resolution and report the same resolved branch, resolution source (`declared-at-head`), request identity, and resolved head. The dry run appends exactly one verification record whose identity is the resolved head, appends no waiver, transaction, or git mutation, and never reports `result=merged` or `squash=`. A pre-flight verdict therefore describes the object the merge would land, and an operator can see which rule answered. (Spec F-5, API-2, AC-F5-1, AC-F5-2, DEC-8.)
  6. **DC-6 — Already-merged convergence, with the parse deleted, decided before the record read.** Convergence is matched by the invocation's change ref against merged delivery requests, from the same one bounded list read, before any change-record read: a merged request whose source ref follows the convention for the ref and whose invocation matches uniquely is replayed from provider truth. `changeRefInBranch` and its failure mode are deleted; no branch-name parsing remains on any merge path. Because the declaration governs a *landing* and convergence performs none, a converged re-run no longer needs a readable record or a declared branch — a declared consequence of the amended read order, and the removal of a wart the previous order carried. Zero or several merged matches refuse rather than guess. (Spec F-1 step 6, AC-F1-3.)
  7. **DC-7 — What this record does not decide, and what it refines.** Required-check authority, membership, and the default gate set are TDR-0072's. The refusal-diagnostics contract, the row-level retryability rule, and `merge.work-item-unresolved` are TDR-0073's; this record decides only the two rows its own causes reach and the closed reason vocabulary they carry, while their exact summary and remediation wording is the change's. A fetch policy for an absent head object is not decided here (the run refuses; see the revisit trigger). The battery's own branch resolution is unchanged (OQ-3), a declaration writer is out of scope (OQ-1, NG-5). **The spec statements this record refines, for `@pm` to apply:** `doc/spec/features/feature-merge-verify-deploy.md:36-45` (the branch comes from the checkout's git facts → the change record's declaration read at the request head) and `:160-165` (the recorded head equals "the current head" → the resolved request head); spec F-1 steps 1–2 (the declaration is read at the request head, not through the working-tree read, and the branch refusal's "zero provider reads" becomes "no provider read beyond the one bounded list read"); spec NFR-10's read budget (one list read plus at most three bounded local record reads); AC-F1-3 (wording per the closed cause set — the zero-provider-read clause now holds for the *declaration* causes and not for the record causes); and the change-lifecycle guidance for change records and the change-convention guide (the authored declaration, its cap, and its refusal vocabulary). This record does not edit the change artifact.

### Decision-Derived Rules (consequences, not gates)

These follow from adopting ALT-6. They are stated so a reviewer can check that the decision was implemented as decided; they are not eligibility tests.

- **DR-1 — One bounded provider read, then a bounded local read; the resolution precedes the freshness envelope.** The delivered open-request list read runs first (one read; it is also the request-detail read), then at most three bounded local record reads at candidate heads, then the freshness envelope, which needs the resolved head to compare against. Nothing runs twice, nothing retries, nothing paginates: the budget is one provider read and at most three record reads (at most six fixed-argv git invocations, `MERGE_CHANGE_RECORD_MAX_BYTES = 262_144` per read), with zero network calls. Only the *order* moves relative to the delivered transaction — and with it the honest claim about the branch refusal, which spends exactly that one list read and no other provider read.
- **DR-2 — A saturated bounded page is ambiguous, not empty; an over-cap candidate set is ambiguous, not ranked.** A bounded list page that reached its limit cannot establish that no other open request matches, so it refuses `merge.request-unresolved` with `ambiguous-open-request` even when exactly one entry on the page matches. The same logic applies to the candidate window: four or more convention-matching candidates cannot be resolved by a bounded read and refuse rather than being truncated. Both reuse the delivered battery rule's shape (`resolveOpenPr` treats `pageItemCount >= limit` as ambiguous) instead of inventing a second convention, and the closed reason set stays at three.
- **DR-3 — An absent, unreadable, or malformed change record is the branch refusal with its own closed reason.** When the record cannot be observed at a candidate's asserted head, the run refuses `merge.branch-unresolved` naming the candidate's source ref, the tree path attempted, and the `branch` key: `record-missing` when the head carries no such file, `record-invalid` when the file does not parse or is not a mapping, `record-unreadable` when the head object cannot be read locally. A malformed record is therefore the same case as an absent one *as a refusal identity* and a distinct reason *as a repair*, because the fixes differ (fix the YAML vs commit the record vs fetch the object). The alternative — a third row — is outside this record's two-row scope and would move the change's error-table count pins; the alternative of one undifferentiated reason would make the remediation untrue, which AC-F3-1 forbids. The reasons and their precedence are the decision's, not the implementation's.
- **DR-4 — An asserted head is a full hex SHA.** A candidate whose asserted head is absent, empty, or not a full 40- or 64-hex SHA refuses `merge.request-unresolved` with `head-unresolved` and is never read. This reuses the delivered full-SHA predicate (`isFullHexSha`, `verify-gates.ts:180-181`) rather than inventing a second validation, and it keeps the exact-head guard meaningful: the envelope compares SHAs for equality, a non-SHA cannot be compared, and a path built from an unvalidated ref is a plan-restriction risk rather than a read.
- **DR-5 — The no-ambient-read proof covers the head, the working-tree record read, and the fetch.** The spec's NFR-6 requires zero reads of the checkout's branch on the merge path. This record extends the same production-source scan, with its mandatory failing control, to (a) the checkout's head, (b) the working-tree change-record acquisition — the declaration may be read only through the tree read at a candidate head, never through `${cwd}/doc/changes` — and (c) any `git fetch`/`pull` invocation. A new consumer of the checkout head, a working-tree record read, or a fetch on the merge path re-opens this record (revisit triggers).

### Constraint Compliance Attestation

ALT-6 satisfies C-1 through C-9. **C-1:** the declaration is one additive key on an existing committed artifact; the configuration key set, record kinds, schema versions, provider adapter operations, capabilities, and credential references are unchanged, and the only new operation is a bounded local git read that no provider contract sees. **C-2:** every failure to establish the declaration refuses by name with a closed reason, zero landing calls, no fetch, and no provider read beyond the one bounded list read; the checkout's branch and head are never candidates; no derivation, and no convention-only acceptance, exists. **C-3:** exactly two additive rows (`merge.branch-unresolved`, `merge.request-unresolved`), both exit 1, `not_landed`, `retryable: false`; no existing row's identity, exit, category, consequence, or projection moves; `merge.work-item-unresolved` stays outside this record. **C-4:** one provider list read (also the detail read), at most three record reads (≤6 fixed-argv git invocations, 262 144 bytes each), zero retries, zero pagination, zero network. **C-5:** the binding surface is AC-F1-1…AC-F1-5, AC-F5-1, AC-F5-2, and AC-F3-2, with AC-F3-1/AC-F3-6 touched only for the two rows this record owns; AC-F1-3 is delivered per the closed cause set, with its zero-provider-read clause restated for the record causes (DC-7). **C-6:** the branch is an authored, reviewed, committed change fact, read at the commit that lands, with the provider list supplying only an address. **C-7:** exact string equality between the declaration and its own request's source ref, saturation as ambiguity, a candidate cap, full-SHA head required before a read, no naming grammar. **C-8:** one resolution shared by the dry run and the merge, deterministic across checkouts, with the dry run's record identity bound to the resolved head and its zero-mutation contract intact. **C-9:** the declaration resolves from the integration base because it is read at the request head — the fixture with no change folder in the worktree resolves, and the record is not read from `${cwd}`. DR-1…DR-5 are accepted as consequences. No accepted-risk exception is claimed against any gate; the accepted risks are recorded separately below.

### Independent Challenge Status (R3 — pending)

`@decision-critic` has **not** reviewed this record, before or after the 2026-11-20 amendment. No `PASS`, `PASS_WITH_RISKS`, or `REWORK` verdict exists, and this record claims none. The challenge, when performed, must verify at least:

1. **That one authority is actually one.** Against the tree, that the merge path resolves the branch from the declaration and from nothing else — no checkout branch, no folder-slug or `change.type` composition, no configuration key, no convention-only acceptance, no working-tree record read, no leftover name parse — and that ALT-0…ALT-3 and ALT-7…ALT-9's rejection grounds hold against the delivered code rather than against the spec's description of it.

5. **That the new read is local, bounded, and offline-provable.** That the tree read is fixed-argv with no shell and no network, that the ref used to build the pathspec is validated before use, that the byte and candidate bounds are enforced, and that the whole resolution is exercisable through the injected child runner with zero network and zero child process in the offline suite.
6. **That the two rows tell the truth.** That `retryable: false` is accurate for every cause each row reaches — including `record-missing`, `record-unreadable`, `record-invalid`, `declaration-disagrees`, the saturated page, and the over-cap candidate set — that each remediation names the condition it clears, that neither row promises convergence it cannot deliver, that `merge.transaction-aborted` no longer reaches these causes, and that the *same row with distinct reasons* is the right call rather than a third row or one undifferentiated reason.
7. **That the read budget survives the reorder.** That resolution-before-envelope adds no read beyond the stated one, that the list read doubling as the detail read is a truthful account, that the branch refusal spends exactly one provider read and no more, and that the restated AC-F1-3/NFR-10 claims in DC-7 match what the code does.
8. **That convergence did not silently change meaning.** That the move of the already-merged case ahead of the record read is a consequence of the order and not a new authority, that it still requires the provider's merged assertion, and that no change can be replayed as merged on a provider that does not assert it.
9. **That the operational consequence is disclosed, not buried.** That spec §19 and RSK-1, this record, the feature spec, the reference page, and the release note all state the one-line obligation and its refusals, in the same change — and that the amendment's spec refinements in DC-7 are actually applied by `@pm`.
10. **That scope held.** That no third row, schema version, record kind, configuration key, provider capability, fetch, or battery-side behaviour change entered under this record's authority — and that `merge.work-item-unresolved` is argued in the sibling record, not here.
11. **That assumptions are labelled as assumptions.** That exact source-ref equality, same-repository requests, and **local availability of the request head's object** are stated with their revisit triggers rather than presented as facts, and that the saturation, candidate-cap, and full-SHA rules are declared as decision-derived rather than smuggled in as gates.
12. **That the amendment is a repair, not a regression.** That the amended mechanism is still the alternative with the fewest viable parts: that ALT-7 and ALT-8 were rejected for a stated decision-relevant reason (verdict divergence across clones) rather than for taste, and that nothing in this amendment weakens the head binding or the exact-equality rule.

## Trade-offs & Consequences

### Positive Outcomes

- A merge verdict is about the delivery request, which is the object the landing mutates: a base-checkout run verifies the request head or refuses by name, and can no longer report `verified` about the base tip.
- The verified head is one value with five consumers, so the envelope, the probe, the expected head, the report, and the dry run cannot disagree.
- The branch is reviewable before the run: it appears in the change's diff, and a wrong branch is a review finding rather than a run-time surprise.
- The branch refusal costs nothing external beyond the read that locates the record: no landing call, no extra provider read, no retry, and a remediation naming the exact cause and repair.
- The branch-name parse and its failure mode are deleted, and the already-merged convergence case becomes exact (the invocation's change ref) rather than reconstructed from a string.
- Post-landing branch deletion now targets the change branch; previously a base-checkout run named the base for deletion.
- Exact matching keeps the resolution explainable in one sentence: one declared value, one equality, closed reasons. There is no heuristic to tune and no ranking to justify.
- A saturated page is refused as ambiguous rather than silently proving a negative, reusing the delivered battery rule; the candidate window refuses beyond its cap for the same reason.
- No configuration key, schema version, record kind, provider capability, or provider operation is added, and only two additive rows appear.
- **The declaration resolves where the run happens.** The amendment moves the read's address to the request head, so a base-checkout merge resolves the real declaration instead of a missing folder — the capability AC-F1-1 asks for, not a refusal that mentions it.
- **One rule, any checkout.** The same provider state resolves the same way from a base checkout, a change-branch checkout, and a second clone; nothing about the verdict depends on which directory or which working tree ran it.
- **The declaration is confirmed twice, from independent surfaces.** The provider asserts the source ref and the record asserts the branch; acceptance requires them to be equal, so a copied, stale, or mismatched record refuses instead of being merged.
- **The new read is the cheapest kind that exists:** local, fixed-argv, bounded, offline-testable through the seam's existing injection, and invisible to every provider contract.

### Negative Outcomes

- **A one-line authoring obligation becomes a delivery prerequisite.** Every in-flight change and every adopter must declare its branch before merging, and a change that forgets stalls at `merge.branch-unresolved` — by design, but it is a real interruption.
- **The obligation is unaudited at authoring time.** Lint treats the key as opaque, so a typo is caught at merge as `no-open-request` or `declaration-disagrees`; the repair is cheap but arrives late.
- **Exact equality is unforgiving.** A fork-origin request whose asserted source ref carries a prefix will not match, and the refusal will be truthful and unhelpful until the flow is decided.
- **The transaction's read order changes.** Resolution must precede the freshness envelope, so an implementation that keeps the delivered read order has no resolved head to compare against when the envelope runs — and the cheapest way to make that compile is to reach for the checkout head again.
- **The ambiguity refusal can fire on a healthy-looking page.** A saturated bounded list refuses even when the intended request is on it, and a fourth convention-matching branch refuses rather than being disambiguated.
- **The branch refusal costs one provider read.** Locating the declaration at the head requires the list read; the zero-provider-read claim is now true of the *declaration* causes only, and the record says so instead of keeping a claim the mechanism no longer supports.
- **Local object availability is a new precondition for resolution.** A fresh or shallow clone that never fetched the branch refuses `record-unreadable`. The refusal is safe and the repair is named, but the capability is conditional on the object being there, and adding a fetch is deliberately out of scope.
- **A non-conforming branch is invisible.** The candidate filter is the repository's convention; a branch that does not follow it is refused as `no-open-request` rather than resolved.
- **A partial delivery is dangerous.** Binding the branch without the head produces a report that names the change while the evidence is about the checkout — the original defect with a misleading label. The two must land together.

### Unresolved Questions

- [ ] Should `merge` fetch the request head when the object is absent locally, instead of refusing `record-unreadable`? A fetch would remove the amendment's main residual limitation and would add a network operation and its credential/failure surface to the resolution path — a decision of its own, not an implementation detail. (owner: the human owner at the GH-366 PR review)
- [ ] Does a fork-origin delivery request belong to the supported flow? If yes, the matching rule and the declaration's meaning must be re-decided rather than patched. (owner: `@decision-advisor` when a fork flow is adopted)
- [ ] Should the `verify gates` battery resolve its branch from the change record so a merge record can be produced from a base checkout (OQ-3)? This record explicitly leaves the battery unchanged. (owner: `@decision-advisor` in the follow-on decision)
- [ ] Should a delivery command author the declaration (OQ-1)? This record requires the declaration and adds no writer. (owner: `@decision-advisor` in the writer decision)

1. **The bounded read at the request head.** Add one bounded, fixed-argv, local git read to the merge seam (no shell, no network) that, for a candidate's asserted head SHA, lists `doc/changes/**/chg-<REF>-pm-notes.yaml` in that tree and reads the matching blob under a byte bound (`MERGE_CHANGE_RECORD_MAX_BYTES = 262_144`), answering `missing`, `invalid`, `unreadable`, or the located path plus text. Validate the SHA with the delivered full-SHA predicate and the ref with the delivered change-ref shape before either is interpolated into a pathspec. Parse the text with the delivered `parsePmNotesText`. Add no provider call and no working-tree record read on this path.
2. **Candidate set and resolution.** Take the one bounded open-request list read first (keep it as the detail read), narrow to the open entries whose source ref matches the delivered branch convention for the change ref, enforce `MERGE_BRANCH_CANDIDATE_MAX = 3` and the saturation guard, then read each candidate's record at its own head and accept exactly one whose declaration equals its own source ref. Refuse with the closed reasons and the declared cause precedence, carrying each read candidate's own cause in the evidence.
3. **Head binding.** Supply the accepted candidate's asserted head as the transaction's head for the whole run — the freshness comparison, the check-run page, the landing's expected head, the reported head, and the dry-run record identity — and remove the checkout head from the merge path. ## Rollback / Reversal

- **Revert steps:** revert the delivery commit(s) as a unit. The two additive rows become unreachable and are then inert (they may remain declared without effect; removing them restores the exact prior inventory). The `branch` declaration stays on change records and stays harmless, because it is an opaque extra key that no other surface reads. The bounded tree read is removed with the resolution; no provider contract changes, so no adapter version moves. No stored state migrates and no historical record is read, so nothing needs backfilling in either direction.
- **Stop conditions that trigger rollback:** (a) a change cannot merge because its record cannot be authored — no committed change folder, or a head whose record the local read cannot observe; (b) the provider's asserted source ref does not equal the declared branch for the supported same-repository flow, making exact equality unusable; (c) a delivery that leaves a **mixed state** — the new branch resolution with the checkout head still bound, or the reverse; (d) the record read turns out to need a network operation to work in ordinary use, which would mean the amendment's constraint was wrong. Case (c) is the serious one: it produces a verdict that names the change while the evidence is about the checkout, which is the original defect plus a misleading label. The branch and head bindings therefore land together or not at all.
- **Irrecoverable state:** a landing that has fired is provider truth and cannot be un-landed by a local revert. That is exactly why the head binding is part of this decision: the guard against landing the wrong head is the refusal, not a rollback. A verification record appended by a dry run is inert evidence and is superseded by the next verification; nothing depends on deleting it.

## Examples & Usage

- **Coordinator on the integration base.** `merge GH-366` takes one bounded open-request read, finds the open request whose source ref is `fix/GH-366/merge-command-conformance` (the convention matches it for `GH-366`), reads `doc/changes/<folder>/chg-GH-366-pm-notes.yaml` **at that request's asserted head** through one local tree read, sees `branch: fix/GH-366/merge-command-conformance` equal to that request's source ref, takes that head, compares the verification record against it, reads the check-run page for it, and lands once with it as the expected head — or refuses `merge.gates-stale` naming the base-tip recorded SHA and the request head. Nothing in the working tree was consulted.
- **A change with no declaration.** `merge GH-999` finds one convention-matching open request, reads its record at its head, finds no `branch` key, and refuses `merge.branch-unresolved` at exit 1 with reason `declaration-missing`, naming the tree path, the key, and the request's source ref, with zero landing calls. The repair is one line, committed with the change.
- **A cloned checkout that never fetched the branch.** `merge GH-366` finds the request and aims at its head, but the commit is not in the local object database. It refuses `merge.branch-unresolved` with reason `record-unreadable`, naming the candidate's source ref and head, with zero landing calls — it does **not** fall back to accepting the request on the convention, because a second clone that holds the object would then decide differently.
- **A record that names another branch.** `merge GH-366` reads a candidate's record at its head and finds `branch: fix/GH-350/declarative-provider-policy`. It refuses `merge.branch-unresolved` with reason `declaration-disagrees`, naming both values. A copied or stale record is an alarm, not a merge.
- **Two open requests for one change ref (a rename).** `merge GH-366` finds two candidates — `fix/GH-366/merge-command-conformance` and `chore/GH-366/retitle` — reads both records, and accepts exactly the one whose record declares its own source ref; the other's cause is carried in the evidence. If neither declares a matching branch, the run refuses on `merge.branch-unresolved` with the declared cause precedence, naming the convention and both candidates. It never ranks them, prefers the newer, or picks the one whose title looks right. Five or more such candidates refuse `ambiguous-open-request` without reading any of them, because a bounded window cannot rank.
- **A branch that does not follow the convention.** `merge GH-999` where the only open request's branch is `gh999-merge-fix`: the candidate set is empty and the run refuses `merge.request-unresolved` with `no-open-request`, naming the convention and the observed open count. Renaming the branch (or opening a conforming request) is the repair; the run does not guess.
- **A dry run as pre-flight.** `merge GH-366 --dry-run` from the base resolves the same object the real merge would land — same `declared-at-head` source, same request, same head — and appends one verification record for the request head, so the coordinator's pre-flight is a statement about the request rather than about the directory they happened to be in.
