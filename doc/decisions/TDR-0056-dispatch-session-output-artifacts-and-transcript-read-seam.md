# TDR-0056: Dispatch Session-Output Artifacts and the Transcript Read Seam

> **Traceability.** Spec §15 **DEC-3** (the bounded per-ref harness-stdout artifact) and **DEC-4** (the persisted-transcript read); §15.1 and §25.4 route both here; §5.1 F-2, F-4, F-7; §8.1 API-7, API-8, API-9; §8.3 DM-2, DM-3, DM-6; §8.4; §9 NFR-3, NFR-11; §17.2 AC-F2-x, §17.4 AC-F4-x, §17.7 AC-F7-x; §21 privacy; §22 security; §25.1 documentation impacts. The loop surface (M4-S10, GH-348) is the named next consumer.

## Context

GH-354 gives the typed dispatch lane the four inspection queries the CEO prompt uses today (`--status`, `--log`, `--is-delivering`, `--last-message`). `status` and `is-delivering` are folds over the deliverable `dispatch.lane` record ([TDR-0049](TDR-0049-dispatch-owned-durable-lane-record.md)). `log` and `last-message` have no source at all, and the reason is structural rather than a missing code path.

- **FACT:** The lane record is dispatch-owned, append-only and latest-wins per ref, and its type contract forbids content — "No prompt, transcript, diff, credential, or provider payload is carried" — with fields limited to identity, counts, and timestamps (`packages/core/src/contracts/dispatch.ts:571-608`). *(read 2026-11-19)*
- **FACT:** The attempt record's evidence list is bounded to 16 identifier-only references (`contracts/dispatch.ts:554`), and the envelope's `lastMessage` is a bounded synthesized summary of the derivation, not session text (`contracts/dispatch.ts:379-380`; `DISPATCH_MAX_LAST_MESSAGE_CHARS = 512` at `:551`). *(read 2026-11-19)*
- **FACT:** `HARNESS_OPERATIONS` is a closed vocabulary of seven entries — `spawn`, `deliver`, `resume`, `steer`, `collect`, `session-list`, and the additive `terminate` (`packages/core/src/contracts/harness.ts:32-40`). The session port's **content** surface is empty: `spawn`, `deliver`, `resume`, `collect`, `liveness`, and `terminate` take a handle or start a session, while the two no-handle reads return no session content — `listSessions` takes `{ workItemRef, descriptor? }` and answers `{ handles, truncation? }`, a listing digest (`harness.ts:314-323,489`), and `classify` is pure over delivered evidence (`harness.ts:485`). `HarnessEvidence` carries completion and exit facts only, with no assistant text (`harness.ts:206-215`). *(read 2026-11-19)*
- **FACT:** The closed lifecycle-capability vocabulary already contains `session-introspection` (`harness.ts:44-50`), and an adapter either declares it supported or declares it as a gap: opencode declares every lifecycle capability, `session-introspection` included (`OPENCODE_CAPABILITIES.lifecycleCapabilities: [...HARNESS_LIFECYCLE_CAPABILITIES]`, `packages/adapters/src/harness/opencode.ts:51-57`), while Claude Code declares it as a gap with reason `headless-mode-limitation` (`packages/adapters/src/harness/claude.ts:47`, documented at `doc/spec/features/feature-harness-adapters.md:321`). Claude's supported lifecycle capabilities are `headless-spawn` and `telemetry-extraction` (`claude.ts:31`), and its persisted-session reader is the telemetry capture, which parses statistics only (`packages/adapters/src/harness/telemetry-claude.ts:1-10`). `declaredGaps` accepts only `HarnessOperation | HarnessLifecycleCapability | HarnessLivenessKind` values with a closed reason (`harness.ts:60-101`). The specification names `session-introspection` but does not define it more narrowly than "session introspection" (`feature-harness-adapters.md:104`). *(read 2026-11-19)*
- **FACT:** The two adapters have different invocation shapes. opencode **streams** stdout: a stream's handle settles on its first identified line, and the engine sees every line (`opencode.ts:373-384`). Claude Code is a **one-shot runner**: its port's `spawn` awaits a bounded invocation through an injected runner and answers with a result, its supported operations are `spawn` and `collect`, and there is no `stream.lines` for the engine to observe (`packages/adapters/src/harness/claude.ts:153-200`). *(read 2026-11-19)*
- **FACT:** The stream's line channel carries `AsyncIterable<string>` with no terminatedness marker: the host implementation splits on `\n`, strips the delimiter, and pushes the final buffered remnant as a value when the stream closes (`packages/core/src/contracts/harness.ts:409-421`; `packages/adapters/src/host/index.ts:186-194,239-241`). Line-level code therefore cannot tell a terminated value from an unterminated remnant. *(read 2026-11-19)*
- **FACT:** Nothing in the typed lane persists per-ref session output. The shell lane writes three distinguishable streams: the **opencode child's stdout** to `tmp/deliver-ticket/<ref>.pm.out`, the **opencode child's stderr** to `tmp/deliver-ticket/<ref>.log` (`scripts/deliver-ticket.sh:1753-1755` — the redirection applies to the child), and the **wrapper's own progress lines** to the wrapper's stderr via `log_info`/`log_warn` (`:229-234`), which reach the operator's terminal rather than `<ref>.log`. `cmd_log` tails `<ref>.log` — the child's stderr — with a default of 50 lines (`:2217-2242`). The wrapper derives `<ref>.last-message` from the last non-blank line of the child's stdout (`:1858-1865`), and `cmd_last_message` prints that derived file (`:2252-2262`). *(read 2026-11-19)*
- **FACT:** For the opencode harness, stdout is a **JSON event stream**, not the shell's human log: the adapter decodes it line by line and skips blank, non-JSON, and non-object lines (`packages/adapters/src/harness/opencode.ts:239-243`). The shell's `<ref>.log` is therefore not the same bytes, not the same stream, and not the same shape as what a typed stdout artifact would hold. *(read 2026-11-19)*
- **FACT:** The state layer already carries artifact families beside the ledger — `ceremony-artifacts.<workspace>/` is a **directory of per-run files**, and `retro-evidence.<workspace>.jsonl` is an append-only sidecar — both documented as living outside the store's record set, derived documents, and salvage/repair path, with least-privilege permissions (`doc/spec/features/feature-state-layer.md`, store layout; [TDR-0009](TDR-0009-retro-evidence-sidecar-keyed-chain-construction.md)). Ledger **record payloads** are identifier- and statistics-only; content lives beside the ledger — which is the split this record follows. *(read 2026-11-19)*
- **FACT:** opencode opens its session store on a read-only connection with the query-only pragma (`packages/adapters/src/harness/telemetry-opencode.ts:1-10`); Claude Code opens transcript files read-only and bounded by the declared per-file caps `HARNESS_MAX_FILE_BYTES = 8 388 608` and `HARNESS_MAX_FILE_LINES = 50 000` (`packages/core/src/contracts/harness-telemetry.ts:271-277`; `telemetry-claude.ts:1-10,195-196`) — for statistics, not for content. *(read 2026-11-19)*
- **FACT:** The opencode adapter already has an injected per-session telemetry sink, `telemetrySinkFor({ workItemRef })`, documented as non-gating, built once per spawn, and swallowed on fault (`opencode.ts:93-103,340-345`), constructed at two call sites — the spawn and the resume path (`opencode.ts:562-566,647-651`). It is **not** a raw-stream seam: the drain decodes each line and skips undecodable lines before calling `observeFrame` (`opencode.ts:365-380`). *(read 2026-11-19)*
- **FACT:** The CLI funnels every envelope through one serialization chokepoint that replaces **registered credential values** with `[redacted]` (`packages/cli/src/output/serialize.ts:19-47`). The values come from the declared credential references (`packages/cli/src/production.ts:521-527`) resolved over the injected environment at the composition root (`packages/cli/src/edge.ts:619-631,1667`), so the set the chokepoint holds is a narrow declared-credential set, not general secret discovery. *(read 2026-11-19)*
- **FACT:** The queue lease is claimed once and never renewed (`doc/spec/features/feature-dispatch-engine.md` §One-shot dispatch step 4: "the dispatch claim … never renews"), and `queue.lease-ttl` defaults to 90 000 ms (`packages/core/src/config/defaults.ts:75`). A second dispatch for the same ref can therefore be admitted while the first is still streaming. *(read 2026-11-19)*
- **FACT:** The attempt read side established the read-only posture: zero appends, zero fence acquisitions, identity resolution with persistence disabled, and an empty history as success ([TDR-0024](TDR-0024-dispatch-attempt-read-side-and-local-evidence-resolve.md)). *(read 2026-11-19)*
- **Why now:** GH-354 cannot answer `log` or `last-message` without deciding two things at once, because both answers hit the same structural wall: the durable plane is identifier-only by contract, so session content has no home; and the port exposes no content read, even though the capability that covers one (`session-introspection`) is already declared.

## Problem Framing (Clarified)

The symptom is "an operator still has to run the shell to see what happened". The cause is that the typed plane deliberately holds no content and no post-hoc session read:

1. **Where may session content live at rest?** The lane record may not carry it (TDR-0049 C-4, and its type contract says so). The evidence list may not carry it (identifier-only, 16 references). A new durable record kind would put content into a ledger whose every record payload is identifier- or statistics-only, and would need a bound, a retention rule, a fencing path, and a privacy statement per record — plus a read that folds content out of the append-only store.
2. **What is the artifact's shape, so that boundedness does not itself become a hazard?** A file that grows with every line is unbounded unless something bounds it — and the obvious bound, modifying the file when it gets large, is the most dangerous sentence in this whole design: it costs work proportional to the file on the delivery path, and it makes two writers of one file mutually destructive. The shape must make the bound free: bound the file by *not writing into it past a size*, and bound the family by *how many files are kept*.
3. **What exactly is written, and what does an incomplete tail mean?** The line channel yields strings with no terminatedness marker, so "line + LF" cannot be applied conditionally; and a writer killed mid-write leaves bytes that are not a line. Both need one declared rule each, or the writer and the reader will disagree about what the file contains.
4. **How does a read reach the harness's transcript without a session?** The port's content surface takes a handle or starts a session, so a content read has to be a seam the adapter owns; the capability vocabulary already has an entry for "the adapter can introspect a session it owns", so the question is whether a content read is that capability or a new one.
5. **What does the read say when it cannot?** An undeclared capability, an unknown session, an empty transcript, and unreadable storage are four different facts; collapsing them into one failure, or inventing a failure identity per case, are both wrong for a closed error table.

**What the typed tail is, and is not (stated up front, because it is easy to overclaim).** The ticket requires persisting the harness's stdout per ref, so the artifact holds the **opencode JSON event stream** (or another streaming harness's stdout) as printed. The shell's `--log` answers a *different* question: it tails `<REF>.log`, which holds the **opencode child's stderr**; the wrapper's own progress lines go to the wrapper's terminal instead. The typed `log` is therefore **not** a tail-for-tail replacement for the shell's `--log`; it is a bounded tail of a streaming harness's own stdout. The file is a **declared transformation** of the yielded values, not a claimed byte-for-byte copy: every yielded value is written followed by one LF, including the stream's final remnant, and an unterminated tail in a file is read as a torn write and dropped. A **one-shot harness** (Claude Code) yields no lines at all, so it produces no artifact. The operator consequences are recorded as divergences (DC-3, Trade-offs, Accepted Risks, and revisit triggers): the child's stderr and the wrapper's progress lines are not captured, the content is the JSON event stream rather than timestamped human text, and a one-shot lane has no log at all.

The root cause is not "missing features": this system puts content **beside** the ledger and identity **inside** it, on purpose, and it treats "the adapter owns its harness's storage" as a contract boundary. Both decisions follow from taking those two existing rules seriously rather than from inventing a new storage model.

Deliberately out of scope, so the boundary is reviewable: no stderr or wrapper-progress capture (deferred, with a revisit trigger); no artifact for a one-shot harness (pinning its output at completion is a different artifact shape and a different decision); no scrubbing pass at write (reasons in DC-6); no retention job beyond the fixed file-count rule; no ledger record kind, no lane or attempt field, no schema version; no new operation, capability, or gap reason; no prompt, diff, tool-argument, or provider-payload capture; no daemon-lane read; no synthesized message as a fallback.

## Constraints (Hard Requirements)

These are the gates an alternative must pass to be *eligible*. They are independently sourced (the change's NFRs, non-goals, and acceptance criteria). Requirements that merely restate this record's own chosen design are listed separately, after the gates, and are **not** used to eliminate alternatives.

### C-1: No new configuration key — every bound is a declared policy constant

- **Statement:** The directory and file naming shape, the 1 048 576-byte per-file cap, and the stream and segment ordinals are declared constants; the tail default and range, the machine and human output bounds, the 5 000-record lane window, and the 512-character message bound are the change's declared constants; the **retained-file count and the resulting family bound are this record's decided policy**, not a spec constant. The configuration key set is unchanged and no key tunes any of them.
- **Source:** AC (spec NG-6, DEC-8, NFR-5 — none of which names a retained-file count)
- **Verification:** test (configuration key-set equality; the resolved constants equal the declared values, including the record's own retained-file count) + code review
- **Negotiable:** no

### C-2: No delivery-contract churn — the artifact is not a record and nothing pinned moves

- **Statement:** No delivery-result token, projection class, exit digit, error-table row, domain kind, attempt-record field, lane-record field, record kind, schema version, or evidence identifier is added or changed; the artifact is a directory of files beside the store, not a self-certifying record.
- **Source:** AC (spec NFR-5, NG-2, NG-3, AC-F5-4, AC-F7-2, AC-F7-3)
- **Verification:** test (token, projection, error-row, record key-set, and attempt-evidence inventories equal their pins; the evidence list stays within 16) + code review
- **Negotiable:** no

### C-3: The operator surface is read-only, and the transcript read administers nothing

- **Statement:** Across all four queries: zero ledger appends, zero fence acquisitions, zero lane-record mutations, zero identity-marker writes, zero process starts, zero network calls, and no deletion inside the artifact family; the transcript read takes no handle, spawns nothing, resumes nothing, terminates nothing, and writes nothing to the harness's storage.
- **Source:** AC (spec NFR-1, NFR-2, F-6, AC-F4-6, AC-F6-1, AC-F6-4; TDR-0024 read-side precedent)
- **Verification:** test (store bytes, lane records, and marker unchanged; zero appends and fences observed; zero child processes; the artifact family's file set unchanged by any query; the seam is never handed a handle) + code review
- **Negotiable:** no

### C-4: The typed surface is the only source — zero shell invocation and zero shell-owned path

- **Statement:** Both answers exist without the shell: no shell is invoked, no script-path literal appears, and no shell-owned artifact (`tmp/deliver-ticket/**`, `.ai/local/delivery/**`, the delivering marker, a PID file, `<REF>.pm.out`, `<REF>.log`, `<REF>.last-message`) is read or written. A checkout whose shell entry points are absent answers all four queries.
- **Source:** AC (spec NFR-6, NG-5, §4.1 shell-independence metric, API-12, AC-F6-2, AC-F6-3, AC-F6-5)
- **Verification:** test (the static no-shell invariant over the declared surface list with a planted-reference control; planted shell artifacts byte- and mtime-identical; shell-absent checkout) + code review
- **Negotiable:** no

### C-5: Reference scoping — one ref's output never mixes with another's

- **Statement:** The artifact is one directory per work-item reference in one project state root; every file in it belongs to that reference. A query never lists, globs, or reads **across** references: the only permitted listing is of the reference's own directory, to choose its newest file, and the only permitted reads are files inside it. The transcript read is addressed by the lane's session identity for that `(repository, ref)`. A foreign ref or foreign repository yields absence, never a foreign answer.
- **Source:** AC (spec NFR-4, API-7, AC-F2-1, AC-F1-6)
- **Verification:** test (two refs with distinct directories: no line of one appears in the other's answer; a query's only directory listing is the addressed reference's own; a same-ref directory under another state root is not read) + code review
- **Negotiable:** no

### C-6: Every bound is declared, and a bound that binds is declared in the answer

- **Statement:** Each artifact file is `0600` and at most 1 048 576 bytes; the cap is enforced by starting the next segment, and a yielded value too large for the remaining room is continued across the boundary rather than dropped (a value longer than the cap itself leaves the next file starting mid-line, declared). The writer retains the newest two files, so the family is bounded at **2 × cap** per reference; removal of older files is best-effort, so a failed removal may leave more than two until the next append. The reader stitches the retained files in name order before splitting on lines, drops an unterminated tail, and declares a truncation fact when the retained window cannot satisfy the request or the oldest returned line is a continuation whose beginning retention removed. The tail default is 50 in the range 1..500 as a canonical decimal, refused rather than clamped, bounded to the retained window; machine `data` and human output each have a declared bound with exactly one truncation fact when it binds; the returned message is ≤ 512 characters and single line with `truncated` true exactly when cut.
- **Source:** AC (spec NFR-3, NFR-8, DM-6, AC-F2-2, AC-F2-5, AC-F4-7). AC-F2-6 is **not** cited as this constraint's source: it is one of the statements this record refines (DR-5), because it asks for an artifact that "ends at a line boundary" and names one bound, where this design has a per-file cap and a family bound.
- **Verification:** test (a stream past the cap yields additional files each at or under the cap; a value larger than the cap is continued and reconstructed by the reader; the retained set is two after a successful removal and never fewer; the reader's stitching, torn-tail drop, and truncation facts including the single-retained-file case; out-of-range and non-canonical tails refused before any read; the message bound and its `truncated` marker) + code review
- **Negotiable:** no

### C-7: The privacy boundary — one content class at rest, one bounded content payload in output

- **Statement:** The engine **adds** no prompt, diff, credential, environment value, tool argument, or provider payload of its own; it removes none either. A file contains exactly the declared transformation of the values its stream yielded — every yielded value followed by one LF, and nothing else — and an unterminated tail in a file is not content. Session content never enters the ledger, any record, any evidence list, any derived document, or any envelope beyond the tail the operator asked for. The artifact family is local to the project state root, `0600`, and never committed.
- **Source:** AC (spec NFR-11, NG-8, §21 privacy review, §22 security, AC-F7-3, AC-F4-2)
- **Verification:** test — three satisfiable assertions with separate fixtures: (a) each file's bytes equal the declared transformation of the values that stream yielded (value + LF, including the final remnant, and dropping the unterminated tail leaves nothing), with nothing else added or removed; (b) no log content appears in any record, evidence list, derived document, or envelope beyond the requested tail, and `last-message` reads no attempt record, derivation payload, or envelope field; (c) the two chokepoint fixtures are kept apart — a credential value injected into **stdout** appears verbatim in the artifact and nowhere in any record, while a credential value injected into the **transcript** fixture is replaced by `[redacted]` in the `last-message` answer. A canary in a *prompt* never reaches the artifact because the engine does not write prompts; a value the harness itself printed is present by design and is not a failure. + code review
- **Negotiable:** no

**Honesty note on the gate set.** An earlier draft of this record gated on "the read seam is not an operation" and on "the final message is never written by the engine". Both are outcomes of choosing this option, not independently sourced requirements, so gating on them made the chosen alternative win by tautology. They are recorded below as decision-derived requirements and are used to describe consequences, not to eliminate alternatives.

**Table stakes.** Every alternative below keeps the closed error table (no new identity for any absence), the additive four-form command family with the delivered `--json` envelope, and the delivered 512-character message bound; none of those eliminates an alternative.

## Decision-Derived Requirements (consequences, not gates)

These follow from adopting ALT-7. They are stated so a reviewer can check the decision was implemented as decided; they are not eligibility tests.

- **DR-1 — The read reuses the existing `session-introspection` capability.** The transcript read adds no operation, no capability-union member, and no gap reason. It is declared by the adapter's existing capability declaration: opencode already declares `session-introspection` supported, and Claude Code already declares it as a gap with `headless-mode-limitation`. In the query answer, `capability-gap` therefore means exactly "the lane's harness declares `session-introspection` as a gap". Because the vocabulary and the declarations are reused unchanged, adapter conformance parity and the gap inventory are unchanged. **Meaning note:** the specification names `session-introspection` without narrowing it to metadata (`feature-harness-adapters.md:104`); the operation already tied to it is the session listing, and the telemetry capture is a separate capability (`telemetry-extraction`, declared by both adapters — `claude.ts:31`). Reading a persisted session's final assistant message from the adapter's own store is the same capability applied to content, not a new one. If the owner reads it as metadata-only, the correct outcome is an additive capability decision at acceptance. The change's working interpretation is the owner question recorded under Unresolved Questions; it is **not** an authority this record delegates to the PM or to the implementation, and acceptance is where it is settled.
- **DR-2 — The artifact is a sidecar directory, not a record.** No record kind, schema identity, key prefix, evidence reference, derived document, salvage input, or repair input names it.
- **DR-3 — Every stream of a streaming adapter gets its own sink, bound before its first value.** The sink is bound on **spawn, resume, and deliver** — every stream the reference opens on a streaming adapter — before that stream's first yielded value, because a handle settles on its first identified line and a later binding would miss that line and everything before it. It receives every raw value — decoded or not — because the artifact is the operator's evidence of what the harness printed. It is supplied as an **additive optional option beside `telemetrySinkFor` at that seam's construction points** (`opencode.ts:562-566,647-651`), which adds no capability, declaration, or operation. `telemetrySinkFor` remains a *pattern* to copy (built once per spawn, non-gating, fault-swallowing) and not the same seam: it receives only decoded frames. A one-shot adapter (Claude Code) has no stream, so it gets no sink and produces no artifact.
- **DR-4 — Append-only per-stream segmentation.** `dispatch-logs.<workspace>/<REF>/` holds one file per stream of a streaming adapter; its files are named from data the writer already holds — the stream's recorded time, the attempt identity, the iteration ordinal, and the segment ordinal, zero-padded — so a plain lexical sort of the directory equals the streams' creation order across restarts and concurrent dispatches, with attempt identity breaking ties (exact widths plan-pinned). A file is created when its stream starts, `0600`, and receives single `O_APPEND` writes; existing bytes are never modified and no coordination file exists in the family. **Writer rule:** every yielded value is written followed by one LF — including the stream's final remnant, which is a yielded value like any other and is never appended verbatim. When a value with its LF does not fit and is longer than the cap, the writer fills the current file to exactly the cap with its leading bytes and continues the remainder at the start of the next file, repeating as needed; a value shorter than the cap that does not fit simply starts the next file whole. Retention per reference is the newest two files by name, so the family is bounded at 2 × cap; a third file's arrival removes the oldest best-effort after the new file exists, and a failed removal leaves more than two until the next append. Two dispatches for one ref write different files, so no write target is shared and each stream's output stays attributable by name. **Tear rule:** a process killed mid-write leaves bytes that are not a line; the reader treats an unterminated tail in a file as a torn write and drops it, and earlier lines stay durable.
- **DR-5 — Non-gating, not non-blocking.** A sink fault never changes the delivery token, exit, attempt record, lane record, or evidence, and adds no evidence identifier. The append runs on the delivered line iteration, so it does add latency to the drain; the claim is non-gating, and the steady-state cost is an assumption below rather than a "never blocks" promise. **The spec statements this record refines — the complete list, for the PM to apply:** DM-2 (a per-ref **directory of per-stream files**, replacing "one file per reference"); DEC-3 (the artifact family's shape, overflow, and retention); F-7 (per-stream history and the retained window); NFR-3 (per-file cap, family bound 2 × cap); DM-6 (the retained-file count and family bound are **decided policy here**, not restated constants); AC-F2-6 (segmentation instead of "ends at a line boundary"; the bound is per file); AC-F7-1 (one file per stream; the reference directory exists; a one-shot adapter has none); AC-F7-4 (the newest two files, not "one artifact"); F-7/API-8 "never blocks the drain" (→ non-gating, not non-blocking); §8.4 "two local reads" (→ one content read for this change — the opencode store — with Claude Code's statistics-only telemetry read unchanged); AC-F4-1 (capability-gated: the answer exists where the harness declares `session-introspection` supported). This record does not edit the change artifact.

## Decision Drivers

1. **A failure must be diagnosable after the fact.** A stalled or failed typed dispatch has to leave a bounded tail of what the harness actually printed, attributed to the stream that produced it. This is the ticket's requirement (persist harness stdout per ref), and it is narrower than the shell's `--log`: it promises neither the child's stderr nor the wrapper's progress lines.
2. **The identifier-only durable plane stays identifier-only.** A log line in the ledger would be a schema change, a privacy change, and a growth change at once; the lane, attempt, and evidence contracts exist to prevent exactly that.
3. **Inspection must be incapable of disturbing a delivery.** A read that can start, resume, or signal a session turns an observation into an operation, and an operator's `last-message` could then move a live delivery.
4. **Boundedness must be free.** A bound enforced by doing work proportional to the artifact on the delivery path is a delivery defect; a shape where the bound is a new file makes boundedness cost one file creation per megabyte and nothing per line.
5. **One ref, one answer — and one stream, one file.** Diagnosis is per work item, and "which iteration said this" should be answerable from the file name rather than reconstructed from lane ordering.
6. **The method is the harness's own words.** A synthesized classifier sentence is exactly what `last-message` must stop being; fidelity to the persisted transcript is the requirement, not a nicety.
7. **The contract surface stays proportionate.** The read must not cost a new operation, a new capability, a new gap reason, an error row, or a configuration key; and it must be declared through the mechanism the contract already has rather than by a claim that no mechanism exists.
8. **Paved road and solo-maintainer cost.** Reuse the state layer's artifact-family-beside-the-ledger pattern, the adapters' existing read-only storage posture and declared file caps, the delivered redaction chokepoint for derived output, and the delivered 512-character bound.
9. **The next consumer inherits a written convention.** M4-S10 should be able to read one statement of where session output lives and how a transcript is read; this is a convenience of the record, not authority over that change.

## Mental Models & Techniques Used

- **First principles:** What must be true for "the operator can diagnose a typed dispatch without the shell" to hold? (i) some durable per-ref output exists for a harness that emits output incrementally, (ii) it is bounded, scoped, and cheap to maintain, (iii) reading it disturbs nothing, (iv) the final message comes from the harness itself, (v) every absence is nameable — including "this harness has no increment to store". Those five requirements produce one sidecar directory and one read seam, and rule out every alternative that spends a pinned contract to get there.
- **Inversion:** What makes this feature worse than no feature? Content inside the ledger (a privacy break with a fencing cost); an unbounded family (a disk defect); a bound enforced by doing work proportional to the artifact on the delivery path (a delivery defect); two writers of one file making each other's output unreadable; a value larger than the cap that is dropped or that crashes the writer; a reader that returns an unterminated tail as if it were a line; a sink bound after the first values have already passed; a read that starts a session; a message synthesized from the classifier; a transcript copy written by the engine; a scan across refs; a missing capability that crashes instead of declaring itself; an operator reading `no-log` on a one-shot lane as "nothing ran". The chosen shape answers the first seven structurally, and C-1…C-7 with DR-1…DR-5 close the rest.
- **Second-order thinking:** One file per stream is more than a storage detail: it restores attribution. A tail can be tied to the attempt and iteration that produced it from the name alone, and a concurrent dispatch cannot corrupt or truncate another stream's evidence, because it never writes the same file. That is why the design can drop coordination entirely: the only shared thing is a directory listing, and ordering is a name comparison. The same clarity forces the one-shot admission: a harness with no stream has no artifact, and saying so is better than manufacturing an empty one.
- **Systems thinking:** The chain is spawn/resume/deliver → segment file created → raw-value append → continuation at the cap → retention by count → operator read that stitches and splits, and separately lane read → session identity → adapter read → redaction → flatten → bound → answer. Each join can substitute a different fact: the sink can be bound too late (a lost first value), the append can be slow (delivery latency), a retention decision can remove the file an operator wanted, a read can land mid-append (a stale tail), the lane can name a session the harness no longer knows (`session-unknown`), the redaction can run after the bound (a cut secret surviving) or before (a bound computed on the wrong text). This record pins the writer rules, the reader's stitching, and the composition order; the lane read is TDR-0049's.
- **Opportunity cost:** Putting content in the ledger buys one storage mechanism and costs the identifier-only invariant, a per-append fence, a growth policy, a privacy review per record kind, and a fold-over-content read. Adding an operation buys symmetry with the other four queries and costs the closed operation set, every adapter's declarations, and the parity matrix — for a read the capability vocabulary already covers. Copying the transcript buys a trivial read and costs a second content family plus a live answer it cannot give. Widening the session listing buys reuse of a delivered read and costs content on a resume path.
- **Paved road / KISS:** One directory per ref, one append-only file per stream, one continuation rule at the cap, one retention count, one reader that stitches at most two files, one read per adapter reusing an existing read-only storage posture, one absence ladder, one message bound, one redaction-before-bound order.

### Alternative 0 — Baseline: No Persistence; Operators Keep the Shell's Captures

- **Eligibility:** Not eligible (fails C-4).
- **Summary:** Ship the lane-fold queries and stop. `log` and `last-message` keep working the way they work today — through `scripts/deliver-ticket.sh`, tailing the child's `<ref>.log` and reading the wrapper-derived `<ref>.last-message`.

- **Driver fit:** Fails drivers 1, 5, 8, 9; serves only the "no new content at rest" instinct.
- **Pros:** Zero change; zero new content class; nothing to bound.
- **Cons:** Goals G-2/G-4 and AC-F7-x are unsatisfiable; the shell cannot stop being the inspection path; a typed dispatch still leaves nothing to read.

### Alternative 1 — Session Content as Durable Ledger Records

- **Eligibility:** Not eligible (fails C-2, C-6, C-7).
- **Summary:** Persist each stdout line (and the final assistant text) as an additive record kind under a per-ref key; `log` and `last-message` fold the prefix.
- **Constraint compliance:** Passes C-1, C-3, C-4, C-5. Fails C-2: a content record kind is a record-kind and schema addition the non-goals forbid. Fails C-7: content would sit inside the ledger, inside every backup, salvage, and repair path the store defines, while every ledger record payload in the system is identifier- or statistics-only. Fails C-6: a fold over content records has no file to bound — the family grows with output and bounding it needs a retention or compaction rule the store does not have.
- **Driver fit:** Serves driver 8 partially (one storage mechanism); fails drivers 1 (a per-line fence cost on the delivery path), 2, and 4.
- **Pros:** One storage mechanism; no new directory; the read is a fold over delivered primitives.
- **Cons:** A privacy class inside the ledger; a fence per append on the delivery path; unbounded growth with no retention rule; every future store consumer must expect content; salvage and repair must reason about content.
- **Why rejected:** It spends the invariant that makes the durable plane reviewable — identity inside, content beside — to save one directory.

### Alternative 2 — Add the Read as a Member of the Closed Operation Set

- **Eligibility:** Eligible on the gates (C-1…C-7 all pass). Rejected on drivers, not by a gate.
- **Summary:** Add an eighth operation (for example `read-final-message`) with a session-port member, an entry in `supportedOperations`, and a gap for adapters that cannot read storage; `last-message` calls the operation.
- **Constraint compliance:** No independently sourced gate forbids it — the NFR-5 list does not name operations, and the operation-set closure is this change's own requirement (spec DM-3), so it is not used to eliminate the option.
- **Driver fit:** Serves driver 3 and partially driver 6; costs driver 7 materially and driver 8's simplicity. Measured net: symmetry worth one query against a widened closed vocabulary, every adapter's declarations, and a parity-matrix move — while `session-introspection` would still be the thing an adapter author reads to answer "can this harness be introspected?".
- **Pros:** One vocabulary; the capability gate is uniform with `terminate`; the read appears where a reader looks for session capabilities.
- **Cons:** `HARNESS_OPERATIONS` grows to eight; every adapter's `supportedOperations` and `declaredGaps` must answer or gap a read (opencode spreads the union and would inherit it silently; Claude Code enumerates and would need an edit); adapter conformance parity and its assertions move (RSK-9); the read duplicates a capability the vocabulary already declares, so the system would answer "can I read a session?" from two places.
- **Why rejected:** A read needing no handle and no session should not be an operation, and the churn lands on every adapter while an existing capability already says what an adapter can and cannot do with a session.

### Alternative 3 — Copy the Transcript into a Per-Ref File at Completion

- **Eligibility:** Eligible on the gates (C-1…C-7 pass). Rejected on drivers and on two facts.
- **Summary:** Keep the stdout family for `log`, and additionally have the engine write the session's final assistant message into a per-ref file when the attempt reaches classification; `last-message` reads that file.
- **Constraint compliance:** Passes all seven gates. (NFR-11's "the final message is never written by the engine" clause is a decided requirement of this design, recorded as DR-2, not an independent gate — so it is not counted as an elimination.)
- **Driver fit:** Serves drivers 1, 4, and 6 for a **finished** lane only; fails driver 3's spirit (a second at-rest content class the engine owns) and driver 6 for a live one.
- **Pros:** `last-message` becomes a plain file read; no adapter seam; no dependency on harness storage layout; an operator can `cat` it.
- **Cons:** Two kill shots that are factual rather than policy — (i) AC-F4-3 requires an `active` lane to answer with the latest message observed so far, and a completion-time copy has no completion to copy from; (ii) `HarnessEvidence` carries no assistant text, so the engine would have no source for the copy at classification without reading the transcript anyway — which is the seam this alternative was meant to avoid. Plus a second content family with its own bound, retention, and privacy lifecycle, and a stale copy that answers after the transcript moved on.
- **Why rejected:** It cannot answer the live case at all, and it would need the very seam it proposes to replace; the copy adds a content class for no capability.

### Alternative 4 — Derive the Tail from the Harness's Persisted Store or Transcript

- **Eligibility:** Not eligible against the requirement it must satisfy — fails spec F-7 / AC-F7-1 ("persist harness stdout per ref"), which names persisting the stdout stream. No gate is violated; the requirement is not met.
- **Summary:** Skip the artifact entirely. `log` reads the harness's own persisted session records and renders a tail from them; `last-message` reads the same storage and takes the final assistant message.
- **Constraint compliance:** Passes C-1…C-7 on paper: a store read can be read-only, ref-scoped, and bounded, and declares no key.
- **Driver fit:** Fails driver 1: the ticket requires the stdout stream as printed, and the persisted store is a different shape (decoded messages, not the raw event lines; a Claude transcript, not stdout). It also fails driver 4 for an opaque store whose read bound the engine neither owns nor can declare.
- **Pros:** No new file; one source for both answers; nothing to bound.
- **Cons:** The persisted shape is not the printed stream, so an operator loses the raw evidence (and for opencode, the JSON event sequence); an opaque or undocumented store cannot serve a declared-bound tail; a store layout change breaks `log` as well as `last-message`, doubling the blast radius of an adapter-internal change; and on Claude Code there is no content read at all.
- **Why rejected:** It answers a different question than the one the ticket asks, and it makes the tail depend on storage the engine does not write.

### Alternative 5 — Read the Shell's Own Output and Message Files

- **Eligibility:** Not eligible (fails C-4; C-3 at risk — ⚠️).
- **Summary:** Point `log` at `tmp/deliver-ticket/<ref>.log` and `last-message` at `.ai/local/delivery/<ref>.last-message`, which already exist for the shell lane.
- **Constraint compliance:** Passes C-1, C-2, C-5, C-6, C-7. Fails C-4: it reads a shell-owned path, which NFR-6 and NG-5 forbid, and it makes the typed answer a second reading of files the shell may delete, heal, or overwrite. C-3 is at risk rather than failed: the shell's own contract includes self-healing a stale PID file, and inheriting that directory invites inheriting the repair habit, which a read must never do.
- **Driver fit:** Fails driver 3 (a second truth source the shell can mutate under the reader), 7 (the change exists to stop this read), and 9.
- **Pros:** No new file to write; the data already exists wherever the shell has run.
- **Cons:** A typed answer that depends on a file the shell may replace or clear; a typed dispatch writes none of it, so the answer would be absent exactly on the typed path; structural drift risk (RSK-10).
- **Why rejected:** It reintroduces the dependency the change removes, from a writer with different lifecycle rules.

### Alternative 6 — Widen the No-Handle Session Listing with the Final Message

- **Eligibility:** Not eligible (fails C-7; C-6 at risk — ⚠️).
- **Summary:** `listSessions` already answers without a handle (`{ workItemRef, descriptor? } → { handles, truncation? }`). Add the final assistant message to each listed handle's entry and let `last-message` call it, so no seam and no artifact are needed.
- **Constraint compliance:** Passes C-1…C-5. Fails C-7: a listing is not a content channel — every consumer of `listSessions` would start receiving session content, which changes the privacy boundary of a delivered read rather than adding a new one under a declared capability. C-6 is at risk: the message bound would have to apply per listed handle, so one call could return up to `HARNESS_MAX_SESSIONS` × 512 characters, and the delivered truncation mark describes handles, not message text.
- **Driver fit:** Fails drivers 3 and 7: the listing is used on a resume path in the production composition (`packages/cli/src/production.ts:3727` recovers a session identity from it), so content in the listing would put transcript reads on a decision path that currently only needs identifiers; and it widens a delivered payload's parity fixtures for one consumer's benefit.
- **Pros:** No new file, no new seam, no new capability; one call answers both questions.
- **Cons:** Content on an identifier channel; a listing that can read every session's transcript; per-handle bounds instead of one; parity fixtures and the listing's privacy statement move; and a listing truncation mark that no longer means what it says.
- **Why rejected:** A listing digest is not a content channel, and putting content there would make a resume path read transcripts and would move a delivered payload's contract and privacy boundary — a worse trade than one optional seam.

### Alternative 7 — Selected: Bounded Stdout Sidecar Directory Plus an Injected Transcript Read Seam

- **Eligibility:** Eligible.
- **Summary:** One artifact directory, `dispatch-logs.<workspace>/<REF>/`, holding one append-only segment file per stream of a streaming adapter, with a per-file cap enforced by segmentation and continuation and retention by file count; plus one injected, adapter-owned, read-only transcript seam, covered by the existing `session-introspection` capability, returning the final assistant message or one closed absence.
- **Constraint compliance:** Passes C-1…C-7 (matrix above). Table stakes satisfied. DR-1…DR-5 are the consequences it commits to.
- **Driver fit:** Best on net across every driver: a durable post-hoc tail of what the harness printed (1), the ledger untouched (2), a read that cannot act (3), a bound that costs one file creation per megabyte (4), one ref one answer plus one stream one file (5), the harness's own words (6), no new operation/capability/gap reason/error row/key (7), the paved road of artifact families beside the ledger (8), and one convention for M4-S10 to read (9).
- **Pros:** Boundedness is structural rather than operational; attribution by file name; two concurrent streams cannot damage each other; a crash costs at most an unterminated tail; the family is operator-local, `0600`, and reviewable in one paragraph; the durable plane keeps its invariant; `last-message` stops being a synthesized sentence; the capability question is answered by a capability that already exists; no key, no token, no record, no operation, no parity change; a pre-change ref answers `no-log` and still answers `last-message` through the transcript, with no migration.
- **Cons:** The first persisted non-identifier content in the dispatch plane; unscrubbed by design (DC-6); the retained window can remove the beginning of a long run; the opencode child's stderr and the wrapper's progress lines are not captured; a one-shot harness contributes nothing, so its `no-log` must be explained; the family is several small files rather than one; the transcript read depends on adapter-internal storage layouts the offline battery cannot prove, and on Claude Code it cannot answer at all.
- **Why chosen:** It is the only alternative that satisfies every independently sourced gate and the ticket's stated requirement, at the lowest net cost across the drivers, with the bound expressed as a property of the layout instead of an operation on the data.

## Decision

- **Decision:** Adopt **ALT-7**.

  1. **DC-1 — Artifact home, and who has one.** `dispatch-logs.<workspace>/<REF>/` is a directory per work-item reference inside the dispatch project state root: outside the store's record set, derived-document set, salvage path, and repair path. It contains only that reference's segment files, and it exists only for a **streaming** adapter — a one-shot adapter (Claude Code) streams nothing, so it produces no files and no directory. (Spec DM-2 refined per DR-5, §25.1; DR-2.)
  2. **DC-2 — Write contract: append-only, per stream, segmented, one rule.** Each stream of a streaming adapter — a spawn, a resume, or a deliver — gets its own file, created when that stream starts and before its first yielded value, `0600`, receiving single `O_APPEND` writes; existing bytes are never modified and no coordination file exists in the family. **The writer applies one rule to every yielded value: the value followed by one LF.** The stream's final remnant is a yielded value like any other and is terminated by that LF; nothing is appended verbatim. A file is capped at 1 048 576 bytes by starting the stream's next segment; a value with its LF that does not fit and is longer than the cap is split at the boundary — the current file is filled to exactly the cap with its leading bytes and the remainder continues at the start of the next file — while a shorter value that does not fit simply starts the next file whole, so only a value longer than the cap can leave a file beginning mid-line. Retention per reference is the newest two files by name (family bound 2 × cap); a third file's arrival removes the oldest best-effort after the new file exists, and a failed removal leaves the extra file until the next append. A restarted iteration's output is captured in its own file. **The tear rule:** a process killed mid-write leaves bytes that are not a line, and the reader drops that unterminated tail. The sink is non-gating per DR-5, which refines spec F-7/API-8's "never blocks the drain" into "non-gating, not non-blocking". (Spec F-7, API-8, AC-F7-1…AC-F7-4; DR-3, DR-4.)
  3. **DC-3 — Read contract, its tolerances, and the divergence it carries.** `dispatch log` reads the reference's own directory to choose the newest file, stitches the retained files in name order into one byte stream, drops an unterminated tail (a torn write), splits on LF, and returns the newest `--tail <n>` lines. When the tail is not satisfied by the retained window, or the oldest returned line is a continuation whose beginning retention removed, the answer carries exactly one truncation fact naming the retained window — including the case where only one file is retained (the stream's first segment). `--tail <n>` is a canonical decimal in 1..500 with a default of 50, refused rather than clamped. Output is bounded at 65 536 machine bytes and 200 human lines / 32 768 bytes, with one truncation fact naming the binding scope. Absent directory or no file → `available=false`, `reason=no-log`, exit 0 — and this is the answer for a **one-shot harness lane**, where the absence means "this adapter streams nothing for `log`", never "the session printed nothing"; an existing file with no complete lines → `available=true` with an empty list; unreadable file → `available=false`, `reason=unreadable`, exit 1. Reads are snapshots: a segment switch or an append in flight may mean the newest bytes are not in the answer, and the answer states what was durable at read time. No listing across references, no shell read, no deletion. **Divergence, stated once:** the typed tail is the harness's own stdout (for opencode, its JSON event stream); it is neither `<REF>.log` — which holds the opencode child's stderr — nor the wrapper's progress lines, which go to the wrapper's terminal. The exit projections and the numeric bounds are **spec constants restated here** (DEC-5, DEC-8, DM-6), not decided by this record. (Spec F-2, API-7, DEC-3, DEC-5, DEC-8.)
  4. **DC-4 — Transcript read seam: opencode reads; Claude Code declares the gap.** `last-message` resolves the newest lane record for `(repository, ref)`, takes its `sessionId` and `harnessKind`, and calls one injected, adapter-owned, read-only seam that reads that harness's persisted session store and returns the session's final assistant message. The seam takes no handle, starts nothing, resumes nothing, collects nothing, terminates nothing, lists nothing, and administers nothing on a live store. It adds no operation, no capability-union member, and no gap reason: the read is covered by the **existing `session-introspection` capability**, which opencode declares supported. **Claude Code does not serve this read**: its adapter declares `session-introspection` as a gap (`headless-mode-limitation`), its persisted-session reader is the telemetry capture under `telemetry-extraction`, and that reader parses statistics only — it is not this seam. A Claude Code lane therefore answers `capability-gap`, and giving Claude Code a `last-message` read would require changing its capability declaration, which is a different decision. `capability-gap` in the answer means exactly "the lane's harness declares `session-introspection` as a gap"; the declarations, the gap inventory, and adapter conformance parity are unchanged (DR-1). (Spec F-4, API-9, DM-3, DEC-4, AC-F4-6.)
  5. **DC-5 — Message fidelity, composition order, bounds, and finality.** The answer is the transcript's final assistant message, never a synthesized sentence: the query reads no attempt record, derivation payload, or envelope field. The composition order is fixed: **redact → flatten → bound → mark.** The delivered chokepoint replaces **registered credential values** with `[redacted]` first, so a credential straddling the 512-character cut cannot survive as a disclosed prefix; the text is then flattened to a single line, bounded to 512 characters, and `truncated` is set from the post-redaction length, true exactly when text was cut. The record does not claim general content scrubbing, and no consumer should read "redacted" as "sensitive prose removed". `final` is true exactly when the lane's newest record is `terminal`; on an `active` lane the answer is the latest assistant message observed so far — it may be partial, and it is declared not final. The absence ladder is closed and ordered: `no-lane`, `capability-gap`, `session-unknown`, `no-message`, `unreadable` — each a data fact at exit 1 with a null message, no new error identity, and the store's typed failure preserved when the lane store itself cannot be read. (Spec F-4, API-4, DM-5, DM-7, AC-F4-1…AC-F4-7.)
  6. **DC-6 — Privacy posture, and the honest reason for no scrubbing.** The artifact is the harness's own stdout: local, `0600`, bounded by layout, never committed, never an evidence reference, never served beyond the tail an operator asks for. The engine adds nothing to it and removes nothing from it beyond the declared transformation. There is no scrubbing pass at write, and the reasons are: the family never leaves the local state root and its files are `0600`; the shell's raw capture is the parity precedent for an unscrubbed local diagnostic file; and a scrubber fed by the **declared-credential** set would create a false sense of safety, because that set is a narrow, explicitly declared set, not general secret discovery. This is a declined option, not an impossibility: the composition root computes the set (`edge.ts:619-631,1667`; `production.ts:521-527`) and could inject a redactor into the engine. The cost is a write-time dependency of the engine on CLI-side secret resolution for a guarantee it cannot honestly make, so it is deferred with revisit triggers in both directions. The final message is read-only, bounded, and chokepointed; the engine never writes it anywhere. (Spec NFR-11, §21, §22, §7.3, NG-8.)
  7. **DC-7 — What this record does not decide, and what it refines.** The `log` and `last-message` exit projections, the numeric output bounds, and the tail range are spec constants restated for traceability (DEC-5, DEC-8, DM-6); the per-file cap is a spec constant; the **retained-file count and the family bound are decided here** as policy. The statement that M4-S10 inherits these conventions is a convention offered to that change, not a binding; GH-348 decides its own surface and may supersede this record. The complete list of spec statements this record refines is DR-5's; `@pm` applies them during delivery, and this record does not edit the change artifact.

### Constraint Compliance Attestation

ALT-7 satisfies C-1 through C-7. C-1: no configuration key; the per-file cap and ordinals are declared constants, the retained count and family bound are this record's decided policy, and none is configurable. C-2: no token, projection, exit, error row, domain kind, record field, record kind, schema version, or evidence identifier changes. ## Trade-offs & Consequences

### Positive Outcomes

- A failed or stalled typed dispatch leaves a bounded tail of what the harness actually printed, readable with no shell script and with no dependency on the shell's files.
- **Attribution is preserved:** each stream has its own file, so a tail can be tied to the attempt and iteration that produced it from the name — which a single-file shape could not do.
- **Boundedness costs nothing per line:** the cap is a new file (and, for a value larger than a file, a continued write), so the delivery path's cost is the bytes it writes, not work proportional to the artifact.
- **No coordination is needed:** no writer shares a write target, so a concurrent dispatch cannot corrupt or truncate another stream's evidence, and a crash costs at most an unterminated tail.
- **One writer rule and one tear rule** mean the writer and the reader cannot disagree about what a file contains: everything written is LF-terminated, and anything not LF-terminated is a torn write.
- The durable plane keeps its invariant: identity, counts, and timestamps inside the ledger; content beside it, in one family with one cap rule, one retention count, and one privacy statement.
- Inspection cannot disturb a delivery: the read path has no way to start, resume, or signal a session, and it deletes nothing.
- The capability story is honest: an existing, already-declared capability (`session-introspection`) covers the read for the adapter that has it, and the adapter that does not says so.
- The scope story is honest too: a one-shot harness has no increment to store, and the surface says so instead of pretending otherwise.
- M4-S10 gets a written convention instead of a re-derivation, and a repository in `dual-run` can use both surfaces without either becoming the other's truth source.

### Negative Outcomes

- **The tail is not the shell's log, in two ways.** An operator who expects the opencode child's stderr diagnostics will not find them; nor will they find the wrapper's progress lines, which the shell writes to its terminal. For opencode the content is the JSON event stream — precise, but not the timestamped human log the shell printed.
- **A one-shot harness has no tail at all.** `dispatch log` answers `no-log` for every Claude Code lane, and an operator must not read that as "the session printed nothing"; the reference page has to say so explicitly.
- This is the first persisted non-identifier content in the dispatch plane. The privacy surface widens from "identifiers only" to "identifiers plus whatever the harness printed", bounded and local but real — and unscrubbed by design, for the cost-and-honesty reasons in DC-6.
- "Redacted" on `last-message` means declared credential values were replaced **before** the bound was applied. Prose, values the harness itself printed, and anything outside the declared set are returned verbatim within the bound — but a credential straddling the cut cannot survive as a prefix.
- The retained window is a window: a long run's beginning is deleted, a still-growing older stream can be the file removed when a newer one arrives, and a single value spanning more files than are retained is reconstructed incompletely with a truncation fact.
- The family is several small files rather than one, so an operator (or a future tool) has to know that the newest file is not the whole story.
- `log` reads at most the retained window, so a deeper tail is answered with a truncation fact rather than a longer read.
- Reads are snapshots: a segment switch or an in-flight append can make the answer a slightly stale tail, and an active lane's transcript read may be partial (marked `final=false`).
- The append runs on the delivered line iteration, so a slow disk adds latency to the drain; it is non-gating, not free.
- `last-message` depends on adapter-internal storage layouts the offline battery cannot prove, and on Claude Code it cannot answer at all until that adapter's declaration changes.

This record reads it as the general "introspect a session the adapter owns" capability; the change's working interpretation is this reading pending owner acceptance, and if the owner reads it as metadata-only the outcome is an additive capability decision at acceptance. (owner: the human owner at the GH-354 PR review)

These are implementation-level and deliberately not decided here. Each carries the test that pins it; nothing below adds protocol machinery.

1. **Exact file naming and ordinal widths** (the recorded-time field, attempt identity, iteration ordinal, segment ordinal, zero-padding, `.out` suffix) — test `artifact-naming`: a plain lexical sort equals creation order across a restart and across two concurrent streams for one ref, with ties broken by attempt identity.
2. **The continuation accounting rule** (byte counting including the LF, the exact "does not fit" boundary, and the case of a value exactly filling a file) — test `segment-switch`: file sizes at or under the cap, no byte dropped or duplicated at a boundary, and a continued value reconstructed byte-identically.
3. **The reader's torn-tail tolerance** (how an unterminated tail is detected and dropped) — test `torn-line-reader`: a file ending mid-line yields its complete lines only, and a complete file's last line is not dropped.
4. **The stitching mechanics** (assemble the retained files in name order, then split; the exact truncation accounting when the window is exhausted, when only one file is retained, and when the oldest line is a continuation) — test `two-segment-tail`.
5. **The ordering source for "newest" and "preceding"** (name order, not mtime) — test `segment-ordering`: a stale mtime does not reorder the family.
6. **The sink-fault taxonomy** (which failures are swallowed as observation and which are absent) — test `sink-fault-observational`: a failed append leaves the token, exit, records, and evidence identical.

## Verification Criteria

- An admitted dispatch on a **streaming** adapter creates `dispatch-logs.<workspace>/<REF>/` and one file per stream with `0600`; every stream (spawn, resume, deliver) is captured from its first value, including values the event decoder skips; a restarted iteration's output lands in its own file; two refs never share a directory. A **one-shot** adapter creates no directory, and `dispatch log` for its lane answers `available=false`, `reason=no-log`, exit 0.
- **Privacy assertion (a):** each file's bytes equal the declared transformation of the values that stream yielded — each value followed by one LF, including the final remnant — with nothing else added or removed, and the unterminated tail of a torn file is dropped rather than read as content.
- **Privacy assertion (b):** no log content appears in any record, evidence list, derived document, or envelope beyond the requested tail; `last-message` reads no attempt record, derivation payload, or envelope field.
- **Privacy assertion (c), two fixtures:** a credential value injected into the stdout stream appears verbatim in the artifact and nowhere in any record; a credential value injected into the transcript fixture is replaced by `[redacted]` in the `last-message` answer; a prompt-only canary never appears in the artifact.
- A stream exceeding 1 048 576 bytes yields additional files, each at or under the cap, with no byte dropped at a boundary; a value longer than the cap is continued and reconstructed byte-identically by the reader; a shorter value that does not fit starts the next file whole; a third file's arrival leaves two, and a failed removal leaves an extra until the next append; the family never exceeds 2 × cap after a successful removal.
- Two concurrent streams for one ref produce two files with no interleaved or cross-contaminated content; a killed writer leaves at most one unterminated tail and its earlier lines intact, and the reader returns the complete lines only.
- `dispatch log` reads the reference's own directory, stitches the retained files, drops an unterminated tail, and answers with one truncation fact when the retained window cannot satisfy the request — including when only one file is retained, when the oldest returned line is a continuation whose beginning retention removed, and when the requested tail is deeper than the window. `0`, `501`, `1.5`, `-1`, `01`, and `abc` are refused `input.value.rejected` before any file read; `no-log` is exit 0 and `unreadable` exit 1; no line from another ref's directory appears in any answer.
- `dispatch last-message` equals the transcript's final assistant message and never the envelope's synthesized `lastMessage`; the order is observable — a credential straddling the 512-character cut is fully removed (no prefix disclosed) and `truncated` reflects the post-redaction length; `final` is true exactly for a terminal lane, and an active lane's partial answer is marked not final; each of `capability-gap`, `session-unknown`, `no-message`, and `unreadable` is reachable with a null message at exit 1 and no new identity; `capability-gap` is produced exactly for a harness that declares `session-introspection` as a gap (the Claude Code fixture) and not for opencode; `last-message` performs zero session operations, starts zero processes, and deletes nothing.
- The operation inventory still has seven entries; the lifecycle-capability and gap-reason vocabularies, every adapter's declarations, the configuration key set, the error-row inventory, the attempt key set, its 16-reference budget, and the lane key set are unchanged; no query changes the artifact family's file set.
- Planted shell artifacts (delivering marker, `<REF>.pid`, `<REF>.pm.out`, `<REF>.log`, `<REF>.last-message`) leave every answer identical and are byte- and mtime-identical afterwards; the no-shell invariant reports zero shell-execution references and zero script-path literals over the extended surface list.

## Confidence Rating

**Medium-High.** The repository facts that carry the decision are direct and current: the lane record's contract forbidding content; the port's empty content surface, with a listing digest as its only no-handle read; the closed lifecycle-capability union that already contains `session-introspection`, declared by opencode and gapped by Claude Code, whose only persisted-session read is its statistics-only telemetry capture; `HarnessEvidence` carrying no assistant text; the two adapter shapes (opencode streams, Claude Code is one-shot); the line channel's `AsyncIterable<string>` with the final remnant pushed unmarked; the three distinct shell streams and `cmd_log`'s target; opencode's JSON stdout and its decode-then-skip drain; the telemetry sink's decoded-frame boundary and construction points; the state layer's artifact families beside an identifier-only ledger; opencode's read-only store access with declared caps; the narrow declared-credential set behind the chokepoint; and the non-renewing 90 s lease. The design's own risk is structural rather than behavioural: append-only per-stream files make corruption between writers impossible by construction, one writer rule and one tear rule leave no ambiguity about a file's contents, and the cap lives in the layout. The remaining uncertainty is external — whether a harness's persisted store always yields a transcript, and whether a two-file window is enough in practice. Both degrade to closed absences or a truncation fact, and neither moves a token.
