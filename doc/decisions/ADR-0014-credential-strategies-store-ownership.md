# ADR-0014: Credential Strategies — Store-Ownership Resolution Behind an Unchanged Port, Without Harness-Owned OAuth

## Context

- **FACT:** The credential port exposes exactly one operation, `resolve(reference) -> { ok: true, material } | classified failure`, and exactly two declared source styles, both environment-backed: `literal` (an environment variable name, used verbatim) and `environment-prefixed` (the brand prefix plus a suffix) (`packages/core/src/contracts/credentials.ts:17-19`, `:67-69`; `packages/adapters/src/credentials/index.ts:36-45`, `:62-80`).
- **FACT:** `resolve` is **synchronous** and is called synchronously on the request path: the GitHub, GitLab and Jira clients resolve per request (`packages/adapters/src/github/client.ts:292`, `packages/adapters/src/gitlab/client.ts:70`, `packages/adapters/src/jira/client.ts:132`), the inference transport per generation (`packages/adapters/src/inference/index.ts:94`), the quota reader and engine per availability decision (`packages/core/src/provider/quota.ts:373`, `packages/core/src/provider/engine.ts:296`), and the harness spawn-environment builder per spawn (`packages/core/src/domain/harness-spawn-env.ts:60-65`).
- **FACT:** The failure variant is a reified mirror of one error-table row, and the two are bound by a suite so drift fails by name (`packages/core/src/contracts/credentials.ts:39-53`; row at `packages/core/src/contracts/error-table.ts:430-437`). Its only code is `config.credential.missing`, with `domainKind: config`, category `user`, `retryable: false`, consequence `not_landed`, projection `user-validation`.
- **FACT:** `config.credential.missing` is constructed or observed at **37 enumerated sites across 16 files** outside the error table — 11 in `packages/cli/src/edge.ts`, 5 in `packages/cli/src/production.ts`, 4 in `packages/mcp/src/serve.ts`, 3 in `packages/core/src/provider/engine.ts`, 2 in `packages/core/src/domain/harness-spawn-env.ts`, 2 in `packages/core/src/contracts/harness.ts`, and one each in ten further files including `packages/adapters/src/inference/index.ts` and `packages/core/src/provider/simulate.ts`. Every one branches on `!ok` and `.code`.
- **FACT:** The port's contract line already forbids the material from reaching any diagnostic channel: "resolved material never enters logs, errors, or diagnostics" (`packages/core/src/contracts/credentials.ts:60-66`), and its header documents the intended extension: "A future credential sidecar becomes the port's second implementation ... the port interface does not change" (`:7-13`).
- **FACT:** Production composes the port from the process environment, either from an injected fact or through `createProcessCredentialPort(brand)`, and composes a second, injected-environment instance for harness spawn (`packages/cli/src/production.ts:2235-2236`). The only ambient environment read in the I/O tier is that production wrapper (`packages/adapters/src/credentials/index.ts:72-80`).
- **FACT:** The **tracker** credential reference has no configuration path. It is a hard-coded literal `GITHUB_TOKEN` (`packages/cli/src/production.ts:674-677`), consumed by a constant `githubInstance()` with no parameter (`:685-693`), and the only `github` key anywhere in the configuration catalog is the poll-interval row (`packages/core/src/config/catalog.ts:926`). The same hard-coded reference is the one registered for serialization redaction (`:683`).
- **FACT:** The installed unit carries exactly one environment binding, `Environment=<PREFIX>_STATE_DIR=<state dir>`, runs `<binary> daemon start --foreground`, and declares `Restart=on-failure` with **no** `RestartSec` and **no** `StartLimitBurst` (`packages/adapters/src/daemon/supervisor.ts:51-54`). A detached start replaces the child environment with the declared re-entry record (`packages/adapters/src/daemon/process.ts:71-76`; TDR-0023 DC-1/DC-7). A user unit does not inherit a login shell's environment, so a fresh `daemon install` yields a unit with no credential of any kind. Because systemd rate-limits restarts by default and the unit sets no start limit of its own, a credential failure that is fatal at start produces **bounded flapping and then a failed unit** — not an unbounded loop, and not a served daemon either. The shipped daemon resolves nothing (see the composition FACT below), so this constrains the **resident** composition: it is retained because the same unit will carry the lane composition in #395.
- **FACT:** What the product needs credentials for is narrow: the tracker clients above, the commit primitive's inference transport, and provider quota/usage reads. Lane spawns do not need a provider key: the shipped profile environment record sets only model names (`packages/core/src/provider/profile-env-record.ts:251`, `:258-269`), and the harness authenticates its own sessions. The spawn descriptor *can* carry a credential entry (`packages/core/src/contracts/harness.ts:144-146`), the catalog allows a `credentialRef` on a harness environment entry (`packages/core/src/config/catalog.ts:388-397`, `:392`), and production maps it (`packages/cli/src/production.ts:3053-3068`) and resolves it at spawn (`packages/core/src/domain/harness-spawn-env.ts:60-65`) — so "the lane environment is model-only" holds for **shipped settings**, not by construction.
- **FACT:** The credential-material boundary is mechanical and directory-scoped: exactly one `credential-material` allowlist entry is permitted and it must be the credential implementation directory, `packages/adapters/src/credentials` (`scripts/checks/secret-read-boundary.ts:35-39`, `:249-256`; `doc/spec/features/feature-adapter-ports.md:173`, `:179`).
- **FACT:** The delivered posture is deny-by-default and names-only: "Production never reads the OS keyring, never inherits an ambient variable implicitly, and declares no fallback key", and the `gh` bridge is documentation plus an operator-performed export (TDR-0019 C-4 and D-7; `doc/spec/features/feature-adapter-ports.md:155`). TDR-0019's revisit trigger routes any keyring request to an owner decision.
- **FACT (external surfaces, observed 2026-11-23):** `gh 2.91.0` exposes `gh auth token [--hostname] [--user]`, non-interactive, defaulting to the active account for the host, with the token stored in the system keyring. `opencode v2.3.2` exposes `opencode auth list` and `opencode auth export [<target>]`, the latter described by its own `--help` as "print stored credentials, including secrets, as JSON", with `target` an "Integration ID or name (exports every integration when omitted)".
- **FACT (export shape, observed 2026-11-23, values never read):** the export is a JSON **array**; each entry carries `id`, `integrationID`, `label`, `active`, `value`; `value.type` is `"key"` (with `value.key`) or `"oauth"` (with `value.methodID`, `value.access`, `value.refresh`, `value.expires`, and optionally `value.metadata`). Supplying a target returns only that integration's entries. One integration id may carry **several** entries: `openai` returned two, one `active: true` and one `active: false`, with distinct `cred_*` ids.
- **FACT (corrected by the critic, observed 2026-11-23):** `gh auth token` hands over **one static, durable bearer token for one host**, and `gh` exposes **no separate refresh grant** and no refresh mechanism of its own. A leak of that token is a **long-lived credential**, not a short-lived one. By contrast a harness OAuth export hands over an explicit `refresh` grant beside `access`.
- **FACT (corrected by the critic):** the harness store in use today holds an **OAuth-only** integration: `openai` has two entries, both `oauth`, one of them past its recorded expiry while `active: true`. The shipped subscription-class provider (`zai-coding-plan`) is stored as an **API key**. Provider `github-copilot` is `oauth` and reports `expires` as the Unix epoch while `active: true`.
- **FACT (this is what re-scopes the record):** the **shipped** daemon has **no credential consumer at all**. The production composition passes no `lane` and no `executor` (`packages/cli/src/production.ts:2191-2219`), so `laneExecutor` and `supervise` are `undefined` (`packages/cli/src/daemon-compose.ts:565-577`) and the mode is `supervise-only` (`:792-796`); the specification is explicit that the production daemon "starts no lane" (`doc/spec/features/feature-resident-daemon.md:259-272`, `:301`, `:327`; `doc/overview/architecture-overview.md:93`, `:504`). A `supervise-only` daemon performs no tracker read and populates no scheduler work-item observation. **Therefore the consumer that receives the benefit of the new styles in this change is the one-shot CLI composition** — `dispatch`, `merge`, `status`, `commit`, `verify`, `queue` — not the daemon.
- **FACT (measured 2026-11-23):** the `--` terminator before the positional is accepted by the harness export — `opencode auth export -- <id>` and `opencode auth export --standalone -- <id>` both exit `0` — and the tracker's closed-grammar host form works: `gh auth token --hostname github.com` exits `0`. The argv shapes this record specifies are therefore executable as written, not merely well-formed.
- **FACT (observed 2026-11-23):** `opencode` is a **symlink** on the reference host (`~/.nvm/versions/node/v24.11.1/bin/opencode` -> the package's `bin/opencode.exe`), which is its normal installation through a version manager; `gh` is a regular file at `/usr/bin/gh`. A non-symlink rule would therefore reject the standard harness install, which is why C-10 resolves symlinks instead of refusing them.
- **FACT:** redaction registration happens at the entrypoint from **environment keys only**: `DECLARED_CREDENTIAL_REFERENCES` (`packages/cli/src/production.ts:683`) reaches `packages/cli/src/bin-launcher.ts:111`, then `entrypointSecrets` (`packages/cli/src/entrypoint.ts:310-318`), which derives a key with `resolveCredentialSourceKey` and reads `options.environment[key]`. For a `command` or `harness-store` key that derivation yields `${environmentPrefix}undefined` (`packages/adapters/src/credentials/index.ts:38-44`), so today a non-environment source would register **nothing** and its material would be rendered unredacted. This is why C-4 requires registration at materialization.
- **Why now:** the product is moving delivery from shell wrappers to a typed engine, and the engine's commands resolve credentials synchronously on every invocation. With a provided-store source unavailable to them, the only supported path is a hand-maintained copy per secret per install — exactly the second store this ticket exists to remove. The declared tracker reference has to become declarable for that path to be reachable at all. The resident lane composition will meet the same problem as soon as it is mounted (#395); this record settles that design too, so it is not re-derived there.

## Problem Framing (Clarified)

The question is not "how does the daemon get a token". It is **who owns each credential, what may the product do in that owner's place, and where in the process may that act happen**.

Seven facts make the naive framing wrong.

1. **The product is not the owner of any of these secrets.** GitHub's owner is `gh`; a provider's owner is the harness. The product needs *use* of a credential, not custody of it. A second store (an environment file, a product keyring entry, a config value) duplicates a fact someone else owns and cannot be revoked in one place.
2. **"Fall back to the environment" is indistinguishable from "silently use a different secret".** The delivered posture is right to reject fallbacks; an unavailable source must be *named* and *refused*, with the operator's alternative stated as a remedy, not taken as a policy.
3. **Not every owner's surface is equivalent.** `gh` hands over one durable static token and no refresh grant. A harness export hands over the **refresh grant** as well. Reading the first is delegation with a long-lived copy; reading the second is custody.
4. **A generic "declared command" is an exfiltration primitive.** A committed argv needs no shell, no interpolation and no clever stdout rule to read an arbitrary local file and send it somewhere on every resolve, unattended, under linger. A review is not a control against a committed line that looks like configuration.
5. **The port is synchronous, so a subprocess cannot live on the request path.** Every consumer resolves synchronously per request. Putting a bounded spawn inside `resolve` would block the daemon's single-threaded cadence on every tracker read.
6. **The daemon that ships today has nothing to resolve.** The production daemon runs `supervise-only`, starts no lane and reads no tracker (Context). A record that promised the daemon a provisioning benefit would be promising it to a component with no credential consumer — and would ship an unverifiable claim. The shipped benefit belongs to the one-shot command path; the resident design is specified forward for #395.
7. **A second failure code is not a message change.** Every consumer already branches on `!ok` and `.code` at 37 enumerated sites. Adding a code means threading it through the inference transport, the spawn-environment builder, the engine's park mapping, `doctor`, the MCP serve state and the CLI renderers — and several of those sites collapse the failure into a fixed shape today, so the new code would silently degrade unless each is edited.

Desired outcomes: a one-shot command that resolves a declared credential from its owner's store with no second copy, and — specified here for #395 — a resident lane composition that does the same without ever making readiness wait for the store; a port whose operation and result union keep exactly one success and one failure variant; a closed vocabulary that is declarative data rather than a discovery mechanism; `command` narrowed to a shipped allowlist so the act is **a pinned owner CLI running a pinned subcommand**, not "a declared program"; a harness-agnostic composition where a harness that cannot serve a declaration says so by name; a failure that always carries its source, a closed reason and a remedy, and never hangs, returns an empty string, or makes the unit flap; resolution ahead of the port so no subprocess runs per request; a declarable tracker reference with the shipped default unchanged; and no use of a harness-owned OAuth grant at all.

Out of scope: rotating or writing back any owner's store; unlocking a keyring; a product-owned keyring or secret file; per-request chained sources; allowlist entries for GitLab's CLI, Jira, or any secret manager; a narrower harness read than the export; the claude-code store strategy; and any change to the tracker adapters' transport, the inference transport, the provider engine's park vocabulary, or the error table's row set.

## Constraints (Hard Requirements)

### C-1: A one-shot command resolves from the owner's store with no duplicated secret file, and the tracker reference is declarable

- **Statement:** The tracker credential reference is declarable data with the shipped default **unchanged** (`literal`, `GITHUB_TOKEN`), so an operator can opt in to another source without a code change, and no documented behaviour or default value moves. When a reference declares `command` or `harness-store`, a **one-shot CLI command** (`dispatch`, `merge`, `status`, `commit`, `verify`, `queue`) resolves it from the owner's store, with no secret value written by the product and no secret value the operator must copy into a product-consumed file on that path. The resident lane composition is specified in the same record for #395; it is not claimed as a benefit of this change, because the shipped daemon consumes no credential at all (Context, D8.1).
- **Source:** AC (GH-394: "manage credential access in the credential owner's place"); verified gap (`packages/cli/src/production.ts:674-677`, `:685-693`; `packages/core/src/config/catalog.ts:926`)
- **Verification:** **CI** — the real production composition with the declared reference and an **injected child seam**, asserting that the declared argv (not the hard-coded literal) reaches the seam, that the resolved material is registered for redaction, and that the default reference resolves exactly as today. **Manual / post-merge, not a CI gate** — one demonstration against a real owner store on a host with `gh` authenticated, proving end to end that no environment file is needed (CI holds no credential, C-9).
- **Negotiable:** no

### C-2: The port keeps one operation and one result union — one success variant, one failure variant

- **Statement:** `CredentialPort` keeps exactly **one** operation with the same input, and its result is a union with exactly **one** success variant and exactly **one** failure variant, so a second implementation — including a sidecar that forwards the call over local transport — satisfies the type with no new member and no new variant. The success variant is unchanged. The failure variant gains **additive optional** fields (`source`, `reason`, `remedy`) and nothing else; resolution context (active harness identity, child runner, environment record, store facts) enters as **construction inputs of the implementation**, never as members of the operation. There is no diagnostic channel: those three fields are identifiers and bounded text, never material.
- **Source:** prior decision (ADR-0007; `packages/core/src/contracts/credentials.ts:7-13`, `:60-69`); AC (GH-394 "behind the unchanged port")
- **Verification:** structure test (operation arity and input unchanged; exactly one success and one failure variant; a forwarding implementation satisfies the type) + test (a planted-secret canary proves the three fields never carry material) + dependency-cruiser boundaries (core imports no implementation)
- **Negotiable:** no

### C-3: Declared mapping, closed vocabulary, no chain, no discovery

- **Statement:** Every reference names one source style from a closed set and carries its own explicit source keys; nothing is discovered by matching a label, an account name, a display name, an environment variable's resemblance, or a provider's name. No strategy has a fallback and no declaration admits a chain: an unresolvable declaration refuses, it never tries a second source.
- **Source:** prior decision (TDR-0019 C-4 and ALT-2 rejection; `credentials.ts:22-31` "declarative data, never derived")
- **Verification:** test (a refusal case per style asserting zero consultation of any other source; validation refuses an unknown style and an unknown reason field) + code review
- **Negotiable:** no

### C-4: Resolved material never persists, and never leaves the process boundary

- **Statement:** Material resolved by any strategy is returned once through the port result and is never written to a log, telemetry event, ledger record, capsule event, error envelope, human diagnostic, status digest, temporary file, child argv, or child environment (the one declared harness-spawn environment path excepted and unchanged). This extends the delivered contract line to strategy internals and to child-process output: a strategy's captured stdout is material or it is discarded, never echoed. **The redaction set is a live registry, consulted at render/redaction time, and material is registered before any emit path can carry it** — before a log line, a throw with a payload, a render, or a return to a caller that logs — one-shot on the resolve that materializes it, resident on swap-in. The achievable property is stated that way on purpose: the value necessarily exists in memory for a moment before `register` can be called, so "never present and unregistered" would be a claim no implementation can honour. What is required is that **the resolver registers before parsing and before any throw**, so a malformed output can never be rendered raw. This is stronger than a construction-time snapshot and it is why the seam must be mutable: the entrypoint builds its registry before the composer runs, so a snapshot could never receive a later registration. Environment-backed styles keep today's entrypoint-static registration unchanged, because their values exist before any command runs.
- **Source:** prior decision (`credentials.ts:60-66`; TDR-0012 name-only diagnostics; TDR-0049 lane records carry no credential value; TDR-0025/TDR-0029/TDR-0030 event taxonomy); verified redaction path — `packages/cli/src/entrypoint.ts:310-318` builds a frozen array from environment keys derived by `resolveCredentialSourceKey` (`packages/adapters/src/credentials/index.ts:38-44`), `packages/cli/src/entrypoint.ts:320-334` passes it as `CliDependencies.secrets: readonly string[]` (`packages/cli/src/index.ts:130`), and the renderer reads that snapshot at `packages/cli/src/index.ts:667-734`; `packages/cli/src/edge.ts:683-692` (`registerEdgeSecrets`) is the same snapshot shape at both of its call sites, `packages/cli/src/edge.ts:1731` and `packages/cli/src/edge.ts:5203`
- **Verification:** test — **materialize a `command`-sourced credential after composition has completed** (the child double emits a canary), then render every surface that carries diagnostics: human output, the JSON envelope, `status`, `doctor`, and the park/log line; assert the canary is redacted on each. **A test that registers before composing does not prove the seam and is not acceptable.** Also assert the pre-existing entrypoint registration is unchanged for the two environment styles; that a **malformed child output throws and the raw output is never rendered** (the resolver registers before parsing and before any throw); and that a fake child's stderr canary never reaches a rendered surface + code review (registry consulted at render time, no second static pass)
- **Negotiable:** no

### C-5: Every source failure carries a named source, a closed reason and a remedy — never empty, never hanging, never fatal

- **Statement:** Every credential-shaped failure carries the delivered single code `config.credential.missing` plus, at minimum, a `reason` from a closed set and a `remedy`; `source` is present whenever a declared reference was being resolved. It never returns empty material, never substitutes a different source, never blocks past a declared timeout, and never exits or fails the daemon process. The closed reason set is: `program-unavailable` · `timeout` · `non-zero-exit` · `empty-output` · `shape-drift` · `ambiguous-account` · `oauth-excluded` · `source-not-supported` · `variable-absent` · `resolution-pending`.
- **Source:** AC (GH-394 "unavailable is classified ... never a hang, never an empty string"); internal standard (fail-closed classification; ADR-0013 D4 precedent for naming an environment-dependent refusal separately while keeping one identity)
- **Verification:** test (one case per reason, including `resolution-pending` and a `timeout` proving the two are distinct; a hanging child asserting a bounded refusal; an empty-output child; a non-zero exit; a malformed-output child asserting the raw output is never rendered, because the resolver registers before parsing and before any throw) + test (a renderer case per surface asserting the three fields survive). **Forward, #395:** that a daemon-side caller survives each reason and continues its cadence is proven with the lane composition, not here.
- **Negotiable:** no

### C-6: Harness identity is a construction fact; a declared harness must match it; no borrowing

- **Statement:** A harness-dependent declaration resolves against the harness the composition is running for. A declared `harness` field must **equal** the active harness identity; the composition's active identity wins, and a mismatch refuses with the named reason rather than reading the declared harness's store or borrowing another store's layout. A harness with no declared support refuses. The capability/gap posture of the harness adapter contract is preserved: an unlisted capability is a declared gap, never implied parity.
- **Source:** prior decision (ADR-0008; `packages/core/src/contracts/harness.ts:86-95`); AC (GH-394 "harness-agnostic by declaration", "claude-code differs")
- **Verification:** test (a declaration resolved under two harness identities, one supported and one not; a declaration whose harness field disagrees with the composition refusing by reason and consulting no source) + code review
- **Negotiable:** no

### C-7: One-shot resolution is synchronous, memoized per process, and off the per-request path afterwards

- **Statement:** `resolve` stays synchronous. In the **one-shot CLI composition** — the composition that actually ships in this change — a subprocess-style reference is resolved **on demand and synchronously** at its first use, the caller blocking for one bounded execution, and the result is **memoized for the lifetime of that process: exactly one execution per reference per process**. The memo is process-scoped, not a cross-invocation or cross-interval cache, and it bounds the count rather than extending a secret's residency beyond the command that needed it. After the first materialization, every further `resolve` of the same reference in that process is a memory read with **zero spawns**, and a repeated reference never spawns twice. Every execution carries a declared per-execution cap (**15 s default, 30 s bound**), closed `stdin`, bounded stdout capture, and a reduced child environment — the path, the home directory, and where the keyring requires it the session-bus facts, plus declared non-secret variables — never the parent's secret-bearing environment. **The resident composition** (asynchronous materialization, readiness that never waits, the reserved `resolution-pending` reason, atomic swap on a declared interval) is specified in the forward-looking section for #395 and is **not** a shipped property of this change: the shipped daemon consumes no credential (Context, D8.1).
- **Source:** AC (GH-394 "least privilege", "no secret in child argv or env"); verified sync call sites (`credentials.ts:67-69`; the seven consumer sites above); the two measured standalone costs (4.4–4.6 s and 5.5–6.0 s, Evidence table), which set the cap; the shipped daemon's `supervise-only` mode (`production.ts:2191-2219`; `daemon-compose.ts:565-577`, `:792-796`)
- **Verification:** test (a one-shot composition resolving one reference twice, asserting **exactly one** spawn and a memory read on the second resolve; a second distinct reference asserting a second spawn; zero further spawns across the remainder of the process; a hanging child asserting the cap; a recorded invocation asserting the exact reduced environment; a failure asserting the reason and remedy). The resident-composition assertions (readiness under a delayed child, `resolution-pending`, atomic swap, heartbeat bounds, interval cadence) are listed in the forward-looking section and marked **not satisfiable in this change; proven in #395**.
- **Negotiable:** no

### C-8: The lane environment stays model-only for shipped settings

- **Statement:** No strategy change causes a credential entry to appear in a lane spawn descriptor or in the profile environment record **built from shipped settings**; the shipped lane contract remains model names only and the harness continues to authenticate its own lanes. An operator who declares a credential entry on a harness environment variable keeps the delivered spawn-time behaviour, which is unchanged and out of scope here.
- **Source:** AC (GH-394 "lane spawn env stays model-only"); delivered profile record (`packages/core/src/provider/profile-env-record.ts:258-269`); catalog capability (`packages/core/src/config/catalog.ts:388-397`)
- **Verification:** test (no credential entry in any lane descriptor built from shipped settings; the profile environment record's key set is exactly the model-name set; a declared credential entry still resolves at spawn with unchanged behaviour) + code review
- **Negotiable:** no

### C-9: Additive and migration-free: no new error identity, park cause, announcement code or exit; hermetic

- **Statement:** No error-table row is added, no **park-record field** is added (the reason is carried in the rendered refusal and the log line only), no park cause or announcement code is added, no delivery-result token or exit is added, and the failure variant grows only by the three optional fields of C-2. Existing `literal` and `environment-prefixed` declarations resolve byte-identically; the shipped defaults — including the tracker reference — are unchanged; no operator must edit configuration to upgrade. The suite never consults a real store, a real keyring, or a real harness: every strategy is constructed over **injected seams**, and CI requires no credential to pass. This is not in tension with C-1: C-1's CI proof is the *real production composition with an injected child seam*, so the composition is real and the credential is not.
- **Source:** internal standard (guarded-set discipline, additive vocabulary, determinism/hermeticity; ADR-0003 tier rules); AC (migration cost); verified blast radius (37 enumerated sites in 16 files)
- **Verification:** test (shipped defaults and every existing provider-config fixture resolve unchanged; the tracker default resolves as today; a suite-level check that no test invokes a real owner CLI or reads a real store) + structure test (error-table row count, documented row set and park-record shape unchanged; no ambient read outside the existing allowlist entry)
- **Negotiable:** no

### C-10: `command` is a shipped allowlist of (program, pinned subcommand prefix) pairs

- **Statement:** A `command` declaration is accepted only when it matches a **shipped, closed allowlist** entry: an absolute program path plus a pinned subcommand prefix, with only the declared parameters the entry permits. The initial table is exactly `gh` → `auth token [--hostname <host>]` and `opencode` → `auth export [--standalone] <integrationID>`. The flag is **permitted and optional**, not pinned for every caller: because it belongs to the declared argv, each declaration is deterministic — the shipped default omits it and uses the background-service path (measured 103–229 ms, which keeps `dispatch`'s one-second admission preflight intact), while the resident declaration sets it (4.4–6.0 s, acceptable only because the resident path never blocks readiness or a request). A declaration that omits the flag on a host without the service fails as a classified `non-zero-exit` or `timeout` whose `(reason, style)`-keyed remedy names the flag. The `--standalone` flag is **permitted by the entry but not forced on every caller**: it is an optional member of the declared argv, so it is deterministic per declaration and never a runtime guess. The shipped default declaration **omits** it (the background-service path, measured at 103–229 ms), which keeps a one-shot command's latency profile; the resident declaration **sets** it, because a lingered unit cannot assume a session-scoped service. A declaration that omits it and finds no service fails with a classified reason (`non-zero-exit` or `timeout`) and the `(reason, style)`-keyed remedy says to add the flag. **Both free slots are grammar-closed and validated at configuration load, failing closed:** `<host>` must match `[A-Za-z0-9.-]+` with no leading `-` and a bounded length; `<integrationID>` must match `[a-z0-9][a-z0-9_-]*` with a bounded length (the observed ids `deepseek` and `zai-coding-plan` both fit) and no leading `-`, so a slot value cannot express a flag — an integration id beginning with `-` would otherwise be flag smuggling into a program that documents a global `--server string`. The constructed argv **inserts a `--` terminator before the positional**, so even a malformed value cannot be read as a flag. Together, the load-time grammar and the `--` terminator close the parameter axis; the tripwire below closes the table axis. Interpreters (`sh`, `bash`, `python*`, `node`, `perl`, `ruby`) and general network clients (`curl`, `wget`, `nc`, `ssh`) are prohibited **by construction**: they are absent from the table, so no configuration can express them. A declared pair outside the table is a validation failure naming the program. No runtime interpolation of any kind is added, **with one exception declared by ADR-0015**: a slot the allowlist entry marks **binding-supplied** — the authentication target — whose value comes only from the committed `integrations.<kind>.host` coordinate, whose grammar is unchanged, and which no profile may supply. Stated honestly, in two parts: **the expressible surface narrows** — no profile may supply the target slot, so a declaration that could have disagreed with the coordinate can no longer be written — **while the interpolation rule gains one bounded exception**, whose only value is one the committed integrations block already defines. The failure it removes is a token issued for one host presented to another. The tripwire therefore diffs three things: the argv **template** (the slot marked, never valued), the **committed `integrations.<kind>.host` coordinate itself** — a change to it is a target change and must be as loud as a change to the argv — and the rule that no profile supplies that slot. The check **enumerates the declared `integrations.<kind>.host` coordinates from configuration itself**, per declared tracker integration, and diffs each — no named constant and no second list to keep in sync, because a hand-maintained list would be the drift the tripwire exists to prevent. This is not a residual and cannot be left to review. **Activation condition.** The exception is **inactive until ADR-0015 is accepted and a `credentials` catalog branch exists**: with no profiles and no coordinate in force, C-10 behaves exactly as it did before this amendment. **Resolution, not symlink refusal.** Validation **resolves every symlink** on the program path and requires the fully resolved target to be a **regular, executable file**. A symlink is **not** refused: `opencode` is a symlink on the reference host (`~/.nvm/versions/node/v24.11.1/bin/opencode` -> the package's `bin/opencode.exe`), which is how that program is normally installed, so an `lstat` non-symlink rule would reject the standard install. An unresolvable path, or a target that is not a regular executable file, refuses as `program-unavailable` with the remedy "declare the program path as installed". A CI tripwire fails when the table changes, or when **either** the raw committed argv **or the effective argv derived from committed configuration** changes, unless the allowlist file itself is in the diff.
- **Stated residual (not a requirement):** the product does not verify that the program is root-owned or that its digest matches a pinned value. Those are hardening measures for a host-integrity threat model outside this decision, and they belong to the operator's packaging choice.
- **Source:** AC (GH-394 "careful by design"); internal standard (fail-closed validation, reviewed vocabulary); critic findings (a committed argv is an exfiltration primitive that needs neither shell nor interpolation; and the two free slots are an unchecked flag channel — `opencode --help` documents a global `--server string`); measurement (the standalone export costs 4.4–4.6 s and 5.5–6.0 s and is the only path available to a lingered unit)
- **Verification:** test (every allowlist entry accepted with its permitted parameters; a program outside the table refused by name; each prohibited interpreter and network client refused; a parameter the entry does not permit refused; a `<host>` with a leading `-`, a `<host>` outside the charset, and an `<integrationID>` with a leading `-`, an uppercase character or an out-of-charset character each refused **at configuration load**; the constructed argv asserted to carry `--` before the positional; a symlinked program path **accepted** when its resolved target is a regular executable, and refused as `program-unavailable` when the chain is unresolvable or the target is not a regular executable) + CI check (the tripwire fails on a table change, on a committed-argv change, and on an effective-argv change, unless the allowlist file is in the diff) + code review
- **Negotiable:** no

> **Table stakes:** the delivered `config.credential.missing` identity, its projection and its exit `1`; the delivered park and announcement vocabulary for a credential failure (`provider.credential.missing`, condition `credential-missing`, the quota policy's `credentialParkTtlSeconds`); the `environment-prefixed` prefix derivation from the branding seam; the name-only diagnostic posture and the registered-value redaction chokepoint; and the three-of-five CLI exit taxonomy. Every eligible alternative below satisfies them and they are not scored again.

## Decision Drivers

**Operator drivers (ranked):**

1. **One place to manage provider and tracker access.** The change exists because an operator currently maintains the same secret twice and repairs it twice.
2. **Failure legibility on an unattended unit.** The daemon is not watched. A failure must name where it came from, what went wrong in one token, and what to do — and it must not be the reason the unit stops.
3. **Provisioning cost of the first install.** "Authenticate where you already authenticate, and declare it" is the whole promise.

**Technical drivers:**

4. **Single-owner safety.** The product must never become a second refresher, never hold a grant it cannot revoke, and never invalidate the owner's session.
5. **Blast radius of a bug or a bad commit.** Material must be reachable through one directory and one operation; a defect must be able to lose at most one credential, not every credential the operator owns; and a committed line must not be able to exfiltrate one.
6. **Harness portability by declaration.** The composition knows which harness it runs; the resolution must not assume opencode's surface elsewhere, and must not silently read the wrong harness's store.
7. **No new vocabulary and no new code path on the request path.** Every consumer already branches on one code; the request path is synchronous and must stay a memory read.
8. **Testability and hermeticity.** CI has no credential. Every failure and success must be reachable with injected fakes, including shape drift, multi-account ambiguity, timeout, and a refused allowlist entry.
9. **Reversibility and migration cost.** Adoptable and abandonable without an operator edit: no renamed style, no required config change, no data migration, no default moved.
10. **Least secret surface.** The mechanical invariant (one credential-material directory, one ambient-read allowlist entry) should stay literally true.

## Mental Models & Techniques Used

- **First principles:** separate *custody* of a credential from *use* of it, and separate *the act of obtaining* a credential from *the act of serving a request*. Every owner already solves storage, refresh and revocation; the product asks the owner, at the moment of use, for the one fact it needs, and on the resident path it asks ahead of the request so that readiness never depends on the answer. The OAuth refusal and both composition shapes follow from this split, not from convenience.
- **Inversion:** what would make this change worse than the status quo? Letting a committed line read and send anything (R5); reading every secret the harness has to obtain one; picking an account silently when the owner holds two; turning a transient keyring lock into a unit that never serves; blocking the daemon on every tracker read; telling an operator to export a variable when the store is locked. Each inversion names a constraint (C-10, C-3, C-6, C-5, C-7).
- **Second-order thinking:** a second failure code looks like better diagnostics and is actually a cross-surface change: 37 enumerated sites, several of which reconstruct the failure instead of forwarding it. One code plus three optional fields gives the operator the same information and keeps every consumer's `!ok`/`.code` branch valid. Likewise a generic `command` looks free and is the one place where configuration becomes an exfiltration surface, which is why the allowlist replaces "reviewed like code" as the control.
- **Systems thinking:** reference declaration → validation → allowlist and slot grammar → materialization (one-shot: on demand with a memo; resident: asynchronous ahead of the request) → redaction registration at the moment of obtaining → caller (tracker read, inference, quota) → reason/remedy → renderer → the installed unit's restart policy. Two of those nodes are compositional: which composition is running decides whether materialization is synchronous or asynchronous, and the components that ship today are the one-shot ones. A change that skips the renderer leaves the fields dead at the surface the operator actually sees; one that skips the restart node makes an unattended failure a failed unit.
- **Opportunity cost:** **shipped**, one bounded execution per reference per process buys the removal of a duplicated secret per install and keeps the rest of that process a memory read; **forward (`#395`)**, one execution per reference per declared interval buys the same for a resident process without blocking its cadence. The asymmetry is in the maintenance of two copies.
- **KISS / least vocabulary:** four styles, one allowlist table with two entries, three optional fields on an existing variant, no new code, no new park cause, no new exit, no renamed style, no chain.

### Alternative 0 — Environment File Only, Documented (Status Quo)

- **Eligibility:** Not eligible (fails C-1).
- **Summary:** Keep the two environment-backed styles and the hard-coded tracker reference; document that a daemon install requires an operator-written environment file loaded by a unit drop-in.
- **Constraint compliance:** Passes C-2 … C-10 trivially — it changes nothing — and fails C-1 by construction: the second copy is the mechanism, not a side effect, and the tracker reference cannot even be pointed elsewhere.
- **Driver fit:** Worst on drivers 1 and 3, and it makes driver 2 harder, because a stale copy fails as `config.credential.missing` naming a variable, not the owner whose store actually changed.
- **Pros:** Zero delivery cost; no new surface; no posture change; maximum reversibility.
- **Cons:** Every install duplicates every secret by hand; the copy is invisible to `gh` and to the harness, so revoking in one place leaves a live copy in the other; an OAuth-only provider cannot be covered at all; and the drop-in is a file the product neither creates nor validates.
- **Why rejected:** It declines the requirement it exists to serve.

### Alternative 1 — Allowlisted Strategies Behind the Unchanged Port (selected)

- **Eligibility:** Eligible (passes C-1 … C-10).
- **Summary:** Four declared styles behind one operation: `literal` and `environment-prefixed` (unchanged), `command` (a **shipped-allowlisted** `(program, pinned subcommand prefix)` pair — `gh auth token [--hostname <host>]`), and `harness-store` (the same allowlisted `opencode auth export [--standalone] <integrationID>`, with the flag optional per declaration, one declared integration, exactly one active entry, API-key entries only). In the **one-shot composition that ships here** each subprocess-style reference is resolved on demand and synchronously at first use and memoized for the life of the process (one execution per reference per process), with the material registered for redaction the moment it is obtained. The resident composition — asynchronous materialization from construction, readiness never waiting, the reserved `resolution-pending`, atomic swap on a declared interval — is specified forward for #395, where the lane composition is what first gives the daemon a credential consumer. One-shot CLI commands use the identical port through a wrapper that resolves on demand and synchronously. The tracker credential reference becomes declarable with the shipped default unchanged; the failure variant gains `source`, `reason`, `remedy`; a CI tripwire guards the allowlist and every committed argv.
- **Constraint compliance:** C-1 — the declared sources resolve from the owners' stores with no product-written file, and the tracker reference is declarable with its default untouched. C-2 — one operation, one success variant, one failure variant, three additive optional fields, construction-time context. C-3 — closed set, declared keys, no chain, no label matching. C-4 — material returned once; child output is material or discarded. C-5 — source, closed reason and remedy on every credential-shaped failure; bounded timeout; never fatal. C-6 — the active harness identity wins and a declared mismatch refuses. C-7 — **shipped form:** one-shot resolution is on demand, synchronous at first use and memoized per process (one execution per reference per process), so every later resolve of that reference is a memory read; **forward (`#395`):** the resident composition's asynchronous materialization, its readiness guarantee and its reserved `resolution-pending` (see the forward-looking section). C-8 — shipped settings carry no credential entry. C-9 — no new identity, park, announcement, token or exit; defaults and fixtures unchanged; injected seams only. C-10 — the allowlist is the control, and prohibited programs cannot be expressed.
- **Driver fit:** Best on 1, 2, 5, 6, 7, 8 and 9; equal-best on 3, 4 and 10.
- **Pros:** Removes the second copy on the path that ships (every `dispatch`, `merge`, `status`, `commit`, `verify` and `queue` invocation); keeps custody with the owner; makes the act a pinned subcommand with a closed parameter grammar rather than an arbitrary program; makes every failure named and actionable; puts another product's shape knowledge into typed, tested code; keeps the mechanical secret boundary at one directory and one allowlist entry; keeps the request path allocation-only after one memoized execution; settles the resident design so #395 does not re-derive it; and leaves the sidecar path open.
- **Cons:** The product executes third-party programs to obtain secrets — bounded to two pinned entries and a closed slot grammar, but still an expansion of what it may do; it depends on another product's CLI stability; a one-shot command pays one bounded execution per reference per process (≈103–229 ms under the shipped default, ≈4.4–6.0 s only if the declaration opts into `--standalone`, so once per `commit` and once per `merge`); the resident half of the design is specified but unproven until #395; and the vocabulary grows from two styles to four.

### Alternative 2 — One Generic `command` Style Only, With Neither Allowlist Nor Harness Style

- **Eligibility:** Not eligible (fails C-5, C-9, C-10).
- **Summary:** Admit one general style: any declared argv whose stdout is the material. `gh` is declared directly; the harness is reached through a wrapper that runs the export and extracts one field.
- **Constraint compliance:** **C-10 fails hardest**: without an allowlist, a committed argv is a full exfiltration primitive — `["/usr/bin/curl","--data-binary","@<home>/.config/gh/hosts.yml","https://<host>"]` needs no shell, no interpolation and no stdout rule, and it runs unattended on every resolve. Once C-10's allowlist is applied, this alternative **collapses into ALT-1 minus the typed harness strategy**, so the only world where it remains distinct is the world where the allowlist does not exist. C-5 fails: the product cannot classify what it does not parse, so shape drift becomes either a plausible wrong string or an unknowable failure, and a misconfigured wrapper that emits the whole export becomes material. C-9 fails: an operator-supplied wrapper is unversioned, untested and outside the one credential directory; a shipped wrapper is ALT-1's `harness-store` without a type. Multi-account ambiguity cannot be refused.
- **Driver fit:** Cheap on 9; fails 5 and 8 outright.
- **Pros:** Smallest type surface; the same style covers tools this record has not heard of.
- **Cons:** Moves the one non-trivial behaviour outside the type system, the tests and the review; makes ambiguity and drift invisible; and is the exfiltration vector the allowlist exists to remove.
- **Why rejected:** Two failures, either of which is disqualifying: without the allowlist it is a security defect, and with the allowlist it is this decision with less structure.

### Alternative 3 — A Credential Sidecar Process Owning All Resolution

- **Eligibility:** Eligible; rejected on driver fit rather than on a constraint.
- **Summary:** Build the sidecar the port header anticipates: a local process that owns every strategy and answers resolutions over local transport.
- **Constraint compliance:** Passes C-1 … C-10 — a sidecar consults the same owner stores behind the same contract, and the unchanged union means it forwards cleanly (which is exactly why C-2 is stated as one success and one failure variant rather than "byte-identical shape").
- **Driver fit:** Weakest on 5, 7, 8 and 9: a new resident process with its own lifecycle, supervision, readiness and failure modes must start before the daemon; it becomes the component holding material between requests, which pre-resolution already avoids without a second process; and a composition that forgets to start it refuses everything.
- **Pros:** Strongest isolation; one place that ever holds material; a natural home for later rotation and audit.
- **Cons:** Delivery cost far beyond the requirement; a second supervised process; a new transport and a new unavailability class; and it does not answer which source to consult, so it is orthogonal rather than alternative.
- **Why rejected:** Pre-resolution already keeps subprocesses off the request path, so the sidecar's remaining benefit is isolation between adapters this product trusts. It stays available: the port's union is unchanged, and a sidecar remains the documented second implementation.

### Alternative 4 — Resolution Implemented by the Harness Adapter Contract

- **Eligibility:** Not eligible (fails C-8 and C-9; C-6 only nominally satisfied).
- **Summary:** Add a credential-resolution operation to the harness adapter contract, so each harness implements store access and the credential port delegates to it.
- **Constraint compliance:** Fails C-8: the harness session descriptor is the lane-spawn contract, and routing credentials through it invites the credential entry C-8 forbids for shipped settings. Fails C-9: it widens a delivered adapter contract (ADR-0008), so every harness adapter, real and fake, must implement it. C-6 is satisfied only nominally: the tracker credential would be resolved by whichever harness is selected for lanes, coupling two unrelated choices, so a GitHub read would fail because the lane harness changed.
- **Driver fit:** Good on 6 in appearance, bad on 5 and 9.
- **Pros:** The harness's own code knows its own store; no new adaptation layer.
- **Cons:** Couples the tracker to lane-harness selection; grows a contract for a need that is declarative data; gives the harness adapter custody of material it has no reason to see.
- **Why rejected:** Wrong seam: the question is which source to consult (configuration), not what a harness can do (capability).

### Alternative 5 — A Declared Chain: Try the Harness Store, Then the Environment

- **Eligibility:** Not eligible (fails C-3 and C-5).
- **Summary:** Let a reference declare ordered sources; resolution walks the list until one yields material.
- **Constraint compliance:** C-3 fails (a chain is the fallback this posture forbids). C-5 fails in practice: the refusal names "none of the declared sources", which is the unactionable aggregate the requirement is written against, and a success cannot state provenance without adding a member (which C-2 would then fail).
- **Driver fit:** Tempting on 3 (it papers over a misconfigured install) and bad on 2, 4 and 5.
- **Pros:** Best first-install resilience; no operator edit when a source moves.
- **Cons:** TDR-0019's rejected ALT-2 with a longer list; makes "which store did that token come from" unanswerable; silently masks a revoked credential by finding a stale one.
- **Why rejected:** A named source that resolves beats an unnamed source that guesses. This record resolves the ticket's "falls back to `environment`" phrasing as a *remedy*, not as an automatic behaviour.

### Alternative 6 — Admit `harness-oauth` as a Fifth Style

- **Eligibility:** Not eligible (fails C-5; would need an accepted risk on C-7).
- **Summary:** Admit an OAuth style that resolves `value.access` while `expires > now`, never refreshing and never writing back.
- **Constraint compliance:** C-5 fails because the source cannot always answer the question: an `active` entry can carry no recorded expiry (epoch), so the rule refuses a live credential while trusting an entry inside an unrefreshed window on a claim the harness may already have invalidated. C-7 needs an accepted risk: the same export object carries the refresh grant, so any code path reaching the OAuth branch holds custody of a durable grant it only wanted to borrow.
- **Driver fit:** Serves no driver better than ALT-1, and degrades 4 and 5.
- **Pros:** Would cover the OAuth-only integration that exists today for quota/usage reads.
- **Cons:** Creates a second refresher in effect; makes a durable grant reachable in the process that renders diagnostics; depends on another product's expiry semantics.
- **Why rejected:** See D5. The loss is named there as an accepted capability loss, not hidden: one integration is OAuth-only **now**, and its product-side quota read is unavailable by design.

### Alternative 7 — A Second Failure Identity (`credential.source.unavailable`)

- **Eligibility:** Not eligible (fails C-9).
- **Summary:** Keep `config.credential.missing` for "the declared variable is absent" and add a distinct identity for "the source could not answer", with its own reason set.
- **Constraint compliance:** C-9 fails: it adds an error-table row, and with it the documented row set and the bidirectional sync. It also fails C-9 in the sense that matters operationally: the new code must be threaded through the inference transport (`adapters/src/inference/index.ts:94-95` rebuilds its own `config.credential.missing` and drops the detail), the spawn-environment builder (`domain/harness-spawn-env.ts:17-26`, `:60-65` rebuilds it too), the engine's park mapping (`provider/engine.ts:285-306`), `doctor`'s closed presence union (`contracts/doctor.ts:376-382`), the MCP serve state (`mcp/serve.ts:258-275`) and the CLI renderers — 37 enumerated sites, several of which would collapse it silently.
- **Driver fit:** Good on 2 in principle (finer-grained diagnostics) and bad on 7 and 9.
- **Pros:** The most legible possible taxonomy; a code an operator could search for.
- **Cons:** Cross-surface change for an operator-facing outcome that one code plus three fields already delivers; and every site that reconstructs rather than forwards the failure would have to be found by hand, which is exactly the class of change the delivered `!ok`/`.code` posture makes safe today.
- **Why rejected:** The operator-facing goal is "never tell an operator to export a variable when the store is locked", and a rendered `reason` achieves it. A second code buys a searchable token and charges a 37-site sweep plus a new row.

## Decision

- **Decision:** Adopt **ALT-1**, with these determinations: four declared styles; `command` restricted to a shipped allowlist of pinned subcommands whose two free slots are grammar-closed; `harness-store` limited to API-key entries and to the export's target selector; **no** `harness-oauth` style; no chain; **one** failure code with three additive optional fields and a fixed per-reason remedy table; the tracker credential reference made declarable with its default unchanged; the port kept synchronous with **on-demand resolution and a per-process memo in the one-shot composition that ships here**; redaction registered at materialization; and the asynchronous resident composition with its reserved `resolution-pending` reason specified as forward-looking for #395. The OAuth and keyring rulings below are product policy, not delivery detail.
- **Rationale (tied to drivers):** only ALT-1 removes the second copy (driver 1) while keeping custody with the owner (driver 4), bounding both a bug and a bad commit to one credential and one pinned subcommand (driver 5), making every failure nameable on an unattended unit (driver 2), surviving a harness that differs (driver 6), keeping the request path free of subprocesses after one memoized execution, keeping readiness free of them entirely in the resident design, and keeping the vocabulary free of a new code (driver 7), staying testable without a credential (driver 8) and migrating nothing (driver 9). Every other eligible option either pays a permanent process cost (ALT-3) or moves parsing out of typed code (ALT-2), and ALT-7 buys a searchable token at the price of a 37-site sweep.

### D1 — Where the change lives, and the tracker reference becomes declarable

The strategies are implemented inside the existing credential implementation directory, `packages/adapters/src/credentials`, which is the sole `credential-material` allowlist entry (`scripts/checks/secret-read-boundary.ts:35-39`, `:249-256`). No new subpath, no new allowlist entry, no ambient read. The resolver is constructed with its context — the active harness identity, a child runner, an environment record, the allowlist table, the declared strategies and the declared re-resolution interval — and the port keeps one operation with one success and one failure variant (C-2). **The same resolver serves both compositions; only the wrapper's timing differs:** the resident daemon is constructed with eager asynchronous materialization (first pass included), a one-shot CLI command is constructed with on-demand synchronous resolution. A second implementation (the anticipated sidecar) remains possible because nothing in the operation grows a member and the union keeps exactly one variant of each kind.

**The tracker reference is declarable, with the shipped default unchanged.** Today the reference is a hard-coded literal in code (`packages/cli/src/production.ts:674-677`), consumed by a constant instance factory (`:685-693`), with no configuration key anywhere (`packages/core/src/config/catalog.ts:926` is the only `github` row and it is a poll interval). A declaration is added: a `github` configuration branch carrying a credential source, defaulting to exactly today's `{ style: "literal", name: "GITHUB_TOKEN" }`. The operator opts in to `command`; nothing moves unless they do, the documented environment bridge keeps working unchanged, and `C-9` is satisfied because the default **value** is untouched and only the *ability to declare an alternative* is added. The reference used for redaction registration (`:683`) must be derived from the declared value, or a token resolved through a `command` source would silently stop being registered for redaction.

Files that change for the declaration: `packages/core/src/config/catalog.ts` (a `github` branch with the credential source shape and its default), `packages/core/src/provider/validate.ts` (the source-key grammar is shared with the provider map, so it must be one validator), `packages/core/src/config/defaults.ts` (the shipped default, expressed as today's literal), and `packages/cli/src/production.ts` (`githubReadReference` becomes a resolved value, `DECLARED_CREDENTIAL_REFERENCES` follows it, `githubInstance()` takes it as a parameter).

**Redaction registration moves out of the entrypoint's static derivation.** `packages/cli/src/entrypoint.ts` (`entrypointSecrets`, `:310-318`) currently turns a declared reference into an environment key and registers that key's value, which for a `command` or `harness-store` style yields `${environmentPrefix}undefined` (`packages/adapters/src/credentials/index.ts:38-44`) and registers nothing. The entrypoint keeps its static registration for the environment styles — those values are present in the environment before any resolution, so registering them up front is still correct and still free — and the **resolver registers each obtained value at the moment of materialization** through the same registry. The entrypoint must **not** resolve anything: doing so would add one execution to every CLI invocation, including commands that never touch a credential.

**The registry must be mutable, and that is a required change, not an implementation detail.** Today the set is a snapshot: `entrypointSecrets` returns a frozen `readonly string[]` (`packages/cli/src/entrypoint.ts:310-318`), `dependenciesFor` passes it as `CliDependencies.secrets: readonly string[]` (`:320-334`; `packages/cli/src/index.ts:130`), and the renderer reads that snapshot at `packages/cli/src/index.ts:667-668`, `:681`, `:703`, `:725` and `:734`; `registerEdgeSecrets` (`packages/cli/src/edge.ts:683-692`) has the same snapshot shape at both of its call sites, `packages/cli/src/edge.ts:1731` and `packages/cli/src/edge.ts:5203`. Because `entrypointSecrets` is computed **before** `composeProgram` runs (`packages/cli/src/bin-launcher.ts:111` supplies the references, `:118` composes), a later registration could never reach a snapshot, and the unredacted window would silently return. Delivery therefore replaces `secrets: readonly string[]` with a live registry — a `register(value)` / `values()` pair consulted at render/redaction time — and the resolver holds that registry as a construction input. Add it to the same change: a second static pass is explicitly not an acceptable alternative, because it cannot see a value that does not exist yet.

### D2 — The closed strategy vocabulary

| Style | Material | `source` identity in a failure | Notes |
|---|---|---|---|
| `literal` | the value of the named environment variable | `literal:<NAME>` | unchanged; the ticket's "environment" names this family, and **no rename is made** |
| `environment-prefixed` | the value of brand prefix + suffix | `environment-prefixed:<SUFFIX>` | unchanged |
| `command` | one line of stdout from an **allowlisted** program and pinned subcommand | `command:<program>` | the pair is validated against C-10's table |
| `harness-store` | one API-key entry from the active harness's declared export | `harness-store:<harness>:<integrationID>` — the identity names the harness beside the integration id; a shape-drift source additionally appends `field=<drift-field>` | exactly one active entry; API-key entries only |

`harness-oauth` is **not** in the vocabulary (D5). A declaration using an unknown style, an unknown field on a known style, or an allowlist pair outside the table is a shape failure naming the field or the program — never silently ignored, never resolved by resemblance to a provider, account, display name or variable. No style has a fallback and no reference declares a chain (C-3).

The ticket's phrase "`environment` (today's `literal`)" is read as naming the family. Renaming the shipped style would touch the shipped defaults (`packages/core/src/config/defaults.ts:5-9`), the catalog (`packages/core/src/config/catalog.ts:78-89`), validation (`packages/core/src/provider/validate.ts:202-214`), the migration helper (`packages/core/src/provider/migrate.ts:405-406`), every provider-config fixture, the conformance double (`packages/testkit/src/conformance/mock-tenant.ts:474-489`) and every operator declaration, in exchange for no behaviour. It is not done.

### D3 — `command`: an allowlisted pair, not a declared program

A `command` declaration names a program and arguments; it is accepted only when it matches a **shipped allowlist entry** (C-10). Semantics:

1. **Allowlist, by construction.** The table is shipped in the credential directory and is a closed set of `(absolute program path, pinned subcommand prefix, permitted parameters)`. Initial entries: `gh` → `auth token [--hostname <host>]`; `opencode` → `auth export [--standalone] <integrationID>`, where **the flag is optional and belongs to the declared argv**, so it is deterministic per declaration rather than a runtime guess. The shipped default declaration omits it and occupies the background-service path (measured 103–229 ms, which keeps a one-shot command's latency and `dispatch`'s one-second admission preflight intact); a declaration that opts in pays 4.4–6.0 s per materialization, which is acceptable **only** where the composition does not block a request or readiness for it — the resident composition of #395, whose declaration sets the flag. A declaration that omits the flag on a host without the service fails as a classified `non-zero-exit` or `timeout` whose `(reason, style)`-keyed remedy names the flag. Interpreters (`sh`, `bash`, `python*`, `node`, `perl`, `ruby`) and general network clients (`curl`, `wget`, `nc`, `ssh`) are simply not in the table, so no configuration can name them. **The two free slots are closed by grammar, not by trust.** `<host>` must match `[A-Za-z0-9.-]+` with no leading `-` and a bounded length; `<integrationID>` must match `[a-z0-9][a-z0-9_-]*` with a bounded length and no leading `-` (the observed ids fit), and the constructed argv inserts a **`--` terminator before the positional**. Without that, an integration id of `--server` would be flag smuggling into a program that documents a global `--server string` (`opencode auth --help`), and the table would be closed on the program axis while open on the parameter axis. `[a-z0-9]`'s restriction to lowercase is deliberate: it is a grammar a flag cannot satisfy. Validation resolves the program's absolute path through every symlink and requires a **regular, executable file** at the end of the chain (a symlink is accepted, because that is how the harness is normally installed); an unresolvable chain or a non-regular/non-executable target is `program-unavailable`. This is the control that replaces "reviewed like code", which the critic correctly showed is not a control: a committed argv can read an arbitrary file and post it without shell, interpolation or a stdout trick.
2. **No shell, no interpolation, and two composition modes.** The pair is executed directly through a bounded child seam; no metacharacter, glob, redirection or substitution is interpreted, and no runtime value is interpolated into it. The one parameter a `gh` entry accepts (`--hostname`) and the one an `opencode` entry accepts (the integration id) come from the declaration, which is committed data. Execution happens in exactly two modes and nowhere else: **in a one-shot CLI command — the composition that ships in this change — on demand and synchronously**, with one execution per reference per process (C-7); and, **in the resident composition** (specified forward for #395), asynchronously from construction with an atomic swap on each declared interval and no synchronous class at all.
3. **No `PATH` dependence; symlinks are resolved, not refused.** The program is the table's absolute path, or resolved once at validation/install time and refused there if absent. Validation resolves every symlink and requires a **regular, executable file** at the end of the chain; an unresolvable path or a non-regular/non-executable target is `program-unavailable`. Refusing symlinks outright would reject the standard install of the harness (`opencode` is a symlink into a version-manager directory on the reference host). A bare name under the installed unit depends on the unit's own `PATH` (`packages/adapters/src/daemon/supervisor.ts:51-54`). Root ownership, digest pinning, and the fact that a same-user-writable path can be redirected remain stated residuals (C-10; Security Model).
4. **Closed stdin, bounded everything.** `stdin` is closed so a prompt fails immediately instead of hanging; a declared per-execution cap (15 s default, 30 s bound — sized against two independent standalone measurements, 4.4–4.6 s and 5.5–6.0 s, with at least 2× margin over the slower) ends each run; stdout capture is bounded; stderr is captured for size and exit status only and is never rendered or treated as material. An execution that hits the cap is a `timeout` reason, never a blocked caller.
5. **Material is one line.** Trailing line endings are stripped; an interior newline, or empty output after stripping, is a refused shape (`shape-drift` / `empty-output`), never material. A misconfigured entry therefore fails closed instead of yielding a JSON blob as a bearer token.
6. **Reduced environment.** The child receives the path, the home directory, and — where a keyring-backed store requires it — the session-bus facts, plus declared non-secret variables; never the parent's secret-bearing environment. A tool that reads its own store needs nothing from the product's environment.
7. **Tripwire.** Any change to the table, to any committed `command` argv, **or to the effective argv derived from committed configuration**, fails CI unless the allowlist file is in the diff (C-10). The residual is stated honestly in the Security Model: a review that widens the table is the same trust as any code change, and the tripwire makes it loud rather than silent.

### D4 — `harness-store`: one integration, one active entry, one field, one allowlisted call

1. **Harness identity is construction context, and a declared harness must match it.** The composition knows which harness it runs for. A declared `harness` field must equal that identity; the **active identity wins** and a mismatch refuses with `source-not-supported`. A harness with no declared support refuses the same way, and never reads another harness's store or file layout (C-6).
2. **Only the declared integration is ever emitted.** The strategy invokes the same allowlisted call with whatever flag the declaration names (`opencode auth export [--standalone] <integrationID>`) so the command's own surface selects it: the export returns that integration's entries and nothing else (verified 2026-11-23). The earlier plan ("the export emits every secret, so select one entry in-process and discard the rest") describes only the target-less form and is **not** the primary control; in-process selection stays as defense in depth, and the raw export is never logged, stored, re-emitted or retained.
3. **Exactly one active entry, or refuse.** An integration may carry several entries (verified: two for one integration). The strategy requires exactly one entry with `active: true`; zero or more than one is `ambiguous-account` — never "the first", never "the newest". The `active` flag is trusted as the harness reports it: the product cannot verify it, so **a mislabelled flag can still select an account the operator did not mean**, and correcting it is the operator's act in the owner's tool. What the product guarantees is only that ambiguity is refused rather than resolved arbitrarily.
4. **API-key entries only.** `value.type` must be `"key"` and the material is `value.key`. An `"oauth"` entry is refused (`oauth-excluded`) because the same object carries the refresh grant (D5).
5. **An integration with no stored entry is not a stored source.** The harness's own listing distinguishes stored credentials from integrations it expects to read from the environment (observed 2026-11-23: two integrations listed as environment-supplied). For such an integration the export yields no entry, which is `empty-output` — because the material is not in the store at all and the operator's real source is the environment declaration they already have. The strategy never falls through on its own (C-3).
6. **Shape drift is a first-class refusal.** A non-array root, a missing field, an unexpected `value.type`, or unparseable output is `shape-drift`, naming the source and the integration. The suite pins the observed shape and the supported version window, so a change in the other product is a red test and a refused resolution, not a corrupted token.
7. **No write-back.** The strategy is read-only against the store, declared as such, and proven by a test double that fails if any write path is reached.

### D5 — The OAuth rule (crisp)

> **OAuth-1.** The product never consumes a harness-owned OAuth grant. It does not read, use, refresh, or write back an access or refresh token from a harness store, and no style in the vocabulary can express one. A provider reachable only through harness-held OAuth is unavailable to the product's own calls — one code, `reason: "oauth-excluded"` — and the delivered degradation applies: the provider's quota/usage read parks under the delivered `credential-missing` condition, best-effort, with no borrowed token. Model work is unaffected, because lanes are authenticated by the harness itself.

Why this rule rather than "use `access` while it has not expired":

- **Custody, not use.** The export hands over `access` **and** `refresh` in the same object. Any code path reaching the OAuth branch holds a durable grant for a credential it wanted to borrow for one request. The blast radius of a leak is a renewable session.
- **A second refresher by accident.** "Use it but never refresh" is a policy, not a mechanism: once the harness refreshes, the product's copy is stale, and the product learns that only by failing at the provider.
- **Expiry cannot be trusted.** An `active` entry can report no recorded expiry while being live, and an entry can be past its recorded expiry while `active`. A time-based admission rule therefore refuses live credentials and trusts unknowable ones.
- **The need is real but narrower than the rule.** One integration in the store today is **OAuth-only** (`openai`, both entries `oauth`), and the shipped subscription-class provider is an API key. So the OAuth refusal costs the product the quota/usage read for the OAuth-only integration. That is an **accepted capability loss**, named here rather than engineered around: the loss is a best-effort status read on one provider, the gain is that the product never holds a grant it cannot revoke.

**Why `gh` is different, and this is the load-bearing distinction.** `gh` is the credential **owner** for the tracker: `gh auth token` is its supported non-interactive surface, it hands over **one static, durable bearer token for one host**, and it exposes **no separate refresh grant**. So there is no custody transfer of a renewable grant — but the copy is **long-lived**, and this record does not pretend otherwise: a leak of the gh token is durable access to that host, which is why `command` is a pinned allowlisted invocation, why the material never persists, why it is registered for redaction, and why the diagnostic posture is name-only. The same posture was already the documented bridge in TDR-0019; this record automates an act the product's documentation already asked the operator to perform.

The distinguishing tests, stated so a future owner can apply them: **(1)** does the surface hand the product a refresh credential? **(2)** can the product's use invalidate the owner's session? **(3)** is the token's validity knowable at use time? A surface that fails (1) or (2) is custody and is refused. `gh` passes (1) and (2) and fails (3) — and failing (3) has a declared consequence rather than a silent one: validity is learned by using the token, and the delivered `401`/`403` → `provider.auth.rejected` mapping (`provider.auth.rejected`, exit `1`) is where a revoked gh token surfaces.

### D6 — The gh keyring under a lingered unit: product duty versus operator duty

**The situation.** A `systemd --user` unit started by linger after boot has no login session, and a login keyring is typically unlocked by a session. `gh` may therefore fail to read its keyring even though the operator is authenticated interactively on the same machine.

**What the product must do:**

1. **Never touch gh's storage.** No moving tokens to plaintext, no `--insecure-storage`, no product-written credential file, no keyring API, no unlock automation, no `systemctl --user import-environment` step performed by the product.
2. **Run the program so it cannot prompt.** Closed stdin, no TTY, bounded timeout: a locked store fails fast rather than waiting for a human who is not there.
3. **Forward what the owner's tool needs.** The child environment carries `HOME` and, where a keyring-backed store requires it, the session-bus facts; without `HOME` a keyring lookup cannot work at all. Whether the session-bus facts are required under linger is `TO-CONFIRM` and is proven by the delivery's integration case, not assumed.
4. **Classify and name it.** One code, with `source` = the program, `reason` from the closed set (`non-zero-exit`, `empty-output`, `program-unavailable`, `timeout`), and a remedy — never an empty string and never a silent fallback.
5. **Never make it fatal.** A failed resolution degrades the one read that needed it and is reported; it must not exit or fail `daemon start`, because the installed unit declares `Restart=on-failure` with no `RestartSec` and no `StartLimitBurst` (`packages/adapters/src/daemon/supervisor.ts:51-54`), so a start-fatal credential failure produces **bounded flapping followed by a failed unit** — the daemon does not serve, and the operator finds it stopped. "Never fatal" is therefore about keeping the unit running and self-describing, not about avoiding an infinite loop.
6. **Carry the cause in the remedy text.** The refusal states that the owner's store may be locked or unavailable in a non-interactive session, and offers the operator's options: unlock or log in on that host; or declare an `environment`-family source for that reference and supply the value through the existing unit environment mechanism. The second duplicates the secret and the documentation says so, with its exposure, because an operator who cannot unlock should not be left without a supported path.
7. **Come up recovering, not stopped — shipped, in the form that applies today.** Under the shipped composition the keyring is read by a one-shot command, not by the daemon: the command resolves at first use and, if the store is locked, refuses with `source`, `reason` and the fixed remedy, and exits cleanly — no unit flaps, because no unit is involved. The daemon-shaped form of the same guarantee is **forward-looking for #395**: materialization starts asynchronously at construction and never delays readiness, a `resolve` before the first pass returns `resolution-pending` ("not yet", not "failed"), and a daemon that starts before the keyring is unlocked comes up **running, named, and recovering** instead of stopping.
8. **Make the state visible before work is queued.** The same identifier-only facts (reference, source, reason) belong in status/verification evidence. Whether that lands in the delivered status digest or a separate surface is a delivery decision for the spec.

**What remains the operator's responsibility:** keeping a session-capable host, or choosing the duplicated-secret path knowingly, or declaring a source that does not need a locked store. The product cannot unlock a keyring on the operator's behalf, and must not try: any product-side unlock would be a privilege escalation the operator never granted.

### D7 — One failure code, three optional fields, and every surface that must carry them

**The code does not change.** `config.credential.missing` stays the **single** credential failure code, with its delivered projection and exit `1` (`packages/core/src/contracts/error-table.ts:430-437`). The failure variant gains exactly three **additive optional** fields:

- `source` — the declared style plus the source identity: `command:/usr/bin/gh`, `harness-store:zai-coding-plan`, `literal:GITHUB_TOKEN`, `environment-prefixed:TOKEN`. Present whenever a declared reference was being resolved.
- `reason` — one token from a closed set: `program-unavailable` · `timeout` · `non-zero-exit` · `empty-output` · `shape-drift` · `ambiguous-account` · `oauth-excluded` · `source-not-supported` · `variable-absent` · `resolution-pending`. The last one means "the reference is declared, the asynchronous first materialization has not completed yet, this is not a failure of the source"; it is kept distinct from `timeout` (an execution that exceeded its cap) because the operator act differs: wait, versus investigate a slow or hanging program.
- `remedy` — bounded text naming the one operator act that helps, taken from a **fixed string in a shipped table keyed by `(reason, style)`** and never interpolated from configuration text or from the source's output. The `command` entry for `non-zero-exit` is **host-aware**: a host-aware program can exit non-zero simply because the operator is not logged in to *that* host, so it reads "the program could not obtain a token; it may not be authenticated to the required host — log in to that host, or declare another source" and never a role-only instruction. The key includes the style because one reason implies different acts: a `timeout` on a `command` source says "raise the cap or check the program", while a `timeout` on a `harness-store` source says "add `--standalone` to the declaration". A reason-only table would tell a `gh` caller to add a harness flag. This is what makes the value safe to exempt from config-summary suppression at `packages/cli/src/index.ts:370-395`: the exemption cannot become a channel for arbitrary committed or remote prose.

**Why one code and not two.** Every delivered consumer branches on `!ok` and `.code`, and the code is constructed or observed at 37 enumerated sites across 16 files (11 in `edge.ts`, 5 in `production.ts`, 4 in `mcp/serve.ts`, 3 in `engine.ts`, 2 in `harness-spawn-env.ts`, 2 in `contracts/harness.ts`, one each in ten more). Several of those do not forward the failure at all: `packages/core/src/domain/harness-spawn-env.ts:17-26` rebuilds it from scratch, `packages/adapters/src/inference/index.ts:94-95` returns its own `failure("config.credential.missing")` and drops the detail, and `packages/cli/src/index.ts:370-372` suppresses a config-shaped failure's summary and hint unless it carries the dispatch engine's trust marker. A second code would therefore have to be threaded through, and in the meantime would silently collapse into `fallback.internal`-shaped behaviour or into the old code at whichever site was missed — in an unattended daemon. One code plus a rendered reason delivers the operator-facing goal (never say "export a variable" when the store is locked) with a far smaller blast radius.

**The row/type binding must be restated, not widened.** The failure variant is bound to the error-table row by a drift test so the two cannot diverge (`packages/core/src/contracts/credentials.ts:39-53`). The table's row shape is closed across its 170 rows, so the three new fields are **projection data on the variant, not columns on the row**; the binding test must state that the *required* fields mirror the row and that `source`/`reason`/`remedy` are optional identifiers carried alongside it. Adding columns to one row would break the row-shape invariant this repository enforces everywhere else.

**No new park cause, no new announcement code, no new exit.** A credential failure in the quota path keeps the delivered condition `credential-missing` and the delivered announcement `provider.credential.missing`, bounded by `credentialParkTtlSeconds` (`packages/core/src/provider/quota.ts:362-378`; `packages/core/src/provider/engine.ts:285-306`; `packages/core/src/contracts/provider.ts:186`, `:215`), so the event-taxonomy records (TDR-0025, TDR-0029, TDR-0030) are untouched. **The park record does not gain a field**: its shape stays closed, and `reason` is carried in the rendered refusal and in the log line only — never the child's output, never a digest of the material. The CLI keeps `{0, 1, 2}` (TDR-0005).

**Every propagation site, by `file:line`.** These are the places where the three fields must survive a real failure. Nothing else in the repository needs to change for R2.

### D8 — What ships, what does not, and where the resident design lives

1. **The shipped daemon has no credential consumer.** The production composition passes no `lane` and no `executor` (`packages/cli/src/production.ts:2191-2219`), so `laneExecutor` and `supervise` are `undefined` (`packages/cli/src/daemon-compose.ts:565-577`) and the mode is `supervise-only` (`:792-796`); the specification says the production daemon "starts no lane" (`doc/spec/features/feature-resident-daemon.md:259-272`, `:301`, `:327`; `doc/overview/architecture-overview.md:93`, `:504`). A `supervise-only` daemon reads no tracker, populates no scheduler work-item observation, and resolves no credential. **This change therefore claims no daemon provisioning benefit**, and the readiness/`resolution-pending`/async-interval model is not presented as delivered.
2. **The shipped consumer is the one-shot CLI composition.** `dispatch`, `merge`, `status`, `commit`, `verify` and `queue` resolve on demand and synchronously through the port, with a per-process memo of one execution per reference (C-7). That is where the declared-source benefit lands, immediately, on every invocation.
3. **Startup reconciliation is state-only, and needs no tolerance rule.** `reconcileDaemon` (`packages/core/src/app/daemon-reconcile.ts:186`) takes `DaemonReconcileInput` (`:44-53`) — `store`, `fenceToken`, `instanceId`, `nowIso`, `restartBound`, `reconcileMaxLanes`, `recover`, `evidence` — with no credential port and no tracker client, and reads durable state only (`:187-200`). Its `daemon.state-recovery-failed` refusal is unrelated and unchanged. It therefore cannot observe a credential state of any kind, including a reserved one.
4. **`resolution-pending` is reserved, not shipped.** It is in the closed reason set so the forward design has one vocabulary (C-5, D7), and **no shipped caller can observe it**: a one-shot command resolves before returning, and the shipped daemon resolves nothing. Its meaning is defined in the forward-looking section below.
5. **The cost is named, not hidden.** A one-shot command using `harness-store` pays one execution per declared reference per process. With the shipped default declaration (no `--standalone`) that is the measured 103–229 ms **only while the harness's background service is running**, and that figure is what leaves `dispatch`'s one-second admission preflight profile intact. The same command from a non-interactive context — a hook, a cron entry, a unit with no login session — may **fail or hang** instead, because the service is session-scoped. A declaration that opts into `--standalone` pays 4.4–6.0 s and does so knowingly, with no session dependence at all. `commit`'s inference call pays it once per commit; `merge` pays exactly **one** execution (one reference); `status` pays one execution per **distinct reference it actually resolves**: at most **two** — the tracker reference plus the one provider credential the shipped defaults declare (`defaults.ts:5-9`, `zai`) — and in the shipped configuration **zero subprocesses**, because every shipped reference is `literal`; two executions arise only when both references are declared subprocess styles. The memo makes the count independent of how many operations the command performs.

### Resident Composition — Forward-Looking (activates when the lane composition is mounted, #395)

This section is the design for the resident composition. **None of it is delivered by this change**, and its verification is marked **not satisfiable in this change; proven in #395**. It is recorded so #395 does not re-derive it and so the vocabulary it needs already exists.

1. **The resident declaration sets `--standalone`.** A lingered unit cannot assume the session-scoped background service, so the resident declaration ships with the flag set and pays 4.4–6.0 s per materialization — acceptable only because this composition never blocks readiness or a request (C-7, D8.5). The shipped one-shot default keeps the flag omitted (R10).
2. **Ready before any lane.** Materialization starts **asynchronously at construction**, the first pass included: the instance record, the listeners, the control socket and the first heartbeat are produced on the delivered schedule, and the readiness poll (`packages/cli/src/daemon-compose.ts:891-895`) is untouched. There is **no synchronous execution class in the daemon** and no startup budget — the two measured standalone costs (4.4–4.6 s and 5.5–6.0 s) exceed the poll by a wide margin, so any design in which readiness waits on the owner's store fails exactly where it must work.
3. **`resolution-pending` is the declared pre-materialization state.** A `resolve` that precedes its reference's first materialization returns `config.credential.missing` with `reason: "resolution-pending"`, its `source`, and the table remedy. It is a declared state — "not yet", never "failed" — and it is distinct from `timeout`.
4. **Deferred passes, not recorded failures.** Every daemon-side caller must treat `resolution-pending` as "defer this pass": it must not record a tracker-read failure, must not park the work item, and must not advance a restart counter. **This requirement binds two call sites in particular and must land with or before the lane composition:** the provider engine, where any `!ok` currently becomes a park (`packages/core/src/provider/engine.ts:285-306`), and the dispatch admission preflight, which must not confuse "pending" with "missing" (TDR-0019).
5. **Re-resolution and swap.** Re-resolution runs on a declared interval as asynchronous child execution, and each result is atomically swapped into the in-memory record; an in-flight refresh serves the previously materialized value by design; a failure is held under a short bounded backoff.
6. **Verification deferred to #395** (recorded here so it is not lost): `daemon start` reaching readiness inside the poll while a child runner delays its first completion beyond it; a `resolve` before the first completion returning `resolution-pending` and never after it; a resolve during an in-flight refresh returning the previous value; a heartbeat and a control-socket response measured across a slow refresh inside their bounds; exactly one asynchronous spawn per declared interval; a daemon-side pass that defers on `resolution-pending` without recording a failure, a park, or a restart-counter advance; and the provider engine's park mapping not firing on the reserved reason.

### Constraint Compliance Attestation

The chosen alternative satisfies all constraints C-1 … C-10. **C-1:** the tracker reference is declarable with its shipped value untouched, and in the **one-shot composition** a declared provided-store reference resolves from the owner's store with no product-written and no operator-copied file on that path, proven in CI by the real production composition with an injected child seam and demonstrated once manually against a real store (D1, D3, D4; C-9). **C-2:** the port keeps exactly one operation and a result union with exactly one success and one failure variant; the failure variant gains only three optional fields, which a forwarding sidecar passes through unchanged; context enters at construction (D1, D7). **C-3:** a closed four-style set, declared keys, no chain, no discovery (D2). **C-4:** material is returned once and registered for redaction the moment it is obtained; child output is material or discarded; the canary runs through the entrypoint → resolver path and covers every rendered surface and every file (D3, D4, D7). **C-5:** source, reason and remedy on every credential-shaped failure; bounded timeout; never fatal (D6, D7). **C-6:** the active harness identity wins; a declared mismatch and an unsupported harness both refuse without borrowing (D4.1). **C-7:** in the shipped one-shot composition a subprocess-style reference is resolved on demand and synchronously at first use and memoized for the process, so every later resolve of that reference is a memory read and no reference spawns twice; the per-execution cap, reduced child environment and closed stdin are enforced at that single execution; and the resident model — asynchronous materialization from construction, readiness that never waits, the reserved `resolution-pending`, atomic swap on a declared interval — is specified forward with its verification deferred to #395 (D8, forward section). **C-8:** descriptors built from shipped settings carry no credential entry, and a declared entry keeps its delivered spawn behaviour (D9; `config/catalog.ts:388-397`; `harness-spawn-env.ts:60-65`). **C-9:** no new row, park cause, announcement, token or exit; defaults, fixtures and the tracker default unchanged; injected seams only (D7, D9). **C-10:** the allowlist is the control, prohibited programs are inexpressible, and the tripwire guards the table and every committed argv (D3, and the Security Model's first row). No accepted-risk exceptions are taken.

**Posture note (explicit, not implied).** This decision changes the product's secret-read posture in one direction, and narrows it while it does so. The product may now cause **a pinned owner CLI to run a pinned subcommand** — not "a declared program": the allowlist means the only acts expressible are `gh auth token …` and `opencode auth export <id>` (C-10). The product still never reads a store itself, never reads the OS keyring through an API, never inherits an ambient variable implicitly, and never declares a fallback — so the delivered guarantees in TDR-0019 C-4 and `doc/spec/features/feature-adapter-ports.md:155` hold in their mechanical sense (one credential-material directory, one allowlist entry, no new ambient read). What changes is the set of acts the product may perform to obtain a credential, and TDR-0019's own revisit trigger reserves exactly that change to an owner decision. GH-394 states the owner's direction; this record is the structure it asks for, and the PR review is where the owner accepts the posture. If the owner declines it, the fallback is ALT-0 with its documented second store, and nothing else in this record needs redesign.

## Trade-offs & Consequences

### Positive Outcomes

- A default install no longer needs a hand-maintained copy of every secret **once the operator opts in**; the default behaviour, the default value and the documented bridge are unchanged.
- Custody stays with the owners: `gh` keeps its keyring, the harness keeps its store and its OAuth, and revocation in one place is revocation everywhere.
- The act is bounded: the product can only run two pinned subcommands, so a bad commit cannot become an exfiltration path without also changing the allowlist file the tripwire watches.
- Every credential failure becomes actionable on an unattended unit: source, one closed reason, one remedy, no hang, and no failed unit.
- **Shipped:** the request path stays a memory read after the first materialization, so a command's many operations cost one execution per reference. **Forward (`#395`):** the resident composition's request path and control socket are likewise unaffected, because the cadence path never blocks — a property proven with the lane composition, not here.
- The failure vocabulary does not grow: one code, three optional fields, no row, no park cause, no exit.
- The mechanical secret boundary stays literally true: one credential-material directory, one allowlist entry, one operation.

### Negative Outcomes

- The product executes third-party programs to obtain secrets, bounded to two pinned entries and a closed slot grammar but still an expansion of what it may do.
- The harness export is another product's surface: a version change can refuse every `harness-store` reference until the shape is re-pinned.
- **The resident design is unproven in this change.** The shipped daemon consumes no credential, so the asynchronous materialization, the readiness guarantee and the reserved `resolution-pending` reason carry no delivered evidence until #395 mounts the lane composition. This is a deliberate trade: the design is written down and its verification is specified, rather than claimed.
- A one-shot command pays one bounded execution per reference per process: ~103–229 ms under the shipped default declaration **while the harness's background service is running**, or 4.4–6.0 s if the operator opts into `--standalone`; once per `commit` and once per `merge`. From a non-interactive context — a hook, cron, a sessionless unit — the default path may fail or hang, so such a caller must declare the standalone form explicitly. Under the shipped defaults `status` pays two (tracker plus one provider credential).
- A cadence and a serving rule to document for #395: during an in-flight refresh the previous value is served by design, so a daemon-side consumer sees a value up to one interval old rather than a failure.
- An OAuth-only provider loses its product-side quota/usage read. That is deliberate, and it is already true of one integration.
- A lingered unit with a locked keyring cannot read `gh`; under the shipped composition that surfaces in a one-shot command, which names it and offers the duplicated-secret path.
- The vocabulary grows from two styles to four, plus an allowlist table with two entries, a slot grammar and a tripwire that will fail if any of them is edited carelessly.
- The tracker reference becomes configuration: one more thing an operator can misconfigure, with a declared default that must be proven unchanged.

### Unresolved Questions

- [ ] Does `--standalone` work unchanged from a `systemd --user` unit with linger and no session, and does it additionally need the session-bus facts? Both measurements (4.4–4.6 s and 5.5–6.0 s) are from logged-in hosts; the unattended cost and failure mode are `TO-CONFIRM`, and so is the failure mode of the **service-less default path**, whose remedy is already declared (add the flag). (owner: `@coder` during GH-394 delivery; either answer is a declared parameter or a reason token, not a contract change)
- [ ] Does `gh` need the session-bus facts under linger, or only `HOME`? (owner: `@coder`; the child environment forwards both, so the answer changes the *reason* an operator sees, not the safety property)
- [ ] Should the allowlisted surface facts be checked at `daemon install` time (a program absent, a symlinked path, or a table entry that cannot run) rather than only at first use? (owner: `@spec-writer`; recommendation: yes where the check is cheap, secret-free and grammar-only, because the first use may be unattended)
- [ ] Where do the identifier-only source facts surface: the delivered status digest's credential sections, or a separate verification surface? (owner: `@spec-writer`; TDR-0019's optional `credentialPrerequisite` node is the precedent and would grow additively)
- [ ] What is the declared **re-resolution interval** for the resident composition (#395)? (owner: `@spec-writer` with `@plan-writer`; ships as daemon configuration with a conservative default, proven by the #395 metrics. **Closed here:** the one-shot per-process memo is a requirement, not a question — C-7 fixes it at one execution per reference per process, which is what makes `merge` cost one execution and `status` two under the shipped defaults.)
- [ ] Does `claude-code` have a non-interactive store surface, and is it narrower than opencode's? (owner: `@pm` to schedule; until then it refuses as unsupported)
- [ ] Should the allowlist gain a GitLab CLI entry, and what is its pinned subcommand? (owner: `@decision-advisor` on a future request; it is an allowlist addition, reviewed as code)

## Implementation Plan

### Ships in #394

1. **Contracts (core, types only).** The failure variant gains `source?`, `reason?`, `remedy?` and nothing else; add the closed `reason` union in core contracts, with `resolution-pending` present and documented as reserved. `CredentialSourceKey` gains `{ style: "command"; program: string; args: readonly string[]; timeoutMs?: number }` and `{ style: "harness-store"; harness: string; integrationId: string }`. Restate the row/type binding test: the required fields mirror the row, the three new fields are projection data, and neither the row set nor the park record shape changes.
2. **Allowlist, slot grammar and tripwire.** Ship the closed table (program path, pinned subcommand prefix, permitted parameters, per-entry slot grammar) inside the credential directory, with `opencode` -> `auth export [--standalone] <integrationID>` (the flag is optional per declaration: omitted in the shipped default, set in the resident declaration) and `gh` -> `auth token [--hostname <host>]`; validate both slots at configuration load against their closed grammar; insert `--` before the positional; resolve every symlink and require a regular, executable target (`program-unavailable` otherwise); and add the CI tripwire that fails on a table change, a committed-argv change, or an effective-argv change without the table file in the diff.
3. **Validation and configuration.** One shared source-key validator covers the provider credential map and the new `github` branch; the shipped tracker default is today's `{ literal, GITHUB_TOKEN }`; unknown styles and unknown fields refuse by path. `defaults.ts`, `catalog.ts`, `validate.ts` are the files.
4. **Materialization wrapper and a mutable redaction registry (one-shot composition).** Resolve on demand and synchronously at first use, memoize the result per reference for the lifetime of the process (one execution per reference per process), and register the obtained material at the moment of materialization into a **live registry** — replacing `CliDependencies.secrets: readonly string[]` (`packages/cli/src/index.ts:130`) and the frozen builder at `packages/cli/src/entrypoint.ts:310-318` with a `register`/`values` pair the renderer consults at render time (`packages/cli/src/index.ts:667-734`). Prove: the same reference resolved twice spawns once, a second reference spawns again, later resolves are memory reads, and material registered **after** composition is redacted on every diagnostic surface (C-4).
5. **Adapters.** Implement the style dispatch inside `packages/adapters/src/credentials` over injected seams (child runner, environment record, harness identity, allowlist table); `literal` and `environment-prefixed` keep their behaviour and their entrypoint-static redaction registration; `command` implements D3; `harness-store` implements D4 through the same allowlisted call. No ambient read is added.
6. **Composition.** Production supplies the active harness identity, the child runner, **the resolved and declarable tracker reference** (default unchanged), and the resolver's redaction hook. A composition that cannot supply the harness identity still resolves the harness-independent styles and refuses `harness-store` by reason.
7. **Propagation.** Carry `source`/`reason`/`remedy` through the sixteen rows tabulated in D7 (37 enumerated sites), with `remedy` from the fixed `(reason, style)`-keyed table, and make the three fields exempt from config-summary suppression while every other config summary stays suppressed. Doctor's `envVar` display becomes a source display; the MCP placeholders gain a reason. **No park-record change** (D7 row 15).
8. **Degradation.** A failed resolution degrades the one read that needed it, is rendered with its reason and remedy, and never aborts a command mid-flight beyond that read; the quota path keeps the delivered park condition and adds no field.
9. **Testkit.** `packages/testkit/src/conformance/mock-tenant.ts:474-489` must represent all four styles, or the conformance suite silently drops the new declarations.
10. **Specs and docs (shipped surfaces).** Reconcile `feature-adapter-ports.md` (port section, the union, the allowlist and slot grammar, the "production never reads the OS keyring" sentence, register-on-materialize), `feature-config-layer.md` (the `sourceKey` grammar and the `github` credential branch), `feature-provider-engine.md` (no park-record change; the reason stays in the refusal), `feature-doctor.md` (the presence variant).
11. **Record registration.** Add this record to `doc/decisions/00-index.md` and its binding to `doc/decisions/00-register.md` in the same change. No error-table documentation row is added, because no row is added.

### Forward-looking for #395 (activated when the lane composition is mounted)

12. **Resident materialization.** Asynchronous from construction, first pass included, readiness untouched; atomic swap on the declared interval; in-flight serves the previous value; bounded backoff on failure. No synchronous execution class in the daemon.
13. **Defer rule at every daemon-side port caller**, including the provider engine's park mapping (`packages/core/src/provider/engine.ts:285-306`) and the dispatch admission preflight: `resolution-pending` defers the pass, and records no tracker-read failure, no park and no restart-counter advance.

## Confidence Rating

**Medium-high for the shipped half; medium for the forward half.** The structural claims are read from the code and are exact: a synchronous one-operation port called at seven request sites; a production daemon that passes no lane and no executor and therefore runs `supervise-only` with no credential consumer; a hard-coded tracker reference with no configuration path; and — measured — a readiness poll of 20 × 50 ms against a standalone harness export that costs 4.4–4.6 s on one host and 5.5–6.0 s on another, one credential directory, a failure code constructed or observed at 37 enumerated sites in 16 files, a hard-coded tracker reference with no configuration path, an environment-replaced child, a unit with one environment binding and no start-limit override, a quota path that already parks on a credential failure, a CLI that suppresses config summaries outside one trust marker, and a doctor variant closed over one code and one variable name. The external surfaces were verified on the machine that produced this record, including the three facts that shaped the design most (the export accepts a target; an integration can carry two accounts; an `active` OAuth entry can carry no expiry) and the one the critic corrected (a harness integration is OAuth-only today, so the OAuth refusal costs a real capability now rather than hypothetically). What keeps this from High: another product's CLI stability and its behaviour from a lingered unit with no session (the ~4.5 s standalone measurement is from a logged-in host, so the unattended cost and failure mode are `TO-CONFIRM`), and the exact requirement of the keyring under `HOME`-only versus session-bus facts. All are bounded by construction — a refused reason, a bounded per-execution cap, a closed stdin, readiness that never waits, an asynchronous cadence with an atomic swap, and a bounded backoff — so a wrong answer costs a refused or `resolution-pending` resolution and a sharper reason token, not a leak, a hang, a starved daemon or a failed unit.
