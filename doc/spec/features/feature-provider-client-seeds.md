# Feature: Provider Client Seeds and Trap Catalogs

## Overview

The tracker and VCS client layer lives in three provider seeds in the adapters package's per-provider subpaths: Jira (`adapters ./jira`), GitLab (`adapters ./gitlab`), and GitHub (`adapters ./github`). Each is a factory-built client that implements behind the delivered primitive ports and returns only normalized views — `WorkItem`, `DeliveryRequest`, and `PipelineRun` — plus an `AdapterContract` capability declaration. Provider-native payload types never cross the subpath surface.

The seeds provide reads for all three providers, the closeout write slice for GitHub and Jira, and — for the GitHub seed — the whole closed operation set. Jira resolves issues, search-shaped tracker queries, bounded reverse-dependent searches, and closeout writes (done transition, full-array label replace, assignee clear). GitLab reads merge requests and the pipelines reported for a commit, including merged-head identity when present, and declares every write and the work-item read as gaps. GitHub reads issues, pull requests, check runs per commit SHA, one bounded page of open issues, one bounded page of open pull requests, bounded reverse-dependent reads, and merged-request lookup, and writes labels, assignee clears, issue transitions, review-thread resolution, carrier-free issue comments, delivery-request content (create and update), and a provider-side squash landing. Capability is declared, never implied: GitHub supports all nine closed operations and declares no gap; GitLab keeps every write and the work-item read as gaps; Jira declares the delivery-request, pipeline, thread, and landing operations provider-unsupported and `write-comment` unimplemented. The Jira read slice answers the four M0-S6 tracker-collector query families — owner hand-backs, blocked dependencies, stalls, and ticket hygiene — from normalized `WorkItem` data alone. Collection and reverse-dependent reads are query-shaped forms of the existing read operations, so they add no closed operation and no capability flag. Closeout work-item reads carry provider-asserted label and relation availability signals, and the bounded reverse-dependent read uses a separate observation that distinguishes an absent surface (`no-surface`) from a currently unavailable signal (`unavailable`).

The GitHub seed is the reference adapter, and its behavior is stated normatively in [Adapter Reference Behavior](feature-adapter-reference-behavior.md): per-operation preferred and fallback transports, primary failure identities, absence semantics, the two bounded evidence reads with their fixed caps, and the injected workflow mapping. Its preferred transport is the vendor CLI used strictly as an authenticated API caller, selected once at composition by a bounded probe with the direct API as the declared fallback; the matrix, probe, and selection contract are described under [Transport](#transport-cli-first-with-api-fallback). Its Issues status and transitions resolve through one injected `WorkflowMap`, seeded with this repository's lifecycle labels; read normalization and the transition write share that one map.

Every known provider quirk is captured as a trap-catalog entry: a named data record pairing the provider behavior, the expected normalized outcome at the port boundary, and one or more fixture references. The catalogs and the fixtures they cite are committed test assets; trap suites replay the fixtures through the production clients with zero live network calls and zero live child processes. Fixtures are hand-authored synthetic captures modeled on recorded provider response shapes, sanitized before commit, and marked with their provenance.

Authentication is credential-port exclusive. Each client receives an `ExternalSystemInstance`, a `CredentialPort`, and an injectable transport; it resolves the instance's declared credential reference on every request and never reads the ambient environment. The runtime-API confinement allowance admits the three provider client subpaths as exact, reason-bearing entries while the provider registry stays non-I/O; the secret-read allowlist admits no provider entry. The GitHub subpath's one process edge — a bounded, no-shell `gh` invocation behind the CLI transport — is admitted by the same exact entry rather than by a new allowance. Provider truth is carried as declared data where the v1 contract has no destination: custom-field mapping rules, merge-status tables, the transport matrix, the issues transition seed, and the fixed evidence caps live beside the normalized view, and optional `WorkItem` and `PipelineJob` fields use one uniform absence rule.

The port substrate is described in [Adapter Ports, Credential Resolution, and Embedded Metadata](feature-adapter-ports.md); the normative adapter contract in [Adapter Reference Behavior](feature-adapter-reference-behavior.md); the surrounding workspace and boundary mechanism in [Monorepo Scaffold and Toolchain](feature-monorepo-scaffold-toolchain.md); failure identity in [Result Contract and Error Table](feature-result-contract.md). Package placement follows [ADR-0003](../../decisions/ADR-0003-oss-monorepo-structure.md); the contract extensions follow [ADR-0004](../../decisions/ADR-0004-workitem-activity-timestamp-additive-v1.md) and [ADR-0006](../../decisions/ADR-0006-workitem-custom-fields-and-comment-omission-representation.md); the confinement refinement follows [ADR-0005](../../decisions/ADR-0005-runtime-confinement-provider-client-subpaths.md); the CLI-first transport follows [TDR-0031](../../decisions/TDR-0031-github-adapter-cli-first-provider-transport.md), the landing and evidence extensions [TDR-0032](../../decisions/TDR-0032-github-adapter-completion-contract-extensions.md) and [TDR-0033](../../decisions/TDR-0033-review-thread-discussion-bodies-bounded-adapter-read.md), and the Issues transition mapping [TDR-0034](../../decisions/TDR-0034-github-issues-transition-mapping-injected-workflow-map.md).

## Business Context

### Problem Statement

- **Problem:** No provider client can read a tracker or VCS system behind the primitive ports, so status, verify, closeout, and conformance stories have no provider facts to consume. When clients arrive without trap discipline, provider quirks — label replacement, custom-field typing, data-driven transitions, comment omission, pipeline multiplicity, and asynchronous merge status — leak into higher layers as silent misinterpretations of provider state.
- **Affected Users:** The status collector, verify-change and verify-gates surfaces, closeout, conformance suite, and full GitHub adapter authors; operators and agents consuming provider facts; security reviewers responsible for credential centralization and the I/O boundary.
- **Business Impact:** The seeds are the first real consumers of the adapter contracts. A seed that overclaims capability, flattens a quirk, or reads a secret outside the credential port converts the whole adapter layer into untrustworthy input for every downstream engine.

### Goals

- Return normalized primitive views and declared writes from three provider client slices behind the delivered ports.
- Declare supported operations and explicit gaps from the closed operation set, with no implied parity.
- Prove every ticket-named provider quirk offline against committed sanitized fixtures, with a firing negative control and a contained process edge.
- Answer the four M0-S6 tracker query families from normalized `WorkItem` data.
- Resolve every credential through the credential port, with zero growth of the secret-read allowlist.
- Keep provider network and process I/O in its declared home with an exact, reason-bearing runtime-API confinement admission.

## User Experience & Functionality

### Client seeds

Each seed is a factory result, never a module-level singleton. Construction takes the instance, the credential port, an optional transport (defaulting to native `fetch` inside the provider subpath), and the provider-specific addressing data.

| Seed | Public surface | Supported operations | Addressing input |
|------|----------------|----------------------|------------------|
| Jira | `createJiraClient`, `JiraClient`, `JiraClientOptions`, `JIRA_ADAPTER_CONTRACT` | `read-work-item`, `write-work-item`, `transition-work-item` | Issue key passed to `readWorkItem`/`writeWorkItem`/`transitionWorkItem`; JQL passed to `searchWorkItems`. |
| GitLab | `createGitLabClient`, `GitLabClient`, `GitLabClientOptions`, `GITLAB_ADAPTER_CONTRACT` | `read-delivery-request`, `read-pipeline-run` | `projectPath` plus the merge-request IID or commit SHA. |
| GitHub | The client factory and its types, `GITHUB_ADAPTER_CONTRACT`, the bounded deploy-trace, log-excerpt, and thread-discussion readers with their fixed caps, the CLI transport factory with its probe, version window, refusal codes, transport matrix, and selection types, and `GITHUB_WORKFLOW_MAP_SEED` | All nine closed operations: `read-work-item`, `read-delivery-request`, `read-pipeline-run`, `write-work-item`, `transition-work-item`, `resolve-delivery-thread`, `write-comment`, `write-delivery-request`, `merge-delivery-request` | `repository` (`owner`, `name`) plus the issue/PR number, commit SHA, thread id, or job id. |

Client operations:

- **Jira:** `readWorkItem(issueKey)` returns one `WorkItem`; `searchWorkItems(jql)` returns a `WorkItem` set from a search-shaped response; `readWorkItemObservation(issueKey)` returns the discriminated closeout read; `listBlockedByDependents({ issueKey, limit })` returns a bounded reverse-dependent `WorkItem` set; `writeWorkItem({ issueKey, add?, remove?, assignee? })` performs full-array label replace and assignee clear; `transitionWorkItem({ issueKey, deliveryState })` executes the declared done transition by workflow-map name.
- **GitLab:** `readDeliveryRequest(mergeRequestIid)` returns one `DeliveryRequest` with optional `headSha`; `readPipelineRun(commitSha)` returns every pipeline the provider reports for that commit as a `PipelineRun` set.
- **GitHub:** `readWorkItem(issueNumber)`, `readDeliveryRequest(pullNumber)`, and `readPipelineRun(commitSha, limit?)` return the corresponding normalized views. `listWorkItems(limit)` returns one bounded page of open issues with pull-request objects filtered out; `listDeliveryRequests(limit)` returns one bounded page of open pull requests. Both list reads report the raw page size alongside the normalized items. `readWorkItemObservation(entityId)` returns the discriminated closeout read; `findMergedDeliveryRequest({ workItemRef, limit })` returns the deterministically selected merged request; `listBlockedByDependents({ entityId, limit })` returns the bounded reverse-dependent set; `writeWorkItem({ entityId, add?, remove?, assignee? })` writes labels and assignee; `transitionWorkItem({ entityId, deliveryState, current? })` resolves the alias through the workflow map and writes the mapped mechanism; `writeComment({ entityId, body })` posts one carrier-free comment and returns its provider identity; `writeDeliveryRequest(input)` performs the two-variant content write (create or update); `mergeDeliveryRequest(input)` performs the one provider-side squash landing; `resolveDeliveryThread({ deliveryRequest, threadId })` runs the GraphQL `resolveReviewThread` mutation.

### Capability and gap posture

| Seed | Declared supported | Declared gaps |
|------|--------------------|---------------|
| Jira | `read-work-item`, `write-work-item`, `transition-work-item` | `write-comment` — `adapter-not-implemented`; `read-delivery-request`, `write-delivery-request`, `read-pipeline-run`, `resolve-delivery-thread`, `merge-delivery-request` — `provider-unsupported`. |
| GitLab | `read-delivery-request`, `read-pipeline-run` | `write-delivery-request`, `read-work-item`, `write-work-item`, `transition-work-item`, `write-comment`, `resolve-delivery-thread`, `merge-delivery-request` — `adapter-not-implemented`. |
| GitHub | All nine closed operations | None. |

Every gap `{ operation, reason }` uses one of the closed reasons (`provider-unsupported`, `adapter-not-implemented`, `plan-restriction`). An operation absent from `supportedOperations` is unsupported; no seed declares an envelope-carrier surface (`writableCarriers` and `readableCarriers` are empty on every shipped adapter, so a supported comment write stays carrier-free). Writes are implemented against the existing injected transport and credential port; a supported read never implies a write, and GitHub's supported set and gap set are disjoint and together equal the closed operation set exactly. The per-adapter postures are compared mechanically with the declarations by [Adapter Reference Behavior](feature-adapter-reference-behavior.md).

### Transport (CLI-first with API fallback)

The GitHub client keeps one transport seam. Two implementations sit behind it: the vendor CLI (`gh`) acting strictly as an authenticated API caller over one fixed argv, and the direct REST/GraphQL API over native `fetch`. Both sit under the same request shaping and the same normalization, so a consumer sees no surface change and a replayed tenant route yields identical normalized views and failure identities through either path.

| Aspect | Behavior |
|---|---|
| Matrix | `GITHUB_TRANSPORT_MATRIX` declares, per closed operation, `gh` preferred and `api` fallback. The matrix is uniform because the CLI is transport-level, not primitive-level. |
| Probe | One bounded version invocation at composition time only — never at module load, never per request, never on a self-description path that does not compose, and never in the mock tier. It returns closed data: a version, or exactly one refusal code. |
| Refusal codes | `provider.cli.unavailable`, `provider.cli.version-unsupported`, `provider.cli.capability-unsupported`. They are adapter-local: no error-table row and no lifecycle failure. |
| Policy | Closed `prefer-cli` (default) or `api-only`, decided once at composition. `api-only` runs no probe and declares no degradation. An absent composition fact selects the native-`fetch` transport with no probe and no selection value; the production launcher always supplies the fact. |
| Selection value | Composition selection produces one `GithubTransportSelection` (`policy`, `selected`, optional `degradation.code`) as the resolver's return value, consumed by the launcher. It is in-memory composition data: never persisted, never a telemetry record or state record, and no new readable surface on the composed program object. |
| Diagnostic | A fallback renders exactly one human diagnostic line naming the refusal code through the existing composition-notice/warnings channel. |
| Failover | None per request. A mid-run CLI failure is a classified transport failure with no status, and a write is never re-issued on the other transport. |
| Child execution | Fixed argv, no shell, no pagination, no output transform, no interactive prompt, bounded timeout and output buffer, and an adapter-constructed environment carrying `PATH` from injected data. |
| Credential | Material arrives from the credential port as child-environment data (the resolved GitHub token); it never appears in argv, stdout, stderr, diagnostics, or a failure detail. The CLI configuration directory is isolated and prompt suppression is set, so an operator's stored login is never used. |

The transport is described normatively in [Adapter Reference Behavior](feature-adapter-reference-behavior.md) and was decided in [TDR-0031](../../decisions/TDR-0031-github-adapter-cli-first-provider-transport.md). The one bounded child invocation is admitted by the existing exact `github` runtime-API confinement entry — the ADR-0005 pointer routes a reader to TDR-0031 for that entry's current meaning — and adds no secret-read allowlist entry.

### Evidence reads (adapter-local)

Two bounded, provider-text reads sit outside the closed operation set and add no operation, no capability flag, and no normalized-contract field:

| Surface | Shape | Caps | Truncation | Classification |
|---|---|---|---|---|
| Failure log excerpt | `{ jobId, excerpt, truncated, byteLength }` — a faithful byte prefix of the provider's log text | 8192 bytes, one read, no pagination, no retry, no archive download, no caller override | `truncated` is the sole authority and `byteLength` equals the returned bytes | 404 → not-found; other non-2xx or transport failure → `provider.payload.invalid`; a malformed 2xx → `provider.payload.invalid` with its status; an empty 2xx is observed empty |
| Review-thread discussion | `{ threadId, resolved, commentCount, comments[], truncated }` with per-comment identity, optional author facts, body, and per-body truncation | 50 oldest-first comments per thread; 4096 bytes per body; no override | Thread-level `truncated` is true exactly when fewer comments were returned than the provider count or any body was truncated | 404 or provider-absent thread → not-found; other non-2xx, transport failure, malformed 2xx → `provider.payload.invalid`; zero count with an empty list is observed empty |

Both reads return text only to their caller: the adapter never renders, logs, or persists a body or an excerpt and never captures one in the conformance artifact, and any consumer surface that renders provider text routes it through the single redaction chokepoint. Discussion bodies and log text are evidence, never lifecycle truth, and carry no write authority. The bounded deploy-trace read is the delivered precedent for the same posture.

### Normalization behavior

**Jira.** An issue normalizes to `WorkItem` with provider-qualified identity, title, native status plus the delivery alias from the declared `WorkflowMap`, labels, optional assignee, typed relations, optional comments, and optional `updatedAt`. The workflow map covers `Backlog` → `backlog`, `To Do` → `ready`, `In Progress` → `in-progress`, `In Review` → `in-review`, `Done` → `done`, and `Won't Do` → `canceled`, each naming its transition mechanism (`manual`, `field-update`, `api-transition`, or `label-swap`). A native status outside the map fails the read visibly instead of flattening. Issue links normalize to the closed relation kinds `blocks`, `blocked-by`, and `relates-to`; unrelated link types are not represented.

**Jira custom fields.** The seed declares which provider custom fields feed normalized labels and the type each value is read as: `customfield_10020` as a `select` value rendered with the `team:` prefix, and `customfield_10021` as a `number` rendered with the `story-points:` prefix. A declared numeric value arriving as a numeric string is parsed to a number before rendering; a value that does not match its declared type is skipped. Unmapped custom fields are visibly unrepresented — no raw `customfield_*` key and no unmapped value crosses the boundary.

**Jira tracker queries.** The read slice answers the four M0-S6 query families from normalized data: owner hand-backs from assignee/ownership signals, blocked dependencies from `blocks`/`blocked-by` relations, stalls from `updatedAt` (absent = activity unknown), and ticket hygiene from label/status conformance plus custom-field conformance for mapped fields. No query requires a provider-native payload.

**Jira closeout observation.** A Jira work-item read returns the discriminated observation: HTTP 404 is `not-found`; any other non-2xx response (authentication, transport, or server failure) and a malformed 2xx payload are `invalid`; a successful payload is `observed` and carries `signals.labels`/`signals.relations` availability (`observed` for a present container including `[]`, `unavailable` when the container is omitted). A credential-resolution failure preserves its `config.credential.missing` identity on the invalid observation instead of collapsing to a payload failure. The bounded reverse-dependent search uses the two-argument `linkedIssues(key, "blocks")` form and keeps only candidates carrying an inward `blocked-by` relation to the source ticket, so relates-to links and tickets that block the source are never treated as dependents. It reports a missing search surface (HTTP 404/410) as `no-surface` and a failing read on an existing surface as `unavailable`.

**GitLab.** A merge request normalizes to `DeliveryRequest` with identity, source and target refs, review state, review threads, and `headSha` copied from the provider head SHA when present. Merge status resolves through a declared rule table: `merged`, `closed`, and `locked` states are terminal; a draft request is `draft`; otherwise `detailed_merge_status` is authoritative when present and `merge_status` is the fallback, and a positive approvals count promotes a rule whose open-state mapping is `open` to `approved`. Asynchronous values such as `checking`, `unchecked`, `ci_still_running`, and `approvals_syncing` map to non-terminal states only; an unknown native value fails visibly.

**GitLab pipelines.** `readPipelineRun(commitSha)` returns every pipeline the provider reports for the commit, each with a distinct identity, closed-set job states, and trace-evidence references where the provider records a trace. Pipeline multiplicity is preserved; nothing is collapsed to a newest-wins singleton.

**GitHub.** A pull request normalizes to `DeliveryRequest` with identity, head/base refs, review state, review threads, and `headSha` copied from the provider head SHA when present. Merge truth is a true `merged` flag or a non-null REST-list `merged_at` timestamp; merged, closed, and draft flags take precedence over the native review decision, which maps `APPROVED` → `approved`, `CHANGES_REQUESTED` → `changes-requested`, and `REVIEW_REQUIRED` → `open`, defaulting to `open`. Check runs per SHA normalize to one `PipelineRun` per run, each carrying one job; a failed run is never hidden behind a check-suite roll-up, and each run's identity includes the commit SHA. A completed run's job carries the provider-asserted `started_at` and `completed_at` timestamps verbatim as the optional `PipelineJob.startedAt` and `PipelineJob.completedAt`; an omitted timestamp stays absent (unknown), and no duration is derived anywhere in the contract. Issues normalize to `WorkItem` with labels, optional assignee, a delivery status resolved through the workflow map, optional issue links only when the payload actually carries them, `updatedAt` from `updated_at` when present, and `comments` absent because this slice does not fetch the comment set. Issue status resolution has exactly one refusal class and four declared outcomes over one injected, seeded `WorkflowMap` whose tokens are native issue states or lifecycle label names and whose rows are declared in precedence order: a `closed` issue resolves to `done` regardless of labels; otherwise the first declared-precedence row whose token equals a present label name exactly wins (a label differing by case alone from a declared `label-swap` token is a visible normalization failure carried by `provider.payload.invalid`, naming the label and the declared token, while a case difference on a `field-update` token is not a collision because that token is a provider state); otherwise the issue resolves through its native-state row. An unrecognized label, an issue carrying no lifecycle label, and an unavailable label signal never refuse a read; only the absence of a row for the resolved native state refuses. The seed maps `closed` → `done` and `open` → `ready` by field update and `review` → `in-review` and `in-progress` → `in-progress` by label swap, so an issue labelled `in-progress` or `review` normalizes to that alias rather than `ready`. The merged-request lookup selects the highest numeric provider entity identity deterministically, then reads that pull request's review threads through GraphQL, requesting the root comment author (`login`, `__typename`) and `authorAssociation`; normalization maps `User` to `human`, `Bot`/`App` to `non-human`, and `Mannequin` or an absent/unrecognized author to `unknown` (fail-closed), carried as optional `authorLogin`/`authorKind`/`authorAssociation` on the thread. A failed thread read keeps the request observed with `signals.threads: "unavailable"`, never an observed empty thread set. The bounded reverse-dependent read uses `/issues/{number}/dependencies/blocking` and normalizes the returned issue array: HTTP 404/410 from the dependency endpoint is `no-surface`, any other non-2xx response or transport failure is `unavailable`, a credential-resolution failure or malformed payload is `invalid`, and a successful payload is `observed`. A work-item read returns a discriminated observation: HTTP 404 is `not-found`; any other non-2xx response (authentication, transport, or server failure) and a malformed 2xx payload are `invalid`; a successful payload is `observed` and carries `signals.labels` from the issue payload and `signals.relations` from the `/issues/{number}/dependencies/blocked_by` read (`observed` when that read succeeds, `unavailable` when it fails or is absent). An invented `issue_links` field is not a production relation signal.

**Closeout writes.** GitHub `writeWorkItem` reads the current observed labels, removes only the named labels, adds the named labels, and clears the assignee when asked; `transitionWorkItem` resolves the alias through the workflow map and writes the mapped mechanism; `resolveDeliveryThread` posts the GraphQL `resolveReviewThread` mutation and validates the returned resolved thread. Jira `writeWorkItem` reads the current observed labels and performs a full-array replace that preserves unnamed labels, and clears the assignee when asked; `transitionWorkItem` resolves the declared done state through the workflow map and posts the named transition. Both label-writing adapters refuse an unavailable label signal instead of computing a replacement from a collapsed empty set. Write failures surface as the adapter-local `provider.payload.invalid` result with a readable detail, never a silent flattening.

**GitHub transition writes (mechanism-scoped).** Only a `label-swap` transition reads, removes, or adds labels: it removes present declared lifecycle label tokens, adds the row's token, never replaces the full label array, and refuses on an unavailable label signal. A `field-update` transition writes only the provider state and performs no label read, no label write, and no label-signal refusal, so the delivered closeout terminal write is exactly one state-only `PATCH` with no new refusal path; closeout's separate `write-work-item` step remains the sole owner of terminal label cleanup. The writable aliases are `done` plus each declared `label-swap` row's alias; a declared non-terminal `field-update` alias is readable but read-only, and a transition to it refuses with a named typed failure and zero provider requests. A `label-swap` write is resolved against the issue's current read result, supplied as adapter-local input data: a write to an issue whose current read resolves to `done` refuses with a named typed failure and zero provider requests regardless of its labels, because terminal precedence would make the added token unobservable. An undeclared alias refuses from the map alone. The map is validated exactly once per client construction on the resolved map (injected map or seed) before the first operation; a failure is captured rather than thrown and every operation then refuses with `provider.payload.invalid` naming the failed check, with zero provider requests and no new error-table row. The mapping is construction data: no configuration key, settings type, or file format exists for it.

**GitHub backlog and landing writes.** `writeComment({ entityId, body })` posts one carrier-free human comment and returns the provider comment identity; the adapter declares no writable carrier, so no metadata envelope is claimed. `writeDeliveryRequest` is the content write in two adapter-local variants: a **create** carrying a source ref, a target ref, a non-empty title, a body, and an optional draft flag, and an **update** carrying the delivery-request identity plus at least one of title and body. A create never lands and never sets merge state, an update never creates, and a write missing its required input is a named typed refusal with zero provider requests; a successful write returns the normalized delivery-request view. `mergeDeliveryRequest({ deliveryRequest, strategy: "squash", commitTitle?, commitMessage?, expectedHeadSha? })` performs the one provider-side landing: the crafted commit title and message are transmitted verbatim, a supplied expected head is the guard and nothing overrides it, an already-merged refusal becomes success only after a read-back that observes provider-asserted merged truth, and the landing commit identity is returned only when the provider supplies it. A landing is at most once per invocation: it is never retried and never re-issued on the other transport, and force, branch-protection bypass, auto-merge, merge queues, rebase, and merge-commit strategies are not representable.

**GitHub pull-request gate facts.** Detail normalization additively populates `sourceHeadSha` from `head.sha`, `commitCount` from `commits`, `changedFileCount` from `changed_files`, and `mergeableState` from the fixed precedence: `mergeable === false` with `clean`/`dirty`, or any `dirty`, is `conflicting`; `blocked`, `behind`, `unstable`, or `draft` is `not-mergeable`; `mergeable === true` with absent or `clean` state is `mergeable`; every other case is `unknown`. Mergeability never defaults to mergeable, and a non-finite or negative count is absent. The list read may populate `sourceHeadSha` only; it does not supply mergeability or the commit/change surface. See [Verify Gates](feature-verify-gates.md).

### Absence semantics

Optional `WorkItem` fields follow one rule: absence means the provider did not supply the signal, so the value is unknown — never derived, fabricated, or collapsed into an empty value.

- `updatedAt` is the provider-native last-modified timestamp copied verbatim as an ISO-8601 UTC string. Absent means activity is unknown, not "no activity"; consumers must report "cannot determine" for absence.
- `comments` is the provider-asserted comment set. Absent means the comment set is unknown (omitted for permission or paging causes, or not fetched). Present — including an explicitly empty array — means the provider asserted that set, so an empty present array means genuinely no comments. An omitted payload never collapses into `[]`.
- `relations` is the provider-asserted relation set. The GitHub issue list does not supply structured issue links, so list-read issues carry `relations: []` only as the normalized value of an absent provider signal; consumers that need GitHub dependency truth read the closeout observation, whose `signals.relations` comes from the `/issues/{number}/dependencies/blocked_by` surface and is never inferred from an `issue_links` field. The same rule applies to review state and review threads on the GitHub pull-request list: the list payload carries no review decision or thread data, so those item signals are unknown, never open or zero; the merged-request lookup re-reads the selected pull request's threads through GraphQL and marks them unavailable if that read fails.
- `headSha` is the provider-resolved merged-head commit copied verbatim. Absent means the provider did not supply the signal (unknown), never an empty or derived value. A consumer comparing it for exact equality must refuse a destructive action when it is absent.
- `PipelineJob.startedAt` and `PipelineJob.completedAt` are provider-asserted timestamps copied verbatim. Absent means the provider did not assert the timestamp or the run has not completed: the value is unknown and is never derived, defaulted, or collapsed to zero. The contract carries no `durationMs`; a duration is never computed from these fields inside the adapter.
- A landing's merge commit identity is returned only when the provider supplies it. Absent means unknown and is never derived from a local commit or a branch head.
- Closeout-relevant reads return a discriminated observation rather than only the normalized value: `observed` (provider-asserted value; an empty collection means none), `not-found` (explicit provider 404), `unavailable` (a genuinely absent surface or a read that cannot produce a value), and `invalid` (malformed or unparsable payload, or an authentication/transport/server failure on a non-404 read). An observed read carries per-signal availability for labels and relations; an omitted container is an `observed` read with an `unavailable` signal, so an unavailable label signal is never collapsed into an empty label set and an unavailable relation signal is never collapsed into an empty blocker set. The bounded reverse-dependent read uses the separate `CloseoutReverseDependentObservation`, which adds `no-surface` for an absent surface so it is distinct from a currently `unavailable` signal.
- The four GitHub gate facts follow the same rule: an absent `sourceHeadSha`, `mergeableState`, `commitCount`, or `changedFileCount` is unknown, never a fabricated SHA, never mergeable, and never a zero or non-empty surface. The list read may omit them; the detail read populates them when the provider reports them.

### Credential resolution and error integration

Each client resolves the instance's declared credential reference through the injected `CredentialPort` on every request. An anonymous auth method sends unauthenticated headers; a credential-bearing method resolves the reference and attaches the material to the request headers. Resolved material is never stored on the client, logged, or returned in a normalized view.

An unresolvable credential surfaces the synchronized `config.credential.missing` failure (domain kind `config`, category `user`, retryable `false`, consequence `not_landed`, projection class `user-validation`). Provider payload and transport failures surface as the adapter-local `provider.payload.invalid` read failure with a detail string, never as a silent flattening or a raw provider error; these failures are not new error-table rows. An HTTP 404 instead surfaces as the additive adapter-local `provider.not-found` read failure with a detail string and no error-table row; the verify gates map that definitive absence per read rather than treating it as a generic read failure.

Both adapter-local failure types carry an optional structured numeric `httpStatus`. The GitHub read slice supplies it on every non-2xx response and on a work-item 2xx response whose payload a normalizer cannot parse, so a rejected credential and a malformed payload are classifiable from structured data rather than prose; transport failures and absent responses omit it, and the Jira and GitLab slices leave the field absent. The field is secret-free, additive, and never promoted to an error-table identity: `provider.payload.invalid` remains the only payload-failure identity, `provider.not-found` remains the definitive-absence read result, and no consumer parses the failure's prose detail for classification.

### Flows

1. **Read:** A consumer constructs an `ExternalSystemInstance`; the seed resolves its credential reference through the credential port; the injected transport issues the request; normalization returns a primitive view or a classified failure. Under the GitHub CLI transport the request travels as one fixed-argv child invocation and returns the same normalized view or failure identity as the direct-API path.
2. **Tracker query:** A collector supplies a JQL query; the Jira seed returns normalized `WorkItem` views; the four query families are evaluated from normalized fields only.
3. **Trap replay:** A trap entry names a quirk and its fixture; the suite replays the fixture through the production client with an injected transport and an injected child runner; the expected normalized outcome is asserted without any network call or live child process.
4. **Fixture authoring:** A maintainer authors a synthetic fixture modeled on a documented provider response shape, applies the sanitization rules, records its provenance, commits it, and references it from one or more trap entries.
5. **Closeout read:** A consumer reads a work item through the discriminated observation (including label/relation availability signals), looks up the merged delivery request and its optional head, and reads bounded direct dependents; an absent reverse surface (`no-surface`) remains distinct from a currently unavailable signal and from an observed empty result.
6. **Closeout write:** A consumer issues a declared write through the adapted client; the adapter resolves credentials, issues the provider request over the injected transport, and returns a landed write or a classified failure. Unsupported operations never reach the transport and remain declared gaps for the caller.
7. **Backlog write:** A consumer requests a delivery alias or issues a comment or content write; the adapter resolves the alias through the workflow map or shapes the content write, issues at most one provider request, and returns the normalized view or a classified failure. Every refusal — undeclared alias, non-terminal `field-update` alias, terminal-resolving current read, unavailable label signal, or a content write missing required input — costs zero provider requests.
8. **Landing:** A caller supplies the delivery request, the squash strategy, and optional crafted commit metadata and expected head; the adapter sends one landing request, classifies a guard rejection or other refusal, and treats already-merged as success only after a read-back observes provider-asserted merged truth.
9. **Evidence read:** A consumer holds a job identity or a thread identity and asks for one bounded evidence read; the read performs one request, returns the closed shape with an explicit truncation signal, and never renders, logs, or persists the provider text.

### API and interface contracts

- **`createJiraClient({ instance, credentials, transport? })`** returns `{ readWorkItem, searchWorkItems, readWorkItemObservation, listBlockedByDependents, writeWorkItem, transitionWorkItem }`; reads return `ProviderReadResult<T>`, `readWorkItemObservation` returns `CloseoutReadObservation<WorkItem>`, `listBlockedByDependents` returns `CloseoutReverseDependentObservation<readonly WorkItem[]>`, and writes return `ProviderWriteResult`.
- **`createGitLabClient({ instance, credentials, projectPath, transport? })`** returns `{ readDeliveryRequest, readPipelineRun }`.
- **`createGitHubClient({ instance, credentials, repository, transport?, timeoutMs?, workflowMap? })`** returns `{ readWorkItem, readDeliveryRequest, readPipelineRun, listWorkItems, listDeliveryRequests, readWorkItemObservation, findMergedDeliveryRequest, listBlockedByDependents, writeWorkItem, transitionWorkItem, writeComment, writeDeliveryRequest, mergeDeliveryRequest, resolveDeliveryThread }`, with the same observation return types as Jira for the work-item and reverse-dependent reads. `workflowMap` is the only additive construction member: absent means the declared seed, and the resolved map is validated once at construction.
- **`readPipelineRun(commitSha, limit?)`** reads one check-runs page, defaulting `limit` to `STATUS_SOURCE_PIPELINE_LIMIT`, and returns `{ items, pageItemCount }`; `listWorkItems(limit)` and `listDeliveryRequests(limit)` each read one bounded page and return `{ items, pageItemCount }`.
- **`ProviderTransport.send(request)`** sends a request with `url`, a closed method, headers, an optional serialized body, and an optional timeout, and returns a provider response with a status and an untrusted body; tests inject a fixture transport, and production composes either the CLI transport or the native-`fetch` transport for GitHub, and the native-`fetch` transport for Jira and GitLab.
- **`probeGithubCli` / `resolveTransportSelection`** return the closed probe result (`{ ok: true, version }` or `{ ok: false, code }`) and the `GithubTransportSelection` value (`{ policy, selected, degradation? }`); `createGithubCliTransport` builds the CLI transport over an injected child runner and injected environment.
- **`createGitHubLogExcerptReader` / `createGitHubThreadDiscussionReader`** return the two bounded evidence readers; each exposes one read over the injected transport and credential port and returns the closed shape with an explicit truncation signal.
- **`ProviderReadResult<T>`** is either `{ ok: true, value }` or a `CredentialResolutionFailure`, a `ProviderPayloadFailure` (`provider.payload.invalid` with a detail and an optional structured `httpStatus`), or a `ProviderNotFoundFailure` (`provider.not-found` with a detail and an optional structured `httpStatus`). **`ProviderWriteResult<T>`** has the same success/failure shape for writes.
- **`CloseoutReadObservation<T>` / `CloseoutReverseDependentObservation<T>`** — the closeout read discriminators. The work-item observation is `observed` (with optional `signals`) / `not-found` / `unavailable` / `invalid`; the reverse-dependent observation adds `no-surface`. They refine reads only and change neither `ProviderReadResult` nor the closed operation set.

All three subpath surfaces export only their client factory, core-built input/return types, the adapter contract, and the declared readers and transport factories each adapter owns; no provider-native payload type crosses a subpath. The GitHub subpath is the widest: besides the factory and the adapter contract it exports the bounded deploy-trace, log-excerpt, and thread-discussion readers with their fixed caps, the CLI transport factory with its probe, version window, refusal codes, transport matrix, and selection types, and the workflow-map seed that the reference-behavior drift check compares against the document. The exact export set is pinned in both directions by `tests/structure/provider-surface.test.ts` and the per-file executable-export inventory; the shared transport module stays internal, imported relatively, and the package's `#io/*` alias remains an internal import map, not a published export.

### Collection-read operation rule

Collection and reverse-dependent reads are the query-shaped form of the existing read operations, following the Jira `searchWorkItems` precedent. `listWorkItems` stays `read-work-item`; `listDeliveryRequests` stays `read-delivery-request`; the page-limited check-runs read stays `read-pipeline-run`; the bounded reverse-dependent query stays `read-work-item`. A collection read adds no operation and flips no supported/gap posture. No new list operation joins the closed operation set, and no declared read gap becomes supported. A future collection read follows the same rule and extends the trap catalog with fixtures and matching assertions in the same change.

### Intra-package imports and packed exports

Shared adapter support modules under `src/io/` are imported by the provider seeds through relative `../io/*.js` specifiers, not through the `#io/*` imports alias. The alias is src-mapped (`./src/io/*.ts`), which resolves only in the repository; a packed adapter tarball ships `dist` only, so the alias would dangle after install. The relative `.js` specifier resolves to the built sibling in both the workspace and the tarball, so it is the only spelling that preserves packed-export parity. This is a deliberate, narrow exception to the alias-only intra-package import rule; `src/io/provider-transport.ts` states the same reason in its module header so a future reader does not "fix" the specifiers. A dist-conditioned `#io` alias would be a reviewed change, not a local rewrite.

## Security and Boundaries

- Credential material is reachable only through `CredentialPort`; no client module reads `process.env`, `Bun.env`, `Deno.env`, or any other ambient source. Under the CLI transport the resolved material is supplied to the child as constructed environment data and never as an argument.
- The secret-read allowlist contains the credential implementation directory and the configuration environment readers; the provider client subpaths add no entry and no `credential-material` reader, and the CLI transport adds none either.
- Runtime-API confinement admits the `core` state driver edge, the non-provider adapter I/O subpaths (`repo`, `file`, `host`, `session`, `legacy`, `credentials`), the dedicated git branch/checkout seam (`git`), the three provider client subpaths (`github`, `gitlab`, `jira`) as exact, reason-bearing entries per ADR-0005, the `cli` build, and the `opencode` host integration. The provider registry subpath and the remaining adapter subpaths stay non-I/O; the allowance is never widened by pattern.
- The `github` admission carries two admitted meanings under one exact entry: network I/O, and one bounded, no-shell, fixed-argv `gh` child invocation in `packages/adapters/src/github/cli-transport.ts` (the ADR-0005 pointer routes a reader to [TDR-0031](../../decisions/TDR-0031-github-adapter-cli-first-provider-transport.md) for the current meaning). No other provider subpath gains a process edge, and the production child-process import sites remain an exactly pinned set.
- Provider-native types and raw provider keys never cross a subpath surface. Normalization is the only place untrusted provider payloads are read.
- Committed fixtures contain no secret, token, credential, private-corpus identifier, personal data, or non-example provider host; placeholders are declared and stable.
- Resolved credential material never enters diagnostics, logs, failure payloads, fixtures, recorded argv, child stdout, child stderr, or a failure detail.

## Operational & Support

### Configuration

Each client is constructed with a configured `ExternalSystemInstance` (instance name, system kind, base URL, auth method), the credential port, and provider addressing data: the Jira issue key or JQL at call time, the GitLab `projectPath`, or the GitHub `repository` (`owner`, `name`). The transport is an optional construction input; production composes the GitHub CLI or native-`fetch` transport from the composition-edge selection and receives native `fetch` for Jira and GitLab. The GitHub client additionally accepts an optional `workflowMap`, whose absence means the declared seed; the mapping is construction data, so no configuration key, settings type, or file format carries it. No ambient configuration, clock, or credential cache participates in a read, and the CLI child environment is built entirely from injected data.

### Observability

Capability declarations, gap records, the transport matrix, the workflow seed, and the fixed evidence caps are inspectable data. Trap failures name the trap entry and its fixture reference, so a normalization regression is diagnosable without reading test code. A transport fallback is operator-visible as exactly one diagnostic line naming the probe's refusal code; the transport selection itself is never persisted and never becomes a telemetry record or state record. Credential failures carry classified identity; payload and absence failures carry a readable detail. Resolved secret material is never observable through a diagnostic path.

### Maintenance

Five surfaces grow deliberately: trap catalogs (new quirks join as four-field entries with fixtures; fixture references stay stable across re-authoring), the confinement allowance (further I/O claims are exact, reason-bearing reviewed extensions), capability declarations (a gap becomes supported only when its consuming story lands, with trap coverage and write fixtures extended in the same change), collection/reverse-dependent and evidence reads (a list-shaped, reverse-shaped, or bounded-evidence read stays an adapter-local read and extends the trap catalog in the same change), and the declared transport matrix with its probe version window (a vendor-CLI change is absorbed by the probe and one argv mapping). Closeout and backlog writes are provider-specific behind the adapter boundary: a change to label-replace, transition, assignee-clear, thread-resolution, comment, content-write, or landing mechanics stays inside the provider subpath and is proven by write fixtures. The reference-behavior page and the exported declarations move together: a divergence fails `tests/structure/reference-behavior.test.ts`. Fixtures age; scheduled read-only live revalidation is delivered by the [adapter conformance suite](feature-adapter-conformance.md). A transport or implementation-basis swap behind the port boundary requires no consumer change.

## Dependencies & Risks

- **Depends on** the monorepo scaffold for package tiers, subpath exports, boundary enforcement, and the aggregate check.
- **Depends on** the adapter ports for the primitive contracts, capability/gap mechanism, credential port, and secret-read boundary.
- **Depends on** the result contract for failure identity and the redaction chokepoint, and on the configuration and branding layers for injected environment facts and brand-neutral credential source keys.
- **Consumed by** the status collector (including its bounded GitHub collection reads), verify-change gates, the [closeout transaction](feature-closeout.md) (including closeout reads and writes), the [doctor diagnostic](feature-doctor.md) (bounded tracker and CI reads plus structured read-failure status), the [adapter conformance suite](feature-adapter-conformance.md), and the cadence that compares adapters against [Adapter Reference Behavior](feature-adapter-reference-behavior.md).
- **Risk — fixture drift:** hand-authored fixtures can diverge from live provider behavior. Mitigation: dated provenance, stable references, and the scheduled read-only live revalidation delivered by the [adapter conformance suite](feature-adapter-conformance.md).
- **Risk — sanitization miss:** a committed fixture could leak a secret or personal data. Mitigation: declared placeholders, example-only hosts, a committed sanitization audit, and a planted-secret canary.
- **Risk — catalog rot:** a catalog can look complete while its assertions stop firing. Mitigation: bidirectional entry↔assertion coverage, a negative control that names the failing entry, and per-provider minima.
- **Risk — allowlist creep:** provider I/O could widen beyond the admitted subpaths. Mitigation: exact reason-bearing entries, registry/`azure`/`ci` negative controls, a guard that rejects pattern widening, and an exactly pinned production child-process site set.
- **Risk — secret-boundary erosion:** client code could acquire credentials ambiently. Mitigation: credential-port-only construction, the binding secret-read invariant, and a fixed five-entry allowlist with exactly one credential-material entry.
- **Risk — capability drift:** a client could be invoked for an operation beyond its declared posture. Mitigation: declared gaps for every unsupported operation, structure tests that pin the posture, and capability-gated conformance execution.
- **Risk — write-semantics drift:** provider label, transition, assignee, thread, comment, content-write, or landing mechanics could diverge. Mitigation: offline write fixtures, trap replay, and the provider-local implementation boundary.
- **Risk — transport misclassification:** a CLI path that cannot report the final status could misreport a rejected credential as a payload fault. Mitigation: the final status block is authoritative, an unparsable block is refused rather than guessed, and both transports are compared on the same replayed routes.
- **Risk — destructive landing:** a provider-side landing could land twice or take an already-merged refusal as success. Mitigation: at-most-once semantics, no retry, no second-transport re-issue, and success only after a read-back observes provider-asserted merged truth.
- **Risk — evidence leakage:** thread bodies or log text could reach state, artifacts, or rendered output. Mitigation: fixed caps, non-persistence, artifact exclusion, no adapter rendering surface, and the single redaction chokepoint for any consumer rendering.
- **Risk — port-shape gap:** the first real adapters may expose contract-shape gaps. The additive rounds — optional `updatedAt` and `comments` under ADR-0004 and ADR-0006, then the ninth operation and the two optional `PipelineJob` timestamps under TDR-0032 — stayed additive within v1; further evolution is governed by a decision record.

## Glossary & References

| Term | Definition |
|------|------------|
| Client seed | The first real provider client implementation behind the primitive ports for one provider, scoped to the operations its consuming stories need. |
| Read slice | The read-operation subset of a client, delivered before any write path. |
| Trap catalog | A named, data-reviewable set of entries pairing a provider quirk with the expected normalized outcome and its fixture; the durable record of each normalization rule. |
| Trap-catalog entry | One record with exactly four fields: trap name, provider behavior, expected normalized outcome, fixture reference. |
| Fixture provenance | The marker on a committed fixture or catalog naming its synthetic origin and date, distinguishing it from a live capture. |
| Sanitization | Authoring-time removal or stable-placeholder substitution of secrets, tokens, private-corpus identifiers, and personal data in fixtures. |
| Declared gap | An adapter's explicit `{ operation, reason }` record for an operation it does not support; parity is never implied. |
| Read observation | The closeout-relevant read discriminator `observed`, `not-found`, `unavailable`, or `invalid`; an observed empty collection means none, while unavailable or unknown signals are never collapsed into empty. |
| Merged head | The optional provider-resolved `headSha` on a delivery request; absent means unknown. |
| Provider transport | The injectable wire edge that sends an already-shaped provider request and returns status plus body; the GitHub client has a CLI-first implementation over `gh api` and a native-`fetch` implementation. |
| CLI-first with API fallback | The GitHub transport policy: prefer the vendor CLI as an authenticated API caller, fall back to the direct API when the CLI is unusable, with the preference declared per operation. |
| Probe | One bounded composition-time check of the vendor CLI's presence, version, and capability, returning a closed success or refusal code. |
| Transport selection | The composition-scoped `GithubTransportSelection` value naming the policy, the selected transport, and the degradation code when the preferred CLI was not selected; rendered as exactly one diagnostic line and never persisted. |
| Evidence read | A bounded adapter-local read that returns provider text for human or agent interpretation; it is not lifecycle truth and carries no write authority. |
| Workflow map | Declared data mapping a native status or lifecycle label token to a delivery alias and a transition mechanism; one injected map drives both GitHub Issues read normalization and transition writes. |
| Landing | The provider-side squash merge performed by `merge-delivery-request`, with optional crafted commit metadata and an optional expected-head guard; at most once per invocation, never retried. |
| Reverse-dependent read | A bounded query-shaped form of `read-work-item` returning open dependents that declare the closed item as a blocker; it adds no closed operation. |
| Pipeline-per-commit normalization | Resolving provider pipeline multiplicity (branch/merge pipelines, per-SHA check runs) into a truthful per-commit `PipelineRun` set. |
| Tracker-collector queries | The four M0-S6 tracker query families: owner hand-backs, blocked dependencies, stalls, ticket hygiene. |
