# Feature: State Layer

## Overview

The state layer is the durable local substrate later verification reads through. A store is opened from an injected identity — level, workspace identifier, fence namespace, schema version, and a concrete state directory — and exposes one driver-neutral port: append, read with a key-set assertion, read the verified record list, replace a derived document, acquire/release/recover a fence, check integrity, repair a terminal torn tail, run the explicit guided salvage operation, and read or get-or-create a store-managed artifact.

The append-only, schema-versioned JSONL ledger is the single durable truth. The declared driver kinds select only the read/index strategy over that same ledger: `jsonl` reads by verified scan, `sqlite` maintains a disposable derived index that is rebuilt from verified ledger truth whenever it is missing, corrupt, or divergent. No operation, result, or type on the public port discriminates by driver kind.

The layer ships no command surface and no configuration read. Its durable consumers append through the fenced port and read through verified reads: the delivery registry writes `phase.transition` records and replaces the per-change phase-state document as a rebuildable fold of verified records; verify change reads transition history; the provider engine writes park and announcement records; closeout writes `closeout.operation` outcome records and reads them to converge on re-run; the commit primitive writes `commit.telemetry` events and reads them as convergence corroboration (the atomic transition record carries the landed SHA as primary evidence); the command audit ledger writes a reservation and an invocation record per audited command invocation under one shared fence and reads a keyed chain and bounded history; the retro registry writes `retro.level`, `retro.run`, and `retro.trigger` records under its own validated boundary while the retro evidence sidecar lives outside the store as a separate artifact family; the owner-gate SLA writes `owner-gate.decision` default-application records and reads them to stay idempotent; closeout writes `harness.telemetry` session-group and capture-outcome records and reads them to skip already-captured session groups; the resume economics path writes `economics.restart` events and one terminal `economics.budget-exhaustion` record per delivery and folds them into the per-delivery economics view; the merge transaction writes and reads the `merge.gate-verification`, `merge.waiver`, and `merge.transaction` records, and the board reads recorded waivers as gate evidence; the blockers channel writes `blocker.question` and `blocker.answer` records and reads them to derive open/answered closure; and the status digest, the queue-ready ready-set, the brief, and the doctor diagnostic read the verified provider park fold and state-store verdicts while the status digest and brief also read the verified blocker fold, all without writing anything. Store identity, paths, clock, and platform arrive as injected parameters; the state tier never imports branding and never derives a name.

## Business Context

- **Problem:** Without durable state and integrity discipline, later verification reads either nothing or unverified bytes; corruption presents as empty truth, concurrent writers corrupt shared stores, and partially written documents masquerade as landed mutations.
- **Affected users:** The delivery registry and later consumer stories (status, verify-change), and the operators and agents that rely on their verdicts.
- **Value:** One truthful substrate with classified failures, so "no data" and "corrupt data" are never confused.

## User Experience & Functionality

### Capabilities

- **Injected identity:** level (`local` implemented; `project` and `global` declared), caller-supplied workspace identifier, fence namespace, schema version (`delivery.state.v1`), and the state directory. Identical inputs yield identical identity; a `project` or `global` request fails `state.level.unsupported` with no filesystem effect and no silent local fallback.
- **Ledger truth:** every append lands one LF-terminated JSON object carrying schema version, record kind, store-scoped key, contiguous store-scoped sequence, checksum, and a JSON-compatible payload. Earlier bytes are never rewritten. Every derived-document mutation is first a ledger record.
- **Driver kinds:** `jsonl` verified scan and `sqlite` derived index. The index is disposable and never truth; divergence is detected on read and rebuilt from the verified ledger — including a post-salvage ledger, where the rebuild converges with the verified scan — and reported, or the read fails `state.write.failed`. Salvage never reads or mutates the index; the next indexed read rebuilds from the salvaged ledger.
- **Torn-state detection:** framing break, truncated tail, sequence gap/duplicate/reset, and checksum mismatch are detected before any value returns and fail `state.store.torn` with a store path and record position only — never payload or checksum bytes — and remediation guidance that points at inspection and the explicit salvage operation. Index/ledger divergence (indexed kind) is detected on read and resolved by rebuilding from verified ledger truth with a reported rebuild, or the read fails `state.write.failed`; it is never served as a stale value.
- **Unknown-kind detection:** a record kind or payload schema that is undeclared at a validated boundary fails `state.store.unknown` with the store path and record position, distinct from the version-scoped `state.schema.mismatch`; a boundary never serves a silent zero or an empty list for it.
- **Boundary validation:** reusable artifact-boundary declarations carry the record kinds, payload schema identifiers, record identities, typed required fields, and closed vocabularies a consumer owns under one store-scoped key prefix. Reads validate every owned record before any value returns and classify the four verdicts distinctly (valid, verified-empty, torn, unknown); writes admit only schema-conforming records and refuse the rest with `state.store.unknown` and `not_landed`, filling in no default. The raw store port stays kind-agnostic; "undeclared" is boundary-relative. The delivery registry declares its own boundary; the retro registry declares three additive kinds under the `retro.` prefix; and reusable declarations applied to test-only ceremony artifacts exercise the same contract in tests.
- **Verified-empty:** an absent (or zero-record) store is explicit verified-empty evidence. It satisfies only an empty key-set declaration; a non-empty declaration fails `state.keys.missing`. Verified-empty and torn are never conflated.
- **Key-set assertions:** a read declares its required keys; a missing declared key fails `state.keys.missing` naming exactly the missing keys. Present keys return recorded values exactly, including `0`, `""`, `false`, `null`, and empty collections. No default is substituted.
- **Terminal-tail repair:** the explicit repair operation removes a terminal truncated tail — the bytes after the last complete frame, accepted only when every complete line before it verifies — and reports the removed byte and frame counts; a verified or empty ledger is a reported no-op, and any other tear, including a truncated tail whose complete-lines prefix is itself broken, refuses `state.store.torn` with zero byte mutation. Repair discards the removed bytes and appends no record; salvage is the guided path that preserves them.
- **Guided salvage:** the explicit, fenced salvage operation truncates a terminal torn tail to its last valid frame, appends one classified `state.salvage` record under the store-scoped key `state.salvage` with payload schema `delivery.state.salvage.v1` describing the salvage (tear position, quarantine reference, counts — never payload or checksum bytes), and returns a salvage evidence report naming the truncation offset, quarantined extent, and record counts. The record kind is additive within `delivery.state.v1`; no schema-version bump or migration exists. No automatic or read-triggered repair exists: reads classify and change nothing. A mid-record integrity break — including a tear whose first break is mid-record and whose final frame is also truncated — refuses with `state.store.torn` and zero byte mutation before any write, preserving the bounded terminal-tail repair model. Salvage is terminal-tail only: on a verified or empty ledger it is a reported no-op, and an absent ledger returns a no-op outcome with verified-empty evidence. Salvage failures reuse existing identities — a mid-record tear is `state.store.torn`, an exhausted write is `state.storage.exhausted`, any other salvage or quarantine write failure is `state.write.failed`, a permission violation is `state.permission.denied`, and fence contention is `state.lock.busy`.
- **Fail-closed storage exhaustion:** an append, derived-document replace, or salvage write that cannot complete for storage exhaustion fails `state.storage.exhausted` with `not_landed` and storage-exhaustion remediation; the ledger stays at its last valid frame, no partial frame is appended, and the document target stays at its previous version (or absent). The runtime edge re-raises a full-device or settled-quota failure (`ENOSPC`, `EDQUOT`, `EFBIG`) in a distinguishable form the facade maps to that code. Every other write error keeps `state.write.failed`; a failed index rebuild keeps `state.write.failed`.
- **Single-writer fences:** acquisition binds a caller-supplied token to a lock file created exclusively. A second acquisition fails `state.lock.busy` (transient, retryable). Writes are unrepresentable without the acquired handle; reads never require it.
- **Staleness and recovery:** a fence whose injected-clock age exceeds the injected staleness window is detectably stale. Writes fail until an explicit, reported recovery clears it; a live fence can never be stolen.
- **Atomic replace:** a derived document is written to a same-directory temporary, flushed, and renamed over the target. The observable target is the previous or the new version, never partial. Stale temporaries are removed on the next open and never read as content.
- **Least-privilege permissions:** creation applies POSIX mode `0700` to the state directory and `0600` to every store-managed file after creation, independent of the inherited umask; open verifies the same exact bits and a violation fails `state.permission.denied` instead of continuing permissively. The quarantine directory and its artifacts are held to the same contract and verified on store open. On Windows the same port applies and verifies a current-user-only ACL.
- **Failure identity:** the nine state codes (including `state.storage.exhausted` and `state.store.unknown`) are declared in both the machine error table and the documented error table, and the bidirectional sync check is binding: a code change in one table without the other fails. All state failures carry consequence `not_landed`, and each is triggerable by a real behaviour.
- **Provider availability records:** the provider engine persists `provider.park` and `provider.announcement` records as additive kinds inside the existing state schema, with payload schemas `delivery.provider.park.v1` and `delivery.provider.announcement.v1`. It folds verified ledger truth into the rebuildable derived document `provider-parks.json` (`delivery.provider.parks.v1`). Park expiry is derived at read time; no expiry write or delete exists, and a park observed after expiry stays `expired` with no `cleared` write.
- **Closeout outcome records:** the closeout transaction persists one `closeout.operation` record per attempted operation outcome as an additive kind inside the existing state schema, with payload schema `delivery.closeout.operation.v1` under the store-scoped key prefix `closeout.operations:`. Each payload carries exactly the new operation record; history is folded from the verified ledger records on read, so storage grows linearly with operations. Apply uses one single-writer fence; reads are verified; the first terminal outcome per operation identity is authoritative; each record's identity, types, closed vocabularies, canonical arguments, target, and evidence validate before admission, and a malformed record is a classified `state.*` failure, never zeros. No schema-version bump or migration is required.
- **Commit telemetry records:** the commit primitive persists one `commit.telemetry` record per landed commit as an additive kind inside the existing state schema, with payload schema `delivery.commit.telemetry.v1` under the store-scoped key prefix `commit.telemetry:<REF>`. Each payload carries the commit identity, message source, transport, token spend, landing timestamp, the transition identity when the commit belongs to an atomic completion, and any recorded transport failovers; it never carries message bodies, diff content, or secret material. Every append uses one single-writer fence, reads are verified, and a malformed record is a classified `state.*` failure. Emission is non-gating: the commit primitive discloses a failed append instead of failing the landed commit. No projection document exists and no schema-version bump or migration is required.
- **Target-profile records:** the profile lifecycle persists one `provider.profile-target` record as an additive kind inside the existing state schema, with payload schema `delivery.provider.profile-target.v1` under the store-scoped key `provider.profile-target`. The payload carries the current target profile, the reason (`selection`, `switch`, or `revert`), the previous target, the revert condition when present, and bounded evidence. The latest record wins; appends use one single-writer fence, occur only on change, and are verified by a post-append read. No schema-version bump, migration, or derived projection exists. The profile contract is in [Provider Profiles and Watching](feature-provider-profiles.md).
- **Economics records:** the resume economics path persists two additive kinds inside the existing state schema under the per-delivery store key `economics/<workItemRef>`, following the `commit.telemetry` record pattern: `economics.restart` with payload schema `delivery.economics.restart.v1`, one record per admitted restart, and `economics.budget-exhaustion` with payload schema `delivery.economics.exhaustion.v1`, one terminal record per delivery. A restart payload carries the work item, run, session identity, ordinal, classified restart reason, optional re-pay token classes, optional observed unique-progress tokens (`null` when observed but unavailable), and recorded time. A terminal payload carries the classified reason `dispatch.restart-budget-exceeded`, the restart count, the resolvable history reference, the terminal marker, the declared option pair, and recorded time. Every append uses a fresh single-writer fence and a post-append verified read; a replay of the same `(run, ordinal)` appends no duplicate; the first refusal that observes exhaustion appends the single terminal record and later refusals re-read it. A duplicate or gapped ordinal, a second terminal record, a malformed payload, or an unknown kind under the delivery key is a classified `state.*` failure, never a fabricated count or zeroed history. No schema-version bump, migration, or derived projection is required; the economics view is a pure fold over verified records.
- **Owner-gate decision records:** the owner-gate SLA persists one `owner-gate.decision` record per default application as an additive kind inside the existing state schema, with payload schema `delivery.owner-gate.decision.v1` under the store-scoped key prefix `owner-gate.decisions:`. Each payload carries exactly the new decision: gate id, gate kind, work-item ref, applied default, application time, crossed threshold in milliseconds, and the declared clock-source marker. The first application per gate id is authoritative; a replay returns the existing record and appends nothing, while a distinct gate id is never suppressed. Appends use one single-writer fence and a post-append verified re-read that requires exactly one new record; a wrong record kind under the prefix, a malformed payload, or two records for one gate id is a classified `state.store.torn`, never a zeroed history. The history read that backs idempotency is performed by the board surface only when a gate is currently default-eligible (conditional-read boundary; see [Owner-Gate SLA](feature-owner-gate-sla.md)); the ledger's own idempotency and torn classification are unconditional once the read happens. No schema-version bump or migration is required.
- **Audit ledger records:** The command audit ledger persists two additive kinds inside the existing state schema: `audit.reservation` (payload schema `delivery.audit.reservation.v1`, payload `{auditSeq, runId, chainValue}`) and `audit.invocation` (payload schema `delivery.audit.invocation.v1`, the 13 audited invocation fields), both under the store-scoped key `audit.invocations`. One shared fence serializes the audit domain; the reservation is appended first and carries the durable ordinal, then the invocation record carries the same ordinal. Both kinds carry a `chainValue` keyed by the store-managed chaining-key artifact, so the chain spans processes and covers orphaned reservations. A reservation whose invocation record is absent from the verified ledger is reported as an in-band skipped-ordinal finding, not an error. The bounded, filtered, library-only read surface validates its query, acquires no fence, and writes no audit record; its underlying verified read may rebuild the disposable derived index as reported evidence. The full contract is in [Command Audit Ledger](feature-audit-ledger.md).
- **Harness telemetry records:** The closeout capture persists additive `harness.telemetry` records inside the existing state schema. One record per captured (session, agent, model) group carries the neutral statistics payload schema `delivery.harness.telemetry.v1` under the store-scoped key prefix `harness.telemetry:<workItemRef>`; one capture-outcome record per delivery run carries schema `delivery.harness.telemetry.capture.v1` under `harness-telemetry-capture:<workItemRef>:<runId>`, using the same record kind. Both payloads carry numeric statistics and identity references only — never prompt text, message bodies, transcripts, diffs, tool output, or credential material. Every append uses the single-writer fence and is verified post-append; session-group capture is idempotent by (work item, run, session, agent, model) and the capture outcome by (work item, run), so a re-run appends nothing for already-captured session groups or runs. A malformed or wrong-kind record under either prefix is a classified `state.*` failure, never a zeroed capture. No schema-version bump, migration, or derived projection exists.
- **Retro registry records:** The retro registry persists three additive kinds inside the existing state schema under the `retro.` key prefix: `retro.level` (payload schema `delivery.retro.level.v1`; level name, level id, scope kind, trigger declaration, and implementation status), `retro.run` (payload schema `delivery.retro.run.v1`; run id, level, mode, scope, counts, consumed-source verdicts, and pipeline-truth verdict), and `retro.trigger` (payload schema `delivery.retro.trigger.v1`; trigger name, kind, cadence, and owning binding). The boundary validates kind, payload schema, identity, required fields, and closed vocabularies; a nonconforming write refuses `state.store.unknown` with `not_landed`. Reads classify valid versus verified-empty, report entry-level malformations in band, and propagate torn/unknown state identities. The six level records and the `memory-audit` trigger are seeded additively and idempotently by identity under one fence. The full contract is in [Retro Evidence Pipeline](feature-retro-pipeline.md).
- **Independent evidence sidecar:** Collector evidence is an append-only JSONL artifact family (`retro-evidence.<workspace>.jsonl`) beside the delivery store, structurally outside its ledger, header, index, fence, and derived documents. Its chaining key is a distinct store-managed artifact (`chain-key.retro.<workspace>.json`), and appends are serialized by `retro-evidence.<workspace>.lock`. The sidecar is collector-write-only and chain-verified on every read; it is not a state record kind and never enters the state store's salvage or repair path. The full contract is in [Retro Evidence Pipeline](feature-retro-pipeline.md).
- **Store-managed artifacts:** The public port exposes `readStoreArtifact` and `ensureStoreArtifact` for the store-layout artifact family beside the header and fence files. `readStoreArtifact` fails `state.keys.missing` when the artifact is absent, `state.permission.denied` when its bits violate the least-privilege contract, and `state.store.torn` when the file cannot be read; a consumer that decodes the content classifies malformed content as torn as well. `ensureStoreArtifact` reads the artifact or creates it once from runtime-edge cryptographic random material under the same permissions; an artifact absent while any guarded record kind exists is `state.keys.missing` and is never silently regenerated. The capability adds no schema-version bump, no driver discriminant, and no new runtime-API location; the only runtime addition is the driver-edge `randomHex` hook.
- **Blocker question and answer records:** the typed blocker channel persists two additive kinds inside the existing state schema — `blocker.question` with payload schema `delivery.blocker.question.v1` and `blocker.answer` with payload schema `delivery.blocker.answer.v1` — under the store-scoped key prefixes `blockers.questions:` and `blockers.answers:`. One boundary declares both kinds under the `blockers.` key prefix with their identity fields, required fields, and the closed `type` and `audience` vocabularies. A question record carries `schemaId`, `id`, `type`, `audience`, `lane`, `ref`, `question`, `options[]`, and `askedAt`; it is immutable once appended and its open/answered status is derived at read time from answer presence. An answer record carries `schemaId`, `questionId`, `answeringAudience`, exactly one of `choice` or `text`, `answeredAt`, `applied: false`, and the embedded `laneResume` projection. The first answer per question id is authoritative. Each append validates the payload against the declared kind, acquires one single-writer fence, appends one record, re-reads for coverage, and requires the verified record count to increase by exactly one. An undeclared kind, an undeclared payload schema, a missing required field, or a closed-vocabulary value is `state.store.unknown`; a duplicate question id, a duplicate answer for one question id, a structural violation inside a declared record, an answer record with both or neither answer channel, an `applied` value other than `false`, or an inconsistent resume projection (mode against `sessionReentry`, `capabilitySource`, and the fallback prefill marker) is `state.store.torn`. A verified-empty store is explicit evidence of no questions. No schema-version bump or migration is required.

### Store layout

One store per workspace inside the injected state directory:

| Path | Purpose |
|---|---|
| `ledger.<workspace>.jsonl` | append-only durable truth |
| `header.<workspace>.json` | store schema version |
| `index.<workspace>.sqlite` | disposable derived index (indexed kind only) |
| `fence.<workspace>.lock` | single-writer lock token |
| `documents.<workspace>/` | atomically replaced derived documents, including `phase-state.<REF>.json` and `provider-parks.json` |
| `chain-key.<workspace>.json` | store-managed chaining-key artifact for the command audit ledger; created once at the runtime edge, read by every later process, `0600`, never served as a derived document |
| `retro-evidence.<workspace>.jsonl` | append-only evidence sidecar outside the delivery ledger; collector-write-only, chain-verified on every read, forever retention |
| `retro-evidence.<workspace>.lock` | collector fence serializing sidecar appends |
| `chain-key.retro.<workspace>.json` | distinct store-managed chaining-key artifact for the evidence sidecar; 32 random bytes generated once at the runtime edge, `0600`, separate bytes from the audit chain key |
| `quarantine.<workspace>/` | post-tear bytes preserved by an explicit salvage, named deterministically per tear, never served as content |

The retro evidence sidecar, its collector fence, and its key artifact live in the same state directory but outside the delivery store's artifact set; they are not store-managed records and never participate in the store's salvage or repair operations.

### Delivery registry consumer

The delivery registry composes the public port without adding a runtime-API location. It appends `phase.transition` records under one store-scoped key per change; each landed payload carries the new transition plus the full verified history, so a verified read returns the history from the ledger record itself. A no-op transition appends nothing.

Reads and landings pass through the registry's declared artifact boundary: the boundary validates the record kind, payload schema, change-ref identity, required fields, and the closed operation/outcome vocabularies before any value returns or is written. A top-level payload that loses a declared field classifies `state.store.unknown`; a malformed nested transition entry remains `state.keys.missing`, and a refused write appends nothing.

The per-change phase state is a derived document (`phase-state.<REF>.json`) produced by a pure fold: a completion records the first-completion start and the latest completion, and a reopen clears `completed` while keeping the start. The projection is replaced atomically through the derived-document kind and is rebuildable from verified ledger truth; a torn store never produces one. Registry behavior is specified in [pm-notes lint and phase transitions](feature-pm-notes-lint-and-phase-transitions.md).

### Provider parks consumer

The provider engine composes the same public port without adding a runtime-API location. It appends `provider.park` records under the store-scoped key `provider.parks` and `provider.announcement` records under `provider.announcements`; each landed payload carries the full verified history, so a verified read returns the history from the ledger record itself. Persistence is fenced and occurs only in a mutating provider `resolve`; `quota` and `parks list` perform zero state writes.

The `provider-parks.json` derived document is a per-park-name fold of the latest record, ordered by expiry ascending then name lexical, with schema `delivery.provider.parks.v1`. It is replaced atomically only when park truth changes. Read paths fold verified ledger truth directly, so a missing or divergent projection is served from the fold with zero writes; the persisted document catches up on the next mutating resolve. A park is active while `expiresAt > now`, expired at `expiresAt <= now` with no write, and `cleared` only when a `cleared` record for a clear observed before expiry was appended; a park observed after expiry stays `expired` with no write, while the next mutating resolve emits its `provider.resumed` announcement. The provider vocabulary and read views are specified in [Provider Engine](feature-provider-engine.md).

### Closeout consumer

The closeout transaction composes the same public port without adding a runtime-API location. The CLI edge bridges the fenced `StateStorePort` to the closeout runtime (`createCloseoutStateRuntime`), so history reads, appends, and post-append coverage verification all execute over the same verified JSONL ledger driver. On apply it reads the verified records for `closeout.operations:<workItemRef>` through the port's `readRecords` view and folds the first terminal outcome per operation identity; it acquires one fence and appends one `closeout.operation` record per attempted operation outcome, with each payload carrying only that new record. Each append re-reads the folded history and fails `state.store.torn` when the verified record count differs from the expected count. A persisted `failed` record is retained as evidence but is not terminal, so a re-run re-observes provider state and retries safely. A malformed record or torn store is the classified `state.*` failure; an absent per-work-item key is an empty verified history, never a zeroed value or a torn store. The closeout record vocabulary and retry semantics are specified in [Closeout Transaction](feature-closeout.md).

### Status consumer

The status digest is a read-only consumer of the state layer. Its providers section folds verified ledger truth into active park views through the same read-only `readProviderParkViews` entry the provider command uses; it reads the `provider.park` history, applies read-time expiry, and never reads the persisted `provider-parks.json` projection as truth. Its `typed-questions` section reads the verified blocker ledger once per invocation through `readBlockerLedger` and folds answer presence into derived closure. One logical park-fold read and one logical blocker-ledger read occur per status invocation, and the fold's documented internal verified reads are not multiplied by status.

Status acquires no fence, appends no record, replaces no derived document, and never repairs or clears a park. An unreadable store is a classified `state.*` evidence code on a `degraded` providers section, never a command failure and never a "no parks" claim. The status contract and evidence model are specified in [Status Digest](feature-status-digest.md).

### Queue-ready consumer

The `queue ready` ready-set is a read-only consumer of the same verified park fold. Its `provider-available` condition reads active park views through the same fold, applies read-time expiry, and never reads the persisted `provider-parks.json` projection as truth. One logical park-fold read occurs per invocation.

Queue ready acquires no fence, appends no record, replaces no derived document, and never repairs or clears a park. An unreadable store surfaces as `state-unreadable` evidence on the provider condition, never a command failure and never a "no parks" claim. The condition contract is specified in [Queue Ready](feature-queue-ready.md).

### Board consumer

The `board` command is the only owner-gate decision writer and reader. The CLI edge bridges the fenced `StateStorePort` to the board runtime, so the history read and the append run over the same verified JSONL ledger driver. A board run reads the decision history only when at least one gate is eligible for a default; a run with no eligible gate performs no decision read, acquires no fence, and appends nothing.

On a default application the runtime calls `appendOwnerGateSlaDecision`, which returns the existing authoritative record without a fence when the gate id is already recorded, otherwise acquires one fence, re-reads the history, appends one `owner-gate.decision` record under `owner-gate.decisions:<gateId>`, re-reads to verify the count increased by exactly one, and releases the fence. A re-evaluation after application therefore honors the existing record and writes nothing. A wrong record kind, a malformed payload, a count mismatch, or two records for one gate id fails `state.store.torn`; no partial decision and no invented zero is served. The board contract is specified in [Owner-Gate SLA](feature-owner-gate-sla.md).

### Blockers consumer

The `blockers` command is the only question and answer writer. The CLI edge bridges the fenced `StateStorePort` to the blockers runtime, so the business read, the append, and the post-append coverage read all execute over the same verified JSONL ledger driver. A publish performs one verified read, one fence, one append of a `blocker.question` record under `blockers.questions:<id>`, and one coverage read. An answer performs one verified read, one fence, one append of a `blocker.answer` record under `blockers.answers:<questionId>`, and one coverage read. A refused publish or answer performs no fence and appends nothing.

`readBlockerLedger` validates every owned record, folds answer presence into the derived open/answered view, and fails closed on duplicate question ids, duplicate answers, an undeclared kind or payload schema, or a malformed payload; an absent or empty store is verified-empty evidence. The status digest and the brief are read-only consumers of the same verified read: each invocation performs one logical blocker-ledger read and renders the `typed-questions` section and its brief mirror without writing, fencing, or repairing. The channel contract is specified in [Typed Blocker and Question Channel](feature-blockers.md).
### Audit ledger consumer

The command audit ledger composes the same public port without adding a runtime-API location. It appends two record kinds under the store-scoped key `audit.invocations`: `audit.reservation` first, then `audit.invocation`, both inside one shared fence acquisition (`audit-<runId>`). The next ordinal is the highest reservation `auditSeq` in the verified audit read plus one, starting at `1` on an empty audit domain, so ordinal consumption is durable and monotonic across processes. The reservation chains from the preceding audit-domain record (or the chain anchor); the invocation chains from its reservation. The shared fence serializes the whole audit domain because every record participates in one chain.

The chaining key is durable store-managed material read and created through `readStoreArtifact`/`ensureStoreArtifact` as `chain-key.<workspace>.json`; the runtime edge supplies the random bytes. Open failures reuse existing identities: absent on a non-first open is `state.keys.missing`, unparsable content is `state.store.torn`, and wrong permission bits are `state.permission.denied`. Every later process reads the same artifact, so chain verification spans processes without false breaks.

The consumer also exposes a bounded, filtered, verified read surface. It validates the mandatory `limit` and the optional `scope`, `repo`, `command`, `outcomeClass`, `from`, and `to` filters (inclusive `[from, to]` over `startedAt`, an omitted side unbounded; exact-match string filters). An invalid query refuses with `input.value.rejected`; it acquires no fence and writes no audit record (a derived-index rebuild, if any, is reported by the store). The result reports matched and returned counts, in-band truncation, the full chain verdict, and the skipped-ordinal finding for any reservation whose invocation record is absent from the verified ledger. There is no unbounded dump path. The record vocabulary, chain alternation, read semantics, and failure behavior are specified in [Command Audit Ledger](feature-audit-ledger.md).

### Retro registry consumer

The retro registry composes the same public port without adding a runtime-API location. It declares one validated boundary over three additive kinds under the `retro.` key prefix: `retro.level`, `retro.run`, and `retro.trigger`. Every read validates the owned records and returns valid or verified-empty, reports entry-level malformations in band, and propagates torn/unknown state identities. Writes are validated at the boundary and appended under a caller-supplied fence carrying the declared `retro-registry` namespace; a wrong kind, payload schema, identity, field type, or closed-vocabulary value refuses `state.store.unknown` with `not_landed`.

Collection seeds the six level records and the `memory-audit` trigger additively and idempotently by identity, under one fence, and appends one `retro.run` record per collection run. Run records carry the level, mode, target scope, counts, consumed-source verdicts, and pipeline-truth verdict. The registry contract is in [Retro Evidence Pipeline](feature-retro-pipeline.md).

### Evidence sidecar consumer

The retro evidence sidecar is a separate artifact family, not a state record kind. It lives in the state directory beside the delivery store but outside its ledger, header, index, fence, and documents, so no state-port write path addresses it and the store's salvage or repair operations cannot mask evidence tampering. Its own collector fence serializes appends; its own store-managed key artifact (`chain-key.retro.<workspace>.json`) backs the HMAC-SHA-256 chain. The sidecar consumer composes an injected runtime edge rather than the public state port. Its contract is in [Retro Evidence Pipeline](feature-retro-pipeline.md).

### Verify-change consumer

Verify change is a read-only consumer of the state layer. It reads the registry's per-change transition history through a presence-tolerant verified read: the store is verified first, an absent store or an absent per-change record is explicit no-evidence (`present: false`), and a torn, schema-mismatched, or corrupt-payload read remains the classified `state.*` failure. The read acquires no fence and writes nothing.

The derived `phase-state.<REF>.json` projection is not evidence for verification: verify folds the verified ledger directly, so a stale or missing projection cannot change the verdict. Verification never mutates the ledger, the header, the index, or a derived document. Its consumer contract is in [verify change and exit taxonomy](feature-verify-change-and-exit-taxonomy.md).

### Doctor consumer

The `doctor` diagnostic is a read-only consumer of the state layer through the same verified provider-ledger read the engine and status use. One verified read per run serves both the provider check's park/announcement fold and the state check's store verdict; when the retro read is composed, the state check additionally verifies the retro registry through its validated boundary and contributes a `retro-registry` verdict. The fold applies read-time expiry and never treats the persisted `provider-parks.json` projection as truth. Doctor acquires no fence, appends no record, replaces no derived document, and never repairs, salvages, migrates, or clears a park.

Store failures become classified diagnostic evidence rather than a command abort. A torn store, schema mismatch, permission failure, or undeclared record kind fails the state check with the delivered remediation guidance as its fix hint; a store read failure outside those classifications makes the state check `unreachable`, and an unreadable provider fold makes the provider check `unreachable` with `state-unreadable` — never a "no parks" claim. The state contract is specified in [Doctor](feature-doctor.md).

The binding is acquired synchronously in the runtime edge (`bun:sqlite` then `node:sqlite`). No third-party dependency is added; the `jsonl` kind and the ledger format never depend on a binding.

### Windows platform contract

The permission contract is one port contract with two platform mechanisms:

- On POSIX the exact bits `0700` (directory) and `0600` (file) are applied after creation and verified on open.
- On Windows an equivalent ACL restricted to the current user is applied at creation (`icacls` with inheritance removed and an explicit current-user grant) and verified on open; a foreign grant or a failed application fails `state.permission.denied`.

Linux CI cannot verify the Windows half. The task suite records an explicit platform conditional with the owner-environment dependency (spec OQ-2); no Linux run claims Windows verification. The current user is resolved at the driver edge from `USERNAME ?? USER`; this is the only state-tier environment read and is an allowlisted `configuration-environment-source` in the secret-read boundary. Both platform branches are selected by the injected platform value on `StateRuntimeEdge`, never by an ambient platform probe in the state tier.

### Evidence model

Every read returns an evidence verdict: the verification classes performed, the record count, and an explicit verified-empty marker for an absent store. Index rebuild reports appear only when a rebuild occurred; repair, salvage, and recovery reports are returned by their operations and only when they ran. Salvage evidence names the truncation offset, the quarantine path and extent, and record counts. Evidence names store paths, record positions, and counts — never payload content, checksum bytes, or ambient data.

### Boundaries

The state tier imports `./contracts` and its own modules only; runtime APIs appear only in the driver edge. Adapters may not import the state subpath; surfaces may. The public port exposes no driver discriminant, and call-site code never branches on a driver kind.

## Operational Notes

- Store format evolution requires a new state schema version and the classified `state.schema.mismatch` path; readers never reinterpret a store from another version.
- Retention is forever, including quarantine artifacts, the audit record kinds, the chaining-key artifacts, the retro registry kinds, and the evidence sidecar. There is no prune, delete, compaction, or scheduled-expiry surface; provider parks become inactive by read-time expiry, but their records remain, closeout operation records accumulate append-only per merge, owner-gate decision records accumulate one per default-applied gate, audit reservations plus invocation records accumulate two per audited invocation, economics restart records accumulate one per admitted restart with one terminal exhaustion record per delivery, and the retro sidecar and registry accumulate evidence and run records per collection. Only two explicit operations remove ledger bytes: terminal-tail repair discards the truncated tail and reports its extent, while guided salvage quarantines the removed bytes and appends a classified record. Losing the chaining-key artifact prevents verification and continuation for subsequently appended records; key rotation, escrow, and backup/restore are outside the current contract.
- The state schema version is carried by the header and by every record; a store artifact without a version is an integrity failure.

## Economics record kinds

Two additive record kinds join `delivery.state.v1` under the per-delivery key
`economics/<workItemRef>` with no schema-version bump. They follow the
`commit.telemetry` additive-record pattern.

| Kind | Payload schema | Writer | Consumer |
|---|---|---|---|
| `economics.restart` | `delivery.economics.restart.v1` | The resume economics path, once per admitted restart, before reporting success | The restart-budget fold, the per-delivery economics view, and the refusal history reference |
| `economics.budget-exhaustion` | `delivery.economics.exhaustion.v1` | The first refusal that observes exhaustion, once per delivery; later refusals re-read it | The terminal state consumed by queue marking, typed-question, daemon, and status data surfaces |

A restart record carries the work item, run, session identity, ordinal, a
classified restart reason, optional re-pay token classes, optional observed
unique-progress tokens, and recorded time. A replay of the same `(run, ordinal)`
appends nothing. The terminal record carries the reason
`dispatch.restart-budget-exceeded`, the restart count, the resolvable history
reference, `terminal: true`, the declared option pair, and recorded time. Every
append uses a fresh fence and a post-append verified read. A duplicate or gapped
ordinal, a second terminal record, a malformed payload, or an unknown kind under
the delivery key classifies as `state.store.torn` or `state.store.unknown`,
never a fabricated count. See
[Session Lifecycle Economics](feature-session-lifecycle-economics.md).
